# 热更新 · 实现契约（v1）

> 姊妹文档：[规范主体](../热更新规范.md) ｜ [可行性依据](01_可行性依据.md)
> **本文是实现唯一依据**：字段名、URL 形态、目录布局、签名口径以此为准。
> v1 范围：**只支持 `web/`（前端）层**。`py/` 层的协议字段已预留，但实现留到 v2。

## 一、信任模型（决定了下面每个字段为什么存在）

| 角色 | 是否可信 | 后果 |
|------|---------|------|
| **补丁 manifest** | 唯一信任根（**RSA 签名**） | 篡改 manifest ⇒ 验签失败 ⇒ 拒绝 |
| 索引 `latest` | **不可信**（未签名） | 最坏是"被冻在某版本/被拒绝更新"，**无法注入代码**（因为清单才是信任根） |
| 包体 zip | 不可信 | 由 manifest 里的 `zip.sha256` + 逐文件 `sha256` 双重校验 |
| 覆盖层文件 | 不可信 | 每次应用都重新校验；不通过就整包丢弃 |

**残余风险（已接受并记录）**：能 MITM 的攻击者可以**拒绝服务**（让你永远看不到新补丁），
但**不能**让你执行任意代码。这个取舍换来了 `latest` 可以是一个极小的未签名文件。

## 二、服务端目录与 URL

```
<base_url>/                       # 例：http://101.200.14.126:8787/hotupdate/0.8.1
  latest                          # {"base":"0.8.1","serial":3}   ← no-store
  patch-3.json                    # {"manifest":{…},"sig":"<base64>"}
  patch-3.zip
```

- `latest` **必须 `Cache-Control: no-store`**（否则 kill switch 不生效）。
- `patch-*.json` / `patch-*.zip` **内容寻址、不可变、可长缓存**（重发即换文件，不覆盖）。
- 公开只读、**匿名可下**（与模型分发同策略；要登录才能拿修复 = 离线用户永远没修复）。

## 三、manifest（**签名对象**）

```jsonc
{
  "format": 1,
  "base_version": "0.8.1",          // 精确匹配底座，不做区间
  "base_version_code": 806,
  "serial": 3,                       // per-base 单调递增
  "issued_at": 1789745000,           // 秒
  "cumulative": true,                // 恒 true：本包 = base → serial N 的完整差异
  "layer": "web",                    // v1 恒 "web"；v2 可 "web+py"
  "zip": {"name": "patch-3.zip", "sha256": "…", "size": 12345},
  "files": [                         // 包内全部文件（不多不少）
    {"path": "web/js/chat_render.js", "sha256": "…", "size": 1234}
  ],
  "rollout_percent": 100,            // 灰度；v1 恒 100，字段先留
  "min_safe_serial": 1,              // kill switch：低于此值视为不安全
  "revoked_serials": []              // kill switch：明确吊销
}
```

### 传输形态（★ 关键设计，别改回去）

`patch-3.json` 里**不直接放 manifest 对象**，而是放**它的规范化字节**：

```jsonc
// patch-3.json
{
  "v": 1,
  "manifest_b64": "eyJmb3JtYXQiOjEsImJhc2VfdmVyc2lvbiI6…",   // canonical bytes 的 base64
  "sig": "Tm90IGEgcmVhbCBzaWduYXR1cmU…"                        // RSA-2048/SHA-256 的 base64
}
```

**为什么必须这样**（第一版设计缺陷）：如果让两端各自把 manifest 对象重新序列化再验签，
就必须保证 Python 与 Kotlin 的 **键序、数字格式、Unicode 转义、浮点写法**逐字节一致——
这是跨语言最容易出、又最难查的一类 bug（表现为"本地测试全绿、真机全部验签失败"）。
改成传**规范化字节本身**，客户端只需 `base64 解码 → 验签 → JSON.parse 同一串字节`，
**跨语言契约就只剩"base64 和 JSON 解析"两件标准到不能再标准的事**。

Python 侧生成时的规范化参数（**只此一处，别处不许再序列化**）：
```python
json.dumps(manifest, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")
```

### 签名步骤

1. 上面那串字节 → `openssl dgst -sha256 -sign <私钥>` → 得到签名
2. 签名 base64（标准字母表、带 `=` 填充）→ `sig`
3. 产出后**立刻用公钥自检**（`openssl dgst -sha256 -verify`），验不过不许发布

## 四、客户端本地布局

```
{FIREFLY_DATA_DIR}/hotupdate/        # 与 user_data 平级：卸载清空、升级保留、不进备份/同步
  web/                               # 生效中的覆盖层
  web.new/                           # 下载暂存（校验通过后原子改名为 web）
  state.json                         # 见下
```

```jsonc
// state.json
{
  "enabled": true,
  "base_version": "0.8.1",     // 上次记录的底座；与当前不符 ⇒ 整个 hotupdate/ 清空
  "base_version_code": 806,
  "applied_serial": 3,
  "applied_hash": "…",          // manifest 规范化字节的 sha256 前 16 位
  "pending_serial": 3,          // 已应用但"启动成功"尚未确认；确认后清空
  "boot_fail_count": 0,         // 连续带 pending 启动失败次数；≥2 ⇒ 自动禁用并回滚
  "last_check": 1789745000,
  "last_error": "",
  "rolled_back_reason": ""      // 非空 ⇒ 「关于」页显示"上次修复已回退"
}
```

## 五、客户端 API（本机 127.0.0.1:8765）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/hotupdate/status` | 状态全量（含 `reload_pending`、三元组、开关、回退原因） |
| POST | `/hotupdate/action` | `{"action":"check"}` / `"apply"` / `"rollback"` / `"set_enabled","enabled":bool` |
| POST | `/hotupdate/boot-ok` | 前端首帧渲染完成后上报 → 清除 `pending` |
| GET | `/config` | **新增** `running: {base_version, version_code, hot_serial, patch_hash}` |

`status` 里 `reload_pending: true` ⇒ 前端应在**空闲**时执行 reload（并保留草稿）。

## 六、空闲判据（前端上报 + 后端判定）

- 前端每次活动变化时 `POST /hotupdate/activity {"busy": bool, "why": "typing|playing|pipeline|download"}`；
  后端另加两个自有判据：模型下载中、已有 pending。
- `busy=false` 持续 **3 秒** ⇒ 空闲。
- 长时间不空闲 ⇒ **推迟到下次冷启动**（新进程天然带上覆盖层，不再重启）。

## 七、生效

| 层 | 动作 |
|----|------|
| `web`（v1 全部） | 覆盖层替换 → 空闲时触发刷新（reload 前把输入框内容+滚动位置存 `sessionStorage`，reload 后恢复） |
| `py`（v2） | 覆盖层替换 → 空闲时**自动重启 App 进程**（Chaquopy `Python.start()` 一进程只能调一次） |

### ★ 刷新触发权必须**壳与前端各一份**（2026-09-19 真机实测发现的设计缺口）

**现象**：apply 成功后 `reload_pending` 一直为真、前端始终没刷新。
**原因**：当前页面上跑的是**补丁之前**的前端 JS —— 它里面还没有轮询代码（那正是补丁要送的东西），
所以**没有任何东西会去问状态**。要修的往往就是那段 JS 本身，指望它自己来取补丁是循环依赖。

**两条触发路径**（谁先满足条件谁触发，都遵守空闲判据）：

| 触发者 | 位置 | 空闲判据 |
|-------|------|---------|
| 前端 JS | `app/static/js/hotupdate.js` 轮询 `/hotupdate/status` | 后端复合判据 + 前端自己上报的 typing/playing |
| **壳（Kotlin）** | `MainActivity.startHotUpdateWatcher()` 每 8s 查一次 | 后端 `reload_pending && idle` **再**用 `evaluateJavascript` 兜底查一次输入框（有字就不刷） |

两者互补：壳那份保证"补丁把前端 JS 改坏了"时仍能生效；前端那份保证草稿保留等细腻行为。

## 八、签名与密钥

- **算法**：RSA-2048 / SHA-256 / PKCS#1 v1.5。
- **私钥**：只在发布机，默认路径 `~/.firefly/hotupdate_key.pem`，**绝不进仓库、不进服务器**。
- **公钥**：PEM 文本硬编码在 Kotlin 侧（`HotUpdateKeys.kt`），随 APK 发布。
- **工具**：`tools/hotupdate_keys.py --gen`（生成密钥对 + 打印公钥）；签名用 `openssl dgst -sha256 -sign`
  （Git for Windows 自带 openssl 3.2.1，已实测可用）。
- **轮换**：先用旧钥发一版带新公钥的**整包**，再用新钥签补丁。v1 只支持单钥。

## 九、v1 明确不做（防越界）

- `py/` 层（协议已留字段）
- serial 级回退（v1 只做"回到 base"，即清空覆盖层）
- 二进制差分、多渠道、按机型灰度
- **删除文件**（补丁只允许新增/覆盖）
- **发新功能**（只修 bug）
