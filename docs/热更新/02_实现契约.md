## 一、信任模型（决定了下面每个字段为什么存在）

| 角色 | 是否可信 | 后果 |
|------|---------|------|
| **补丁 manifest** | 唯一信任根（**RSA 签名**） | 篡改 manifest ⇒ 验签失败 ⇒ 拒绝 |
| 索引 `latest` | **不可信**（未签名） | 最坏是"被冻在某版本/被拒绝更新"，**无法注入代码**（因为清单才是信任根） |
| 包体 zip | 不可信 | 由 manifest 里的 `zip.sha256` + 逐文件 `sha256` 双重校验 |
| 覆盖层文件 | 不可信 | 每次应用都重新校验；不通过就整包丢弃 |

**残余风险（已接受并记录）**：能 MITM 的攻击者可以**拒绝服务**（让你永远看不到新补丁），
但**不能**让你执行任意代码。这个取舍换来了 `latest` 可以是一个极小的未签名文件。

## 二、服务端目录与 URL

```
<base_url>/                       # 例：http://101.200.14.126:8787/hotupdate/0.8.1
  latest                          # {"base":"0.8.1","serial":3}   ← no-store
  patch-3.json                    # {"manifest":{…},"sig":"<base64>"}
  patch-3.zip
```

- `latest` **必须 `Cache-Control: no-store`**（否则 kill switch 不生效）。
- `patch-*.json` / `patch-*.zip` **内容寻址、不可变、可长缓存**（重发即换文件，不覆盖）。
- 公开只读、**匿名可下**（与模型分发同策略；要登录才能拿修复 = 离线用户永远没修复）。

## 三、manifest（**签名对象**）

```jsonc
{
  "format": 1,
  "base_version": "0.8.1",          // 精确匹配底座，不做区间
  "base_version_code": 806,
  "serial": 3,                       // per-base 单调递增
  "issued_at": 1789745000,           // 秒
  "cumulative": true,                // 恒 true：本包 = base → serial N 的完整差异
  "layer": "web+py",                 // "web" / "py" / "web+py"，必须与 files 前缀互相印证
  "zip": {"name": "patch-3.zip", "sha256": "…", "size": 12345},
  "files": [                         // 包内全部文件（不多不少）
    {"path": "web/js/chat_render.js", "sha256": "…", "size": 1234},
    {"path": "py/modules/polisher.py", "sha256": "…", "size": 5678}
  ],
  "rollout_percent": 100,            // 灰度；**仍未实现**，字段先留
  "min_safe_serial": 1,              // kill switch：低于此值视为不安全
  "revoked_serials": []              // kill switch：明确吊销
}
```

### 两层的**内容口径**（v2 新增，发布端强制）

| 层 | 前缀 | 收什么 | 拒什么 |
|----|------|--------|--------|
| `web` | `web/` | `app/static/**` 全部文件 | — |
| `py`  | `py/`  | `app/**/*.py` | 非 `.py`、`app/hotupdate/**`、`app/assets/**`、`__pycache__` |

- **`app/hotupdate/**` 不许进补丁**：它是补丁链路的**自身加载器**。安卓端在注入覆盖层*之前*
  就已经 import 了它（`start_server.py` 要靠它定位覆盖层），覆盖它 = "写 state 的和读 state 的
  不是同一份代码"，属最难查的一类不一致。要改热更自己 ⇒ 发整包。
- **`app/assets/**` 不许进补丁**：角色卡资产属用户数据域（规范 §一）。
- 上述两条由 `tools/check_hotupdate.py` 门禁逐条钉死。

### 传输形态（★ 关键设计，别改回去）

`patch-3.json` 里**不直接放 manifest 对象**，而是放**它的规范化字节**：

```jsonc
// patch-3.json
{
  "v": 1,
  "manifest_b64": "eyJmb3JtYXQiOjEsImJhc2VfdmVyc2lvbiI6…",   // canonical bytes 的 base64
  "sig": "Tm90IGEgcmVhbCBzaWduYXR1cmU…"                        // RSA-2048/SHA-256 的 base64
}
```

**为什么必须这样**（第一版设计缺陷）：如果让两端各自把 manifest 对象重新序列化再验签，
就必须保证 Python 与 Kotlin 的 **键序、数字格式、Unicode 转义、浮点写法**逐字节一致——
这是跨语言最容易出、又最难查的一类 bug（表现为"本地测试全绿、真机全部验签失败"）。
改成传**规范化字节本身**，客户端只需 `base64 解码 → 验签 → JSON.parse 同一串字节`，
**跨语言契约就只剩"base64 和 JSON 解析"两件标准到不能再标准的事**。

Python 侧生成时的规范化参数（**只此一处，别处不许再序列化**）：
```python
json.dumps(manifest, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")
```

### 签名步骤

1. 上面那串字节 → `openssl dgst -sha256 -sign <私钥>` → 得到签名
2. 签名 base64（标准字母表、带 `=` 填充）→ `sig`
3. 产出后**立刻用公钥自检**（`openssl dgst -sha256 -verify`），验不过不许发布

## 四、客户端本地布局

```
{FIREFLY_DATA_DIR}/hotupdate/        # 与 user_data 平级：卸载清空、升级保留、不进备份/同步
  web/                               # 生效中的前端覆盖层（server._static_file 优先命中）
  py/                                # 生效中的 Python 覆盖层（进程启动时插 sys.path 首位）
  web.new/  py.new/                  # 下载暂存（校验通过后原子改名成 web/ 与 py/）
  web.old/  py.old/                  # 换入中途的旧层备份（正常路径上不存在）
  state.json                         # 见下
```

```jsonc
// state.json
{
  "enabled": true,
  "base_version": "0.8.1",     // 上次记录的底座；与当前不符 ⇒ 整个 hotupdate/ 清空
  "base_version_code": 806,
  "applied_serial": 3,
  "applied_hash": "…",          // manifest 规范化字节的 sha256 前 16 位
  "applied_layer": "web+py",   // v2：本 serial 实际含哪些层（"web"/"py"/"web+py"）
  "pending_serial": 3,          // 已应用但"启动成功"尚未确认；确认后清空
  "boot_fail_count": 0,         // 连续带 pending 启动失败次数；≥2 ⇒ 自动禁用并回滚
  "last_check": 1789745000,
  "last_error": "",
  "rolled_back_reason": ""      // 非空 ⇒ 「关于」页显示"上次修复已回退"
}
```

**两层换入是原子的**：先把两层都解到 `{layer}.new/` 并逐文件校验（一层不过就整包丢弃），
**再**逐个 `rmtree(旧) → rename(新)`；中途失败按逆序从 `{layer}.old/` 还原。
所以盘上永远不会出现"web 换了、py 没换"的中间态。

## 五、客户端 API（本机 127.0.0.1:8765）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/hotupdate/status` | 状态全量（含 `reload_pending`、`restart_pending`、`layer`、三元组、开关、回退原因） |
| GET | `/hotupdate/restart` | `{restart: bool, idle: bool, status: {...}}` —— 壳问"现在该重启进程吗"（v2） |
| POST | `/hotupdate/action` | `{"action":"check"}` / `"apply"` / `"rollback"` / `"set_enabled","enabled":bool` / `"set_urls"` |
| POST | `/hotupdate/boot-ok` | 前端首帧渲染完成后上报 → 清除 `pending`、`restart_pending` |
| POST | `/hotupdate/activity` | `{"busy": bool, "why": "typing|playing|pipeline|download"}` |
| GET | `/config` | **新增** `running: {base_version, version_code, hot_serial, patch_hash}` |

`status` 里的两个标志**分工明确，不许合并**：

| 标志 | 含义 | 消费方动作 |
|------|------|-----------|
| `reload_pending` | 有 `web/` 层待生效 | 空闲时 `location.reload()`（或壳 `webView.reload()`） |
| `restart_pending` | 有 `py/` 层待生效**且重启确实会换掉代码** | 壳重启 App 进程（前端只显示提示） |

`restart_note` 非空 ⇒ 补丁改的是**本进程早已 import 的模块**，重启也换不掉，
本次只落盘、等下次整包生效（见 §七「生效性判定」）。

## 六、空闲判据（前端上报 + 后端判定）

- 前端每次活动变化时 `POST /hotupdate/activity {"busy": bool, "why": "typing|playing|pipeline|download"}`；
  后端另加两个自有判据：模型下载中、已有 pending。
- `busy=false` 持续 **3 秒** ⇒ 空闲。
- 长时间不空闲 ⇒ **推迟到下次冷启动**（新进程天然带上覆盖层，不再重启）。

## 七、生效

| 层 | 动作 |
|----|------|
| `web` | 覆盖层替换 → 空闲时触发刷新（reload 前把输入框内容+滚动位置存 `sessionStorage`，reload 后恢复） |
| `py`  | 覆盖层替换 → 空闲时**自动重启 App 进程**（Chaquopy `Python.start()` 一进程只能调一次） |

含 `py` 的补丁**不触发** web 那条 reload：页面 reload 换不掉已经 import 的 Python 模块，
只会白白闪一次屏。两个标志分开报（§五），消费方各走各的。

### 7.1 生效性判定（★ v2 新增，`hotupdate._overlay_effective`）

`py/` 层能生效的**全部前提**是"进程启动早期把覆盖层插进 `sys.path` 首位"，因此
**已经 import 过的模块换不掉**。如果补丁恰好改了启动链路上早就加载的模块，
重启只会再次加载底座那份 —— 此时若还报 `restart_pending=true`，壳就会**为一无所获而重启用户**。

判定用 `sys.modules`（权威、不依赖路径推测）：

| 情况 | 判定 | 结果 |
|------|------|------|
| 模块名不在 `sys.modules` | 新进程一定会走覆盖层 | `restart_pending=true` |
| 在 `sys.modules`，且 `__file__` 落在 `hotupdate/py/` | 已经是补丁那份（热更进程再装下一版） | `restart_pending=true` |
| 在 `sys.modules`，`__file__` 在底座 | 重启也换不掉 | `restart_pending=false` + `restart_note` 留痕 |

> 早期版本用 `find_spec` 的 origin 判落点，被真机 E2E 抓到两个假信号：
> ① 子模块不存在时 `find_spec` 会拿父包 `__path__` 兜底回答一个 origin ⇒
> "补丁新增的模块"被误判成"已从底座加载" ⇒ 永远不报 restart；
> ② "底座里有、本进程根本没 import"的模块同样被误判。`sys.modules` 两个都能判对。

### 7.2 两层换入原子性

`apply_available()` 的顺序写死为：**下载 → 两层都解到 `.new/` 并逐文件校验 → 换入**。
一层解压失败 ⇒ 整包丢弃，另一层也不换（避免"web 已更、py 没更"的中间态）。
换入用 `rename`（同分区内近似原子）；中途异常按逆序从 `{layer}.old/` 还原。

### 7.3 ★ 刷新触发权必须**壳与前端各一份**（2026-09-19 真机实测发现的设计缺口）

**现象**：apply 成功后 `reload_pending` 一直为真、前端始终没刷新。
**原因**：当前页面上跑的是**补丁之前**的前端 JS —— 它里面还没有轮询代码（那正是补丁要送的东西），
所以**没有任何东西会去问状态**。要修的往往就是那段 JS 本身，指望它自己来取补丁是循环依赖。

**两条触发路径**（谁先满足条件谁触发，都遵守空闲判据）：

| 触发者 | 位置 | 空闲判据 |
|-------|------|---------|
| 前端 JS | `app/static/js/hotupdate.js` 轮询 `/hotupdate/status` | 后端复合判据 + 前端自己上报的 typing/playing |
| **壳（Kotlin）** | `MainActivity.startHotUpdateWatcher()` 每 8s 查一次 | 后端 `reload_pending`/`restart_pending` **且** `idle`，**再**用 `evaluateJavascript` 兜底查一次输入框（有字就不动） |

两者互补：壳那份保证"补丁把前端 JS 改坏了"时仍能生效；前端那份保证草稿保留等细腻行为。
**`py/` 层只有壳这一条路** —— 前端没有重启进程的能力，它只把这件事显示给用户。

### 7.4 重启进程怎么做（v2 定案）

`AlarmManager` 定一个 ~800ms 后的 `PendingIntent` 自拉起 `MainActivity`，然后 `finishAffinity()`。
**不用 `Process.killProcess()` 作为首选**：杀进程没有回头路，被系统限制（电池策略/后台限制）
就永远起不来，用户只能手动点图标。排程失败时才退回杀进程（下次点图标同样是新进程，一样生效）。
Android 12+ 无精确闹钟权限时降级为 `set()`（差几秒不影响"重启生效"）。
需要 `SCHEDULE_EXACT_ALARM` 权限（已加进 `AndroidManifest.xml`）。

#### ★ 7.4.1 真机实测改掉的两处（2026-09-25，都别改回去）

**① 后台不许自杀（BAL_BLOCK 死循环）**

真机（OPPO PJE110 / Android 15）日志：

```
I FireflyHotUpdate: 含 py 层的补丁就绪且空闲 → 壳重启 App 进程
W ActivityTaskManager: Background activity launch blocked … (BAL_BLOCK) result code=102
```

Android 10+ **拦截后台应用的 Activity 启动**。原实现无条件 `finishAffinity()` ⇒ 闹钟被拦、
界面却已被结束 ⇒ **补丁永不生效，且每 8 秒重试一次**（实测循环十几分钟，App 打不开）。

修法三条（`MainActivity.restartForHotUpdate`）：
1. `KeepAliveService.isAppForeground()` 为真才重启（前台点名自己不受 BAL 限制）；
2. 后台时**什么都不做** —— 覆盖层已落盘，用户下次冷启动就带上了（规范 §5.2.1 允许的路径）；
3. 30 秒节流，且**只在真的要发起重启时计时**（后台推迟不消耗窗口），
   否则用户切回前台还得白等最多 30 秒。

**② boot-ok 不许伪造 py 层的"启动成功确认"**

真机现象：重启被推迟后，前端 polling 触发页面 reload → 页面重跑 `boot()` →
**无条件**上报 `boot-ok` ⇒ `pending` 在同进程里被清掉。真机日志里进程 PID 没变，
却打印"新进程已完成启动确认"。后果是**安全模式（坏补丁自动回滚）被绕过**。

修法：`apply` 时把 `os.getpid()` 记进 `state.applied_pid`；`boot_ok()` 若判断
"同一个进程 + 本次含 py 层" ⇒ **不清 pending**（返回 `same_process: true`），
只清 `reload_pending`。web 层补丁不受影响（它的生效方式本来就是 reload，同进程确认是正确语义）。

> 这两条都是**只有真机能抓到**的：单测里没有 ActivityManager、也没有真实 WebView 生命周期。
> 回归钉在 `tests/test_android_install.py` E2 组（源码不变量）与
> `tests/test_hotupdate_py.py` M 组（语义）—— 详见 `docs/错误总结.md` #18。

## 八、签名与密钥

- **算法**：RSA-2048 / SHA-256 / PKCS#1 v1.5。
- **私钥**：只在发布机，默认路径 `~/.firefly/hotupdate_key.pem`，**绝不进仓库、不进服务器**。
- **公钥**：PEM 文本硬编码在 Kotlin 侧（`HotUpdateKeys.kt`）+ Python 侧（`app/hotupdate/pubkey.py`），
  两份由第 5 门禁强制逐字节一致。
- **工具**：`tools/hotupdate_keys.py --gen`（生成密钥对 + 打印公钥）；签名用 `openssl dgst -sha256 -sign`
  （Git for Windows 自带 openssl 3.2.1，已实测可用）。
- **轮换**：先用旧钥发一版带新公钥的**整包**，再用新钥签补丁。只支持单钥。

## 九、v2 明确不做（防越界）

- serial 级回退（只做"回到 base"，即清空覆盖层）
- 二进制差分、多渠道、按机型灰度
- **灰度**（`rollout_percent` 字段仍在，客户端还没按 user_id 取模）
- **删除文件**（补丁只允许新增/覆盖）
- **发新功能**（只修 bug）
- 改 `app/hotupdate/**` 自身（补丁链路的加载器，必须走整包）

## 十一、v2 的验收方式（真机步骤，发布前必走）

真机没有自动化入口，靠 `tools/e2e_hotupdate.py`（本机真签名）+ 真机手工四步：

1. `build_hotupdate.py --init` 建基线 → 改一个 `app/modules/*.py` → 产出补丁 →
   `check_hotupdate.py --dist ...` 门禁必须全 PASS；
2. 补丁与 `latest` 放到更新源（PC 目录 + `adb reverse` 或服务器 `hotupdate/<base>/`）；
3. 真机 `POST /hotupdate/action {"action":"check"}` → `{"action":"apply"}`：
   `status` 应给出 `restart_pending=true`、`reload_pending=false`、`layer="py"`；
4. 停手 3 秒（空闲）→ 壳应在 8 秒内重启 App → 重启后
   `GET /config` / `/hotupdate/status` 的 `applied_serial` 与 `pending_serial=0`，
   且**改动的行为真的变了**（这是唯一能证明"重启生效"的一步，缺了它等于没验）。
