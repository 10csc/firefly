# 错误总结（已犯，禁止再犯）

## 1. 跳步——没做需求分析就动手建项目

**表现**：在用户还没明确 Agent 要做成什么样子之前，直接创建了 CLAUDE.md、skills/、memory/、knowledge/、validation/ 等完整目录结构。

**为什么错**：用户当时连"独立 Agent 还是 Claude Code Skill"都还没定，我替用户做了架构决策。

**正确做法**：先读需求文档，先讨论，先确认方向。方向没定之前不动文件。

---

## 2. 方向误判——把独立 Agent 项目做成了 Claude Code Skill

**表现**：创建了 CLAUDE.md、skills/firefly/SKILL.md、memory/firefly/ 等 Claude Code 生态的目录结构，把流萤当成 Claude Code 的一个 persona 来做。

**为什么错**：用户的目标是构建独立运行的角色扮演系统（不依附于任何外部框架），而 Claude Code Skill 是依附于 Claude Code 的。

**正确做法**：确认项目的运行环境、依赖边界、独立性要求后再设计文件结构。

---

## 3. 文档堆砌——所有内容塞进一个文件

**表现**：需求设计.md 膨胀到 400+ 行，把判定流水线、上下文分层、工具设计、违规分级、好感度、上下文伪装、记忆方向、判定器规格、提示词、验证规则、监控规格全部塞在同一个文件里。

**为什么错**：违反了文档管理规范（树状分文件，单文件超过模型有效注意长度时必须拆分）。长文档消耗上下文窗口，且不易维护。

**正确做法**：按模块分文件，每个模块的规格独立存放。顶部文档只做总览和索引。

---

## 4. 约束层次混乱——把流程步骤当成代码模块设计

**表现**：在状态判定器规格中把"审查约束"作为独立的流程步骤列出，将代码层的基本判空/截断设计得跟业务逻辑并列。

**为什么错**：模块铁律（接收输入→审查约束→模块处理→验证结果→最终输出）是针对代码模块的约束，不是要求每个模块必须列出五个步骤。输入空的处理是代码层的一行判断，写在模块处理里即可；LLM 本身能处理"无法理解"类输入。

**正确做法**：
- 代码层：简单判空，不合法直接拒绝不调 API
- 业务逻辑：由 LLM 在判定过程中自然处理（如"无法理解"作为第 0 步的一种违规类型）
- 验证门：只做基本的输出结构校验（JSON 合法、关键字段存在）

---

## 5. 过早过度设计——没讨论就先写死细节

**表现**：在用户还没确认错误处理方案时，先写了 5 条验证规则和 9 项监控指标。

**为什么错**：用户明确说"错误处理也要后续讨论"，我在讨论之前就把规格定死了。

**正确做法**：当前只写明确的部分，不确定的标注"后续讨论"，不替用户做决定。

---

## 6. 替用户做决定——没有确认就执行

**表现**：多次在未经确认的情况下创建文件、移动目录、修改文档结构。

**为什么错**：用户是项目 Owner，我是协作者。涉及范围广的操作必须经过确认。

**正确做法**：任何超出当前讨论范围的改动，先确认再动手。

---

## 7. 子代理烧钱——用多智能体编排做本可主会话直接做的事（2026-09-11）

**表现**：语音模型调研任务中，主会话为「并行提速」派出 2 个 `subagent` 做联网调研。这两个子代理**自行继续派生下级**——depth 2 的再派 depth 3，最终形成 **24 个子代理的树（最深 3 层）**。用户发现后要求立刻全部停止。

**代价**：**不到 5 分钟花掉 18 元**。当日 token 消耗 **131,765,764**，其中未命中缓存的输入 **9,832,494**、输出 1,525,078。用户原话：「你今天这一堆子代理5分钟不到花了我18块！！！！！！！！！」

**为什么错**：
1. **子代理会不受控地自我繁殖**——派出去的子代理自己也有 `subagent` 工具，会为了"并行"继续派生，成本呈树状放大且主会话无法预估。
2. **任务本身不需要子代理**——联网调研用 `web_search` / `web_fetch`、代码审计用 `grep` / `read`，主会话顺序做完全够用，只是慢一点。
3. **把"工具便利"当成"任务需要"**，没有先问成本。

**正确做法（硬约束，永无例外）**：
- **绝对禁止**调用 `subagent` / `subagent_fork` / `workflow` / `ralph`，或任何形式的派生执行体。
- 需要调研 → 主会话自己 `web_search` / `web_fetch`；需要并行 → 顺序做。
- 长任务 → 用后台 job（`run_in_background: true`）+ `job_output` 收结果（job 不产生额外模型调用）。
- 即使用户某次说"可以并行"，也必须**先报成本估算**再执行。

## 8. 陈腐缓存 + 先怀疑素材 —— 语音参考音频排查走 7 轮弯路（2026-09-12）

**表现**：整合包官方参考合成 **8/8 内容完好**，而我从《夜间车厢》提取的参考只有 **7/15**，
于是判定"电话录音这条素材线不可用"，并围绕这个结论连做 6 轮排查（采样率、特征退化、
低码率编码、文本错配、边界切错、拼接不连续）——**六轮全部被实测证伪**。

**真正的根因**（第 7 轮才找到）：**参考音频时长**。短参考（3.5–4.3 s）13 次合成过守卫 12 次；
长参考（8.75 s）20 次只过 7 次。而**官方参考的内容完好率并不比我高**（2/3 vs 3/4、4/5）——
之前"官方 100% vs 我的 47%"是拿**短参考比长参考**，比较本身无效。

**顺带挖出的事故**：`_find_heavy_voice.py` 的 `to_16k()` 里
`if W16.exists(): return`（无校验）+ 本该分块落盘的逻辑写成了 `pass`（空操作），
于是一次被中断的运行留下的 **残次 `heavy_16k.wav`（810 s，源文件真实 1703.8 s，
是整段的 2.10 倍时间压缩版）** 被后续所有运行当正确缓存复用，
导致 243 条 ASR 时间戳全部错位，据此切出的候选**内容相似度 0.000–0.095**。

**为什么错**：
1. **结论下在控制变量之前**。该先做的是「官方素材 vs 我的素材」× 「短 vs 长」的
   2×2 对照，而不是先认定"素材不行"再去找理由——这是**确认偏误**，6 轮排查都是它的产物。
2. **把"文件存在"当成"文件正确"**。长时间任务（解码/转写/量化）的产物会被中断，
   复用前必须校验不变量（时长、样本数、哈希）。
3. **凭直觉定阈值**。发现截断问题后我第一反应把 token 下限定成 3.0，
   实测标定后正确值是 2.0——**3.0 会误杀 24/28 条正常输出**。

**正确做法**：
- **先控制变量，再下结论**。多个可疑因素时，设计能**分离变量**的对照实验（2×2 起），
  而不是逐个"证伪+换下一个"。
- **缓存一律带完整性校验**：解码产物比对容器时长，不符则删缓存重解并**拒绝继续**。
  参考实现见 `FireflyVoiceResearch/_heavy_rescan.py` / `_scan_days.py`。
- **阈值必须由实测分布标定**，并写清样本量与适用范围（含 `[待确认]` 标注）。
- **官方口径 ≠ 好用口径**。"3–10 秒"只是"不报错"，实测"好用"上限是 ~4.5 s。
