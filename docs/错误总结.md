# 错误总结（已犯，禁止再犯）

## 1. 跳步——没做需求分析就动手建项目

**表现**：在用户还没明确 Agent 要做成什么样子之前，直接创建了 CLAUDE.md、skills/、memory/、knowledge/、validation/ 等完整目录结构。

**为什么错**：用户当时连"独立 Agent 还是 Claude Code Skill"都还没定，我替用户做了架构决策。

**正确做法**：先读需求文档，先讨论，先确认方向。方向没定之前不动文件。

---

## 2. 方向误判——把独立 Agent 项目做成了 Claude Code Skill

**表现**：创建了 CLAUDE.md、skills/firefly/SKILL.md、memory/firefly/ 等 Claude Code 生态的目录结构，把流萤当成 Claude Code 的一个 persona 来做。

**为什么错**：用户的目标是构建独立运行的角色扮演系统（不依附于任何外部框架），而 Claude Code Skill 是依附于 Claude Code 的。

**正确做法**：确认项目的运行环境、依赖边界、独立性要求后再设计文件结构。

---

## 3. 文档堆砌——所有内容塞进一个文件

**表现**：需求设计.md 膨胀到 400+ 行，把判定流水线、上下文分层、工具设计、违规分级、好感度、上下文伪装、记忆方向、判定器规格、提示词、验证规则、监控规格全部塞在同一个文件里。

**为什么错**：违反了文档管理规范（树状分文件，单文件超过模型有效注意长度时必须拆分）。长文档消耗上下文窗口，且不易维护。

**正确做法**：按模块分文件，每个模块的规格独立存放。顶部文档只做总览和索引。

---

## 4. 约束层次混乱——把流程步骤当成代码模块设计

**表现**：在状态判定器规格中把"审查约束"作为独立的流程步骤列出，将代码层的基本判空/截断设计得跟业务逻辑并列。

**为什么错**：模块铁律（接收输入→审查约束→模块处理→验证结果→最终输出）是针对代码模块的约束，不是要求每个模块必须列出五个步骤。输入空的处理是代码层的一行判断，写在模块处理里即可；LLM 本身能处理"无法理解"类输入。

**正确做法**：
- 代码层：简单判空，不合法直接拒绝不调 API
- 业务逻辑：由 LLM 在判定过程中自然处理（如"无法理解"作为第 0 步的一种违规类型）
- 验证门：只做基本的输出结构校验（JSON 合法、关键字段存在）

---

## 5. 过早过度设计——没讨论就先写死细节

**表现**：在用户还没确认错误处理方案时，先写了 5 条验证规则和 9 项监控指标。

**为什么错**：用户明确说"错误处理也要后续讨论"，我在讨论之前就把规格定死了。

**正确做法**：当前只写明确的部分，不确定的标注"后续讨论"，不替用户做决定。

---

## 6. 替用户做决定——没有确认就执行

**表现**：多次在未经确认的情况下创建文件、移动目录、修改文档结构。

**为什么错**：用户是项目 Owner，我是协作者。涉及范围广的操作必须经过确认。

**正确做法**：任何超出当前讨论范围的改动，先确认再动手。

---

## 7. 子代理烧钱——用多智能体编排做本可主会话直接做的事（2026-09-11）

**表现**：语音模型调研任务中，主会话为「并行提速」派出 2 个 `subagent` 做联网调研。这两个子代理**自行继续派生下级**——depth 2 的再派 depth 3，最终形成 **24 个子代理的树（最深 3 层）**。用户发现后要求立刻全部停止。

**代价**：**不到 5 分钟花掉 18 元**。当日 token 消耗 **131,765,764**，其中未命中缓存的输入 **9,832,494**、输出 1,525,078。用户原话：「你今天这一堆子代理5分钟不到花了我18块！！！！！！！！！」

**为什么错**：
1. **子代理会不受控地自我繁殖**——派出去的子代理自己也有 `subagent` 工具，会为了"并行"继续派生，成本呈树状放大且主会话无法预估。
2. **任务本身不需要子代理**——联网调研用 `web_search` / `web_fetch`、代码审计用 `grep` / `read`，主会话顺序做完全够用，只是慢一点。
3. **把"工具便利"当成"任务需要"**，没有先问成本。

**正确做法（硬约束，永无例外）**：
- **绝对禁止**调用 `subagent` / `subagent_fork` / `workflow` / `ralph`，或任何形式的派生执行体。
- 需要调研 → 主会话自己 `web_search` / `web_fetch`；需要并行 → 顺序做。
- 长任务 → 用后台 job（`run_in_background: true`）+ `job_output` 收结果（job 不产生额外模型调用）。
- 即使用户某次说"可以并行"，也必须**先报成本估算**再执行。

## 8. 陈腐缓存 + 先怀疑素材 —— 语音参考音频排查走 7 轮弯路（2026-09-12）

**表现**：整合包官方参考合成 **8/8 内容完好**，而我从《夜间车厢》提取的参考只有 **7/15**，
于是判定"电话录音这条素材线不可用"，并围绕这个结论连做 6 轮排查（采样率、特征退化、
低码率编码、文本错配、边界切错、拼接不连续）——**六轮全部被实测证伪**。

**真正的根因**（第 7 轮才找到）：**参考音频时长**。短参考（3.5–4.3 s）13 次合成过守卫 12 次；
长参考（8.75 s）20 次只过 7 次。而**官方参考的内容完好率并不比我高**（2/3 vs 3/4、4/5）——
之前"官方 100% vs 我的 47%"是拿**短参考比长参考**，比较本身无效。

**顺带挖出的事故**：`_find_heavy_voice.py` 的 `to_16k()` 里
`if W16.exists(): return`（无校验）+ 本该分块落盘的逻辑写成了 `pass`（空操作），
于是一次被中断的运行留下的 **残次 `heavy_16k.wav`（810 s，源文件真实 1703.8 s，
是整段的 2.10 倍时间压缩版）** 被后续所有运行当正确缓存复用，
导致 243 条 ASR 时间戳全部错位，据此切出的候选**内容相似度 0.000–0.095**。

**为什么错**：
1. **结论下在控制变量之前**。该先做的是「官方素材 vs 我的素材」× 「短 vs 长」的
   2×2 对照，而不是先认定"素材不行"再去找理由——这是**确认偏误**，6 轮排查都是它的产物。
2. **把"文件存在"当成"文件正确"**。长时间任务（解码/转写/量化）的产物会被中断，
   复用前必须校验不变量（时长、样本数、哈希）。
3. **凭直觉定阈值**。发现截断问题后我第一反应把 token 下限定成 3.0，
   实测标定后正确值是 2.0——**3.0 会误杀 24/28 条正常输出**。

**正确做法**：
- **先控制变量，再下结论**。多个可疑因素时，设计能**分离变量**的对照实验（2×2 起），
  而不是逐个"证伪+换下一个"。
- **缓存一律带完整性校验**：解码产物比对容器时长，不符则删缓存重解并**拒绝继续**。
  参考实现见 `FireflyVoiceResearch/_heavy_rescan.py` / `_scan_days.py`。
- **阈值必须由实测分布标定**，并写清样本量与适用范围（含 `[待确认]` 标注）。
- **官方口径 ≠ 好用口径**。"3–10 秒"只是"不报错"，实测"好用"上限是 ~4.5 s。

## 9. 把资产放进 Gradle `Sync` 任务的输出目录——构建"成功"，文件却被静默删掉

**表现**：接入语音插件时，把语气库 `mood_lib/`（14 个文件）和 4 张映射表直接写进
`android/app/src/main/assets/`。`assembleRelease` **BUILD SUCCESSFUL**，`adb install -r`
**Success**，APK 也打得开——但**包里根本没有这些文件**：解包一看，`assets/mood_lib` 条目数 **0**。

**根因**：`android/app/build.gradle.kts` 的 `syncFrontendAssets` 是 Gradle **`Sync`** 类型任务。
**`Sync` 的语义 = 让目标目录与自己的输入完全一致**，因此它会**删除目标目录里所有不属于它的文件**。
`preBuild` 依赖它 → 每次构建都把我的资产清一遍，**顺序恰好是"先拷进去、再被删掉"**。

**为什么容易漏掉**：
1. **构建不报错**——删文件是 `Sync` 的正常行为，不是警告；
2. 症状要到**运行期**才暴露（`AssetManager` 读不到 → 引擎装载失败），此时离构建已经隔了几步；
3. 我是在**主动解包列条目**时才发现的，纯看构建日志永远看不见。

**正确做法**：
- **资产源放受版本管理的目录**（本项目的约定：`app/assets/`，已有 `background.jpg`/字体/图标），
  再在 Gradle 任务里**显式 `from(...)` 登记**——放进 `Sync` 的**输出目录**等于没放。
  本次实现：`app/assets/voice/` + `syncFrontendAssets` 里一行 `from("../../app/assets/voice")`。
- **构建后要验产物**，不能只看 `BUILD SUCCESSFUL`：解包确认关键资产真的在
  （本次用 `System.IO.Compression.ZipFile` 列条目，见 `android/firefly.apk` 核对输出）。

**推广到同类**：`syncBackend` / `syncFrontendAssets` 这两个任务**都是 `Sync` 类型**——
任何"想让它出现在 APK 里"的文件，都必须走它们的输入，不许手放进输出目录。

## 10. 两个口径不一致却当成一个——记忆整理的游标用了"被截断的内存窗口"

**表现**：长对话（>40 轮）重启一次后，点「让流萤休息」永远回"没有新内容"，
**记忆再也不更新，全程零报错**。

**根因**：`api/chat_ops.rest` 传给 `MemoryManager.rest` 的两个入参取自**内存会话上下文**：

```python
full_history = session["context"].get_full()        # 被 hydrate_context(max_turns=40) 截断过
result = mm.rest(full_history, session["context"].turn_count, ...)
```

而记忆游标 `last_integrated_turn` 是**磁盘全量**轮号，`_slice_new_dialogue` 也按这个口径切。
于是：磁盘 100 轮 → 重启后内存只有 40 轮 → 游标写入 **40** →
`verify_index` 检查 `40 <= 100` **判定正常、不修** → 下次切 `history[turn>40]` = 空 →
永久跳过。

**为什么容易漏掉**：
1. **两个变量同名同义**（"全量历史""轮数"），实际一个是"盘上全量"、一个是"内存窗口"——
   这种"语义一致、口径不一致"是最难看的 bug；
2. 已有的自愈（阶段 3.6）只覆盖"游标**偏大**"，这次的偏大来自窗口截断，方向恰好躲过；
3. 失败是**静默降级**（返回 `success=True, error="无新对话，跳过"`），前端显示"没有新内容"，
   用户只会以为"这段时间确实没什么好记的"。

**正确做法**：
- **凡是要写盘/当权威的口径，一律从盘上取**：`conversation_store.load_all(mode)` +
  `count_user_turns(mode)`，不要用内存里的近似值（内存值只服务"给 LLM 看的历史窗口"）。
- **两个东西语义相关就显式对齐一次**：本处 `全量历史` 与 `游标口径` 必须同源；
  只改一个就是下一个 bug。
- **静默跳过要能被看见**：`RestResult.error` 文案保留，同时补了回归测试
  （`tests/test_memory_auto.py` B/C 组 + `count_user_turns` 断言）。

**同族的第二次踩坑（2026-09-18 当天，更隐蔽）**：修上面那个 bug 时把 `rest` 的入参从
`ctx.get_full()` 换成了 `load_all()` —— 口径对了，但**形状不对**：
`load_all()` 给的是 **jsonl 原始行**（字段 `who`/`type`），而 `rest` 的切片与
`format_history` 读的是 **`role`**。于是每行都落进"（行为）"分支、`turn` 永远不涨、
`turn <= last_turn` 恒真 → 切出来是空的 → 又是"无新对话，跳过"（换了个原因）。
**当时的测试只断言了 `success`，没断言切出来的内容**，所以全绿骗过了我。

**教训（已写进 `load_all_context` 的 docstring）**：
- 修"口径不一致"时，要**同时**检查**形状/字段**是否一致——名字一样不代表结构一样。
- **断言要落在产物上**，不能只断言"函数返回成功"：`success=True` 但内容是空，
  正是这个 bug 能躲过 60 个测试脚本的原因。
- 两个口径必须**同源**：现在 `load_all_context()` 与 `count_user_turns()` 都按
  "jsonl 里 `who=="user"` 的行数"定义（**逐条 1:1、不合并连发**），
  并有 B4-B6 三条断言钉死。

## 11. 告警去重键选了"每次都变"的字段——一次封禁弹 4-5 次窗

**表现**：用户报「服务器频繁提示我遭到攻击」。日报显示 `2026-09-18 22:03/04/06/07` 四条告警、
`2026-08-28 16:01-16:05` 五条告警，而每次**其实只有同一个来源 IP**，其余计数全 0
（主服务 429=0 / 网关 429=0 / SSH 失败=0 / 服务全 active）。

**根因**：两头各错一半，叠起来把**一次**封禁放大成 4-5 次打扰。
1. `server/attack_watch.sh` 统计「**最近 5 分钟** fail2ban 日志里的 `Ban` 行数」，阈值 `>= 1`
   → 一次封禁在 5 分钟窗口里**每分钟都命中** → cron 每分钟重写了标记文件，
   而标记里的 `time` 字段是 `date` 取的**当前时间**，每次都变；
2. `tools/attack_sentinel.py` 的去重键正是 `flag["time"]`
   → 「同一攻击不重复处理」这行注释从来没生效过。

**教训**：
- **去重键不能选会随时间自然变化的字段**。判断"是不是同一个事件"要用**事件本身的特征**
  （来源 IP、计数、类型），时间戳只能做**冷却窗口**，不能做等值比较。
- **"检测到什么"与"报几次"是两件事**。阈值宽 ≠ 不刷屏；上报链路的去重是独立的一环。
- **告警要能被证伪**：本例里"If the trigger is `fail2ban_bans`, then it must be inbound SSH,
  which my test never touched"一句话就能排除嫌疑——先看**触发字段**，别先怀疑自己刚做过的事。
- 附带：模型返回 `{"analysis":"","need_user":true}` 时照样弹了窗（空的"分析"+ "需要你行动：是"），
  **LLM 输出必须有本地兜底**，否则最烦人的那次恰好最没信息量。


## 12. 测试里写死"会随产品变更而变化"的数字——每次合理变更都报假失败（2026-09-19）

**表现**：同一天里，因为**加功能**而失败的断言出现了 4 次，全不是 bug：
| 位置 | 写死的东西 | 变更原因 |
|---|---|---|
| `tests/test_routes_split.py` | `"OK 70 39"`、`72 POST / 41 GET` | 新增 4 个公告端点 |
| `tests/test_snapshot.py` | 教程步骤 `nums[:9]` | 引导加了"公告""自动修复"两步 |
| `tests/test_core_split.py` | 字面量 `"VER 0.8.1"` | 版本升到 0.9.0 |
| `tools/check_hotupdate.py` | 「无补丁」直接 `return 0` | 新增了"公钥一致性/公告"两项必查 |

**根因**：断言写的是**当前状态的快照**，而不是**应当成立的性质**。
"端点数是 70"不是性质，"端点集合与 oracle 一致"才是。

**怎么防**：
- 门禁/测试里的数字**必须有一处真相源**，别处**读**它（本轮的修法：
  `test_routes_split` 用 `ast` 解析 `test_routes_oracle.py` 的集合字面量；
  `check_hotupdate` 把与补丁无关的检查提到早退之前）。
- 写断言前先问：**"产品正常演进时，这条断言该不该变？"** 该变的就不是断言。
- 版本号这类"必然会变"的值一律**现读**（`config.py`），绝不写进断言。

## 13. "先回缓存、后台刷新"的接口，前端不跟第二次 = 功能像没做（2026-09-19）

**表现**：真机装上 0.9.0，后端 `/notice` 明明 `serial=1`、`unread=1`，
但公告面板只显示内置指南、首页也不亮小圆点 —— 看起来"公告通道根本没生效"。

**根因**：`GET /notice` 的设计是**先回缓存、后台联网刷新**（为了不阻塞面板），
首次安装时这一次返回的是**空 payload + `refreshing: true`**；
前端 `notice.js` 拿到空结果就渲染空、然后**再也不请求** ⇒ 刷新结果没人取。
后端每处都对，错在**两端对"异步"的约定**。

**怎么防**：
- 只要接口有"`refreshing`/`pending`/`async` 之类字段"，消费方就**必须**处理它
  （重试、订阅、或下次进入时强制拉）。**返回了字段却没人读，等于没设计**。
- 这类 bug **单测抓不到**（单测里后端是同步的），**必须真机/真链路跑一次首装路径**。
  本轮正是"真机截屏"抓到，而不是 52 项单测。

## 15. bundle 是**单作用域拼接**，跨模块在顶层调用会撞 TDZ，把整块代码静默打死（2026-09-19）

**表现**：0.9.0 真机装上后，**公告功能整体不存在** —— 首页不亮未读小圆点、公告面板只有内置指南。
同时：后端 `/notice` 一切正常（`serial=1 unread=1`）、52 项公告/热更单测全绿、
APK 里也确实有 `notice.js` 与渲染代码。**唯一能看出问题的地方是真机界面**。

**根因**：`templates` 说清了 —— `bundle.js` 不是模块系统，而是把 `js/*.js`
**按 ORDER 拼进同一个作用域**（`import`/`export` 行被删掉）。ORDER 是
`… guide, main, hotupdate, notice`，而我在 `main.js` 顶层写了 `initNotice();`
⇒ 执行到那一行时，`notice.js` 顶层的 `let _payload = null;` **还没执行** ⇒
`ReferenceError: Cannot access '_payload' before initialization`（TDZ）⇒
**main 的顶层从这里中断，`notice.js` 整块再也没执行**（连末尾
`window.noticeOnOpen = …` 都没跑到），于是 `views.js` 里
`typeof window.noticeOnOpen === "function"` 恒为假 → 面板打开什么都不做。
后端的异步错误全被 try/catch 吞掉了，所以**没有任何日志**。

**为什么老的单测抓不到**：源码逐行都对，错在**拼装后的执行顺序**；
后端测试碰不到 JS；真机只是"看起来没功能"，不报错。

**怎么防**：
- **跨模块引用只允许发生在事件/函数调用期**（本项目 `build_frontend_bundle.py` 的注释里
  早就写了这条，我违反了它）。模块顶层只注册事件，不调别的模块的函数。
- 需要"启动即运行"的模块，**自己挂 `DOMContentLoaded` 自启动**（顺带保证 DOM 已就绪），
  不要指望别人在顶层调你。
- 新增 **`tests/test_frontend_boot.py`**：用 Node + 极简 DOM 桩把**产物 bundle 真跑一遍**，
  断言"顶层不抛异常 + 关键入口已注册"。它当场复现了这条 bug
  （`THREW:ReferenceError:Cannot access '_payload' before initialization`），
  也在修好后转绿 —— **产物级的冒烟测试是这类问题的唯一有效防线**。


## 14. 字符串切 URL / 切文件 = 早晚出错（2026-09-19，两处都被自己的测试抓住）

**表现 A**：`_to_notice_root("http://127.0.0.1:12345")` 返回 `"http://notice"`
（把 `//` 里的斜杠当成了路径分隔符）→ 公告源指向一个不存在的主机。
**表现 B**：`_pem_body()` 比对两份公钥时，把整份源文件当成了 PEM 正文
（Kotlin 的 `package` 行、Python 的 docstring 全进来了）→ 门禁报"公钥不一致"。

**根因**：对**有结构的东西**用了字符串操作。URL 有 scheme/netloc/path；
PEM 有 BEGIN/END 边界。`rpartition("/")`、`replace(标记)` 都懒得管结构。

**怎么防**：
- URL 一律 `urllib.parse.urlsplit/urlunsplit`（或等价的结构化解析），
  别用 `split("/")` / `rpartition("/")` —— 主机端口写法里"没有路径"是常态。
- 有边界标记的文本，先按标记**抽出块**再做后续处理；不要"删掉标记当成正文"。
- 这两处都是**写测试时当场抓到的**（`test_notice.py` A 组、`check_hotupdate.py` 公钥项）——
  说明"给新写的解析函数配一条边界用例"的成本远低于事后排查。

## 17. `str.find()` 返回 -1 后再切片 = 静默截断文件（2026-09-20）

**表现**：给 `app/static/js/diag.js` 删一个函数时写了 `s = s[:i] + s[j:]`，
其中 `j = s.find("/** 一键清理", i)` 实际返回 **-1**（锚点没匹配上）
⇒ `s[-1:]` 只剩最后一个字符 ⇒ **文件尾部被整段截断**，
`clearDiagnostics()` 与它的 `window` 挂载一起消失。而脚本照样打印了 `V 已删除 diagSendAgain()`。

**用户看到的现象**：点「清理」**毫无反应** —— 连兜底提示都不出现，因为内联
`onclick="clearDiagnostics()"` 抛 `ReferenceError`，清理前后两张截图**逐像素相同**。
（对照：同一排的「导出并发送」正常，所以我一开始误判成"坐标点偏了"，白试了三轮。）

**根因**：把"找不到"当成了"找到了"。`find()/indexOf()` 用 -1 表示失败，
而切片语法对负索引是**合法**的（`s[-1:]` = 最后一个字符）⇒ 失败被伪装成成功。

**怎么防**：
- `find()/indexOf()` 的结果**只要用于切片或删除**，下一行必须 `assert i != -1`
  （或 `if i < 0: raise`），**不允许**直接进切片。
- **改完立刻断言目标关键字仍在文件里**（如 `assert "function clearDiagnostics" in t`），
  不要只打印一句 "V"。
- 语法检查**不足以**发现这类问题：截断后的 JS **语法仍然合法**，只有运行时才炸。
