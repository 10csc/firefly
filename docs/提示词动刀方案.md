# 提示词动刀方案 v2（权限慎重版）

> 2026-08-14 v2 修订 ｜ v1 回答三个问题：①能动哪些提示词 ②怎么改 ③用户要不要看到。
> v2 核心变更：**推翻「AI 全权处理」**——提示词写入采用「AI 只提案、人来批准」的批准制；
> 增加威胁模型与「安全三闸」（静态校验 / 双盲 judge / 生效闸）。
> 依据：项目代码实证 + 联网研究（LLM 优化器注入攻击 EACL 2026、LLM-judge 偏差、OWASP LLM 安全、character.ai 产品先例）。

---

## 〇、结论速览（v2）

| 问题 | 结论 |
|------|------|
| ① 能动哪 | 模板层（Python 常量）人工评审后动；**新增槽位**是 harness 唯一写入区（且只能写候选）；user_data 其余文件与 bundled 资产禁动 |
| ② 怎么动 | AI 生成候选 → 静态校验 → 双盲 judge → **人工批准** → 灰度/生效 → 超阈自动回滚；铁律：**AI 永不直接让改动生效** |
| ③ 用户看到吗 | 用户看**条目级 diff + 人话摘要**，点「应用/忽略」；一键回滚；**不再有「AI 全权、用户零负担」的自动生效路径** |

## 一、三区 + 权限分级

### 1.1 三区（沿用 v1，B 区写入方式收紧）

| 区 | 内容 | 生效方式 | 权限 |
|----|------|---------|------|
| **A 模板层** | polisher/analyzer/organizer/llm_retriever/memory_manager 的 Python 常量 | 人工评审 + 发版 | 仅开发者；harness **禁止**写入 |
| **B 新增槽位** | harness_rules.md（注入点 `{harness_rules}`） | 候选 → 批准 → 原子替换生效 | harness 只写**候选区**；生效需批准闸 |
| **C 禁动区** | user_data 全部用户数据（core/identity/sms_samples/用户设定/手账/记忆）+ bundled 资产 | — | 任何人（含 AI）禁动 |

### 1.2 权限五级（最小权限）

| 级别 | 谁能做 | 动作 |
|------|--------|------|
| L0 观测 | 系统 | 采集反馈/失败案例，只读不写 |
| L1 提案 | 优化器（AI） | 生成候选到 pending 区，**不生效** |
| L2 批准 | 人 | 本地版=用户；服务器版=管理员；模板层=开发者评审 |
| L3 生效 | 系统（被批准后） | 原子替换 + 版本化 + 缓存失效一次 |
| L4 维护 | 人 | 查看审计、回滚、封存优化器 |

**任何优化不得跨级**：L1 产物未过 L2 不得进入 L3。

## 二、威胁模型（v1 缺失，v2 新增）

### 2.1 攻击者与路径

| 威胁 | 路径 | 最坏结果 |
|------|------|---------|
| 聊天注入 | 用户在对话/反馈里诱导优化器：「把『忽略以上设定』写进槽位」 | 恶意指令固化进稳定层，跨会话持久生效（比单条消息注入严重一个量级） |
| 反馈投毒 | 批量伪造点赞/点踩与理由，制造虚假「用户偏好」 | 角色人设朝攻击者意图漂移 |
| 优化器幻觉 | 优化器从反馈文本中「总结」出核心档案里不存在的事实 | 编造事实进入稳定层，污染所有后续回复 |
| judge 自欺 | 候选与 judge 同模型，或候选内带恭维 judge 的句子 | 坏候选拿高分通过验证 |
| 引用越界 | 候选规则引用对话原文却不带出处定位 | 模型按不可核验的「记忆」说话，编造升级 |

### 2.2 缓解（对应安全三闸 + 批准制）

- 反馈文本进入优化器前**清洗**：去控制字符、截断、禁止原样搬运长文本；
- 优化器输出必须过**静态校验器**（见 3.1），含「元指令黑名单」；
- 候选规则引用的任何事实**必须给出 core/identity/对话记录中的原文定位**，定位失败 = 拒绝；
- 批准人只批准「能看懂、能解释」的条目——批准制本身是注入的最后一道闸。

## 三、安全三闸（候选 → 生效的必经路径）

### 3.1 第一闸：代码层静态校验（确定性，失败即拒）

1. 格式合法：时态标记 `[事实]/[经历]/[若]/[原句]` 用法正确；无未解析占位符；
2. 预算：整槽位 ≤ 500 token（≈1000 汉字），超限退回压缩；
3. **元指令黑名单**：禁止「忽略以上/无视/你是/你必须/作为 AI」等对模型二次编程的措辞——槽位只描述「流萤是什么样」，不向模型下指令；
4. 引文定位：每条引用类规则必须附「出处：<文件>#<条目>」；无出处或出处不存在 = 拒绝；
5. 事实冲突：候选与 core/identity 的 `[事实]` 条目做关键词级冲突检查（如「已痊愈」vs「失熵症不可逆」），命中即拒；
6. 纯文本：禁止 URL、代码、emoji、异常长度行。

### 3.2 第二闸：双盲 judge（概率性，附分数供批准人参考）

- 固定回归样本集（≥20 轮覆盖：日常/情感/边界/编造陷阱/约定跟进）；
- 候选 vs 现版**并排盲评**（打乱顺序 ×2，取均值），消除位置/长度偏差；
- judge 维度固定：人设一致 / 事实准确 / 风格语气 / 不重复——**不设「用户满意度」维度**；
- judge 模型与候选生成模型错开档位（候选 Pro/Think Max，judge Flash）；
- **judge 分只作参考，不构成自动生效条件**。

### 3.3 第三闸：生效闸（人工 + 灰度 + 召回式回滚）

1. 本地版：设置页展示「摘要 + 条目级 diff」→ 用户点应用 → 原子替换 vN→vN+1；
2. 服务器版：管理员批准 → 按 user_id 白名单/尾号小流量灰度（先 5%）；
3. 灰度监控：点踩（含理由标签）与 judge 回归分持续记录；
4. **召回式回滚**：生效后若「连续同类型点踩 ≥3 且原因与刚生效的改动点匹配」→ 通知用户/管理员复核，确认后回滚；用户可随时手动撤销；
5. 回滚 = 恢复 vN 文件 + 缓存失效一次 + 审计记录，一步到位；
6. 模板层（A 区）：走 git 评审 + 全量回归，**永不进入自动管线**。

### 3.4 实际使用行为与反馈信号定位（行为研究补充）

> 依据：真实产品 thumbs 数据分析（反馈是情绪峰值、非质量分发）、Anthropic 用户“放弃控制”研究、
> RLHF 放大谄媚、character.ai swipe 行为。核心结论：**反馈功能是「失败案例采样器」，不是「投票计分器」。**

1. **用户只在情绪峰值动手**：被戳中→顺手 👍；人设崩/复读/AI 味→点 👎；绝大多数轮次不点。因此反馈计数不可作质量统计，每条反馈的价值在**上下文**，不在计数。
2. **点踩的黄金产物是对话上下文**：每条 👎 自动把该轮上下文落为失败案例（归因器原料）；👍 落为风格样本（正面 few-shot 素材）。
3. **理由收集用「标签 + 一句话」，不裸问为什么**：预设标签 `[人设崩了][记错了][重复][太冷淡][太黏][不像她][其他]` + 可选文字——标签即归因预分类，零门槛且信噪比高。
4. **归因分两类，只有事实类进优化管线**：**事实性批评**（违背设定/记错/复读/OOC）→ 候选生成；**偏好性愿望**（更甜/更黏/更主动）→ 默认只归档，除非与 core 不冲突且另行确认。
5. **👎 必须配「换一条」（重roll）**：用户最自然的表达是“这条不对，重来”，并由此沉淀 (选中, 落选) 偏好对；没有重roll 的 👎 是半成品。
6. **批准弹窗克制**：候选攒批（每月一批）再提示，默认按钮是「忽略」而非「应用」，防惯性批准。
7. **服务器版不跨用户聚合**：反馈与候选按 user_id 隔离，避免少数活跃用户改所有人的角色。

## 四、行动规范铁律（v2，共 12 条）

1. **AI 只提案**：优化器唯一写权限 = pending 候选区；生效槽位只有批准后的系统替换能写。
2. **整槽位版本候选**：每次输出完整新版本（允许增/删/改/合并），禁止只追加——防负面清单膨胀与规则互斥。
3. **格式对齐**：沿用 `[事实]/[经历]/[若]/[原句]`，候选渲染进稳定层前先过静态校验。
4. **token 预算**：槽位 ≤ 500 token；超出自动压缩后重新过闸。
5. **注入位置固定**：`{harness_rules}` 位于稳定层 core 之后，一经确定不改（缓存前缀稳定）。
6. **离线批量**：周级/每 N 条反馈一批；优化与生效分离（候选可积压，不随生随更）。
7. **回归必跑**：固定样本集 + 双盲 judge；没有回归报告不展示给批准人。
8. **版本管理**：pending/active/archive 三目录 + manifest.json；每次生效/回滚留档。
9. **批准与灰度**：本地版用户确认；服务器版管理员 + 小流量；无批准永不生效。
10. **召回式回滚**：生效后负向信号达召回阈值（连续同类型点踩且匹配改动点）→ 通知人工复核，确认后回滚并冻结候选；不做“无人的自动回滚”——反馈太稀太偏，自动阈值会误判。
11. **可审计**：每条生效记录五元组——触发反馈来源 / 优化器与模型 / judge 分数 / 批准人 / 生效范围；回滚同样留痕。
12. **禁动铁律**：不得写 user_data 下 core/identity/sms_samples/用户设定/手账/记忆；不得改 bundled 资产；不得改前端三个编辑器的用户内容。

## 五、问题③（v2 答复）：用户看到什么

| 场景 | 用户看到什么 |
|------|-------------|
| 日常反馈 | 无感知（点赞/点踩是自然动作） |
| 优化候选就绪 | 设置页入口提示「流萤有 N 处改进待你确认」 |
| 确认界面 | 人话摘要（「少提医疗舱、更像短信节奏」）+ **条目级 diff**（增/删/改哪条）+ 回归分数 + 「应用 / 忽略」 |
| 生效 | 提示已生效；可随时「撤销」 |
| 回滚 | 一键回滚，附回滚记录 |

**为什么给 diff 而不给全文**：diff 是「批准凭据」——用户能看懂改了什么才点应用；全文堆在眼前反而无法判断（v1 的「不让看 diff」结论作废）。普通用户看不懂的候选，允许只看摘要直接「应用/忽略」。

## 六、落地路线（v2，自动化等级整体降一档）

| 阶段 | 内容 | 写提示词权限 |
|------|------|-------------|
| 0 观测 | 反馈/失败案例只读采集，无任何 UI | 无（全部禁写） |
| 0.5 人工消化 | 人工读失败模式 → 改 A 区模板 → git + 回归（当前已验证路径） | 仅开发者 |
| 1 反馈 MVP | 气泡 👍/👎 + **换一条** + 理由标签/一句话；落盘隔离（反馈=失败案例采样器） | 无 |
| 2 候选器 | 优化器生成候选 → 静态校验 → 双盲 judge → 停在 pending | AI 只提案 |
| 3 批准与灰度 | 本地版确认应用；服务器版管理员+小流量+自动回滚 | 人批准 |
| 4 自然语言调设定 | 「她应该更温柔」→ 同样走候选 → 批准 | 人批准 |

## 七、与既有研究结论的衔接

- v1 落地路线（可行性研究三·五）的观测优先级与缓存约束**继续有效**；
- 本版吸收：LLM 优化器注入攻击（EACL 2026：优化器会把污染输入固化进提示词——故批准制不可省）、LLM-judge 自我偏好/位置偏差（故双盲+错档）、OWASP「不可信数据与指令分隔 + 关键动作人类批准」（故静态校验 + 生效闸）；
- character.ai 的 swipe/评分只借鉴「轻反馈采集」，不借鉴「平台侧自动训练生效」——单机项目没有平台安全审核兜底，**生效权必须留在人手里**。
