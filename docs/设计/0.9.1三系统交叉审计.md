## A2 交叉四组

### A2-1 公告 × 热更 —— **无 bug（1 处设计耦合 + 1 处滞后见 F-01）**
- 热更**不改** `APP_VERSION`（`__init__.py:662-667 running_id`），公告定向只读 `cfg.APP_VERSION`（`notice.py:229`）⇒ 热更不改变公告的版本定向。
- 热更 web 层可覆盖 `web/js/bundle.js`（含 notice.js 代码），但公告**数据缓存**在 `notice/`（与 `hotupdate/` 平级、独立，`paths.py:95-136`）⇒ 缓存不清、仍有效；公告端点 `/notice`、`/notice-image` 由后端路由（`api/router.py:190-191`）决定，补丁不改路由常量 ⇒ **不会指向失效入口**。
- 唯一真实耦合：`notice.base_urls()` 由热更 `url_roots` **翻译**而来（`notice.py:111-120`）——用户改热更源会同时改公告源（设计如此，"一个配置两条通道"）。
- `refreshing` 期间返回的是**缓存那份 manifest**（`notice.py:449-467`），且该缓存是**取回当时**按 base 过滤后落盘的 ⇒ 与"当前前端版本不匹配"只可能发生在**底座刚升级**那一拍（F-01，真跑见 A5-④）。

### A2-2 公告 × 平台 —— **无 bug**
- 平台页**不走公告通道**：`platform.html`/`platform.js`/`platform.bundle.js` 中 `notice` 出现次数 = **0**（实测 `grep -c`）⇒ 不存在"共用通道/缓存键/令牌"问题（令牌与缓存键问题不适用）。
- 令牌隔离：平台用 `localStorage["firefly_token"]`+Bearer（`platform.js:52-53`）；公告端侧同源 `fetch`、`/notice-image` 公开不带头（`routes_notice.py:23-56`、`notice.js:70`）⇒ 两套令牌互不相关。缓存键：端侧 `localStorage["firefly_notice_cache"]`（`notice.js:20`）仅 App 壳用，平台页无此键。
- **XSS 红线：不适用**（平台页无公告块渲染路径）。附带核查平台页自身：`platform.js` 唯一 `innerHTML` 在 `_pfGate`（`:33`，只喂**硬编码字符串**）；plaza 面板的 `innerHTML` **全部是清空**（`="`，plaza*.js 11 处）⇒ 无服务器数据经 `innerHTML`。加固建议见 F-06。

### A2-3 热更 × 平台 —— **无 bug（1 处一致性提示见 F-05）**
- 热更 scope = `app/static/**`（`app/server.py::_static_file` 覆盖层优先、回落 `cfg.STATIC_DIR`=`app/static`，`paths.py:37`）。服务器页由 `server/app.py` 从 `FRONTEND_DIR`=`server/frontend` 提供，**无覆盖层**（`server/app.py` 内无 `web_dir`/hotupdate 引用，实测）⇒ **平台页不被热更覆盖**。
- 三副本同步：`sync_frontends.py` 已**不再** `app/static → server/frontend` 拷贝（`SERVER_PLATFORM` 白名单 + 写模式只自检，行 55/317-325；`server/frontend` 仅 3 个文件进安卓 assets）⇒ **平台页不被同步误改**。
- 升版本号后旧补丁/新整包：`on_startup` 比较 `state.base_version != APP_VERSION` ⇒ `_clear_overlay()`+重置（`__init__.py:679-691`）；`apply_available` 另卡 `manifest.base_version != APP_VERSION`（`:488-489`）⇒ **不混用**。§5.4 反向铁律"底座内容变了必须升版本号"本次正被满足，机制正确。

### A2-4 三向（以**版本号**为枢纽）—— 后果路径（真跑见 A5-③）
改一处会波及：`app/core/config.py:93 APP_VERSION`（后端）→ `app/static/js/update.js:18 CURRENT_VERSION`（前端源）→ **必须重跑** `build_frontend_bundle.py` 重生 `app/static/js/bundle.js:7438`（内嵌 CURRENT_VERSION）+ `index.html` 指纹 → `android/app/build.gradle.kts:96-97 versionName/versionCode`（versionCode 须 > `check_version.py:93 PREV=805`）→ `package/firefly.iss:5` → `server/version.json:2`。
- **未纳入 check_version 的暗处**：`app/static/js/bundle.js`、android assets 两镜像（由 `sync_frontends` 管）、**`server/update.json`**（`/version.json` 的**运行时投影源**，`server/app.py:481-485`）、`notice_src/source.json` 版本文案、热更 `latest.json` 的 `base_version`。
- **具体后果**（A4 中细化为 F-03/F-04）：`APP_VERSION=0.9.1` 而 `server/update.json` 仍 `v0.9.0` ⇒ 服务器 `/version.json` 投影出 `v0.9.0` ⇒ 老客户端"检查更新"显示"已是最新"（F-04）；公告标题仍写 `Firefly 0.9.0 更新说明`（F-03）。

## A4 发现清单（格式：严重度｜证据｜影响面｜触发条件｜建议修法｜本轮是否已改）

**F-01 ｜低｜公告版本定向在"底座升级"后滞后一拍**
证据：`notice.py:229`（`validate()` 用 `cfg.APP_VERSION` 过滤后才落缓存）+ `:449-467`（`payload` 先回缓存、仅在 `last_check` 过期才刷新，`CHECK_INTERVAL=3600`）；对照片 `hotupdate/__init__.py:679-691`（base 变更 `_clear_overlay()`，公告**无**同类清理）。真跑复现：A5-④（缓存未被重定向，`min_app_version` 达标的条目仍不可见）。
影响面：全部端（公告面板内容）。触发条件：装了新整包（base 变）且距上次公告检查 < 3600s ⇒ 新 base 专属公告最多滞后 1 小时（或下线旧 base 专属公告滞后同理）。
建议修法：`notice.py` 增加 base 变更检测（如 state 存 `base_version`，与 `cfg.APP_VERSION` 不同则 `_load()` 视为需重定向：要么清 `manifest` 强制重拉，要么对缓存 manifest 重跑 `_in_range`）。
是否已改：**未改**。

**F-02 ｜低｜服务器版公告缓存/已读状态全局共享（跨账号）**
证据：`paths.py:135-136 notice_root()=USER_DIR.parent/notice` 不用 `_user_ctx_dir()`（对比 `install.py:59-61` 用账号目录）；`routes_notice.py:59-69 mark_read` 写入同一 `state.json`。
影响面：服务器版（App-服务器模式用户）；公告内容为公开运营内容、无用户数据，故危害有限。
触发条件：同一服务器多个账号各自读公告 ⇒ 已读状态互相覆盖。
建议修法：若要让服务器版"已读"按账号隔离，`notice_root()` 需按 `_user_ctx_dir()` 分桶；否则在文档显式声明"已读在服务器版是共享的"。
是否已改：**未改**。

**F-03 ｜低｜公告版本文案未纳入版本一致性门禁**
证据：`notice_src/source.json:9`（`"title": "Firefly 0.9.0 更新说明"`）；`tools/check_version.py` 的 7 处来源不含公告文案。A5-③ 实测升 0.9.1 后该文案仍为 0.9.0。
影响面：用户可见文案（公告面板）。
触发条件：升版本号时忘记改 `notice_src/source.json` ⇒ 面板显示旧版本号文案。
建议修法：把"公告文案版本号"写入发版检查清单；或在 `build_notice.py --check` 里对 `title` 中的版本号与 `APP_VERSION` 做一致性提示。
是否已改：**未改**。

**F-04 ｜中｜版本一致性门禁的盲区：不校验 `server/update.json`（`/version.json` 的运行时投影源）**
证据：`tools/check_version.py:47-48` 只校验静态 `server/frontend/js/update.js`（**已不存在⇒SKIP**）与静态 `server/version.json`；而 `server/app.py:481-485` 的 `/version.json` 实为 `update_manifest.load(update.json)` 的**动态投影**。A5-③ 实测：`APP_VERSION=0.9.1`、`server/version.json=0.9.1`，但 `server/update.json=0.9.0` ⇒ 静态文件与运行时投影源**不一致**且门禁全绿。
影响面：服务器 `/version.json`、`/update-manifest`；老客户端"检查更新"提示（会显示"已是最新"）。
触发条件：只改 `server/version.json`（或不改 `update.json`）而误以为一致；发布时随 `update.json` 部署即暴露。
建议修法：`check_version.py` 增加对 `server/update.json` 的 `tag` 校验（与 `version.json` 同口径），或注释说明"发版必须同步 `update.json`"。**注**：当前版本冻结期是否该改 `update.json` 属发版策略，建议 Lead 拍板。
是否已改：**未改**。

**F-05 ｜信息｜App 端广场与服务器平台页的 plaza 代码在不同副本，热更可致两端行为不一致**
证据：平台页逻辑来自**独立产物** `server/frontend/platform.bundle.js`（`build_frontend_bundle.py --platform`，`PLATFORM_ORDER` 行 38-45），源与 App 共用 `app/static/js/panels/plaza*.js`；热更 web 补丁可覆盖 App 侧 `web/js/panels/plaza*.js`，但**不**覆盖平台 bundle（A2-3 已证）。
影响面：App 端 vs 服务器平台页的广场修复不同步。触发条件：对 plaza 面板发 web 层热更补丁后，未重出/重部署平台 bundle。
建议修法：文档明示"plaza 域热更只惠及 App；平台页需重跑 `--platform` 并部署"。
是否已改：**未改**（只读审计）。

**F-06 ｜信息｜平台页唯一 `innerHTML`（加固提醒）**
证据：`server/frontend/platform.js:33 _pfGate(html)` → `card.innerHTML = html`，当前调用只传**硬编码字符串**（`:39-40`）。
影响面：平台页 DOM。触发条件：未来若有人把服务器返回数据接进 `_pfGate` ⇒ 变成 XSS 口子。
建议修法：保持"`_pfGate` 只接收字面量"的约定并加注释（公告块渲染红线见 `公告通道规范.md §四`）。
是否已改：**未改**。

**F-07 ｜信息｜`notice.payload().app_version` 与前端 `CURRENT_VERSION` 可能不同源**
证据：`notice.py:460` 上报后端 `cfg.APP_VERSION`；前端另有 `update.js:18 CURRENT_VERSION`。二者本应一致（`check_version` 钉死），但若只改一处（F-04 同类），公告定向按**后端** base 走 ⇒ 与用户看到的版本号不符。
影响面：公告定向口径。触发条件：版本号只改一处。
建议修法：由 F-04 的门禁加固一并解决。
是否已改：**未改**。

## A5 真跑结果（脚本在 `_harden/audit091/`，只读、不写功能代码；以下为脚本自判 + 原始输出摘要）
