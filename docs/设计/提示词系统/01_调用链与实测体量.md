## 三、缓存架构（动刀前必须理解的铁律）

### 原理

DeepSeek 按"这次请求开头和上次一模一样的那部分"计费打折——命中部分约为未命中部分的 **1/50**（`llm_base._PRICING`：flash 命中 0.02 元/百万 tok，未命中 1 元/百万 tok）。

于是整套提示词是按这个规则**刻意分层**的：

- **system = 稳定层**：人设、知识库、禁令、样本、输出协议。跨请求一字不变 → 第二轮起几乎免费。
- **user = 变化层**：日期、环境句、对话历史、记忆头、检索摘要、本轮输入。每轮全变 → 全部按未命中计价。

检索器那 13.6 万字符的 system 是缓存命中率的绝对主力，也是冷启动（首轮/改动后首轮）成本的大头。

### 两条红线

1. **不能把动态内容挪进 system。** 日期、历史、记忆头、环境句一旦进 system，缓存前缀被打断，整段重新计价。
2. **system 段内改一个字，全量用户当轮缓存重建。** 所以提示词改动应当**批量做、低频发**，并预期"发布当轮成本尖峰"。

### 已接受的例外

system 里住着两个低频变量，是明知代价仍然接受的：

| 变量 | 何时变 | 影响 |
|------|--------|------|
| 手账 | 每次 rest 后 | 该用户下一轮回复器缓存重建 |
| 用户设定 | 纠错应用后 | 该用户下一轮分析器 + 回复器缓存重建 |

### relay（服务器托管）模式的占位符链路

静态资产不下发真实内容，改发占位符，由 APP 本地填充（资产在用户设备上，服务器只告诉 APP"用哪几个资产"）：

`__CORE__` / `__IDENTITY__` / `__SMS_SAMPLES__` / `__KNOWLEDGE__`（定义在 `llm_base.py:121-124`，浏览器端 `relay.js:53-65` 负责替换）。

**用户设定与手账不走占位符**——它们是用户数据，存在服务器侧。

## 四、流程编排的硬参数

> **2026-09-18 二次修订（用户口径：活跃窗口 30–100 轮）**
> 分析器 / 回复器读的是**活跃窗口**——"自上次整理以来"的**完整对话原文**，除刚开场外常驻
> **30–100 轮**；整理只把"最近 30 轮以外"的部分搬进「历史对话存档」（**只进检索器**）。
> 阈值故意放得很宽（100 轮才触发）：整理一次要花 2 次 LLM 调用，频繁整理就是烧用户 token。
> 接近上限（80 轮）时聊天页顶部出现状态条 + 「现在整理」入口。
>
> ⚠️ **缓存命中率铁律（改动前必读）**：「## 最近对话」在 user 消息**最前面**，
> DeepSeek 按**前缀**打折。窗口 30→100 的**增长期**里历史块只往后追加 → 老部分是稳定前缀、
> 每轮只有新那一轮没命中；一旦有逻辑**从窗口头部裁剪**（token 预算、固定轮数滑动窗口），
> 第一行每轮都在变 → 历史块**永远命中不了缓存**。所以 `BUDGET_*` 是**兜底**不是裁剪手段，
> 必须宽到 100 轮窗口不触发（现 30000 ≈ 200 轮）。

| 参数 | 值 | 位置 |
|------|----|------|
| 活跃窗口上限（触发整理） | 100 轮（`memory_window_turns`） | `modules/auto_rest.py` |
| 整理后保留（仍在窗口内） | 30 轮（`memory_keep_turns`） | 同上 |
| 顶部提醒阈值 | 80 轮（`memory_warn_turns`） | 同上 |
| 重启回灌 | 活跃窗口上限（100 轮） | `routes_common.get_session` → `hydrate_context` |
| 分析器 / 回复器历史 | 活跃窗口全量（预算 30000 兜底） | `orchestrator.py` |
| 组织器历史轮数 | 5（token 预算 3000） | 同上 |
| 检索器话题锚点 | 最近 10 条里的**最后一条用户消息**（预算 3000） | 同上 |
| 主动消息历史 | 判断 8 / 生成 15（预算 30000）/ 组织 5 | `proactive_gen.py` |
| 历史 token 裁剪下限 | 至少保留 3 轮 | `context_manager._MIN_TURNS_KEEP` |
| 单轮总预算 | 210s 硬顶 | `_TURN_BUDGET_SEC` |
| 单阶段超时（思考档） | 90s | `_STAGE_TIMEOUT_THINK` |
| 单阶段超时（非思考档） | 30s | `_STAGE_TIMEOUT_NON_THINK` |
| 剩余预算不足 | < 5s 立即放弃本轮，抛 `timeout` | `_stage_timeout()` |
| 回复条数硬顶 | 6 条（实测出现过 46 条循环输出） | `polisher._MAX_REPLY_MESSAGES` |
| 防复读注入 | 最近 3 条流萤消息，每条截 60 字符 | `polisher.py:356-367` |

"轮"按 **user 消息数**计——历史里夹杂的 system 行为记录（表情包/旁白）不挤占轮数（`context_manager.get_recent`）。

### 窗口外内容去哪了（记忆四层）

| 层 | 文件 | 内容 | 谁读 | 何时更新 | 清历史时 |
|----|------|------|------|---------|---------|
| L0 出厂记忆 | `{pack}/memory/default.md` | 角色开局记忆 | 分析器 + 回复器 | 角色卡管理手改 | **不动**（角色卡资产） |
| L1 用户记忆 | `{mode}/data/memory.md` | **压缩摘要** | **回复器**（`memory_head`） | 整理时自动 / 用户点「AI 压缩」 | **删** |
| L2 历史对话存档 | `{mode}/data/archive/YYYY-MM.md` | **完整对话原文**（按月分片、只增不改） | **只进检索器** | 整理时把滚出窗口的原文追加 | **删** |
| L3 活跃窗口 | `{mode}/data/conversation.jsonl` 里"自上次整理以来"的部分 | 对话原文 | 分析器 + 回复器 | 每轮；整理后保留最近 30 轮 | 清空 |
| L4 手账 | `{mode}/journal/手账.md` | 第一人称记录 | 回复器 system 稳定层 | 整理时 | **删** |

优先级：**L0 < L1 < L2（近）< L3**（越近越权威）；L2 只作事实来源、不作口吻依据。
「菜单 → 设定文件」副页 = L1 + L2 + L4 的可见可编辑入口（都是**用户私有数据**，属角色包、
不进角色卡）。L2 可被用户直接编辑（改完检索器看到的就是改后的），也可点「AI 压缩」压进 L1。

自动整理的成本：每达上限（默认 100 轮）**2 次 LLM 调用**（记忆 + 手账），模型 `cfg.MODEL`，
在**后台线程**跑、不占用户等待（对齐 Letta 的 sleep-time compute）；**不新增任何每轮调用**。
L2 存档只在整理后变化 → 每次整理后该包下一次检索缓存重建一次（与"手账"同一量级的已接受代价）；
注入检索器时按最近 12 个月 / 80000 字符截断（`memory_archive.MAX_*`）。
