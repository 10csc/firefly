## 一、这套系统一句话说清

用户发一句话，后端串行调 **4 次大模型**（haruno 模式 3 次，因为它没有知识库可查）：

| # | 节点 | 干什么 | 代码 |
|---|------|--------|------|
| ⓪ | 检索器 | 把 58 个设定文件整体塞给模型，问"和这句话有关的资料有哪些"，输出一段摘要 | [llm_retriever.py](../../../app/modules/llm_retriever.py) |
| ① | 分析器 | 读 20 轮历史 + 检索摘要，判断"他这句什么意思、说的是谁、有没有说错事实" | [analyzer.py](../../../app/modules/analyzer.py) |
| ② | 回复器 | 真正写流萤的短信。人设、禁令、短信样本都在这一步 | [polisher.py](../../../app/modules/polisher.py) |
| ③ | 组织器 | story 挑表情包；haruno 写旁白 | [organizer.py](../../../app/modules/organizer.py) |

编排在 [orchestrator.py](../../../app/orchestrator.py)。另有按需触发的独立调用（主动消息动机决策、休息时记忆整理、手账更新、识图、设定纠错），不在这条主链上。

## 二、五条核心结论（细节见分册）

1. **成本结构是刻意设计的，不是巧合。** 不变的内容全放 system 开头吃缓存，每轮变的内容全放 user。检索器那 13.6 万字符的 system 之所以敢每轮发，就是因为第二轮起几乎不要钱。→ [01](01_调用链与实测体量.md)

2. **禁令有 27 条（story 16 + haruno 11），其中 9 条是通用大模型腔病，两份是手抄副本且已经分叉。** story 有「复读自己」这条，haruno 漏了。→ [02](02_禁令清单与分类.md)

3. **最有效的约束不是禁令，是数据注入。** 代码注释自己承认："规则约束依赖模型自觉，效果有限"（`polisher.py:353-355`）。防复读真正起作用的是把"你最近说过的 3 句原文"直接列给模型。→ [02](02_禁令清单与分类.md)

4. **旧向量数据库（RAG）设计的残留已于本次清理。** 检索器是它的替代品、是活的；死的是 4 个无人消费的字段和一段每轮白做的提示词任务。→ [03](03_结构问题与清理记录.md)

5. **耗时只由"模型吐出多少字"决定，与输入体量无关（已验证）。** 四个节点服从同一条公式 `耗时 ≈ 1.84s + 产出字符/192`（R²=0.67，去长尾后 0.88）；以 system 体量为自变量则 R²=0.001。分析器占 55% 是因为它的产出量是回复器的 6.6 倍，其中 71% 是思考文本——**那是"仔细"的代价，不是浪费**。同时这也推翻了"先把组织器后台化"的直觉（story 只占 4%）。→ [04](04_耗时实测与并行方案.md)

## 四、边界（哪些能动、哪些不能动）

| 层 | 内容 | 能不能动 |
|----|------|---------|
| A 角色资产 | `user_data/{mode}/character/` 的 core / identity / sms_samples / 用户设定、`knowledge/`、手账、memory.md | **不动**。这是角色本体和用户数据，改动走[设定纠错助手](../设定纠错助手设计.md)的"AI 提案 → 人批准"链路 |
| B 系统提示词 | 各节点模板里的工程件：时空口径、底色条款、禁令、输出协议、JSON 契约、降级话术 | **可设计面**。本目录讨论的就是这一层 |
| C 流程编排 | 调用顺序、历史轮数（20/15/5）、超时降级链、占位符链路、三通道门控 | 可动，但每处都牵连错误透传，要整体改 |
