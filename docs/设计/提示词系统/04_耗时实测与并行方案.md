# 04 耗时实测与并行方案

> 数据来源：`user_data/{mode}/data/pipeline.jsonl`（编排器每轮把四阶段 `elapsed` 落盘）。
> 统计时间：2026-08-29。样本：story 44 轮（2026-08-11 ~ 08-17）、haruno 15 轮（2026-08-11 当天）。
> **样本量小、时间跨度短、配置单一**（44 轮全部是 `deepseek-v4-flash`，分析器/回复器 high、检索器/组织器 none）。下面的结论按此前提读。

---

## 二、数据推翻的两个直觉

### 直觉 A：「先把组织器摘出串行链，收益最大、风险最低」→ **story 模式站不住**

组织器在 story 只花 0.98s，占 4%。把它后台化，用户感知延迟从 23.7s 降到 22.7s——**几乎没有价值**。

但在 **haruno 它值 5.01s（26%）**——因为那里的组织器不是分类任务，是 Think High 的旁白创作。

> 结论：这个改动**只在 haruno 模式有意义**。同一个优化在两个模式的收益差 5 倍，不能一概而论。

### 直觉 B：「瓶颈在那个 13.6 万字符的检索器」→ **不成立**

检索器 6.18s（26%），而且波动极小（P90 只有 7.63s，最大 8.51s）——巨大的 system 因为几乎全部命中缓存，反而是**最稳定**的一段。

**真正的大头是分析器：12.98s，占 55%，且极不稳定（P90 25.28s，最大 54.71s）。**

## 三、分析器为什么慢？——已验证：**因为它想得多，不是因为输入长**

> 验证于 2026-08-29，同一份 `pipeline.jsonl`（story n=42、haruno n=15）。统计量自实现，无第三方库。
> 显著性标记：\* p<0.05　\*\* p<0.01　\*\*\* p<0.001（Fisher-z 近似）

### 证据 1：输入长度与耗时无关，产出量强相关（story）

| 因素 | 与分析器耗时的相关性 | R² |
|------|--------------------|-----|
| 输入：检索摘要长度 | r = +0.100（不显著） | 0.01 |
| 输入：用户消息长度 | r = +0.118（不显著） | 0.01 |
| 输出：思考文本长度 | **r = +0.624 \*\*\***（Spearman +0.852） | 0.39 |
| 输出：JSON 结果长度 | r = +0.439 \*\* | 0.19 |
| 输出：思考 + JSON 合计 | **r = +0.651 \*\*\***（Spearman +0.884） | 0.42 |
| **控制住产出量后，输入长度的偏相关** | **r = −0.021（解释力归零）** | — |

### 证据 2：最慢的轮和最快的轮，输入几乎一模一样

| story | 耗时中位 | 思考字符 | JSON 字符 | 检索摘要字符 | 用户消息字符 |
|---|---|---|---|---|---|
| 最快 25% | 5.34s | 480 | 368 | **973** | 12 |
| 最慢 25% | 24.91s | **3,515** | 606 | **1,016** | 16 |

慢 4.7 倍的那批轮，**输入体量几乎相同（973 → 1,016）**，差别全在思考量（**7.3 倍**）。

### 证据 3：haruno 是天然对照组

haruno 没有检索器，注入分析器的检索摘要**长度恒为 0**。若"输入长导致慢"成立，它应该明显更快。实测：

| | 分析器耗时中位 | 最快 25% 思考量 | 最慢 25% 思考量 |
|---|---|---|---|
| story（有检索摘要） | 12.98s | 480 | 3,515 |
| haruno（**无任何检索摘要**） | 11.67s | 673 | 3,715 |

**输入里一个字的检索摘要都没有，分析器照样慢。** 假设被证伪。

### 证据 4：四个节点服从同一条规律（217 个样本点合并回归）

```
耗时(秒) ≈ 1.84 + 产出字符数 / 192        R² = 0.669
去掉最慢 2% 的长尾后：1.92 + 产出/217     R² = 0.877
```

用这一条公式反推每个节点：

| 节点 | 产出中位 | 实测中位 | 公式预测 | 误差 | 该节点 system 体量 |
|------|---------|---------|---------|------|------------------|
| 检索器 | 933 字符 | 6.18s | 6.71s | +0.53s | 135,875 字符 |
| 分析器 | 2,088 字符 | 12.55s | 12.73s | **+0.18s** | 10,053 字符 |
| 回复器 | 296 字符 | 3.23s | 3.38s | +0.15s | 14,161 字符 |
| 组织器 | 16 字符 | 1.11s | 1.92s | +0.81s | 303 字符 |

**反证**：以 system 体量为唯一自变量做回归，**R² = 0.001**。检索器的 system 是组织器的 **448 倍**，耗时只有 6.3 倍——而且那 6.3 倍完全能用产出量解释。

### 三条结论

1. **耗时几乎只由"模型吐出多少字"决定**（思考文本 + 正式输出），与输入体量、system 大小基本无关。这符合自回归生成的机制：输入是并行预填充且大部分命中缓存，输出是逐字串行生成。
2. **分析器慢是因为它的产出量是回复器的 6.6 倍**（2,249 vs 340 字符），其中 **71% 是思考文本**。它在按提示词逐项做分析——**这是"仔细思考"的直接代价，不是浪费**。
3. **组织器的 0.98s 几乎全是固定开销**（产出仅 16 字符，公式里 1.84s 的常数项就是网络往返 + 调度）。它已经没有可压缩空间。

### 一个可证伪的预测

本次清理删掉了分析器 4 项任务中的 1 项（`knowledge_query`/`memory_query`，见 [03](03_结构问题与清理记录.md)）。按上述规律，它的思考产出量应下降，耗时随之下降。

**清理前基线（story，n=42）**：思考中位 1,606 字符 + JSON 474 = 2,249 字符，耗时中位 12.98s。

再积累 20+ 轮后重测即可比对。若产出量没降，说明"任务项数量 → 思考量"的链路不成立，本预测作废。

## 四、三种并行方案（收益已用实测数据折算）

先看真实依赖（`orchestrator.py`）：

```
检索器  ← 本轮输入 + 上一条用户消息         （不依赖任何模型输出）
分析器  ← 本轮输入 + 20轮历史 + 环境 + 检索器输出   ← 唯一一处真依赖
回复器  ← 分析器结果 + 15轮历史 + …
组织器  ← 回复器刚生成的文字 + 5轮历史
```

| 方案 | 做法 | 实测收益 | 代价 |
|------|------|---------|------|
| **A 组织器后台化** | 文字先返回前端，组织器在后台跑，表情包/旁白稍后补发（前端已有 `/chat-stage` 轮询通道） | story **0.98s（4%）**；haruno **5.01s（26%）** | 零语义风险，纯返回时机改动 |
| **B 检索器提前发车** | 检索器不依赖任何前序输出，可在用户按下发送的瞬间发出，甚至借 `typing_long` 信号预热 | ≤ 排队等待时间（未直接测量） | 预热可能白跑（用户改词/不发） |
| **C 检索 / 分析并行** | 检索摘要不再进分析器，直接进回复器；两者同时发出，回复器等齐 | story **6.18s（26%）** | **分析器的 `fact_check` 失去知识库支撑**，只剩 core/identity/用户设定可依据，冷门设定的核查会变弱 |
| **D 分析器减负** | **只有一条路：让它少吐字**——减任务项 / 减 JSON 字段 / 降 effort 档 | 占比最大（55%），但按 §三 公式，产出减半也只换约 6s | **直接拿理解质量换速度**——分析器的思考量就是它"仔细"的程度 |

### 依据 §三 修正后的判断

- **"缩短注入分析器的检索摘要 / 减历史轮数"这条路已被数据排除**：输入长度对耗时的解释力为零（控制产出量后偏相关 −0.021）。砍输入只会削弱理解，**换不到时间**。
- **方案 C 的 6.18s 仍然成立**——它省的是"检索器这次调用本身的排队时间"，与输入长度无关。代价（事实核查失去知识库支撑）也不变。
- **方案 D 要非常谨慎**：分析器 12.98s 里约 71% 花在思考文本上，那正是它在逐项核查、判断主语指代的过程。压缩它 = 让它想得更少。**在有回复质量回归手段之前不动。**
- **方案 A 在 story 已无空间**：0.98s 里几乎全是固定开销（公式常数项 1.84s 量级）。haruno 的 5.01s 仍值得后台化。

**优先级（依据实测）**：haruno 做 A（26%）→ 评估 C（story 26%，拿核查质量换）→ D 需先有质量回归手段，暂不动。

## 五、组织器该不该也给 20 轮历史？

**story（挑表情包）：不该。**
它只需要两件事——这串消息的情绪、最近有没有连着发过表情包（频率控制）。5 轮完全覆盖这个频率窗口。它是 Non-think + temperature 0.3 的分类任务，给 20 轮只会多花钱、多噪音、更容易被无关内容带偏。实测 0.98s 也说明它现在毫无压力。

**haruno（写旁白）：现状偏紧，但解法不是加轮数。**
旁白是 Think High 的创作任务，需要知道"人在哪、刚发生了什么、上一段旁白写过什么"。而旁白是以 system 行为记录的形式混在历史里的（`orchestrator.py:508-510`），5 轮里可能只剩两三条。

**更好的做法**：与回复器防复读同一套路——把**最近 N 条旁白单独抽出来**，作为"已经写过这些"的数据清单注入，而不是把窗口从 5 拉到 20。更省、更准，还顺带解决旁白自我重复。

## 六、复现方法

统计脚本为一次性用途，未入库。全部输入来自 `user_data/{mode}/data/pipeline.jsonl`（跳过带 `error` 字段的异常轮）：

| 分析 | 取哪些字段 | 算什么 |
|------|-----------|--------|
| 阶段耗时（§一） | 各节点 `elapsed` | 中位 / 均值 / P90 / 最大 |
| 归因（§三 证据 1–3） | `retriever.knowledge`、`analyzer.reasoning`、`analyzer.raw_json`、`user_input` 的**字符长度** vs `analyzer.elapsed` | Pearson / Spearman / 偏相关（控制产出量） |
| 统一规律（§三 证据 4） | 四节点各自的「思考 + 输出」字符数 vs `elapsed`，合并为一个总体 | 最小二乘线性回归 + R² |

注意事项：
- story 的分析器与回复器有效轮数是 42（不是 44）——2 轮 `elapsed` 缺失或为 0，已剔除。
- `organizer.reasoning` 恒为空（Non-think 档不产生思考文本），组织器的产出量只算 `raw`。
- 用字符数而非 token 数是因为 `pipeline.jsonl` 不记 token；两者在中文文本上近似线性，不影响相关性结论。
