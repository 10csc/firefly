## 二、本次清理记录（2026-08-29）

### 背景：这里的 "RAG" 指什么

指的是**已抛弃的本地向量数据库设计**，不是现在的检索器。检索器（`llm_retriever.py`）是它的替代品，是活的、每轮真在跑。

放弃向量方案的原因记录在 `llm_retriever.py:4-10`（保留，它解释了当前设计的由来）：安卓端装不下 95MB embedding 模型 + numpy 索引；向量 top-k 截断会丢掉"间接关联"（相关的人、过去的约定、类似情境），而角色扮演恰恰依赖这种全局关联。

核对结果：`app/` 与 `server/` **没有任何向量库实现**——grep `embedding`/`vector`/`faiss`/`numpy` 只命中注释，`build_index.py` 已不存在。死的只是几个字段和一段提示词。

### 副作用与验证

- **提示词缓存**：分析器 system 段改动 → 全量用户下一轮分析器缓存重建一次（预期内的一次性成本尖峰）。同时 user 段少了两行 hint、输出少了两个字段，此后每轮略省。
- **android 副本**：`android/app/src/main/python/backend/` 与 `build/python/sources/` 下的同名文件是**构建期自动拷贝产物**（`android/app/build.gradle.kts:10-25` 把仓库根的 `app/`、`knowledge/`、`database/` 拷进去），**不需要手工同步**，重新构建即生效。
- **前端**：流程日志面板只读 `retriever.knowledge`，不读已删的 `retriever.memory`（`app/static/js/panels.js:234-236`），无需改动。
- **测试**：analyzer 16/16、orchestrator 17/17、polisher 14/14、organizer 13/13、llm_retriever 12/12，五套全绿，退出码全 0。
