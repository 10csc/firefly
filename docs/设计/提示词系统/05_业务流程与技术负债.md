# 05 业务流程梳理与技术负债

> 成文 2026-08-29。范围：`app/`（本地版 + 服务器版后端）+ 前端源码；`server/` 不入 git，仅职责提及。
> 目的：改动图片链路时反复用到同一张图——发图前后到底经过哪些环节、哪些代码可动、哪些是别的系统的东西。

---

## 一、主链：一条消息从发送到渲染

```
[前端 chat.js] 用户输入/选图/表情包 → _chatSend() 入批（5s 合并窗口）
   |  发送 ≠ 提交：输入框内容永不自动提交；批次窗口内连续消息合并为"一轮"
   ▼
[routes.py chat()] 窗口合并（_CHAT_WINDOW_SEC=5s，最多 10 条）
   → 每类消息落 jsonl（即时写盘，刷新不丢）
   → 文本拼 user_input（[图片：desc] / [表情包：x] / [引用xxx]）
   → 图片另取字节 → vision_urls（≤4 张，仅当轮）
   ▼
[orchestrator.handle_chat()]
   ⓪ 检索器（story；haruno 跳过）→ 知识摘要
   ① 分析器 → intent / fact_check / summary
   ② 回复器 → [MSG] 行序列（≤6 条硬顶；带图时原图作 image_url block 注入）
   ③ 组织器 → story 表情包 label / haruno 旁白（失败只丢装饰）
   → messages 返回；每条即时落盘（带 time）；pipeline.jsonl 记全过程
   ▼
[前端渲染] 消息流 + 表情包/旁白按 after 穿插
```

**关键不变量**（动主链时的边界）：
- **窗口语义**：后端 5s 窗口 + `hint`（打字中）延长 + `/chat/flush` 立即提交；`chat_flush`/窗口是队列逻辑，**不属于核心流程**，上文图片改动没碰它。
- **写盘即时性**：用户消息在窗口内就写 jsonl（防刷新丢失）；撤回/撤销走 `remove_last_turn` + 记忆游标回退（`undo()` 里"游标 > 轮数"是修过的真 bug）。
- **回复通道锁**：`reply_lock/reply_unlock`（模式级）——主 chat 与主动消息互斥，防顺序错乱。

## 二、旁路：按需触发的独立调用

| 触发 | 位置 | 干什么 | 与主链的关系 |
|------|------|--------|-------------|
| 主动消息 | `proactive.py`（gate+gen） | 门控（代码层，零 LLM）→ 动机决策（轻量 Non-think）→ 生成复用 polisher 完整角色 prompt | 与 chat 共用 reply_lock 互斥；写盘前检查用户是否刚发消息 |
| 休息 rest | `memory_manager.rest()` | 旧头部+新对话（带时间戳）→ 新头部/已解决/新增条目；日期铁律三道防线 | 用户手动触发；顺手更新手账 + `reload_journal` + 刷新 `memory_head` |
| 设定纠错 | `setting_fix.py` | 对齐（≤6 轮）→ 提案（≤4 处）→ 用户批准 → 应用（白名单 6 文件）→ 回滚 | 独立两阶段 Agent；应用后清 llm_base/polisher 缓存 |
| 识图 | （已取消自动链路） | 图片理解统一由模型原生识图 | 见 [03](03_结构问题与清理记录.md) |
| 表情包 | `sticker_picker.py` | label → 文件；组织器仅选 label | 组织器输出消费 |
| 收藏/引用 | `conversation_store` | quote 快照白名单字段；引用合成 [引用xxx] | 用户消息组装处 |

| 观测 | pipeline.jsonl / request log | orchestrator / llm_base | 前端流程日志面板 / 管理台 | 内存环形 + 落盘 |
