> 上游：[09 本地卡发布到广场](09_本地卡发布到广场.md)（限制表与"按份数拦截"的全量扫描在那边）。

## 一、知识库文件名/分组名：**分段**校验（2026-10-02 修）

**故障**：用户载入自己的官方卡时被拒 —— 「知识库文件名不合法：只能用中文/字母/数字/-/_（≤24 字）」，
但他的卡完全合法。根因：一层分组 `knowledge/<域>/<名>.md` 被按**扁平名**规则校验，`/` 不在允许集。

**现在**（`plaza_forge_files.js::_pffSeg` / `_pffKbCheck`，与后端 `card_format._is_free_text` 逐条对齐）：

| 项 | 规则 | 依据 |
|---|---|---|
| 分段 | 域、名**各自**校验；域为空 = 扁平 `knowledge/<名>.md` | 契约 06 §3.1 允许一层分组 |
| 允许字符 | 中文/字母/数字/`-`/`_`/空格/`.`/`·`/`（）`…… **只要不是控制字符、`/`、`\` 都允许** | 后端 `_TEXT_NAME_RE = ^[^\x00-\x1f/\\]{1,40}\.(md\|txt\|json)$` |
| 长度 | 每段 **≤40 字** | 后端 `dir: len(group) > 40` 与 `_TEXT_NAME_RE{1,40}`（⚠ **不是** Lead 建议的 64：服务端没改，前端不额外放宽） |
| 仍挡 | `..`、控制字符、`/`、`\`、以 `.` 开头、超长、路径重复 | 路径穿越 / 隐藏文件防护 |
| 报错 | **指名道姓**：哪一段、哪个字符（含编码）、当前多长 | 用户要求"别只给一句笼统话" |

实测（`tests/manual_plaza_publish_local.py`）：
```
㊳ 分组卡能载入：dirs=['factions','我的 域（一）',''] names=['势力志','设定 v1.2·草稿','扁平名.md']
㊴ 分组卡能存草稿（服务端也认一层分组）
㊵ 「../x」→ 知识库文件名不能包含「..」（防路径穿越）。
㊶ 控制字符 → 知识库文件名里有控制字符（不可见字符，编码 7），请删掉后重试。
㊷ 41 字 → 知识库文件名太长：当前 41 字，上限 40 字（请缩短）。
㊸ 域含「/」→ 知识库分组名不能包含「/」：要分组请填在左边的「域」栏（一层分组）。
```
> 行内实时提示（`.pff-kb` 下的 `pf-idtip`）与提交预检**共用同一个函数**（`_pffKbCheck`），
> 所以"看着是绿的就能存"，不会再出现"两处规则漂移"。

## 二、载入已有卡时**自动压缩图片**（2026-10-02 修）

**故障**：载入官方卡时头像/详情图**原图透传** ⇒ UI 直接红字（`头像 54KB/30KB`、`详情图 338KB/300KB`），
等于"载入即坏"，只能手改。

**现在**：`plaza_forge_images.js::_pfiNormalizeLoaded()` 对每个已有槽位走**与选图完全同一条**逐级压缩
（`_pfiCompress` ⇒ `imgzip.compressImage` + 逐级降尺寸/质量）：

- 只在"超体积**或**超长边"时才压（合规的原图不动，避免无谓重编码）；
- 压到合规 ⇒ 替换，并记 `meta.from` ⇒ 槽位旁显示 **「5.8 KB → 2.1 KB，已自动压缩」（合格）**；
- 压不动 ⇒ 保留原图，交给 `_pfiValidate()` 红字（人话），不静默丢图；
- 载入消息里也汇总一行：`已自动压缩：头像 5.8 KB → 2.1 KB、详情图 15 KB → 13 KB`；
- 顺序：**先归一化、再派生 thumb**（thumb 从合规图派生）；改编态下归一化会重拍基线快照，
  避免"自动压缩"被 diff 误判成"用户改了图"而多传字节。

实测：`㊺ 头像 ≤30KB ✓ ㊻ 详情图 ≤300KB ✓ ㊼ thumb ≤12KB ✓ ㊽ 压完可直接存草稿`。

## 三、管理员**免审**（2026-10-02 修）

**故障**：管理员仍被要求「提交审核」才能发布（服务端 `drafts.publish_draft` 对 admin 本就跳过 verdict 闸）。

**现在**（`plaza_forge_review.js::_pfSyncBtns` + `_pfPublish`）：

- `role == admin` ⇒ **隐藏「提交审核」**，显示 `#pf-admin-note`「管理员免审：存一次草稿后可直接发布」；
- 发布闸门改为：admin 只要**存过草稿拿到 id** 就能发布；非 admin **不变**（必须"审核通过 + 未改动"）；
- 角色未知时按**非管理员**处理（失败即严），角色拿到后 `_pfSyncBtns()` 立刻重算。

实测：`㉑c 管理员看不见强制审核 ㉑d 未送审即可发布 ㉑e 免审直接发布成功`；
非管理员回归 `㊱b 提交审核可见 + 未过审时发布禁用`；本地模式同样生效
（`manual_plaza_publish_local_app.py` ⑦b2/⑦b3：`/auth/state` 带 role=admin ⇒ 提交审核隐藏、直接发布）。

## 五、审核结论：**系统异常 ≠ 审核未通过**（2026-10-02）

用户截图里"审核输出无法解析"被显示成"审核未通过"那种口吻 ✗ ⇒ 现在分两类：

| 类型 | 判据 | 界面 |
|---|---|---|
| **系统异常**（调用失败/无法解析） | HTTP 非 2xx（`ReviewError`），或返回带 `error_kind`/`raw_excerpt`，或 `reasons` 里是"无法解析/解析失败/调用失败" | 「**审核服务异常（<error_kind>），可重试**」+ **重试按钮**（提示区 `#pf-msg` 与结果区 `#pf-rev-retry` 各一个）+ `<details id="pf-rev-detail">` 折叠 `error_kind`/服务端原因/`raw_excerpt`；`draftStatus` 留在 `draft`（**不是** rejected：卡本身没被判有问题）；**弹窗故意留着**，用户可改 Key 直接重试 |
| **转人工**（业务结论） | `verdict == "manual"` 且**无**上述系统标记 | 「模型判为转人工复核（**业务结论，不是系统故障**）：等复核结果，…」 |
| 未通过（业务结论） | `verdict == "reject"` | 原来的"按下面的理由改好，改完必须重新提交审核" |

**管理员不被系统故障卡死**：`_pfSyncBtns` 对 admin **不看 verdict**（只要存过草稿拿到 id 就能发布）；
非 admin 维持 `verdict==="pass" && !dirty`（回归断言保留）。实测：
```
㊾ 系统异常不写成「审核未通过」  ㊿ 两个重试按钮都在  🅐 error_kind/raw_excerpt 折叠可见
🅑 draftStatus 仍是 draft       🅒 非管理员不能发布  🅓 转人工是业务口吻  🅔 非管理员不能发布
㉑f 管理员在 verdict=manual / reject / (空=系统异常) 三种下**都能发布**
```

## 六、真机视口的布局守卫 + 层叠断言（2026-10-02）

用户真机实测视口（Lead `adb`）：**Physical 1264×2780 / density 560 ⇒ DPR 3.5 ⇒ CSS ≈ 361×794**。

- **我这边量不到相交**：几何 + `elementFromPoint` 在 **9 个视口**（361×794 / 360×794 / 393×864 /
  393×873 / 360×780 / 412×915 / 393×500 键盘态 / 390×844 / 1280×900）都通过；`#pf-form` 是独立滚动区
  （`scrollHeight≈12400 / clientHeight≈300`），槽位按钮在滚动内容内、不越出。
- **唯一层叠/合成嫌疑**：祖先链上的 `#plaza-view { backdrop-filter: blur(10px) }` —— 非 none 的
  `backdrop-filter` 会**新建层叠上下文 + 成为绝对/fixed 后代的包含块**并多一个合成层；安卓
  Chrome/WebView 上"`backdrop-filter` 容器 + `overflow:hidden` + 绝对定位子层（`.pfc-cols`）"是已知的
  **合成/裁切异常**组合，症状正是"视觉重叠但几何不相交"。
- **定向修复**：`#plaza-view.plaza-forge-on { backdrop-filter: none; -webkit-backdrop-filter: none; }`
  —— **只在制卡态**去掉毛玻璃（广场列表态原样），布局零变化（守卫输出里 `forgeBackdrop` 已从
  `blur(10px)` 变为 `none`，form/pane/box 与按钮坐标逐像素一致）。
- **加固（结构上不可能越界）**：`.pfi-img`/`.pfi-bar` `position:relative` + 按钮 `static`、
  `.pfi-bar{flex-wrap:wrap}`；`.pfc-pane`/`#pf-body{overflow:hidden}`；`#pf-form{overflow:auto}`（两轴都裁）；
  `.pfc-box{position:relative;z-index:2}`。
- **守卫（`manual_platform_smoke.py`，9 视口 × 3 条）**：① B20 提示条与草稿箱标题不相交；
  ② B20b **所有** `.pfi-bar .pf-btn` 与 `.pfi-stkdel` 与标题不相交；③ **B20c 层级断言**（Lead 要求）：
  在屏且未被裁掉的槽位按钮，其中心点 `elementFromPoint()` 必须命中它自己或其后代。
- 诊断已核实为**正常**的一例：真机"滚到底"时按钮中心命中 `cv-back`/`pz-msg-txt` —— 那些按钮此时
  已滚出 `#pf-form` 裁切框，命中点自然属于 header/提示条 ⇒ 守卫按"与滚动框相交"过滤后再断言。
- `adb` 不在本机 PATH（真机接在 Lead 那台）⇒ 视口取"真机物理尺寸 ÷ DPR"的常见组合；
  若用户仍能复现，需要**该机型的 CSS 视口值**（`adb shell wm size` + `wm density`）才能精确对齐。
