# 06 制卡自由度与图片规格（2026-10-01 用户追加要求）

> **本文是冻结的接口契约**：后端（`serverops`）与前端（`frontend`）各自实现，**不得单方面改动**；
> 要改先改本文并在此记一行「谁、何时、改了什么」。

## 一、用户原话与由此确定的目标

> 「服务器开放平台上的角色卡制作应该是和 app 里的用户个人『角色卡管理』里的角色卡制作是一样的才对
> （**自由度要高**），当前这个自由度不够高。另外，**可以从源头缩减流量大小**（比如服务器上的公开
> 角色卡展示时图片只有 **几 KB** 大小，创作时也**限制图片大小或者干脆不要图片，只保留头像和有限
> 数量的表情包以及文本**）。」

⇒ 两件事同时做：

| # | 目标 | 判据 |
|---|---|---|
| G1 | **web 制卡自由度 = App「角色卡管理」**：能自由写/增删文本文件，能配头像与有限表情包 | 制卡页可创建/编辑多份文本；分类、标签、开场白、展示模式都能改；与本地包编辑的**所见能力**对齐 |
| G2 | **从源头砍流量** | 广场**列表只用几 KB 的缩略图**；创作时就卡死图片数量与单张体积；详情页才用大图 |

## 二、现状（为什么要改）

- 卡片格式 `app/plaza/card_format.py` 的 `character/` **文件白名单是固定的**：
  `preset.json`（后端生成）/`core.md`/`identity.md`/`sms_samples.md`/`opening.json`，
  图片只有 `assets/cover.*` 与 `assets/avatar.*` ⇒ **多一份知识库文件都不行**。
- `_card_zip_from_payload()` 只认这几个字段 ⇒ 前端表单只能填固定几栏。
- 广场**列表**每条返回 `cover` 原图（实测 **151KB/张**）：20 张一屏 ≈ **3MB** ⇒ 这是流量的真正大头
  （`tests/test_plaza_budget.py` 已实测：封面占单卡流量 87%，卡体 zip 仅 10.9KB）。

## 三、冻结契约（V1）

### 3.1 卡片 zip 布局（`character/` 之下）

```
character/
  preset.json               # 后端生成，**用户不可提交**（安全边界，保持不变）
  core.md identity.md sms_samples.md opening.json      # 原有，语义不变
  stickers.json             # ★新增：表情包标签映射 {"sticker-1.webp": "开心", …}（可省）
  knowledge/<name>.md       # ★新增：知识库，**份数不限**（受"单卡文字总量"与文件数 ≤500 约束）
  knowledge/<域>/<name>.md   # ★新增：也允许**一层分组**（App 编辑器写的就是 world/factions/… 五域）
  assets/avatar.<ext>       # 头像：≤256px、≤30KB
  assets/thumb.<ext>        # ★新增：**列表用小图**：≤320px、≤12KB
  assets/display.<ext>      # ★新增：详情用：≤1024px、≤300KB
  assets/sticker-<n>.<ext>  # ★新增：表情包，n=1..8，每张 ≤160px、≤20KB
```

- **知识库命名（2026-10-02 放宽 + 按段校验）**：`knowledge/<名>.md|txt|json` 或
  `knowledge/<域>/<名>.md|txt|json`（**一层分组**）——**每段各自 ≤64 字**（原 24/40），可用字符
  中文/字母/数字/`-`/`_`/**空格**/`.`/`·`/`（）`（其余可打印字符也不主动拒）。**必须按段校验**：
  把 `域/名.md` 当扁平名一起量，正是用户 00:34 载入自己的官方卡时被误拒的原因（前后端同口径）。
  仍**保留**（路径安全、管理员也不豁免）：`..`、`\`、控制字符、隐藏段（`.` 开头）、段首尾空白/结尾点、超长。
  拒绝文案**指名道姓**（哪一段、哪个字符、当前长度），例：
  `知识库文件名含控制字符 U+0001：'坏\x01名.md'`、`知识库分组名不能以 `.` 开头（隐藏文件/目录）：.git`。
- **体积口径（2026-10-01 松绑，用户要求「不要限制那么多，只是图片限制」）**：
  - **文字按"单卡总量"管**：知识库 + core/identity/sms_samples 等文本之和 **≤8MB**（普通账号）；
    **不再限知识库份数**（原 6 份已删）、**不再限单文件**（原 64KB 已删）。
    ⚠ 压缩比守卫（zip 炸弹）**只对非文本**生效 —— 文本已受总量约束，markdown 表格/重复章节
    天然高压缩比，拿炸弹规则去拒它是误杀（实测 200KB 重复样本就是这么被拒的）。
  - **图片仍逐张按槽位规格限**（上表；这条**不许松**）：thumb ≤12KB、avatar ≤30KB、
    display ≤300KB、sticker ≤20KB×8（`cover` 老槽位 ≤300KB 沿用）。
  - **卡体**：zip 本体与解压后均 ≤**10MB**（文字 8MB + 图片余量）；`character/` 下文件数 ≤**500**（2026-10-02 由 24 放宽：用户实测 33 个文本被挡）、深度 ≤3 不变。
  - **管理员**（`role == admin`）：文字总量**不限**、卡体天花板抬到 **64MB**
    （"不限"也留个安全上限，防手滑把服务器磁盘打满；安装配额同样豁免，见 04）。
    > 用户原话："我不是管理员账号吗？""难道我作为管理员，连发布官方的角色卡都不行吗？"
- 文本扩展名仅 `.md`/`.txt`/`.json`；目录仅 `character/` 根、
  `character/knowledge/` 与其**一层子目录**（`world/factions/story/character/dialogues` 或用户自定名）
  —— **不许**出现其它目录、不许更深，防越界。
  > 为什么允许一层分组：App 自己的包编辑器写的就是 `knowledge/<域>/x.md`；
  > 若只认扁平，**App 里做好的卡发布到广场会被拒**（互操作漏洞，2026-10-01 由 `clientpack` 审计发现）。
- 图片仅 `assets/` 下、仅上述槽位；扩展名 `.png`/`.jpg`/`.jpeg`/`.webp`；
  **服务端必须自己解析图片头部拿宽高**（不能只信客户端声明的尺寸）。
- 表情包与知识库都是**可选**的。**图片侧只硬性要求 `thumb`**（列表离不开它）——
  作者只提供头像时，**由客户端用头像派生一张 thumb**（≤320px/≤12KB）后再提交；服务端不代劳。
- **兼容槽位 `cover`（历史遗留，不在新布局里，但必须继续接受）**：存量卡/老客户端/老草稿都在用，
  上限 ≤300KB、**不限长边**；列表在有 `thumb` 时**不下发**它，只有老卡（无 thumb）才回落。
  这是「无法迁移又必须兼容」的折中，**新卡不要再用 cover**。
- **`thumb` 的强制面**：只在**新格式提交路径**（payload 带 `files` 或 `images`）强制
  `CARD_MISSING_THUMB`；老形状 payload 与存量老草稿仍按老规则可读可存（向后兼容是硬要求）。
  验证者测「缺 thumb 被拒」**必须走新格式路径**；直接调 `parse_card_zip()` 默认参数会看到放行，属预期。

### 3.2 制卡 payload（`POST /plaza/api/draft`、`/plaza/api/publish`）

```jsonc
{
  "display": "可选，展示名",
  "card": {
    "id": "…", "name": "…", "char_name": "…", "user_name": "…",
    "presentation": "sticker|narration|…", "desc": "…", "tagline": "…",
    "category": "…", "tags": ["…"],            // ≤5 个、每个 ≤12 字（不变）
    "opening": {"narrations": ["…"], "first_messages": ["…"]},
    "files": [                                  // ★新增：自由文本文件
      {"path": "core.md", "text": "…"},
      {"path": "knowledge/世界观.md", "text": "…"}
    ],
    "images": {                                 // ★新增：图片一律 data URL，客户端已压好
      "avatar": "data:image/webp;base64,…",
      "thumb":  "data:image/webp;base64,…",
      "display":"data:image/webp;base64,…",
      "stickers": [ {"data": "data:image/webp;base64,…", "label": "开心"} ]
    }                                           // label 可选、≤12 字；**建议填**：App 组织器按
                                                // label 语义选图，没 label 的表情包基本选不中
  }
}
```

- 表情包上限 8 张；`label` 落到 zip 里的 `character/stickers.json`（`{"sticker-1.webp": "开心"}`）；
  缺 `label` 合法（App 侧以卡名生成占位标签，见 07 文档），但 UI 要提示"建议填"。`label` 一律
  `textContent` 渲染，不许当 HTML。

- **兼容**：原字段（`core`/`identity`/`sms_samples`）**继续接受**，服务端等价映射到 `files` ⇒
  旧客户端/老草稿不会坏（`tests/test_compat_081.py` 同级要求）。
- `files[].path` 必须过白名单正则；超限一律 400 + 明确中文原因（沿用 `CardError.code`）。

### 3.3 图片规格（客户端压到目标，服务端复核）

| 槽位 | 列表用？ | 目标尺寸 | 体积上限 | 一屏 20 张的量级（观察值） |
|---|---|---|---|---|
| `thumb` | **是（列表只发它）** | ≤320px 长边 | **≤12KB（硬线）** | 实测 9.9KB（噪点样本）～2KB（真实卡）⇒ 一屏约 **40～200KB**（原 3MB） |
| `avatar` | **否（详情用；列表响应不下发）** | ≤256px | ≤30KB | 列表用 thumb 即可；avatar 只在详情/装卡后使用 |
| `display` | 否（详情才拉） | ≤1024px | ≤300KB | 详情单张 ≤300KB |
| `sticker-N` | 否 | ≤160px | ≤20KB | 详情/使用卡时按需拉 |

> ⚠ **验收线只有两条硬线**：① 单张 `thumb` ≤12KB；② **列表 JSON 响应 ≤60KB**（实测 1.2KB、gzip 559B）。
> 「一屏 20 张合计 KB」是**观察值、不是验收线** —— `verifier` 实测一张合规 thumb（320px/q25 噪点样本）
> 就有 9.9KB、20 张 198KB；当作验收线会误杀真机缩略图。原稿"≈120KB（↓96%）"是按 6KB/张的估算，**已作废**。

> **列表图片字段 = `thumb`（+老卡 `cover` 兜底）**（2026-10-01 task-20 收紧）：列表响应**不下发
> `display`/`avatar`/`sticker-*` 的任何地址** —— `avatar` 原先在列表里给文件名，今天虽不产生流量，
> 但**将来任何客户端顺手按它取图就是一屏 20×≤30KB**，正好抵消"从源头砍流量"。
> 现在用**结构性保证**（列表响应里连文件名都没有）取代"前端别请求"的 UI 纪律；
> `avatar`/`display`/`sticker-*` 只在 `GET /plaza/api/card`（详情）出现。

### 3.4 尺寸校验的边界（裁决留痕，2026-10-01）

「不能只信客户端声明的尺寸」指的是**不信 JSON 里的字段**，必须**解析图片自身头部** —— 已实现
（PNG IHDR / JPEG SOFn / WebP VP8X 与内层 VP8/VP8L）。**不要求**像素级重解码，理由是实测：

| 攻击样本 | 真解码器（Chrome）读出 |
|---|---|
| PNG：IHDR 写 320×10、IDAT 塞 4000×10 的数据 | **320×10** |
| JPEG：SOF 写 320×213、scan 塞 800×800 的数据 | **320×213** |

⇒ IHDR/SOFn 是**格式定义的权威画布**，多塞的数据只被解码器忽略（体积另受 ≤12KB 兜底），
**不可能造成超额解码** ⇒「头部与内容不一致」**不构成缺陷**（`verifier` 的 H03/H03b 按此结案）。
反证保留：**真实 320px 而头部谎报 4000px 必须被接受**（防"只看头部"被误判）。

- 客户端压缩：复用 `app/static/js/imgzip.js`（canvas 逐级降质），**先按尺寸再按质量**降；
  webp 优先、jpg 兜底（`imgzip` 已有能力）。
- 服务端**必须**复核：体积、魔数、宽高（解析 PNG IHDR / JPEG SOFn / WebP VP8X），
  超限即 400；把 `thumb` 缺失的卡视为**校验不通过**（列表离不开它）。
- 列表响应**只给 `thumb` 的地址**（老卡回落 `cover`）；`display`/`avatar`/`sticker-*` 只出现在详情。

## 五、边界（明确不做）

- 不做卡内数据（对话/记忆/手账）随卡分发（既有产品决策不变）。
- 不引入 Pillow/nginx：服务端保持**纯标准库**，缩略图由**客户端**生成、服务端只校验。
- 不做富文本/HTML（沿用"结构化块 + textContent"纪律）。
