# 角色卡共创平台 · 04 流量与资源管理（M4）

> 目标（用户 2026-10-01 说明）：服务器是 99 元/年阿里云，**固定带宽约 0.3MB/s（3Mbps）**，
> 流量是送的、不计费。所以本方案的目标**不是省钱，而是防抢占**：
> 任何人下载 81MB 安装包或刷广场图片，都不能把聊天与业务 API 拖垮。

## 一、改造前的事实（2026-10-01 实测）

| 项 | 现状 |
|---|---|
| 带宽 | 固定 ≈0.3MB/s；eth0 累计 RX 6.0GB / TX 18.5GB（开机 50 天，出向均值 ≈370MB/日） |
| 内存 | 1612MB，**无 swap**（Load≈0；不能加常驻新进程） |
| 磁盘 | 40G，用 4.9G |
| **字节级限速** | **完全没有**：`_send_file`/`_proxy` 以 64KB 块**全速**写 socket |
| 既有并发/次数控制 | `DL_SEM=2`（>5MB 大文件）、同 IP ≤2 个下载、网关 `RATE_PER_MIN=3000`、`MAX_THREADS=64`、socket 空闲 120s |
| 压缩 | 全仓 Python **无任何** `Content-Encoding`（唯一压缩是前端 Canvas 预压图片） |
| 记账 | 下载统计**只记次数、不记字节** |

## 二、方案：加权令牌桶 + 优先级借用门槛（`server/traffic.py`）

三级分类，各自保底，空闲带宽可借但不许抢：

| 类 | 内容 | 权重 | 保底份额 | 借用门槛（占空闲池容量） |
|---|---|---|---|---|
| `api` | 聊天 / relay / 业务 API / 广场 JSON | 10 | 62.5% | 0（永远可借） |
| `asset` | 广场图片、`/assets/`、`/hotupdate/` | 4 | 25% | 25% |
| `bulk` | 安装包、卡片 zip 等大文件 | 2 | 12.5% | 50% |

- **全局预算**：默认 2800kbps（约留 7% 给 TCP 头与突发）；`FIREFLY_BW_KBPS=0` 关闭（本地调试）。
- **突发容量**：每类 = 该类速率 × 0.25s ⇒ 小响应（一次 API 回包）永远不排队。
- **空闲池只吸收"各类没用掉的配额"**：这样全局总容量恒等于预算。
  ⚠ 第一版实测到的错误：把空闲池按全局速率**独立补充**，总容量变成 2×
  （实测 15360 B/s vs 应 10000 B/s）——已修，并在测试里钉死"总吞吐不超上限"。
- **借用门槛的意义**：没有门槛时，三类会被"谁先问谁借走"**抹平成均分**，带宽分配形同虚设。
  有门槛后：链路繁忙（空闲池被高优先级抽干）时低优先级只能吃自己份额；链路空闲时人人可突发。
- **诚实说明**：轮询式低频请求（api 每次只要一个小回包）**用不满自己的份额**，
  剩余额度会流向 asset/bulk —— 这是 work-conserving 的设计意图，不是 bug。
  要保证的不是"固定比例"，而是"api 的响应永远不必排在大文件后面"。

> ⚠ **单连接上限**（2026-10-01 追加）：上面的权重只管**类之间**，空闲池仍能被单条大文件流抽干 ⇒
> 另有 `ConnLimiter` 给**单条连接**加天花板（默认全局 50%），见 §4.8。

## 三、其余三层配套

1. **单 IP 字节日配额**（`IPBudget`）：`FIREFLY_BULK_IP_BYTES` 默认 1GB/24h，
   超额 → 429 + `Retry-After`；防"一个人把 3Mbps 占满一整天"。窗口滚动自动恢复。
2. **响应压缩**（本仓库第一个 `Content-Encoding` 压缩点）：JSON/HTML/JS/CSS/SVG，
   仅当客户端声明 gzip、体积在 1KB~4MB、且**压缩后确实更小**时才压（否则原样，避免负收益）。
   网关反代路径上做，主服务零改动。
3. **缓存纪律**：广场图片 `Cache-Control: public, max-age=86400` + `ETag`/304（已在 02 文档落地）；
   热更 `latest` 强制 `no-store`、补丁 `immutable`（既有）。
4. **并发上限**（既有，保持不变）：大文件 `DL_SEM=2`、同 IP ≤2；网关线程 64；超限 429/503。
5. **断点续传（M4b，2026-10-01）**：`/download/<文件>` 支持单段 `Range`
   （`bytes=a-b` / `bytes=a-` / `bytes=-N`），返回 206 + `Content-Range`，
   并**始终声明 `Accept-Ranges: bytes`**（不声明客户端就不会尝试续传）。
   - 为什么要做：3Mbps 下 81MB 安装包约 4 分钟，**任何中断（网络抖动、限速拿不到额度而断流）
     原本都要从 0 重来**；续传直接省掉这部分冤枉流量。
   - **畸形/越界/多段一律退回 200 全量**：续传是优化，不能因为一个坏请求头让下载失败
     （也不回 416 把简单客户端卡死）。
   - 续传单独记 `server-range` channel，`/download/stats` 的 `by_channel` 能看出续传占比。

> 📄 **可观测与验收明细（含线上实测数字）已拆到 [04b 流量验收与观测](04b_流量验收与观测.md)** —— 本文只讲方案与部署参数。

## 四、部署参数（随 0.9.1 一起上）

```ini
Environment=FIREFLY_BW_KBPS=2800          # 全局下行预算；0=关闭
Environment=FIREFLY_BULK_IP_BYTES=1073741824   # 单 IP 大文件日配额（1GB）
```

- 巡检阈值（M4 第二层）**不配就用默认值**：`FIREFLY_WATCH_IP_BYTES=314572800`（300MB）、
  `FIREFLY_WATCH_TLS_DAYS=10`、`FIREFLY_WATCH_IP_COOLDOWN=1800`。
  ⚠ `attack_watch.sh` 由 **cron** 执行，**不继承 systemd 的 `Environment=`**：
  要改默认值就写进 crontab 或脚本头部，写在这里无效。
- 网关仍是**同一个进程、同一个 8787**，零新增常驻进程（内存约束）。
- 上 TLS（05 文档）后 `traffic.py` 不需要改：限速发生在**应用层写 socket**处，
  与是否 TLS 无关（TLS 只增加一点头开销，预算里已留余量）。

## 五、明确不做 / 后续

- **不做** nginx / 付费 CDN（无预算、无域名）；**不做** `tc` 内核级整形（应用层更可控，
  但 `tc` 可用作兜底，见 `docs/服务器管理规范.md` 的运维记录）。
- **未做**：动态调整（按负载自动升降 `FIREFLY_BW_KBPS`）——先要真实数据再谈自动化。
- **未做**：**按 IP 的历史字节报表**。`downloads` 表刻意不存 IP（隐私），`requests` 表有 IP 却无字节，
  两者当前无法关联；要做必须先定隐私口径（存 IP？聚合到 /24？只留 top-N？）。
- **未做**：`tools/attack_sentinel.py` 的事件签名纳入 `big_ip`/`tls_not_after`
  （该文件不在 M4 第二层范围内，见 §四的已知缺口）。
- **本次已做、从此移出清单**：大文件 `Range` 断点续传（§三.5，M4b）；
  字节记账入库 + `/download/stats` 字节口径（§四）；异常大流量与证书临期接入 `attack_watch.sh`（§四）。
