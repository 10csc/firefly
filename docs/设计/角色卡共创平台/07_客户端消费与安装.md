## 一、安装落到哪（`app/plaza/install.py`）

```
取卡体 → cf.parse_card_zip 全量校验 → 只写 character/ 子树 → 登记 packs.json → reload_presets()
      → 附属链路：知识缓存失效 + 卡表情包桥接（失败只告警，不影响"卡已装好"）
```

| 项 | 行为 |
|---|---|
| 落点 | 永远"当前数据根"：服务器模式 `user_data/{uid}/{卡id}/character/`，本地模式 `user_data/{卡id}/character/` |
| 只写 character/ | 绝不创建/覆盖 `data/`、`journal/`、`images/`（用户数据铁律） |
| `preset.json` | 落盘前剥掉 `knowledge_dirs`（否则一张别人发的卡能指挥**你的**检索器读仓库内任意目录） |
| 覆盖安装 | 先整体留档到 `{数据根}/backups/plaza/{id}-{时间戳}[-n]`，再写；卡里已不含的旧文件删掉 |
| 卸载 | 只允许 `source=plaza` 的包；删目录 + 注销清单 + **清包外产物**（见 §四） |
| 配额 | **仅服务器模式**：每人 ≤5 张、总量 ≤8MB；本地版不限额 |
| 安装回执 | `{id, name, char_name, size_bytes, backup, upgraded, knowledge_files, stickers}`——后两项可直接自证"接住了" |

| 卡里的东西（06 §3.1） | App 侧消费点 | 谁负责 |

## 三、知识库如何进检索（本轮修的核心）

`llm_retriever._knowledge_roots(mode)` 按**优先级顺序**给出三层根，`_load_knowledge` 逐层读：

1. `preset.json.knowledge_dirs` 声明的仓库相对目录（各自独立，互不遮蔽）；
2. **包内用户副本** `{数据根}/{包}/character/knowledge/` ←**广场卡的知识库与软件内编辑的知识都在这**；
3. 包自带 `app/assets/character/{包}/knowledge/`（bundled 回落）。

- **遮蔽规则**：②③ 同属一个遮蔽组，同一相对路径**用户副本优先**（与 `/pack-knowledge`
  的读取链同序）⇒ 同一份知识不会被注入两次，改过的版本一定赢。
- **缓存**：`_KNOWLEDGE_CACHE[mode::用户作用域]`；安装/覆盖/卸载都会
  `clear_knowledge_cache(卡id)`（漏掉 = 覆盖安装后仍用旧知识）。知识文件在 App 内保存时
  `/pack-knowledge/update` 自己清缓存 ⇒ "下轮对话生效"是真的。
  **用户作用域是隔离的必要条件**：知识源自本轮起含用户副本 ⇒ 第一次进了提示词，
  缓存键少了它就会 A 的知识被 B 读到（错误总结 #10 同族）；测试 ⑪/⑪b/⑪c 用"同名卡、
  不同知识"两账号钉死，并已用**变异测试**确认这三条有鉴别力（把缓存键改回 `mode` 即红）。
- **踩过的老 bug（已修，同族 #10）**：此前这里只认声明目录与 bundled 包目录，
  于是"卡自带的知识库"和"用户改过的知识库"**都进不了检索** —— 表现为 `has_knowledge=False`、
  检索阶段整段跳过，**零报错**。现在 `has_knowledge` 与 `_load_knowledge` 同源同口径。
- **包编辑界面**：`routes_pack._safe_kb_rel` 收两种形态（扁平 `knowledge/<名>.md` 与
  一层分组 `knowledge/<域>/<名>.md`，均只允许 `.md`、拒绝 `../绝对/盘符/更深`），
  `/pack-knowledge` 列表、读回、保存、删除、新建全部走同一条白名单。
  历史：只认五域分组 ⇒ 广场卡的扁平知识"只显示数量、点开是空的、也改不了"。

## 四、表情包与 label 如何进选择器

**为什么需要桥接**：App 的表情包只有一条可用链路——`{数据根}/stickers/registry.json`
加 `stickers/<文件名>` 的图片（`domain/stickers/picker.py` 的路径校验只认 `stickers/` 前缀）。
卡里的图在 `{包}/character/assets/` 下，**全项目没有任何代码读它** ⇒ 不桥接就是"装上了但没有"。

**安装时做什么**（`install._install_pack_stickers`，幂等：先清该卡旧条目再写）：

1. `assets/sticker-<n>.<ext>` → 复制为 `{数据根}/stickers/plaza-<卡id>-<n>.<ext>`；
2. 登记条目 `{id: plaza_<卡id>_<n>, file: stickers/<上面的文件名>, category: 可爱,
   label: <见下>, enabled: true, pack: <卡id>}`。

**label 来源**：卡内 `character/stickers.json`（契约 §3.1，`{"sticker-1.png": "开心"}`，键=真实文件名，
按 stem 容错匹配、≤12 字截断）。**缺 label 合法**（§3.2），此时用 `{角色名}的表情{N}` 兜底——
注意这只是**占位**：组织器按 label 做语义选图（`pick_sticker_by_label` 字符重叠），
占位标签基本选不中，所以 UI 应提示作者"建议填 label"。

**可见性边界**：组织器/主动性按 `get_enabled_stickers(mode)` 取"全局共享 + 本包专属"（**按 pack 过滤**）；
聊天表情面板走 `/stickers?enabled=1`（既有实现**不按包过滤**）⇒ 卡专属表情包在聊天面板里
对所有角色可见（与用户自己上传的包专属表情项同状）；管理页带归属标注。

**为什么绕过公开的 `add_sticker`**：它校验 `pack in cfg.MODES`（**全局内置包**），
而服务器模式下用户经广场安装的卡不在全局 `MODES` 里 ⇒ 走它必抛。桥接是"系统按卡定义登记"，
不是"用户在某个当前包下上传"，故直接用同模块的写入口 `_save_user_entry`（**同一个 JSON 格式、
同一把锁的调用点**），不改 picker 的公开校验。
**风险（知情）**：① 依赖 `picker._user_registry_file` / `_save_user_entry` 两个**私有名**，
若将来重命名要同步这里（测试 ⑧m–⑧q 与 ⑩e/⑩f 会立刻红）；② 桥接失败只告警 ⇒
"卡装好了但表情包没进选择器"是可能的，日志有关键字`卡表情包`。

**卸载/覆盖清理**：`_drop_pack_stickers(卡id)` 删掉 `pack==卡id` 的全部条目（**删除**而不是
降级为全局共享——卡的表情包随卡走）并通过 `delete_sticker` 的孤儿清理删掉不再被引用的图片。
触发点有三处：① 覆盖安装（**先清后写**，新版删光表情包也要清，测试 ⑨f–⑨l 钉住）；
② 新版减少张数（只留新版带的那几张）；③ 卸载（测试 ⑩e/⑩f 钉住"条目 0 条 + 图片 0 个"）。

## 五、形象资产槽位回落（`routes_config.pack_asset_slot_url`）

契约允许卡只有 `thumb`（§3.3"头像列表可省略，用 thumb 即可"）。只按同名槽位 glob 的话，
**合法卡**在 App 里就是白图。回落链（用户副本优先 → bundled）：

`avatar → thumb` ｜ `cover → display → thumb` ｜ `user_avatar → 不回退`（那是用户自己的形象，
拿角色图顶上会把用户画成角色）。`/modes` 与 `/pack-files` 共用这一个函数（`routes_pack._slot_url` 改为调它）。

## 六、新旧格式兼容边界

| 情况 | 行为 | 依据 |
|---|---|---|
| 旧卡（只有 preset/core/cover，无 thumb/知识/表情包） | 照旧装、照旧能开对话；`/modes` 封面正常、无头像时不回落出假图；`has_knowledge=False` ⇒ **不白烧一次检索调用** | 测试 ⑥/⑥b/⑥c |
| 缺 `thumb` 的旧卡 | `parse_card_zip(require_thumb=False)` 兼容通道放行（只有**新格式提交**才强制） | 契约 §3.3 + 06 §3.1 注 |
| 缺 `label` | 合法；App 用卡名占位 | 契约 §3.2 |
| 缺 `avatar` / `cover` | 合法；走 §五 回落链 | 契约 §3.1/§3.3 |
| 只有 `knowledge/` 没有 `assets/` | 合法；检索照常，头像为空 | 契约 §3.1 |
| 卡内数据（对话/记忆/手账）随卡分发 | **不做**（产品决策不变） | 契约 §五 |

## 七、已知边界 / 未覆盖

1. **前端显示扁平知识文件名**：`panels/pack_tree.js::_toggleKB` 用
   `f.path.split("/").slice(1).join("/")` 取名 ⇒ 扁平路径（新允许）**行内名字是空串**
   （能点能存，但看不见文件名）。一行修：`f.path.includes("/") ? f.path.split("/").slice(1).join("/") : f.path`。
   **归 frontend（task-8）**，已报 Lead。
2. 缺 label 的卡表情包"进得了选择器、选不中"（见 §四）——契约已建议作者填 label。
3. 本轮**没验**真机/真浏览器（后端消费链是纯 Python，产物级断言已覆盖）；界面侧由 frontend 负责。
4. `app/core/pack_structure.py` / `pack_registry.py` **审计结论：无需改动**——
   知识库节点走 `rglob("*.md")` 计数（实测 3/3 正确），表情包域是前端嵌入块（桥接后自然出现），
   形象资产域前端整体不渲染（由 `/pack-files` 的资产回落链承载）。
