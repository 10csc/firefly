# 04b 流量验收与观测（M4/M4b/M4c）

> 本文是 [04 流量与资源管理](04_流量与资源管理.md) 的**验收与观测**分册：
> 可观测字段、已跑的验收数字、线上交叉验证、单连接上限的实测对比。
> 方案与部署参数在 04 正册。

## 一、可观测（M4 第二层补齐，2026-10-01）

- `GET /download/traffic`（**仅回环可访问**，公网 403）：分类速率、剩余令牌、空闲池、
  已发字节、累计等待时长、单 IP 配额配置。**不含任何 IP 信息**。
- `GET /download/stats`（公开，只有数字，无 IP/账号）：
  - 次数口径（既有，不动）：`total`（只数安装包 apk+exe）/ `by_file` / `by_channel`；
  - **字节口径（M4 第二层新增，只增不改）**：`bytes_total`（全部下载实际发出字节之和）、
    `bytes_by_channel`（分通道）、`bytes_app_total`（与 `total` **同口径**，只算安装包）。
  - ⚠ 为什么字节要给三个而不是一个：`total` 只数安装包，若字节只提供"全量"口径，就会出现
    「次数 3 / 字节 4.2GB」这种看似互校、实则两个口径的组合（`docs/错误总结.md` #10）。
- **字节怎么记**：`_send_file` 在**流结束之后**按真正写出 socket 的字节记账（`downloads.bytes`）。
  三条理由：① `Content-Length` 是**声称值**——Range 续传只发一段（可能只有几十字节），
  按 size 记会把 81MB 的包记成全量；② 限速拿不到额度会中途断流，实际发出量 < 声称量；
  ③ 客户端半途断开时，这个计数恰好就是真实消耗。续传单独记 `server-range` 通道。
- **老库幂等迁移**：`_db_connect` 先 `PRAGMA table_info(downloads)` 检测，缺列才
  `ALTER TABLE downloads ADD COLUMN bytes INTEGER NOT NULL DEFAULT 0`——老库自动升级、
  **老数据一行不丢**（老行 bytes=0），重复执行无副作用（新库由 `CREATE TABLE` 直接带列）。
- **权威口径在盘上，不在内存**：`/download/traffic` 的 `sent_bytes` 是**进程生命周期**计数，
  重启归零；要写盘/当权威一律取库里的 `bytes_total`（错误总结 #10 的教训）。
- `server/attack_watch.sh` 新增两项巡检（cron 每分钟读，结果写 `attack_flag.json`）：
  ① **单 IP 大流量**：`ss -tin` 的 `bytes_sent` 按 IP 汇总（内核 TCP 计数，零新依赖），
  当前活跃连接超阈值（默认 300MB，可用 `FIREFLY_WATCH_IP_BYTES` 调）即告警；
  ② **证书临期**：`curl -s http://127.0.0.1:8787/download/tls` 的 `days_left < 10` 即告警。
  **去重键一律用事件本身的特征**：① 用 **IP**（状态文件记 IP + 冷却窗口），
  ② 用**证书到期日 `not_after`**；`time` 取事件自身时间（首次检测/封禁时刻），
  不是每轮 `date` 的现值——这是错误总结 #11「一次封禁被弹 4-5 次」的直接对策。
  ⚠ 能力边界（诚实说明）：`ss` 只能看到**仍在建立**的连接，两次 cron 之间已完成的大流量
  看不到；累计口径以 `/download/stats` 的 `bytes_total` 为准。`sar` 已在服务器上可用，可交叉验证。
  ⚠ 已知缺口：`tools/attack_sentinel.py` 的事件签名还不含 `big_ip`/`tls_not_after`
  （该文件不在本卡范围），同冷却窗口内**不同 IP** 的大流量事件会被哨兵合并为一次；
  脚本侧不会再重复写标记（已修），哨兵侧待后续卡跟进。

### ★抢占控制（本节是需求原话「多任务流量占用可能会出现抢占」的正面验收）

设计文档里 M4 的验收一直是「**压测：下载大文件时业务 API 的 P95 不劣化 >20%**」，
但此前只测了限速器**自身**的速率与配额，**从没端到端量过这个性质**。
2026-10-01 补上 `tests/test_preemption.py`（**10 项，连跑 3 次全绿**）：
起一个**桩上游**（模拟业务 API）、网关经 `FIREFLY_PROXY_TARGET` 指向它、
开一个后台线程**限速下载 1.5MB 大文件**，在下载进行中打同一批业务 API。

| 指标 | 无下载（基线） | 限速下载进行中 |
|---|---|---|
| 业务 API p50 | 19–21ms | 18–20ms |
| 业务 API p95 | **30–46ms** | **24–35ms** |
| 结果 | — | **p95 劣化 0%**（验收要求 ≤20%） |

同时断言：并发期 API **全部 200**（没被饿死/拒连）、下载窗口内只推进 128KB
（证明限速真的生效，不是无限速跑完）、吞吐 ≤ 预算 2 倍、
`/download/traffic` 的 `sent_bytes` 把两类分开记（api 1683B / bulk 131072B）。

**顺带修掉一个只影响部分客户端的真 bug**（见 `docs/错误总结.md` #22）：
网关对"200 + 已知 Content-Length ≤4MB"的响应会**先缓冲读走正文**再看值不值得 gzip；
若**不值得压缩**（客户端没发 `Accept-Encoding: gzip`、体积 <1KB、类型不在白名单），
原实现却落到**流式**分支 —— 而流已读干 ⇒ 发出 `Content-Length: N` 却写 **0 字节**。
浏览器都发 gzip 所以线上从未暴露，但 **curl（不带 `--compressed`）/ `urllib` / Go 会拿到空正文**。
现已在 `_proxy` 里把"已缓冲的正文"单独接住（`buffered`），并让上游截断如实报 502；
守卫见 `tests/test_gateway_proxy_body.py`（**9 项**，覆盖 identity / 压缩 / 流式 / 截断四条路径）。

## 三、线上交叉验证（2026-10-01 实测，P4-4 收口）

在生产服务器上并发做「客户端 Range 拉 4MB」+「`sar -n DEV` 采样 18 秒」，互校三个独立口径：

| 口径 | 字节 | 说明 |
|---|---|---|
| 客户端实收 | 4,194,304 | `curl.exe -r 0-4194303`，HTTP 206，用时 11.9s |
| 网关字节记账 | 4,194,304 | `/download/stats` 的 `bytes_total` 增量（与客户端逐字节一致） |
| 令牌桶 bulk | 4,194,304 | `/download/traffic` 的 `sent_bytes.bulk` 增量（独立计数器，偏差 0.0%） |
| `sar` eth0 出向 | 4,063,119 | 18 样本 × 220.44 KB/s |

**偏差 3.1% < 20% 验收线**（差值来自 sar 的秒级采样边界与 KB/s 取整）。
同时印证：4MB/11.9s = **352 KB/s ≈ 满 2800kbps 预算** ⇒ 空闲时单流吃满、有竞争才让路。
⚠ 量具自身的两个坑（`sar` 12 小时制列位、PS 5.1 不让改 `Range` 头）见 `docs/错误总结.md` **#29**。

## 四、单连接上限 `ConnLimiter`（2026-10-01 用户追加要求）

> 用户原话：「这个占用十几秒**满载**太多了，我想优化好。」

**问题**：`Governor` 只管**类之间**的分配（api 62.5% / asset 25% / bulk 12.5% + 空闲池借用），
空闲池能被**单条** bulk 连接抽干 ⇒ 实测一个 4MB 下载拿到 **344 KB/s ≈ 满 2800kbps**，
整线十几秒没有余量。

**修法**：给**单条连接**再加一层天花板，与 `Governor` **同时生效**（`server/traffic.py::ConnLimiter`）：

| 项 | 值 |
|---|---|
| 默认上限 | 全局预算 × `CONN_RATIO`（默认 **0.5**）⇒ 2800kbps 时 **1400kbps ≈ 175KB/s** |
| 覆盖 | `FIREFLY_CONN_MAX_KBPS=<kbps>` 直接给绝对值；`0` = 关闭 |
| 作用面 | **只压 >5MB 的大文件**（`size > BIG_FILE`）——公告图/小卡不受影响，免得"防大文件"把图也拖慢 |
| 观测 | `/download/traffic` 新增 `conn_max_kbps` 字段 |

**线上实测（2026-10-01，同一台生产机）**：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 单流 4MB 吞吐 | 344 KB/s（≈满） | **172 KB/s**（= 50% 上限） |
| 该流耗时 | 11.9s | 23.8s（**该流自身变慢，换来整线始终留一半**） |
| 同时 API `/health` p95 | 97 ms | 94 ms（空闲对照 97 ms） |

**权衡（要说清）**：整线不再被一条流吃满，代价是**单流变慢**（4MB 12s→24s；85MB 安装包 4min→8min）。
若要恢复"空闲即满速"，设 `FIREFLY_CONN_MAX_KBPS=0` 即可（无需改代码）。

**测试**：`tests/test_server_traffic.py` §10（10 项确定性单测：速率、突发、开关、环境变量覆盖）；
新增 `tests/test_server_connlimit.py`（端到端**接线**验收：大文件被压 / 小文件不受影响 / 关闭即回退）。
