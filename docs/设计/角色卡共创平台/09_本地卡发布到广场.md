# 09 已有角色卡 → 发布到广场（本地卡上行）

> 建立：2026-10-01（用户点名要的功能）。上游：[06 卡片格式](06_制卡自由度与图片规格.md)、
> [07 客户端消费与安装](07_客户端消费与安装.md)（那是"广场卡下行"，本文是**上行**）。
> 实现：`app/static/js/panels/plaza_forge_local.js`（App 与平台**共用**，进两份 bundle）。

## 一、做什么、不做什么

用户原话：「用户自己的角色卡直接发布做了吗？没有的话，先把这一个功能做一下。」

- **做**：把用户**已有的角色卡**（App 本地包 / 平台该账号的包）一键载入制卡页 → 走**已有**的
  三步 API（`POST /plaza/api/draft` → `/plaza/api/review` → `/plaza/api/publish`）。
- **不做**：不新造发布协议、不新造服务端端点、不改 plaza 的发布/审核语义。
  "上行协议"就是既有的三步；本模块只负责**读已有卡 → 组装成制卡页认得的卡对象**。

**两处入口**：

| 入口 | 位置 | 行为 |
|---|---|---|
| ① App「角色卡管理」包详情页 | `panels/packs.js` 动态注入 `#pv-publish-btn`（绑定 `_packViewMode`） | 直接载入**当前这张卡** |
| ② 制卡页头部「载入已有卡」 | `panels/plaza_forge.js`（App 与平台都在） | 弹选择器列 `/modes`，任选一张载入 |

平台的「我的卡」就是制卡页，所以 ② 同时覆盖平台侧。

## 二、读数据用的端点（**全部是现成的**）

| 用途 | 端点 |
|---|---|
| 包元数据 + 形象资产投影 | `GET /modes` |
| 固定三件文本 | `GET /pack-files?mode=` |
| 知识库清单 / 正文 | `GET /pack-knowledge?mode=`、`GET /pack-knowledge/file?mode=&path=` |
| 开场白 | `GET /pack-file?mode=&path=opening.json` |
| 本包专属表情包（含 label） | `GET /stickers?enabled=1`（`pack === 卡 id`） |
| 图片（服务器模式回落） | `GET /plaza/api/card?id=` + `GET /plaza/api/asset?id=&slot=` |

## 三、字段映射（本地卡 → 广场 payload）

| 广场 payload（06 §3.2） | 来源 | 说明 |

| `card.files[].path` = `knowledge/<名字>.md`、`knowledge/<域>/<名字>.md` | `/pack-knowledge` + `/pack-knowledge/file` | 扁平与一层分组都带（06 §3.1 两种都收） |
| `card.opening{narrations, first_messages}` | `opening.json` | 新形状直取；老形状（单字符串）映射成一条 `first_messages` |
| `images.avatar` | `/modes.avatar` →（服务器模式）`/plaza/api/asset?slot=avatar` | |
| `images.display` | `/modes.cover` →（服务器模式）`/plaza/api/asset?slot=display` | 本地包没有单独"详情图"概念，用封面 |

## 四、限制（**客户端预检先给人话**，不靠服务端 400 才说）

载入/发布前先做本地预检，不过就**拒绝**（人话说明实际值/上限），**不动表单、不产生草稿**。

**2026-10-01 松绑（用户原话：「为什么知识库还限制份数？」「不要限制那么多（只是图片限制，
文字资料存储总大小限制在合理范围内即可）」）**：

| 限制 | 值 | 依据 |
|---|---|---|
| ~~单文本 ≤64KB~~ | **取消** | 松绑：文字只在总量上卡 |
| ~~知识库 ≤6 份~~ | **取消** | 松绑：份数不限（受整卡文件数约束） |
| **单卡文字总量** | 普通账号 **≤8MB**（UTF-8 字节）；**管理员不限** | ★ **唯一口径**：前端 `plaza_forge.js::_PF_TEXT_TOTAL_MAX` ↔ 后端 `card_format.py::MAX_TEXT_TOTAL_BYTES`（管理员 `parse_card_zip(is_admin=True)` ⇒ 文字不设限）；两边都**只写一处** |
| character/ 下文件数 | **≤500**（2026-10-02 由 24 放宽） | 安全天花板、**不是配额**（`card_format.MAX_FILES` / 前端 `_PF_FILES_MAX`）；用户实测 33 个文本曾被旧值挡住 |
| **图片规格**（**不松**） | thumb ≤320px/≤12KB；avatar ≤256px/≤30KB；display ≤1024px/≤300KB；sticker ≤160px/≤20KB | 06 §3.3，实测"大图卡"仍被人话拒绝 |
| 表情包 | ≤8 张 | 06 §3.1 |
| 卡体总量 | 普通账号 ≤10MB；管理员 ≤64MB | `MAX_TOTAL_BYTES` / `ADMIN_MAX_TOTAL_BYTES`（"抬高上限"而非真无界：那是 DoS 防护，不是配额） |

前端上限**随角色走**：`_pfTextTotalMax()` / `_pfDataMax()` 按 `_pfIsAdminSync()` 取值；role 未知时
按**普通账号**处理（宁可严一点，绝不因为"没问到"而放宽）。

口径细节：文本体积按 **UTF-8 真实字节**算（中文 1 字 3 字节）。前端历史上按 `.length` 算，
与后端（按字节）不一致 ⇒ 本次一并改成 `_pfTextBytes()`（`new Blob([t]).size`）。

**发布条数不受"安装配额（≤5 张）"限制**：那是我"装别人的卡到本账号"的配额，与"我发布"无关。

## 四之二、改编：「以此为模板改编」

广场**详情页**动作行新增 `#pz-adapt-btn`（`plaza_detail.js`）→ `window.plazaAdaptFromPlaza(id)`
（`plaza_forge_local.js`）。产物是一张 **新 id** 的卡（`<原 id>-2`、`-3`…）⇒ **绝不覆盖原卡**，
走的是普通"首发"流程。

正文来源（只为"填进表单给人看"，不影响上传量）：
1. `/plaza/api/draft?id=` —— **我自己的卡**（发布后仍保留卡体，作者可回看/改版）；
2. 本机已装的副本（`/pack-files` + `/pack-knowledge`，同 §三 映射）；
3. 都没装 ⇒ 弹**二次确认**"先安装再改编"（说明会占 1 个安装名额、随时可卸载）→
   `POST /plaza/api/install {id}` → 再走 ②。

**提交 = 只传 diff**（`POST /plaza/api/derive`；契约 02 API 表 / `app/plaza/api.py::plaza_derive`）：
- 载入时记下**基线快照**（各文件、开场白、图片的内容指纹，`_pflHash`）；
- 提交时只把"与基线不同"的部分放进 body：
  `{base_id, card: {id, 改过的元数据, files:[{path,text}]（只新增/替换的）, images:{只换了的图}},
    remove: {files:[路径], images:[槽位]}, display}`；
- **未改的图片既不下载也不上传** —— 服务端从原卡复制（回执 `copied` 里的数量就是它复制的量）；
- UI：顶部横幅「基于《原卡名》改编 · 只上传你改动的部分（未改的图片不下载也不上传）」+「放弃改编」
  （放弃只清基线、**保留表单内容**，之后按普通整卡制卡走）；
- **保守回退**：derive 返回 404/405/501/连不上 ⇒ 自动退回原"整卡上传"路径并给人话，**不白屏不丢内容**。

实测（真 `server_app`，只改 `core.md` 里一段字）：
```
请求体：{"base_id":"custom_loc1","card":{"id":"custom_loc1-2","files":[{"path":"core.md",…}]}}
         —— 只有 1 个文件；**没有** images 键；**没有** remove 键
上传字节：只传改动 193 B  vs  整卡 4360 B   ⇒ **省 96%**
服务端回执：copied={files:10, images:4}   uploaded={files:["core.md"], images:[]}  ← 4 张图 0 上传
新草稿 custom_loc1-2 里图片仍在（avatar/display/thumb/stickers）；原卡 meta 与文件字节不变
```

**来源标记**：服务端把它写进草稿 meta（`derived_from`，发布时随卡记录）⇒ 前端**不需要**额外发参。

| 分支（前端） | 原值 | 判定 | 理由 |

> **成本与输出上限（实测，2026-10-02）**：价目表 `modules/llm_base._PRICING`（flash：命中 0.02 / **未命中 1** / 输出 2 元/百万 tok）。
> 实测顶格卡（`reviewed_chars=36144`）⇒ prompt ≈ **2.45 万 tok** + 输出 ≈ 120 tok ⇒ **单次 ≈ 0.025 元**（重试翻倍，`usage` 按两次求和；普通几千字的卡 **1 分钱以内**；正文每张不同 ⇒ 按未命中价估）。
> **关键修复**：原来 `max_tokens=800` **且没传 thinking** —— 本项目 thinking **默认开启** ⇒ 推理文本先吃光 800 token，JSON 根本轮不到 ⇒ 结论退化为"转人工"、**发布按钮永久关闭**（用户 00:55 实测）。
> 现在 `max_tokens=10000`（同聊天核心）+ **显式 `{"thinking":{"type":"disabled"}}`**；解析宽松（围栏/说明/尾随逗号/全角引号）+ 截断兜底重试一次；
> 失败带 `error_kind`（`truncated`/`parse_error`）与 `raw_excerpt`，草稿保持 `draft` ⇒ **系统错误不冒充"审核未通过"**，管理员仍可发布；UI 需显示 `model` 与 `usage.total_tokens`。

**留下的一条硬教训**：前端"顺手加个上限"要写清**依据来源**（服务端常量名 or 明确的 spec），
否则它会静默变成用户撞得到的墙 —— 本表就是这条的落地形式。

## 四之五、制卡页两条 UI 守卫（2026-10-01 用户手机截图）

1. **提示条不得压住内容**：`#pf-msg`（人话提示/错误条）在手机上曾与「我的草稿箱」标题糊在一起。
   现在它是**不透明独立块**（背景 + 边框 + 圆角 + `position:relative; z-index:2` + 上下留白），

   手机 390 与桌面 1280 各一次）。
2. **「下架」只对已发布的卡显示**（`plaza_forge_review.js`）：

     并在**发布成功 / 覆盖发布成功 / 下架成功**三处都重新同步（原来发布成功没同步 ⇒ 状态不刷新）；
   - 草稿箱每条：`status === "published"` 才 append「下架」，草稿/待审/未通过都不显示。
   守卫：B21（新卡视图里不存在可见的「下架」）+ B 系列 ⑱j（发布后它才出现，证明是状态驱动而非删掉）。

## 四之六、官方发布（管理员）

`role == admin` 时，制卡页提交区多一个 `#pf-official` 勾选（`#pf-official-wrap`，**默认不勾**）；
发布时带 `official: <勾选值>`，广场列表按既有徽标逻辑显示「官方」（`plaza_list.js` 的 `pz-badge-off`）。

- **非管理员看不到**该勾选（前端不给入口；**服务端仍会拒**，权威判定永远在服务端）。
- role 取值：服务器/平台 `/auth/me`（`server/app.py` 返回 `role`）；本地版没有该端点 ⇒
  退到 `localStorage.firefly_role`，都拿不到就**隐藏**（失败即隐藏，宁可不显示也不越权）。
- 历史行为：服务端原来把 `official=is_admin` 写死（管理员发布**必然**官方）；改成按参数后
  "管理员也可以发非官方卡"，这正是用户要的"能选"。

## 五、已知边界（本轮实测发现，已回报 Lead）

1. **取图必须显式带凭证**（`/assets/` 已是**账号作用域**，serverops 2026-10-01 修复）：
   `{user_dir}/<包>/character/assets/*` 与 `{user_dir}/assets/stickers/*` 是账号内资产，
   未登录给 **401**（全局/bundled 资产未登录仍 200）。`<img src>` 与**裸 fetch 都不带凭证**
   ⇒ `_pflDataURL()` **显式加 `Authorization: Bearer <localStorage.firefly_token>`**。
   **不用 `?token=` 形式的 URL 令牌**（token 进 URL 会落到日志/Referer —— 安全决策，Lead 已拍板）。
   实测：未登录(绕过 fetch 包装用 XHR) ⇒ 401；带凭证取自己的包图 ⇒ 200 且请求头里确有 `authorization`。
   加载顺序：先 `/assets/character/<包>/assets/*`（账号作用域，两条模式都通），拿不到再回落
   `/plaza/api/asset`（已发布/已安装的卡），都没有就走"没读到图片"的人话提示让用户手动补缩略图。
2. **更新我已发布的卡**（2026-10-01 补，用户要求）：主发布按钮**永远** `replace:false`（服务端拒同 id
   ⇒ 防误覆盖）。被拒后 `#pf-msg` 给出「覆盖发布」入口 → 点击打开**二次确认**弹窗（说清"会用当前草稿
   替换广场上这一张的**已发布版本**、旧版本不留副本不可恢复" + 服务端原话）→ 确认后才传 `replace:true`。
   两道门都要能验：**取消 ⇒ 什么都不发生**（实测摘要不变）；**确认 ⇒ 真正覆盖**（实测摘要变化、状态仍 published）。
   平台页与 App 共用同一模块 ⇒ 两侧入口一致。
3. **平台侧"我的卡"范围**：平台没有"新建本地包"的入口，所以那里能发的通常是**从广场装到本账号的卡**
   —— 这类卡首发会被拒（本来就在广场上），要更新就走 §五.2 的覆盖发布。真正的"首发新卡"场景在 **App 本地模式**。
