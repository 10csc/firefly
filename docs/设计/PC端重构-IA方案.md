# PC 端重构 · 信息架构（IA）方案 —— 已评审通过 · 已实现（T1~T5 已落地，2026-10-02）

> 用户方向（原话要点）：
> 「可以仿照 QQ。（**角色卡为联系人**，聊天框内的**设置是菜单页**，左侧侧边栏下放**首页按钮、设置按钮**什么的）」
> 「我们的 UI 需要依托实际业务逻辑，**只有本身在角色卡外的功能能放侧边栏，其他的都只能放聊天页内**
> （菜单页则是收起在聊天页内）。这方面的组织需要**小心**。」
> 「因为是 PC 端的开发，**手机端没接入**。」
>
> 前情：2026-09-19 那一版是「手机界面 + 右侧停靠菜单 + 底部状态栏」（`docs/设计/PC端前端重构.md`），
> 它是**镜像手机**而不是 PC 自己的信息架构；本方案是**重做**，不是修补。

## 一、判定规则（先定规则，再摆面板）

| 归属 | 判据（**业务语义**，不是布局方便） | 反例（不许这么放） |
|---|---|---|
| **卡外 → 侧边栏** | 不依赖"当前是哪张卡"：作用于**账号/全局**，或作用于**卡的集合**（卡库、共创平台） | 把"收藏/记忆/表情包"放侧边栏（它们是**本卡**的） |
| **卡内 → 聊天页内** | 换一张卡就该换一份内容：会话、本卡文件、本卡状态、本卡流水线、本卡设定 | 把"设置/公告"塞进聊天菜单页（它们是全局的） |
| **菜单页** | 聊天页内**本卡动作/本卡页面的收口**（手机上就是 ☰ 抽屉），PC 上仍是"聊天页里的一层"，**不升级为窗口级导航** | 让它常驻成一列（= 第二套导航，2026-09-19 已被否） |

依据补一条外部准则（微软 UX 指南，2026-09-19 已引用过）：
**"Present each command on only one tab. Avoid multiple paths to the same command."**
⇒ 侧边栏与菜单页**不许出现同名重复入口**；"首页展示菜单页内容"这类错误不许再犯。

## 二、全量面板盘点（逐个定归属）

### 卡外（→ 侧边栏）
| 面板/功能 | 现有入口 | 为什么是卡外 |
|---|---|---|
| 首页 `#home-view` | 顶栏 / `showHome()` | 启动器 + 账号区：不针对某张卡 |
| 角色卡库 `#cards-view`（含新建角色 `#pack-create-panel`） | 首页「角色卡管理」 | 管本机**全部**卡（新建/导入/删除/安装位置）⇒ 集合级 |
| 角色卡广场 `#plaza-view`（+制卡 `#plaza-forge`、治理台 `#plaza-admin`） | 卡库头部「角色卡广场」 | 共创平台：浏览/创作/治理的是**卡库**，与"当前卡"无关 |
| 语音插件 `#voice-view` | 首页「语音插件」 | 全局插件（模型下载/TTS 就绪）⇒ 换卡不变（★见开放问题 ②） |
| 设置 `#settings-panel` | 首页右上 ⚙ | 账号与连接/模型与速度/外观/数据（版本·快照·同步）⇒ 全局 |
| 公告与更新说明 `#notice-panel` | 首页右上 📣 | 服务端下发的全局内容 |
| 反馈 + 诊断导出 `#feedback-panel` | 首页右上 ✉ | 全局支持面（`exportDiagnostics()`） |
| 账号（登录/注册/登出） | 首页账号区 | 全局 |
| 底部状态栏 `#pc-statusbar`（版本·修复·同步·公告未读） | PC 已有 | 全局**信息**、不是命令 ⇒ 不构成重复路径（沿用 2026-09-19 结论） |

### 卡内（→ 聊天页内；菜单页 = 其收口）
| 面板/功能 | 现有入口 | 为什么是卡内 |
|---|---|---|
| 对话流 `#app` | `showChat()` / 「继续聊天」 | 就是这张卡的会话 |
| 收藏 `menu-tab=fav` | 聊天 ☰ | 收藏的是**本卡**对话里的句子 |
| 表情包 `menu-tab=sticker` | 聊天 ☰ | 本卡启停/分类/含义（卡的三件套之一） |
| 设定文件 `menu-tab=char`（用户记忆/历史存档/手账） | 聊天 ☰ | 本卡文件（stage 2a 两栏化可复用） |
| 角色状态 `menu-tab=state`（当前隐藏） | 聊天 ☰ | 本卡状态 |
| 请求记录 `menu-tab=log` / 流程日志 `menu-tab=pipeline` | 聊天 ☰ | 本卡流水线诊断 ⇒ 上下文命令 |
| 「让角色休息」（立即整理记忆） | 聊天 ☰ 动作 | 只作用于本卡 |
| 记忆进度 `n/100` | 聊天页名字行尾 | 本卡状态 ⇒ PC 上做成**聊天页卡头常驻条**，不上侧边栏 |
| 角色卡详情 `#pack-view`（人设/知识库/形象/主动消息） | 卡库点卡 | 本卡内容 ⇒ PC 从**聊天页卡头**进入（点卡名） |
| 设定纠错 `#fix-view` | 包详情/菜单 | 只作用于本卡设定 ⇒ 上下文 |
| AI 辅助改文件 `#assist-view` | 卡域内 ✨ | 只作用于本卡文件 |

> ⚠ 最容易摆错的两个：**主动消息**与**用户形象**都是 `pack_structure` 里的**按卡**域 ⇒ 必须在卡内，
> 不许因为"看起来像设置"就放进侧边栏或全局设置页。

> 归属不同但各自成立（详见 §八 冲突检查）。

**每栏职责（一句话）**
1. **侧边栏**：**只放卡外**（首页 / 卡库 / 广场 / 语音 / 公告 / 设置 / 账号）。底部固定"首页 + 设置 + 账号"，正文入口在上方分组。
2. **联系人列**：角色卡 = 联系人（头像/卡名/角色名/模式 + 未读/主动/记忆状态点），**点一下即切卡**（解决旧审计 A6"切包比手机还绕"）。列底「+ 新建角色」直达卡库的新建表单。
3. **聊天页**：卡内一切。卡头是**本卡的状态与入口**（记忆进度、菜单页、卡详情），菜单页永远收在聊天页内，**不常驻成一列**。

> **口径收敛（T6 补注，2026-10-02）**：上面 ASCII 图与职责 1 里的「**账号**」按钮**已收敛为删除**。
> 先后关系：§三（本方案）先写"底部固定 首页 + 设置 + 账号"；任务单 `01_PC前端任务单.md` 的 **T2** 随后判定
> 「首页」与「账号」**都调 `showHome()`**（同一命令两个入口，违反 §一"每个命令只出现一处"），
> 给出二选一（删账号 / 为账号新写视图）并**推荐删**，实现采纳**删**。
> **最终口径：账号不单列按钮——账号就是首页的一段**（登录/注册/登出仍在 `#home-view` 的 `#auth-module`，
> `index.html:314-368`；实测侧边栏 `#pc-nav` 无账号按钮，`index.html:252-269`）。
> 故 §三 那处「账号」是**被 T2 取代的旧口径**，不是"实现偏离方案"。

## 四、手机端完全不受影响（三端红线）

- 新增 DOM 一律**默认 `display:none`**；只有在 `pc.css` 的 `@media (min-width:1100px)` 里才显形。
- 新增逻辑只在 `js/pc_shell.js`（classic script，**不进 bundle**），入口用 `matchMedia('(min-width:1100px)')` 守卫；窄屏分支直接不 boot。
- `index.html` **只追加**互不干扰的容器：既有 view 的 `id`/`class`/`window` 入口**一律不改**（`showChat/showHome/openSettings/openMenuTab/...` 零改动即可复用）。
- 验收沿用 2026-09-19 的口径：390×844 与 768×1024 下 DOM/样式与重构前**逐像素一致**（无头 Chrome 断言 + 截图）；APK 构建与真机由 Lead 跑（我不跑）。
- 本阶段是 **PC-only**：手机端既不接入三栏，也不改任何行为。

## 六、风险

1. **`style.css` 是三端共用** ⇒ PC 规则只准进 `pc.css`，否则手机被牵连（#15 类"源码全对、拼起来崩"的教训同源）。
2. **重复路径**：侧边栏与菜单页若出现同名入口，等于回到 2026-09-19 被否的形态 ⇒ 归属表就是防这条的闸门。
3. **按卡功能误放全局**：主动消息 / 用户形象 / 表情包 / 记忆若进了侧边栏或全局设置，业务上是错的（换卡不换内容）。
4. **手机无真机复验**（上次的遗留）⇒ 窄屏只能给结构不变量断言；真机请在 PC 版完成后由 Lead 排。
5. **旧 pc.css 停靠规则的残留**：改菜单呈现时必须**删掉**旧规则，否则"菜单同时停靠又在页内"。

## 七、请评审时拍板的四个开放问题

1. **首页是否保留？** 我倾向保留但轻量化（账号 + 继续上次会话 + 公告/更新摘要）——QQ 里没有"首页"，但本项目有登录与公告要落地。
2. **语音插件的"语气库"是否按卡？** 若按卡 ⇒ 语音拆两处（全局模型/设置进侧边栏，卡的语气进聊天页菜单）；若全全局 ⇒ 整体留侧边栏。
3. **联系人列只列本机已装卡？** 我倾向是（广场/安装走侧边栏的"广场"），避免联系人列变成第二个卡库。
4. **聊天页进"卡详情"用哪种呈现？** 页内抽屉（保留会话上下文）还是整页覆盖（编辑空间大）——我倾向**页内抽屉**，与"卡内一切都在聊天页内"一致。

## 八、冲突检查（T6，2026-10-02）

**结论：无冲突。** 核对范围 = 本次补的三域（上表）+ §二 两张表全部行 + 已实现的侧边栏 `#pc-nav`。

- **三域归属与代码语义一致**：`identity` / `assets` / `danger` 均为**卡内**（判据见 §二 补盘表），
  没有任何一个"按卡"的域被登记成侧边栏或全局设置；
- **无同一命令出现两处**：侧边栏命令集合 = `data-pc` 的 `home/cards/plaza/voice/notice/settings/feedback`
  （`index.html:252-269`，**无账号**，见 §三 补注），与卡内命令集合（聊天页卡头 / ☰ 菜单页）不重叠；
- **唯一跨归属的是 `danger`**，但那是**两条不同命令**（「归档本卡」=卡内 / 「已归档包恢复或彻底删除」=卡外首页区），
  不是"同一命令两处"，业务语义上各自成立 ⇒ **不算冲突**；
- **语音插件**：其"语气"是**全局默认**（`set_mood`，转语音时选用；`bundle.js:9145-9147,9213-9218`），
  非按卡 ⇒ 语音整体留侧边栏与代码相符（§七 开放问题 ② 由此收敛为"全全局"）。
