# 0.9.1 安全审计（对抗视角）

> 审计范围：0.9.1 三个新功能（公告 / 完整热更新 / 角色卡开放平台）、服务器侧存储与数据安全、
> 多并发流量安全，以及三块与既有功能的交界面。
> 方法：先画信任边界 → 再从攻击者视角（冒充/越权/绕过/注入/资源耗尽/竞态/信息泄露）逐条验证；
> 能真跑的都在**本机 127.0.0.1** 起真进程跑（脚本 `_harden/audit091_sec/`，可复现）。
> 硬约束遵守：**只读**（未改任何功能代码/配置）、**未对生产服务器做任何测试**。
> 本文只登记问题，修不修由用户拍板。**未覆盖范围见 §5（未测 ≠ 没问题）**；猜测单列 §4「疑点」。

## 1. 信任边界与入口

| 边界 | 谁能访问 | 入口 | 鉴权 |
|---|---|---|---|
| B1 公网 → 网关 | 任何人（未认证） | `8787`（`download_server.py`）：`/download/*`、`/notice/*`、`/hotupdate/<base>/*`、其余反代 8765 | 无（限流：`_rate_ok`，仅覆盖反代路径） |
| B2 网关 → 主服务 | 仅本机回环 | `127.0.0.1:8765`（`server/app.py`），MAX_THREADS=128 | Bearer token（闸门在 `:442-455`/`:561-579`） |
| B3 本地进程内 | 本机 | `/plaza/api/*`、`/notice`、`/notice-image`、`/sync/*` 等 | 同 B2；`/notice-image`、`/version.json`、`/update-manifest`、`/time`、`/health` 公开 |
| B4 管理面 | 仅本机 + 令牌 | `127.0.0.1:8766`，`X-Admin-Token`（`admin.py:37-48,167-168`，`compare_digest`） | 双因子 ✓ |
| B5 端侧 App | 设备持有者 | 覆盖层 `hotupdate/{web,py}`；公告缓存 `notice/` | 签名（RSA，公钥在 APK） |

**结构性观察**：B1 是整个系统**唯一**的公网面，也是全部三个新功能的公共入口 ⇒ 针对 B1 的可用性问题会同时打掉公告、热更、下载与**全部业务 API**。

## 2. 确认问题（按严重度）

### S-1 ｜**阻断**｜单 IP ~70 条半开连接即可完全打停公网入口 8787
> 定档理由：唯一公网面、未认证、成本极低（70 个 socket）、效果是**全站不可用**（含全部业务 API），
> 且现有监测设施看不见 ⇒ 按「发布前必须处置」处理。
- **证据（真跑，本机复现）**：`_harden/audit091_sec/_audit_t3b_slowloris.py` —— 70 条只发半截请求头
  （不发结束空行）的连接 ⇒ 控制请求 `[503, ConnectionAbortedError×4, 503]`，`/download/stats`、
  `/health` 同时不可用；关闭连接 5s 后恢复 200。
  代码：`download_server.py:158`（MAX_THREADS=64）、`:170`（Handler.timeout=120s）、
  `:643-657`（超限对所有新请求回 503）、`:159-161`（`MAX_IP_DOWNLOADS` 只管大文件下载，与本路径无关）。
- **影响面**：8787 全站 —— 下载页与文件、`/notice`、`/hotupdate`，以及**经反代的全部业务 API**
  （App/PC/手机的登录、`/auth/verify` 滚动续期、同步、relay、广场）。影响所有用户。
- **触发条件**：能连 8787；约 64-70 个并发 socket；无需登录、无需知道域名（IP 直连即可）。
  半截请求头会稳定占住线程至 120s ⇒ 可持续压制。
- **能否被外部利用**：**是**（未认证）。
- **建议修法**：① 每 IP 并发连接上限（且必须覆盖自服务路径）；② 缩短「读请求头」超时到 15s 级并限制单连接头部字节；
  ③ 自服务路径也纳入名额控制；④ ufw `connlimit`/`hashlimit` + nginx 前置 `limit_conn`；
  ⑤ 注意 `attack_watch.sh` 只扫 fail2ban/429/SSH 爆破 ⇒ **本次形态不会产生 429 也不会触发告警**，需补连接维度指标。

### S-2 ｜**高**｜反代限流可被「轮换 Authorization」完全绕过，并会清空全局限流计数
- **证据（隔离单测，不涉网络/磁盘）**：`_harden/audit091_sec/_audit_t1b_limiter_unit.py`
  - A）固定键：第 **3001** 次请求才被拒（阈值与 60s 滑窗确实生效）；
  - B/B2）**同一 IP、每请求换一个令牌指纹：3050 次请求 0 次拒绝 ⇒ 限流被完全绕过**；
  - C）喂 5200 个不同键触发 `_RATE.clear()` ⇒ **其他客户端的限流计数被一并抹掉**。
  代码：`download_server.py:410-423`（键 = IP + `sha256(Authorization)[:12]`）、`download_lib.py:49,59-70`。
- **影响面**：网关为「防代理层 DoS 打满主服务」而设的 3000/min 限流形同虚设（覆盖所有反代 GET/POST）；
  主服务因此暴露在任意高并发下（与 S-1 叠加时危害更大）。
- **触发条件**：任意客户端，请求头带 `Authorization: Bearer <每次随机>`。上一轮「没触发 429」是本机吞吐
  （37-40 req/s，被每请求 SQLite 落盘拖住）所致，**不是限流生效**；本轮用隔离单测排除该干扰。
- **能否被外部利用**：**是**（未认证）。
- **建议修法**：以**纯 IP** 为主键设总上限（令牌指纹只作同 IP 内的细分，不放大总配额）；
  `_RATE` 改 LRU 逐出，不做整体 `clear()`。

### S-3 ｜**高**｜`/notice` 与 `/hotupdate` 自服务路径完全绕开流量调度与并发名额
- **证据（真跑 + 计数器正面证据）**：`_audit_t2b_traffic.py` / `_audit_t2c_positive.py`
  - 同一网关（`FIREFLY_BW_KBPS=8000` ⇒ 全局 1MB/s，bulk 保底 125KB/s）下：
    1MB `/hotupdate/…/patch-1.zip` **31 MB/s**、1MB `/notice/img-big.png` **33 MB/s**（不限速）；
  - 两次 `/download/traffic` 快照：`sent_bytes{api,asset,bulk}` 增量 **全 0**（连字节都没计入调度）；
  - 正对照：经反代的 1MB 响应 `api` 计数 **+1048576**、耗时 0.71s ⇒ 调度确实生效，故「0 增量」是**绕过**而非关闭。
  代码：`download_server.py:230-261`（`_serve_notice`/`_serve_hotupdate` → `_reply` → 无 `GOV.take`，
  且**不占 `DL_SEM`**，注释表明是刻意）、`traffic.py` 的 `classify_path` 只在 `_proxy`/`_send_file` 生效。
- **影响面**：3Mbps 固定带宽下，单客户端可用不限速、不限并发的方式拉取补丁与公告图，
  直接挤占聊天/业务 API 的带宽 —— 正是 M4「防抢占」要解决的问题被绕过；补丁可与整包下载并行（不排队）。
- **触发条件**：`latest` 公开可读，补丁名 `patch-<N>.zip` 可枚举（serial 单调递增）。
- **能否被外部利用**：**是**（未认证）。
- **建议修法**：自服务路径纳入 `GOV`（可用 `asset` 类）并设独立并发上限；把 per-IP 字节/连接配额从「仅大文件」扩展到全部路径。

### S-4 ｜**中**｜网关每请求缓冲最大 16MB 请求体 + 每请求两次 SQLite 连接与一次 commit
- **证据（代码 + 本机量级）**：`download_server.py:462-466`（`n ≤ MAX_PROXY_BODY=16MB` 后 `rfile.read(n)` 一次性入内存）、
  `download_lib.py:56`（16MB）、`:214-233`（每个已记录请求：connect + 2×`CREATE TABLE IF NOT EXISTS` + 2×PRAGMA + INSERT + commit + close）、
  `:187-211`（另开一次只读连接做邮箱归因）。本机实测该写入路径把吞吐压到 37-40 req/s（`_audit_t1_ratelimit.py`）。
- **影响面**：64 线程 × 16MB ≈ **1GB 峰值**（服务器 1.6GB 内存、**swap=0**，P3-2）⇒ OOM 风险；
  且每请求一次带 commit 的写库在 `DB_LOCK` 上全局串行 ⇒ 磁盘 I/O 放大、正常请求被拖慢。
  攻击在**鉴权之前**就完成 body 读入，401 也救不回内存。
- **触发条件**：并发发送大 body 的 POST（未认证）。**注：内存峰值未在本机测到**（见 §4 D-3）。
- **能否被外部利用**：**是**。
- **建议修法**：反代 body 上限降到 1-2MB 或改流式转发；`_record_request` 批量/异步落盘或换持久连接；
  邮箱归因查询加按 token 的短 TTL 缓存。

### S-5 ｜**中**｜广场「下载计数」触发全量索引失效 ⇒ 可被登录账号反复逼出 O(卡数) 重扫
- **证据**：`api.py:288`（每次 `/plaza/api/download` 都 `bump_download`）→ `store.py:554-566`
  （重写 `meta.json` + `_touch_cards_dir()` + `_invalidate_index()`）；`store.py:246-282` 自述
  480 张卡冷读 283-490ms。交替请求 download 与 list ⇒ 每次 list 全量重扫 + 写盘。
- **影响面**：CPU/磁盘放大，多线程并发可把 1-2 核小机器打满，波及同机所有账号。
- **触发条件**：任一已登录账号（注册门槛：QQ 邮箱验证码 + 群号 + **自造 `install_id`** ⇒ 门槛偏低）。
- **能否被外部利用**：是（需登录）。
- **建议修法**：下载计数改为内存累加 + 定时批量落盘；不要在计数路径上 invalidate 全量索引。

### S-6 ｜**中**｜广场「覆盖/卸载前备份」无上限 ⇒ 登录账号可无限占用共享磁盘
- **证据**：`install.py:154-176`（`_backup_existing` 复制整包到 `user_data/{uid}/backups/plaza/{pid}-{stamp}`）；
  `:94-116`（`plaza_usage` 只统计**安装目录**，**不含 backups/**）；`:119-138`（配额只按当前安装的卡计，
  覆盖/卸载仍会再备一份）。实测可复现条件：一张 ≤4MB 的卡即可反复 replace（配额只挡安装目录）。
- **影响面**：单账号可把共享磁盘写满；磁盘满会同时打掉全部账号的数据写入、日志与备份（1.6GB 小盘机器尤甚）。
- **触发条件**：已登录账号，循环 `POST /plaza/api/install {replace:true}` 或 install→uninstall。
- **能否被外部利用**：是（需登录，门槛见 S-5）。
- **建议修法**：`backups/plaza` 纳入配额统计；或按卡只留最近 N 份（轮转）；或仅当内容确有变化才备份。

### S-7 ｜**中**｜公告 `action=check` 可被登录用户无限触发服务端对外抓取
- **证据**：`routes_notice.py:59-69`（`check(force=True)`）；`notice.py:343-431`（force 跳过 `CHECK_INTERVAL`，
  流程 = 拉 latest + manifest + 逐图下载；单源超时 20s、最多 2 源）；`notice.py:449-455` 的 `_RT["refreshing"]`
  互斥**只在 `payload()` 里**，force 路径不受保护；服务端模式下更新源即自身公网 8787
  （`hotupdate/__init__.py:48-51`）⇒ **服务器打自己的网关**。
- **影响面**：每次请求引发多次出网/自环 HTTP + 图片落盘（≤8MB/次）+ `state.json` 写；并发调用无互斥。
- **触发条件**：任一登录账号循环 POST `/notice/action {"action":"check"}`。
- **能否被外部利用**：是（需登录）。
- **建议修法**：check 加全局冷却/互斥（复用 refreshing 或时间窗），并限制单账号触发频率。

### S-8 ｜**低**｜公告图/热更清单的 `_reply` 响应未做 `Cache-Control` 之外的访问控制与计账
- **证据**：`download_server.py:155-184`（`_reply` 只 `_record_request` + 写 socket，无 GB 级 I/O 计量与异常隔离）。
- **影响面**：与 S-3 同源，属其子项（不单列修法）；此处仅登记「自服务路径无任何计量」这一事实。
- **能否被外部利用**：是。**建议修法**：并入 S-3。

| 交界面 | 结论 | 证据 |

## 4. 疑点（**未确认**，不要与 §2 混看）

- **D-1（低，可用性）** 网关反穿越校验用字符串相等：`fp == os.path.join(BASE, want)`。本机以**相对** BASE 启动时
  `realpath` 与 join 形态不一致 ⇒ 所有白名单文件 404（本轮实测踩到）。生产 BASE 为绝对路径故不成立。
  验证：用相对 argv 启动再请求 `/download/firefly.apk`。
- **D-2（低，不可利用）** `_NOTICE_NAME_RE`/`_HU_NAME_RE` 用 `$` 结尾，Python 的 `$` 可匹配末尾换行前 ⇒
  `img-a\n` 能过校验；但需 `NOTICE_DIR` 里**恰有**带换行名的文件，发布流程不会产生。验证：手工放 `img-a\n` 再请求。
- **D-3（中，内存）** S-4 的 1GB 峰值**未测到**：本机 12 条慢读 32MB 补丁时网关 RSS 稳定 43MB
  （疑似写入被本机 TCP 缓冲吸收）。验证：真机对 `firefly-downloads` 进程采样 RSS/容器 memory，并发 POST 16MB body。
- **D-4（低）** 服务器版公告缓存/已读跨账号共享（既有 P6-4）：本次**未起服务器版进程**验证，仅代码判读。
- **D-5（中）** 平台页令牌存 `localStorage` 且站点为明文 HTTP（既有 P0-2/P0-12）：同源 XSS 或中间人可窃取会话；
  本轮无生产账号，**未做浏览器侧验证**。

## 5. 未覆盖范围（未测 ≠ 没问题）

1. **生产服务器**：遵约束**零测试**（无端口扫描、无接口探测、无压测）。所有真跑均在 127.0.0.1。
2. **服务器版端到端**：未启动 `server_app.py` 跑真实账号 ⇒ `/notice`、`/plaza/*`、`/sync/*` 的鉴权边界
   仅代码审读（交叉审计 `0.9.1三系统交叉审计.md` A5 与 P4-6 已做过部分 401 边界，可复用）。
3. **热更真机链路**：重启自拉起、`sys.path` 首位注入、`boot_ok` 新进程判据 —— 缺真机与私钥，未跑。
4. **安卓/Kotlin 侧**：`verifyRsaSha256`、`installApk`（FileProvider）未审。
5. **管理台 8766 运行时**：仅代码审读（令牌比较用 `compare_digest` ✓）。
6. **生产 3Mbps 真实带宽下的抢占影响**：本机为 loopback，S-3 的「挤占业务带宽」是**机制推断**（计数器已证绕过），未在真线量化。
7. **PC 端语音**（0.9.1 PC 工作）不在本次范围。
