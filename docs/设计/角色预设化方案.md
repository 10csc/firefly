# 角色预设化方案（全角色扩展）

> 状态：设计定稿（2026-09-05，8 项不确定点已由用户拍板，按方案倾向执行）。
> 依据：全部判断来自当前代码逐处核实（盘点附录见同目录 `角色预设化方案_盘点清单.md`），不凭文档记忆。
> 硬需求（用户拍板）：除模型本身的风格与角色核心资产外，其余全部做成可替换预设；
> **预设包内资产（头像、封面、表情包、提示词文案等）必须能在软件内修改**。

---

## 一、总纲：把「模式」拆成三样东西

现状 `story`/`haruno` 捆绑了三个维度，预设化就是解耦：

| 维度 | 内容 | 预设化方式 |
|------|------|-----------|
| 角色 | 人格、口吻、禁令、示例短信 | 预设包 |
| 剧本/世界观 | 知识库、事实核查口径、可用地点、环境后缀 | 预设包 |
| 演出形态 | 短信+表情包 / 短信+旁白 / 纯短信 | 包内声明字段，框架按声明分发 |

**一包 = 一个角色 × 一个剧本**（拍板 #1）。流萤主线（story）与流萤·春日手信（haruno）各成一个内置包；同角色新剧本 = 再做一个包，人格段复制后微调。

## 二、预设包格式

```
app/assets/character/{preset_id}/
├── preset.json        # 清单与声明（框架读取的唯一入口）
├── core.md            # 核心设定（角色灵魂）
├── identity.md        # 人际关系与认知边界
├── sms_samples.md     # 短信样本
├── 用户设定.md         # 用户补充设定（默认空模板）
├── opening.json       # 可选：开场演出脚本（无则无开场）
├── knowledge/         # 可选：知识库目录（有则检索器挂载，无则跳过）
├── stickers/          # 可选：包默认表情包（registry.json + 图片）
├── prompts/           # 可选：提示词覆盖段（见 §四.3 槽位清单）
│   ├── polisher.md    #   回复器人设段
│   ├── analyzer_extra.md  # 分析器剧本核查段
│   ├── organizer_sticker.md / organizer_narration.md
│   ├── proactive_context.md # 主动消息情境文案
│   └── env_suffix.md  #   环境句世界后缀
└── assets/            # 视觉资产：avatar.png（角色头像）、cover.png（首页卡片）、
                       # user_avatar.png（用户侧头像，可选）
```

`preset.json` 字段：

```json
{
  "id": "haruno",
  "name": "春日手信",
  "char_name": "流萤",
  "user_name": "开拓者",
  "presentation": "narration",
  "bans": "default",
  "version": 1
}
```

- `presentation`：`sticker`（表情包）/ `narration`（旁白）/ `none`（纯短信）——替代 `organizer.py:141` 的硬分支（拍板 #2）
- `bans`：`default`（框架通用禁令底座）/ `replace` / `append`（拍板 #8）
- 缺省字段全部有框架默认值：无 opening.json 不开场、无 knowledge/ 不检索、无 stickers/ 表情包调度返回空（haruno 已证明降级路径可用）

## 三、数据与读取规则（全部沿用现有机制，零新发明）

1. **包发现**：启动时扫描 `bundled_character_dir` 上级目录（`app/assets/character/*/preset.json`），替换 `app_config.py:298` 写死的 `MODES`；非法 id 回退默认包的逻辑保持（`:302-308`）。
2. **用户副本优先**：现有 `resolve_character_file`（`llm_base.py:24-27`）语义不变——用户改的是 `user_data/{mode}/` 副本，bundled 不动，**删副本即恢复默认**（软件内修改资产的天然"撤销"机制）。
3. **包 id 沿用 `story`/`haruno`**：现有用户数据目录零迁移（拍板 #7）。
4. **服务器版**：首版只能用全局预设包 + 用户副本覆盖文案；自定义整包上传不做（拍板 #5，注入面与配额后续再议）。

## 四、框架层机制设计

### 1. 角色名/用户称呼变量化（最容易漏的一类）

全后端模板与文案里的"流萤"/"开拓者"字面量 → `{char_name}`/`{user_name}` 注入：
- `llm_base.py:85-102` `format_history`（所有模块共用，单点收口）
- `memory_manager.py:98,125,134-137,240,288`（rest/手账提示词与手账标题）
- `proactive_gen.py:65-149`（动机决策全段）
- `conversation_store.py:82`（引用合成的 who 映射）
- 各模块 user 段"开拓者刚才说"（polisher/analyzer/organizer/retriever/proactive）

### 2. 提示词槽位化（骨架+段拼装，拍板 #3）

**框架锁死**（不进包）：输出协议（`[MSG]` 格式、`narrations` JSON 契约、sticker label）、分析对齐段、said_section 数据注入、JSON 契约、降级话术结构。
**包可覆盖**：polisher 人设段（时空/底色/短信风格/感情表达/划边界/角色专属禁令）、analyzer 剧本核查段、organizer 两个提示词、proactive 情境文案、环境句后缀。
拼装规则：包有 `prompts/xxx.md` 用包的，没有用框架默认文案（现 story 版内容下沉为框架默认）。

### 3. 演出形态分发

`organizer.organize()` 按 `preset.presentation` 分发：sticker→表情包调度、narration→旁白生成、none→直接返回空。表情包提示词与旁白提示词的包级覆盖同 §四.2。

### 4. 环境句

时间部分框架生成（`orchestrator.py:149-159` 不动），世界后缀从包 `prompts/env_suffix.md` 读（haruno 的"黄金时刻仍亮如午夜前…"移入包）。

### 5. 软件内资产编辑（新需求落点）

现有能力（已核实）：表情包 CRUD 完整（`routes_assets.py:56-147`）；"用户设定.md"可编辑（`:150-172` 白名单制）；图片上传链路完整（`:21-53`）。
扩展设计：
- **文本类**：`character-file-update` 白名单从 `{"用户设定.md"}` 扩为"包内可编辑清单"（prompts/*.md、opening.json 以结构化表单编辑而非裸 JSON）
- **图片类**：头像/封面新增上传端点（复用 multipart 解析与扩展名白名单，落 `user_data/{mode}/character/assets/`）
- **表情包**：注册表加包维度——包默认集（bundled）+ 用户添加（用户域，现有隔离机制不变），organizer 清单按当前包取
- 前端：菜单「设定文件」页扩展为「角色包」管理页（包信息、头像/封面上传、提示词段编辑、表情包按包管理）

### 6. relay 占位符扩展（拍板 #6）

`llm_base.py:121-124` 的 `ASSET_*` 占位符机制保留；`assets_index`/`assets_raw`（`routes_assets.py:292-341`）的资产清单从写死 4 件（knowledge/core/identity/sms_samples）改为按包清单生成；前端 `relay.js:59-62` 的占位符替换清单同步按包清单驱动（不再是 4 个写死键）。md5 版本指纹机制不变——用户在服务器端改了包文案，APP 端靠版本指纹自动重拉。

### 7. 服务器版适配（与双端并列的第三条工作线）

已逐处核实 server/ 触点：
- `server_app.py:484-488` `/assets/` 静态服务走 `resolve_asset`（用户目录优先退回 bundled）——包内头像/封面等资产的服务路径要能解析到 `user_data/{uid}/{mode}/` 副本与包目录，resolve_asset 的包路径感知要补上
- `shared_http.py:82-88` `preload_knowledge()` 无参调用 = 只预热 story——改为按注册表预热所有带 knowledge/ 的包（或改懒加载，实施时定）
- relay 链路三件套（占位符 → `routes_relay.py:17` 下发 → `relay.js` 本地替换）——按 §四.6 泛化
- 用户数据 `user_data/{uid}/{mode}/`：mode 维度天然继承（包 id 即目录名），零改动
- `server/frontend/` 由 `sync_frontends.py` 从 app/static 同步——前端泛化自动跟随，无独立工作
- `db.py`/`download_server.py`/`mail.py` 已核实零业务模式相关，不动
- 部署链路：`docs/部署说明.md` 的 scp 清单（app/ + knowledge/ + server/ + database/）随 knowledge 入包改路径；服务器管理规范同步更新
- 服务器版边界保持拍板 #5：首版只用全局包 + 用户副本覆盖，自定义整包上传不做

## 五、不纳入预设的（框架固有，冻结）

输出协议与消息结构、流水线四段编排与超时降级链、数据目录公式（`app_config.py:302-320` 已参数化）、存储/undo/rest/窗口合并机制、主动性门控（`proactive_gate.py` 已按 mode 参数化）、表情包 CRUD 机制、同步/导出/备份（`sync_engine.py` 模式无关）、供应商/Key/模型配置、前端渲染器与消息队列、设定纠错机制（六文件白名单）、通用 9 条禁令底座（`default_bans.md`，拍板 #8）。

## 七、风险

1. **缓存**：阶段 3 改动 system 段 → 全体用户下一轮提示词缓存一次性重建（不可避免，一批做完）。
2. **范围**：触碰 10+ 后端文件与前端大部分页面，本项目迄今最大重构——阶段 1-2 先行小步验证，任何一阶段验证不过不进入下一阶段。
3. **兼容性**：包 id 沿用 story/haruno 保证老用户数据零迁移；preset.json 缺字段全有默认值，老包（无 preset.json 的目录）按 story 默认补齐。
