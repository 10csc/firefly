### ⚠️ 噪声地板（必须与上表一起读，否则会误判）
`final_default` 与 `refcache_on` **是同一个配置**（`ref_cache=True` 是引擎默认；`dict()` 不传参就是它），
却分别测得 **19.60±2.77** 与 **16.30±1.38** ⇒ **同配置跨会话的总耗时噪声 ≈ ±3s**，主因是
**采样随机导致 token 数在 63~71 之间波动**（`04 §M5` 早写了"禁单样本 A/B"）。

**因此本轮不拿"总耗时差"当采纳依据**，只用两类**稳健证据**：
1. **阶段归因**：`vits` 是唯一被改动阶段，且**所有 ref_cache=True 的配置**（含 arena/threads/bert 各行）
   都出现 `vits ≈ 0.98s`、`vits_ref ≈ 0.26`（= 首次 1.30s ÷ 5 次的均值）⇒ 与总耗时噪声无关；
2. **逐位等价证明**（下节）⇒ 这条把"零质量代价"从"统计上没变差"升级为"**数值上完全相同**"。

## 2. 「零质量代价」的决定性证据：参考侧 vits **逐位可复现**

`_harden/w1_refcache_equiv.py`（直接用 onnxruntime 加载 `firefly_vits_int8.onnx`，喂
`mood_lib/<mood>` 的**同一批张量**，分两次独立 `run()`）：

```
[happy] out.shape=(1,512,496)  np.array_equal=True  最大绝对差=0.000e+00
        sha256(第一次)=249eb722085d245b4a0ef7f3  sha256(第二次)=249eb722085d245b4a0ef7f3
[sad]   out.shape=(1,512,528)  np.array_equal=True  最大绝对差=0.000e+00
        sha256(第一次)=4349a7b2b51ab433a7fe6810  sha256(第二次)=4349a7b2b51ab433a7fe6810
反向对照（截短一个 phone 的输入）：输出是否不同 = True   ← 证明该图对输入敏感，"一致"不是假象
结论：参考侧 vits 输出逐位可复现 ⇒ 缓存与重算等价（零质量代价成立）
```

**为什么这项优化在原理上就是零代价**：参考侧 vits 的输入
（`ref_phones` / `prompt_sem` / `refer_spec`）**全部来自 `_refs[mood]`、与输入文本无关**，
图内**没有任何随机采样** ⇒ 同语气下每次请求重算的是**同一份结果**。
缓存的是原始输出 `(1,512,T_ref)`；下游 `fea_ref_2d[:, :t_min].copy()` **先复制后改写**，不会回写缓存。

## 3. 三条「动音质」杠杆 —— 选项清单（**本轮不启用**，交用户拍板）

> 为什么需要它们：本轮只做零代价项后，**12s 线仍未过**（零代价档 ≈16~17s，与手机最好档 17.7s 持平）。
> 要再往下压，只剩下会**直接改动音质**的路。三条都**已在代码中留有开关**（`steps` 已是参数），
> 但**默认值一律保持不动**，等用户明确点头再启用。

| # | 杠杆 | 改动点 | 预期收益（本机实测口径） | 音质风险 | 回退方式 |
|---|---|---|---|---|---|
| L1 | **CFM 步数 4 → 3** | `pc_engine.CFM_STEPS`（或 `PcVoiceEngine(steps=3)`） | CFM **−24.4%**、总耗时 −13.8%（`_pc_voice_v4_speed.log`） | **少一步欧拉积分 ⇒ 高频细节/尾音可能变化**；必须靠盲测（§5）判定 | 把 `steps` 改回 4 |
| L2 | **CFM 4-bit 量化**（MatMulNBits） | 需**重做模型**（332.7→~170MB），非运行时开关 | 磁盘 −160MB；**CPU EP 上常更慢**（未验） | 量化误差进 CFM ⇒ 音色/稳定性风险最高的一个 | 保留原 int8 模型文件 |
| L3 | **缩短参考音频**（4.4s → ~3s） | `app/assets/voice/mood_lib/*/refer_spec` 等参考张量 | 参考同时压在 AR/CFM/vits 三条路径 ⇒ 三处一起变短 | **直接改音色**；且会改守卫通过率 | 保留原 mood_lib 参考（换回即恢复） |

**建议顺序**：若要动，**只动 L1**（收益确定、回退最便宜、且已有盲测材料）；
L2/L3 都属"换音色/换模型"量级，建议不做（与用户"不换模型、不下滑"的口径冲突）。
**L1 的启用前置条件**：W2 盲测（§5）判为"更好"或"不可区分"。

### ★ 7.1 抓到真缺陷：**AR 早停 ⇒ 音频说到一半就断，而守卫放行**（tier-2 失败）

`S04-B-default_steps4`：期望「太好了！我们终于把这件事做完了。」，ASR **只回读出「太好了。」**。
同句另一档正常。原始对照（不是猜测）：

| 同句 `太好了！我们终于把这件事做完了。` | tokens | 音频时长 |
|---|---|---|
| `default_steps4`（被截断那条） | **30** | **1.85 s** |
| `cand_steps3` | 90 | 4.29 s |

**复现率实测**（`_harden/w1_trunc_rate.py`，同一句重复 12 次，判据 `tokens < 0.6×中位`）：

```
N=12  tokens: 中位=75 最小=34 最大=89   早停判据 = 45.0
疑似早停（音频说到一半就断）: 1/12 = 8.3%     #6 tok=34 dur=2.01s
```
两批独立样本各命中 1/12（W2 的 pack 1/12 + 本率测 1/12）⇒ **≈8%（2/24）**。

**为什么守卫没拦住**：`pc_engine._run_chain` 的输出侧守卫只判两件事 ——
① 未在 `cap` 内收敛；② `idx < MIN_TOKENS(12)`。**30~34 token 既收敛又 >12 ⇒ 守卫返回 ok**，
但对该句（正常 ~75 token）就是**说到一半**。与之对照，`_harden/pc_voice_engine_integration.py` 里
sad 的 **tier-1** 失败（`tok=1`）**被守卫正确拦下**并触发重试（attempt 2 成功）。

**影响面**：这是**用户可见**的质量问题（听感上就是"话说一半没了"），且
**在现行默认档上发生**（不是本轮改动引入：截断样本来自 `default_steps4`）。
它与 `01 §3.3` 记录的"采样不可控（图内 top-k 无种子）"同源，但**后果比"指标波动"严重**：
属于"守卫通过率"口径**没覆盖**的那一类。

**建议（未实施，需用户拍板）**：给输出侧守卫补一条**下限比例判据**（如
`tokens < 0.5 × (音素数 × MIN_TOK_PER_PHONE)` ⇒ 判"过早收敛"并重试）；
`MIN_TOK_PER_PHONE = 2.0` 常量**已存在**（Kotlin 侧定义了但端侧未启用，见 `_run_chain` 注释）。
**本轮不动**：它改的是"何时判失败/是否重试"，属行为变更，且需要先定重试策略（现有上层**已有重试**）。
