# 03 · PC 技术方案与预算（不实现，只给决策材料）

> 目标（用户原话）：**在手机端 900MB 基础上提速即可** · **常驻内存尽量 ≤4GB** · **质量相对手机端不下滑**。
> 全部数字：`[实测]` 本次运行本仓库探针 · `[已有实测]` 仓库内既有日志 · `[未测]` 明确无数字（测法见 04）。

## 1. 候选路线对比

| 路线 | 磁盘 | 常驻内存（语音部分） | 单句 | 质量 | 结论 |
|---|---|---|---|---|---|
| **R1 同模型 ONNX int8 + 独立子进程 + 纯 Python 文本前端（推荐）** | 872MB（手机同款） | **约 1.1~1.5GB** `[推断: 待 04 M3 测]` | **≈15~19s** | **与手机逐条同逻辑 = 持平** | ✅ 首选 |
| R2 同模型 + 保留官方 PyTorch 文本前端 | 872MB + torch/transformers ≈2.5GB 安装 | **≈2.7GB（实测 2.72GB 峰值）** | 18.7s 均值 | 略高（g2pw 多音字/数字归一化） | ⚠️ 内存吃紧、包体暴涨，仅作高精度备选 |
| R3 换更小/更快的 TTS（VITS 微调 / Matcha / sherpa-onnx） | 60~120MB | 150~250MB | 亚秒级 | **必须重训/重选音色 —— 不再是流萤的声音** | ❌ 与「900MB 基础上提速」相悖 |
| R4 系统 TTS 兜底（Windows SAPI） | 0 | ~0 | 快 | **断崖式下滑**（音色完全变了） | ❌ 只作 R1 彻底失败的退路 |
| R5 GPU（CUDA） | +2.5GB 权重 | 显存 2.2GB + 内存 5.5GB | 3.6~4.2s | 同级 | ❌ 用户设备不可控、超 4GB 预算 |

**推荐 R1。** 理由：用户的要求是「**提速**」而非「换音色」；R1 与手机端**同一套 8 个模型、同一量化档**，
磁盘不变、质量口径天然持平，且**唯一被砍掉的重物（torch/transformers）与音质无关**——它只被用来做文本前端。

## 2. 推荐路线（R1）的形态

```
主进程（app/server.py，常驻 ~17MB）
   └─ voice/engine.py  ← 新增 PC 后端分支（现在这里返回"无引擎"）
        └─ 独立子进程 voice_engine_worker（空闲 300s 自退，内存真正归还）
             ├─ onnxruntime CPU EP：6 组件 int8 + vocoder fp32 + BERT int8（手机同档）
             ├─ 文本前端：TextFrontend.kt:60-145 的纯 Python 移植
             │    （读 app/assets/voice/{pinyin.json,char2id.json,symbols.json,opencpop-strict.txt}）
             └─ 语气参考：直接读 app/assets/voice/mood_lib/{happy,sad}/*.raw（零推理，无需 ssl.onnx）
```

- 上层接口**一个字不用改**：`app/voice/engine.py:8` 的注释本来就写着「接入时只需在这里补一个后端」；
  `available()/ensure()/status()/synthesize()/release()` 五个函数签名已定（`engine.py:44-131`）。
- 子进程通信形态**已有可复用原型**：`FireflyVoiceResearch/_proto/engine_host.py`（223 行，含超时即杀、
  空闲 reap、崩溃重拉）+ `engine_worker.py`（110 行，stdout 与 print 隔离）。
  已实测：主进程全程 17~18MB、空闲退出后系统可用内存回到基线差 21MB（`docs/工具/tts.md:138-152`）。
- **Windows 打包必做**：子进程用 `CREATE_NO_WINDOW`（主 exe 是 `console=False`，
  `firefly.spec:64`），否则会弹黑窗 `[未测/待验]`。

## 3. 预算账（三本账）

### 3.1 磁盘`[已有实测]`

| 项 | 体积 |
|---|---|
| 6 组件（E5 去重后，含共享 `weights.bin`） | 520.6 MB |
| BERT int8（手机默认档） | 351.4 MB |
| 映射表 + mood_lib（**已在 PC 包里**） | 4.8 MB |
| **合计** | **≈877 MB**（与手机 880.8MB 同量级；用户说的「900MB」即此） |
| 新增可执行依赖 | onnxruntime + numpy（打包体积 `[未测]`，量级 ~60~90MB） |

> 不需要 `firefly_ssl.onnx`（377.7MB）——参考特征已预计算（`_proto/voice_engine.py:240-252` 的替代逻辑）。

### 3.2 延迟`[实测]`（本机 Ryzen 7 6800H / 16GB，ONNX 全链 int8）

| 阶段 | 手机（一加 Ace 3） | PC（原型实测） | 差因 |
|---|---|---|---|
| 引擎装载 | session 4801ms | **27.9s**（含 torch/transformers import 14.1s） | PC 省掉 torch 导入后预计 **≈11s**（6 组件 session 10.3s + BERT 0.9s，`[实测]` 探针） |
| 单句合计 | **17.7~67.4 s** | **14.3~25.4s（44 次均值 18.7s）** | `[已有实测]` `_rate.log:57-63` |
| 本次抽测 | — | 62 token / 3.09s 音频 → **22.4s** | `[实测]`（含采样线程干扰，取上行为准） |
| AR 占比 | 71% | **PC 上顺序变了**：FP32 全链 31.3s 里 **CFM 13.9s（最大头）**、AR 8.8s | `docs/09 §F2`、`_session_hist.txt:9039` |

> ⚠️ **PC 与手机的瓶颈排序不同**（重要）：手机是 AR 主导（71%），**PC 是 CFM 主导**
> （`_session_hist.txt:9039` 原话：「CFM 才是 PC 侧的瓶颈，而手机上 INT8 CFM 只要 7.3s——CFM 的 int8 收益比 AR 大得多」）。
> 但 PC 也要跑 int8 CFM（速度差 12× 的 vocoder int8 已排除），所以 PC 的提速杠杆应**先看 CFM（步数/4-bit）**，
> 再看 AR（线程数）。研究轮次里 ONNX int8 的一次同类记录：AR 5850ms / CFM 8137ms（42 token，未固化进文档）。

**结论：R1 的延迟与手机最好档持平（≈18s vs 17.7s），比手机最差档（67.4s）快 3.7×。**
若要「明显优于手机」，按下面杠杆继续压（§3.4）。

### 3.3 内存`[实测 · 本次探针]`

| 口径 | 数字 | 说明 |
|---|---|---|
| 主进程（app 本体） | **17~18MB** | `[已有实测]` `docs/工具/tts.md:144-149` |
| 语音子进程：只 import numpy+onnxruntime | PRIV 545MB / WS 47MB | PRIV 含「已提交未驻留」（numpy 单独就 +523MB 提交）⇒ **PRIV 与 WS 必须同时看** |
| 语音子进程：7 个 session 常驻（未推理） | PRIV 551MB / WS 54MB | ONNX 权重是 **mmap / 文件页**，不触碰不驻留 |
| **原型全路径（含 torch 前端）装载后** | WS/RSS **1588MB** | `[实测]` |
| **原型全路径：1 次合成后** | WS/RSS **2534MB**；**峰值 2722MB** | 与既有记录 2826MB(`docs/工具/tts.md:144`) 同量级 ✓ |
| 其中 torch + transformers 的提交 | **+1164MB**（torch 503 + transformers 661） | **这就是纯 Python 移植要砍掉的部分** |
| **R1 预期** | **≈1.1~1.5GB 常驻、峰值 ≤2GB** | `[推断]`：去掉 torch/transformers 后，权重+ORT+Python 的实际占用；**必须按 04 §M3 复测** |

⇒ **即便按原型的 2.72GB 峰值算，PC 端（主进程 18MB + 语音子进程）也仍在 4GB 之内**；
R1 有 2 倍以上余量。**唯一超预算的路线是 R2/R5**（torch 全栈 7.8GB 峰值，见 `docs/10:30-46`）。

### 3.4 提速杠杆（按「先测再改」排序，见 04）

| # | 杠杆 | 预期 | 风险 |
|---|---|---|---|
| L1 | **CFM 步数 4→3**（PC 瓶颈项，见 §3.2 注） | CFM ≈ −25%（PC 上 ≈ −2s） | 音质需 N≥5 统计对比（`docs/10:176-179` 纪律） |
| L2 | ORT 线程显式设定（`intra_op_num_threads=物理核数`、`inter_op=1`、`ORT_SEQUENTIAL`） | `[未测]` 1.0~1.5× | 无（原型/手机都没设） |
| L3 | 参考音频 4.4s → ~3s（F3：参考同时压在 AR/CFM/vits 三条路径） | AR/CFM 上下文变短 | **直接改音色与守卫通过率**，需先做通过率对照 |
| L4 | CFM 4-bit（MatMulNBits，332.7→~170MB） | 磁盘 −160MB，速度 `[未测]` | PC CPU EP 支持性未验；4-bit 在 CPU 上常**更慢** |
| L5 | 关 CPU arena（**已默认开启**，`FIREFLY_NO_ARENA=1`） | 防内存单调上涨 | 已生效，勿改回 |
| ❌ | GPU / 蒸馏剪枝 / 换架构 | — | 超范围或设备不可控 |

## 4. 风险与退路

| 风险 | 影响 | 退路 |
|---|---|---|
| onnxruntime 打进 PyInstaller 失败（DLL/hook/UPX） | PC 发不出去 | `upx_exclude` 排除 ORT DLL；最差把语音引擎**单独打第二个 exe**（引擎本就设计为独立执行体，天然可分离） |
| 纯 Python 文本前端与 Kotlin 版**不一致** | 音质相对手机下滑 | 移植后用 `_equiv_dump.py` 同款方法做**逐位对齐**（现成的等价性验证套路，`docs/工具/tts.md:157`） |
| 首次使用要下 872MB（与手机同） | 用户流失 | 二期加「导入本地 zip / 指定本地目录」入口（**当前没有**；属新功能） |
| 卸载残留 872MB（02 §G4） | 磁盘债 | `[UninstallDelete]` 或依赖插件页「卸载」 |
| 采样随机性导致「感觉音质变了」 | 误判 | 任何音质结论必须 N≥5 看分布，禁止单样本 A/B（`docs/10:176-179`） |
| **R1 彻底失败** | PC 无语音 | R4 系统 TTS 兜底（**质量必降**，需用户明确接受）；或暂缓 PC 语音随 0.9.1 发布 |

## 5. 需要用户拍板（D1~D4）

| # | 问题 | 建议 |
|---|---|---|
| D1 | 文本前端：移植 Kotlin 版（省 1.7GB、与手机持平）还是保留官方 PyTorch 版（质量略高、+2.5GB 依赖） | **A：移植 Kotlin 版** —— 用户的验收线是「不下滑」，不是「变好」 |
| D2 | 是否批准 PC 引入 `onnxruntime`（+numpy）打包依赖 | 是（任务 4.1 原卡即要求明示批准，`docs/架构重构计划/05_阶段4…md:13`；手机早已用 ORT，只是不在 Python 侧） |
| D3 | 首次下载 872MB 是否可接受 | 可（与手机一致）；若要离线，需另立「本地导入」小任务 |
| D4 | BERT 档位：int8（351MB / 与手机同档 / 持平）或 fp16（571MB 磁盘、**770MB 常驻**） | **int8**（持平即达标，且省 400MB 常驻） |

## 6. 分阶段实施顺序（获批后）

1. **M0 可验证性**：跑 04 的 M1/M2，把「未测」补成数字（线程数、ORT 常驻）。
2. **M1 PC 可用**：移植文本前端（含逐位对齐测试）→ 在 `app/voice/engine.py` 补 PC 后端（子进程）→
   `firefly.spec` 放开 onnxruntime/numpy → 本地 exe 实跑「转语音」出可播 wav。
3. **M2 补齐生命周期**：卸载/覆盖安装（02 §G4）、无窗口子进程、诊断日志。
4. **M3 提速**：按 L1→L2→L3 顺序，每步**先量再改**（04 的验收线）。
5. **M4 验收**：PC 实测三本账（磁盘/延迟/内存）+ 质量 N≥5 对照 + `tools/check_*` 门禁 → 随 0.9.1 整包发版。
