# PC 端前端重构（审计 + 设计）

> ## ⚠️ 2026-09-19 第二版：**第一版被用户否掉，这里是重做的结论**
>
> 第一版我在 PC 上自造了一整套导航：左侧图标栏（9 项 emoji）+ 第二列目录 + 工作区顶栏 +
> 右侧上下文栏。用户当场否掉，理由三条，都成立：
> 1. **"这是在首页，首页你展示一堆菜单页里的东西干什么？那你菜单页有什么用？"** ——
>    我把**手机 ☰ 菜单页里的东西**（收藏/表情包/设定文件/请求记录/流程日志）抄成了全局入口。
> 2. **"左边留个侧边栏不明所以（还有残留功能比如纠错）"** —— 那一栏没有对应的信息架构。
> 3. **"UI 风格完全的廉价 AI 味，我手机改好的 UI 不学（甚至照抄导致电脑端完全没适配）"** ——
>    我既没学手机的**设计语言**（用 emoji 而不是它自己的 SVG 精灵），也没做**适配**
>    （把手机的三层结构原样搬成并排的栏，而不是换一种呈现）。
>
> **查到的正式依据**（微软官方 UX 指南，[Windows Ribbons](https://learn.microsoft.com/en-us/windows/win32/uxguide/cmd-ribbons)）：
> - *"**Present each command on only one tab. Avoid multiple paths to the same command** …
>   having duplicate commands makes it harder for users to find other commands they are scanning for."*
> - *"**Reserve commands that belong in the Application menu only for that menu.** Don't place them redundantly in any of the tabs."*
> - *"Use context menus and mini-toolbars for **in-place, contextual** commands"* ——
>   只作用于当前对象的命令（收藏/记忆/日志）不该升格为窗口级导航。
>
> **第二版准则：层级与命名 100% 沿用手机，PC 只改"呈现"。**
>
> | | 手机 | PC 第二版 |
> |---|---|---|
> | 全局顶栏 | 首页右上：反馈 · 公告 · 主题 · 设置 | **同一套**（不新增第二个导航） |
> | 首页 | 角色包轮播 + 入口（继续聊天/角色卡管理/语音插件）+ 账号 | **同一个组件**，轮播 → 多列网格，内容居中一列 |
> | 聊天页 | 消息 + ☰ 菜单 | 同一套，限宽可读列 |
> | ☰ 菜单 | 覆盖式抽屉（屏幕小必须盖住） | **停靠到右侧**（屏幕宽，不必挡对话）；内容/分组/四个动作一字不动 |
> | 额外信息 | 记忆进度在名字行尾、版本在设置里 | **只加底部状态栏**（版本/热更/同步/公告未读）—— 状态是信息不是命令，不构成重复路径 |
>
> 结果：**删掉了 pc-shell / pc-rail / pc-list / pc-main-head / pc-chat-side 五块自造结构**，
> `pc_shell.js` 从 700+ 行缩到 ~120 行（只剩状态栏）。守卫 `tests/test_pc_shell.py` 相应重写，
> 把"不许再出现第二套导航""☰ 必须可见""菜单必须停靠""气泡宽度上限只设一次"钉死。
>
> 顺带修掉一个**真实渲染 bug**（第一版就有、这次原尺寸截图才发现）：
> `.msg-row .bubble{max-width:68%}` 与手机上 `.msg-col .bubble{max-width:100%}` 同优先级相加，
> 而 `.msg-col` 又是 shrink-to-fit ⇒ 两级互相挤压，`嗯，我在` 只剩 29px 内容宽、**一个字一行**。
> 现在上限只由 `.msg-col` 承担、气泡吃满列宽。


> **为什么重构**：PC 端不是"专门做的 PC 界面"，而是**把手机界面塞进一个右侧卡片 + 左边加了一条导航**。

## 二、数据逻辑 / 业务逻辑（界面必须表达出来的东西）

按**数据的真实层级**排（来源：`app/core/presets.py`、`modules/*`、`api/router.py` 的端点表）：

```
全局
├─ 账号（服务器版）：登录态 / 云端同步 / 快照（每账号最近 5 份）
├─ 设置：账号与连接 · 模型与速度（检索/分析/回复/组织四阶段）· 外观 · 数据（版本/自动修复/快照/同步）
├─ 公告与更新说明（服务端下发，未读/已读）
├─ 插件：语音（模型下载 + 语气库 + TTS，模型是否就绪决定可用性）
└─ 诊断：请求记录 / 流程日志 / 指标
角色包（pack，可多个，各自独立）
├─ 角色卡：人设与口吻（core/identity/sms_samples）· 知识库 · 出厂记忆 · 用户形象（称呼+头像）· 危险区（归档/删除）
├─ 聊天：对话流（按 seq）· 撤回 · 清除历史 · 引用 · 图片/表情包
├─ 记忆：活跃窗口（30–100 轮，实时进度）· 用户记忆（memory.md）· 历史对话存档（按月只增不改）· 手账
├─ 表情包：启用/停用 + 分类 + 含义描述
└─ 主动消息：开关 + 软/硬频率（按包独立）
```

**关键推论**：
1. **角色包 = 一等公民**。PC 端必须有一列常驻的角色包列表（头像 + 名字 + 未读/主动/记忆状态），切包一步到位 —— 这是 A6 要解决的。
2. **记忆是有"进度"的**：活跃窗口 `n/100` 是用户能感知的状态（手机端在名字行尾显示 `· 记忆 92/100`）。PC 端应该把它做成常驻状态条。
3. **设定文件是"三份文件"**，不是三个 tab：用户记忆（可编辑文本）/ 历史存档（按月分片，只增不改）/ 手账。桌面端适合"左列表右编辑器"。
4. **设置是"4 组 + 版本/热更/快照/同步"**，桌面端适合"左分组导航 + 右内容"，且**全部展开**（屏幕够高，不需要手风琴）。
5. **登录前置是真实业务规则**，PC 端要把它表达成"聊天区显示未登录引导"而不是"首页塞一个表单"。

## 三、设计方案：真三栏（rail + 列表 + 工作区）

```
┌──────┬────────────────┬─────────────────────────────────────────────┐
│ rail │ 上下文列 300px │ 工作区（现有各视图挂这里）                  │
│ 68px │                │                                             │
│ 💬   │ 角色包列表     │  顶部：包名 · 模式标签 · 记忆 n/100 · 状态点 │
│ 🎴   │  ┌──────────┐  │  ─────────────────────────────────────────  │
│ 📂   │  │头像 流萤 │  │                                             │
│ 😊   │  │剧情模式  │  │  聊天流 / 设定文件编辑 / 角色卡 / 设置 …    │
│ ⭐   │  └──────────┘  │                                             │
│ 🔊   │  ┌──────────┐  │  ─────────────────────────────────────────  │
│ 📣   │  │头像 春日 │  │  底部：输入栏（仅聊天视图）                 │
│ 📋   │  └──────────┘  │                                             │
│ ⚙    │                │                                             │
│ ──── │                │                                             │
│ 账号 │                │                                             │
│ v0.9 │                │                                             │
└──────┴────────────────┴─────────────────────────────────────────────┘
              底部状态栏：版本 · 热更 serial · 同步 · 公告未读
```

**实现要点（三条硬约束）**

1. **移动端一行 DOM/CSS 都不改行为**：外壳 `#pc-shell` 在 <1100px 时 `display: contents`，
   各视图仍是 `position: fixed` 铺满视口 —— 与现在**逐像素等价**（用 390×844 视口回归验证）。
2. **视图宿主**：PC 端把 `#pc-main` 里的 `#view-host` 设 `position: relative`，
   视图层改 `position: absolute; inset: 0`。**所有 view 的 id / class / JS 入口保持不变**，
   所以 `showChat()/showHome()/openSettings()/openMenuTab()` 等现有函数零改动即可复用。
3. **PC 导航用纯 JS 重写**（`js/pc_shell.js`），**去掉 petite-vue 依赖**：
   现在 `pc_nav.js` 为了一个 6 项列表按需下载一个框架，且它的 `openMenuTab` 路径正是 A3 的根因。
   重写后 rail 只负责"切导航"，列 ② 与列 ③ 由同一份状态驱动。

**分阶段**

- **阶段 1（本轮已完成）**：外壳 + rail + 上下文列（角色包 / 设定域 / 设定文件 / 设置分组 / 公告 / 收藏 / 日志 / 语音 / 纠错）
  + 主区标题栏 + 底部状态栏；各视图接进宿主；`pc.css` 独立成文件（旧 PC 块从 style.css 整段移除）。
- **阶段 2a（本轮已完成）**：**设定文件两栏化** —— 列② 选「用户记忆 / 历史对话存档 / 手账」，
  右栏**只显示这一段**（`#tab-char[data-pc-sec]` + pc.css 的三条显示规则；没设属性时三段全显示，
  所以窄屏与"pc_shell 没跑起来"都退回手机行为）。
- **阶段 2b（本轮已完成）**：**角色卡域导航两栏化** —— 列② 列出 `/pack-structure` 的九个域
  （用户形象 / 人设与口吻 / 检索器 / 分析器 / 组织器 / 主动性 / 环境与演出 / 形象资产 / 危险区，
  带 `desc` 说明），点某一域 → 打开包编辑页并**只展开该域**（`details.pt-domain[data-key]` 的 `open`，
  用户之后仍可手动展开别的）。
  ★ 这里踩到一个**只有出图才发现**的 bug：**桌面是单工作区，切视图前必须显式关掉其它视图** ——
  从左栏选「角色卡 → 主动性」时 `#menu-drawer` 还开着（z-index 更高）把包编辑页整个盖住，
  截图上看着像"没打开"。手机端有返回链，桌面没有。修法：统一 `closeAll()`，`go()` 与所有
  "打开某个视图"的列表动作先清场。
- **阶段 2c（待做，登记 P2-14）**：收藏/请求记录在列② 里直接列条目（现在只给一个入口）——
  **刻意排在最后**：本机开发数据里收藏 0 条、请求缓冲为空，列出来也**没法当场验收**。
- **阶段 3（本轮已完成）**：**聊天区右侧「包上下文」栏**（`#pc-chat-side`，300px）。
  直接把审计 A5（聊天列居中后右侧 40% 空白）转成信息位，内容按数据逻辑取：
  ① **记忆 · 活跃窗口**：进度条 + `活跃窗口 43 / 100 轮` + `整理后保留最近 30 轮原文 · 到 80 轮提醒，
  到 100 轮自动整理`（数据源 `GET /memory-status`）+「让角色休息（立即整理）」按钮（复用菜单里那个按钮的既有接线）；
  ② **历史对话存档**：`已有 2 个月份：2026-09、2026-08`（`GET /archive`）+「查看 / 编辑存档」→ 跳到设定文件存档段；
  ③ **快捷动作**：撤回上一轮 / 表情包 / 转语音 / 公告。
  实现要点：`--pc-aside-w` 变量统一宽度；`#app { right: var(--pc-aside-w) }` 只让**聊天视图**让位；
  栏的显隐在 2.5s 轮询里按 `#app` 可见性切换（`hidden`），窄屏 `display:none`。

## 五、实现记录（2026-09-19 阶段 1，含两个当场踩到的坑）

**文件**
| 文件 | 作用 |
|---|---|
| `app/static/pc.css` | **新增**：PC（≥1100px）唯一样式源。旧 `style.css` 末尾那段 PC 规则已整段删除 |
| `app/static/js/pc_shell.js` | **新增**：三栏外壳控制器（纯 classic script，独立于 bundle） |
| `app/static/index.html` | `#pc-sidebar`（petite-vue 双栏）→ `#pc-shell`(rail+list) + `#pc-main-head` + `#pc-statusbar`；`pc.css` 链接放在内联 `<style>` **之后** |
| `app/static/js/views.js` | 加 `window.__getCurrentMode()`（只读 getter，外壳读当前包用） |
| `app/static/js/update.js` | 加 `window.__appVersion`（状态栏用） |
| `tools/build_frontend_bundle.py` | `pc.css` 指纹更新；`pc_shell` 登记进 `NON_BUNDLE`；指纹替换锚定到 `href=`/`src=` |
| `tools/sync_frontends.py` | `pc.css` 纳入三端同步；`pc_nav.js` 进 `_remove_stale`；空 `vendor/` 校验 |
| 删除 | `app/static/js/pc_nav.js`、`app/static/vendor/petite-vue.iife.js`（PC 不再依赖框架） |

**踩到的两个坑（都是"改完看着不对，查了才知道"）**
1. **PC 覆盖样式被内联 `<style>` 压住**：`index.html` 的 `<head>` 里有一个内联 `<style>`，
   其中 `#settings-panel .settings-body > *{max-width:720px;margin:auto}` 与 pc.css 同优先级，
   而内联块在 `pc.css` **之后** → PC 的两栏设置栅格被压回一条 720 窄柱。
   **修法**：`pc.css` 的 `<link>` 挪到内联块**之后**（PC 覆盖必须最后加载），并提一级特异性双保险。
2. **不能跟"手风琴"对着干**：设置面板 JS 里一次只开一组（移动端刻意设计）。
   阶段 1 曾想"桌面全展开"，实现是逐个 `head.click()` —— 结果是**开一个关一个**，
   最后只剩最后一组开着。**修法**：顺应它 —— 折叠组排成两列瓦片、**展开的那组独占整行**；
   分组导航交给上下文列（点列表项 = 展开对应组并滚动）。

## 六、验收结果（2026-09-19）

- **桌面 1600×1000 / 1280×800**：三栏齐备、无横向滚动、无视图互相压盖、无整屏模态；
  首页变成角色包网格；聊天列限宽居中；公告是阅读列；设置是"瓦片 + 展开占整行"。
  截图：`.tmp_test/ui/pc/*.png`（采集脚本 `.tmp_test/pc_audit.py`）。
- **窄屏 390×844 / 768×1024**：外壳三件 `display:none`；首页在 390 满幅、在 768 仍是既有
  "居中 640 单栏"过渡档；聊天铺满可用高度；设置面板未被强制全展开（手风琴行为保留）。
  **14/14 断言通过**（`.tmp_test/mobile_regress.py`，截图 `.tmp_test/ui/mobile/*.png`）。
  ⚠️ 手机被用户拿走了，本轮**没有真机复验**，窄屏结论来自无头 Chrome 的结构不变量断言。


## 四、验收标准

1. 1600×1000 / 1280×800 下：三栏齐备、无横向滚动、无视图互相压盖、无"整屏模态"。
2. 390×844（手机）与 768×1024（平板）下：DOM 与样式**与重构前逐像素一致**（截图对比）。
3. 角色包在列 ② 可见且可一键切换；记忆进度、同步、热更、公告未读在 PC 上常驻可见。
4. `build_frontend_bundle.py` / `sync_frontends.py` 门禁通过；`tests/test_frontend_boot.py` 绿；
   全量测试与五门禁不回退。
