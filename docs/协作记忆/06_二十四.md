## 二十四、2026-09-25 用户校准重点：**APP 内下载行版才是关键**，热更只是添头

### 一、用户这一轮的两句话（决定了优先级）

> ①「因为热更新是需要变更版本号的（不然无法确定用户处于哪个版本）」
> ②「所谓热更新其实只是修复 bug 的添头而已，增加新功能是检查更新按钮提供的
>    **APP 内下载行版**才是关键」

**①的答案不是"热更改版本号"**（那会破坏"补丁针对哪个底座"的契约），而是"让用户能一句话
说清自己在跑哪份代码"。按用户拍板的口径落地为**`0.9.0_hot1`**：下划线后缀、`hot` 是热更新
的英文缩写、数字是第几个；没打补丁就只显示 `0.9.0`（不显示 `_hot0`，后缀的含义就是"打过补丁"）。
实现：`hotupdate.running_id()` 多返回 `display_version`，`GET /config` 的 `running` 带上它，
设置页「版本与更新」给一行 + **一键复制**（含 `patch_hash`，两个用户都报 hot1 时靠它区分），
诊断包顶层加 `running`。

**②的核查结果（用户说得对）**：查完发现"检查更新"这条主线**只做了一半**：

| 环节 | 之前状态 |
|------|---------|
| 服务器 `GET /update-manifest` + `server/update.json` | 已写，**线上根本没部署**（线上无该文件、线上 app.py 无该路由）⇒ 点「检查更新」只会"检查失败" |
| PC 自动更新（静默安装器） | 已有 |
| **安卓 APP 内安装** | ❌ **没有**：下完 85MB 让用户"去下载页再下一次" —— 一个包下两遍、一次都不装 |
| 线上 `firefly-setup.exe` | ❌ **还是 8-23 的 0.8.1** |

### 二、本轮做完的四件（A / D / E / C 准备）

**A. 安卓 APP 内下载并安装更新包**（`app/routes_update.py` + `MainActivity.kt` + `update.js`）
- 下载落**固定文件名**（`firefly-update.apk`，回执带 `name`）；壳只认这个名字、只从
  `cacheDir/update/` 取（**绝不接受页面传来的路径**），FileProvider 白名单加 `update/`、
  manifest 加 `REQUEST_INSTALL_PACKAGES`；Android 8+ 未授权时引导到「安装未知应用」页；
  带 `clipData`（部分安装器只从 ClipData 取读权限）；`startActivityForResult` 以便回执"用户取消"。
- 契约由 `tests/test_android_install.py`（**57 项**，含"三端名字必须逐字一致""白名单不许放开
  `path=.`""产物 bundle 必须已同步"）钉死 —— 这条链没法用单测跑通，源码级不变量是唯一防线。

**D. 运行版本一键复制**（见上）

**E. 明文 HTTP 的零成本对策（审计 §2.1 方案 1+2）**
- `app/static/js/session_crypto.js`：把 `Authorization`/`X-API-Key`/`X-API-Base` 装进信封
  `enc.v1.<b64u(RSA-OAEP(key))>.<b64u(iv)>.<b64u(HMAC流密文)>`；`api.js` 的 fetch 包装器改成 async。
- `app/session_crypto.py`：纯标准库解密（PKCS#8 解析 + **CRT + `pow(m,e,n)==c` 自检** + OAEP 去填充），
  `server/app.py` 新增 `_hdr()`（**加密优先、明文回落**，只解一次并缓存）。
- 灰度开关：`FIREFLY_ENC_ENABLED=1` 才启用，`FIREFLY_ENC_REQUIRED=1` 才拒绝明文（默认关，
  否则老客户端会被锁在门外）；失败限流 40 次/60 秒（防"拿垃圾信封逼服务器做模幂"）。
- `SESSION_DAYS` 30→7、`RENEW_BEFORE_DAYS` 7→2。
- **抓到的第一个 bug 就是它自己**：JS 侧 OAEP 漏了 EM 的前导 `0x00`（RFC 8017 §7.1.1），
  客户端"看着正常"、服务端全部拒收 —— 被 `tests/test_session_crypto.py` 的
  **跨语言往返**（Node 真加密 → Python 真解密）当场抓住。这条正是"文案级断言做不到"的活例子。
- 密钥：`tools/build_session_keys.py`（openssl 生成私钥 + 用私钥反算公钥写进 JS），
  私钥不进仓库；门禁并入 `check_hotupdate.py`（会话区：公钥一致 + 真往返 + 期限收紧）。

**C. 部署前提（只准备，不执行）**：`docs/部署前提清单-待上线.md` —— 13 项单文件挑传清单、
systemd 两个环境变量的灰度顺序、部署前硬门禁、部署后六项验证、四条"不要做"。

**两个自己踩的坑（都记在这，别再犯）**：
① Edit 把 `def _current_tag() -> str:` 与 docstring 挤到一行 ⇒ `IndentationError`，
   **6 个测试文件同时红**（server 侧全炸）—— 症状看起来像"改坏了服务器"，其实是语法。
   教训：改函数头这种"边界行"时，Edit 后**立刻**跑一次 `ast.parse`。
② 全量测试与 `build_frontend_bundle.py` **并行**跑 ⇒ `test_hotupdate.py` 的 zip 校验失败
   （zip 记录文件 mtime，工具正在重写 bundle.js）。**重写产物的工具不能与全量测试并行**。
