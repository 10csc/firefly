## 十四、2026-09-18 记忆机制二次设计（活跃窗口 30–100 + 原文存档 + 极简提醒）

用户否掉了上一轮的形态，给出新口径（**这是现在的唯一权威口径**）：

> 历史记录自动整理的限制可以较大放宽，避免频繁消耗用户 token。轮次或上下文余量快耗尽时
> 再在聊天页顶部显示状态/提醒。**活跃窗口需要随时保持**（除刚开始外应保持 30–100 轮，
> 用户点「休息」压缩后也仍加载近 30 轮完整对话进分析器和回复器）。**整理后的历史记录只保留
> 近 20–30 轮**（仍旧加载进分析器和回复器），多出来的都在**检索器阶段**加载。
> 休息时整理的部分记忆在菜单页设定文件副页下，那么**整理后的记忆原文也应该放在设定文件下**
> （保存完整的历史对话记录，允许用户调用 AI 压缩）。这部分是用户对话内容产生的记忆，
> 属于**用户的私有数据，放在角色包（不进入角色卡）**，使用时加入检索器。
> 核心流程为：**检索-分析-回复-调用/环境**。

**据此落地（改掉了上一轮的 P2 形态）**：

| 层 | 内容 | 谁读 | 更新 |
|----|------|------|------|
| L0 出厂记忆 `{pack}/memory/default.md` | 角色开局记忆 | 分析器 + 回复器 | 角色卡管理手改（**不动**） |
| L1 用户记忆 `{mode}/data/memory.md` | **压缩摘要** | 回复器（memory_head） | 整理时自动 / 用户点「AI 压缩」 |
| L2 历史对话存档 `{mode}/data/archive/YYYY-MM.md` | **完整对话原文**（按月分片、只增不改） | **只进检索器** | 整理时把滚出窗口的原文追加 |
| L3 活跃窗口（conversation.jsonl 里"自上次整理以来"的部分） | 对话原文 | 分析器 + 回复器 | 每轮；整理后**保留最近 30 轮** |
| L4 手账 | 第一人称记录 | 回复器 system | 整理时 |

- **阈值**：`memory_window_turns=100` 触发 / `memory_keep_turns=30` 保底 / `memory_warn_turns=80` 提醒。
  三项已接入 `/set-config`（含 0..1000 钳制；`window=0` = 关自动整理只留手动），**Settings 面板滑条仍缺（P2-10）**。
- **rest 语义改了**：不再"把未整理的**全部**压缩一遍"，而是切 `(last_integrated, 总轮数−keep]`——
  搬走的那段**原文进 L2**、同一段文本交给 LLM 压进 L1、游标推进到 `总轮数−keep`。
  所以"用户点了休息，分析器/回复器照样看得到最近 30 轮完整对话"。

  窗口 30→100 的**增长期**里历史块只往后追加 → 老部分是稳定前缀、每轮只有新一轮没命中。
  **一旦从窗口头部裁剪，窗口就从"增长"变"滑动"，历史块缓存永远命中不了**——等于把省的 token 又赔回去。

## 十五、2026-09-18 攻击哨兵「一次封禁弹 4-5 次」修复（用户报障）

**用户报障**：「服务器频繁提示我遭到攻击，是真机测试导致的吗？」
**结论：不是。** 真机测试全程只碰手机**本机**的 `127.0.0.1:8765` 与 App 自己的登录/同步 HTTPS，
一次都没碰 SSH；而告警的触发字段是 `fail2ban_bans`（**从公网进来的** SSH 密码尝试），方向也反。

**真实证据**（只读诊断，服务器未改任何东西）：
- `2026-09-18 22:02:03~22:02:05` fail2ban `Found 47.104.232.1` ×8 → `22:02:05 Ban 47.104.232.1`
- 日报里 `22:03/04/06/07` 四条，全是**同一个** IP；8-28 那次同样 `16:01-16:05` 连续 5 条同一 IP
- 其余计数全 0（主服务 429=0、网关 429=0、近 30 分钟 SSH 失败=0、服务全 active）

**根因（两头叠加，一次封禁被放大成 4-5 条弹窗）**：
1. `server/attack_watch.sh` 统计「**最近 5 分钟** fail2ban 日志里的 `Ban` 行数」且阈值 `>=1`
   → 一次封禁在 5 分钟窗口里**每分钟都命中** → cron 每分钟重写标记文件，`time` 每次都变；
2. `tools/attack_sentinel.py` 的去重键正是 `flag["time"]` → **去重完全失效**，
   每分钟当成新事件：弹窗 + 调模型 + 写日报各来一遍。

**修的四件**：
- **服务器侧**（`server/attack_watch.sh`，已单文件部署 + 备份，`bash -n` 通过）：
  改「新封禁」语义——状态文件 `/opt/firefly/.attack_seen` 记住上次已上报的 Ban 时间戳，
  只统计更新的；标记里的 `time` 用**封禁时间本身**（同一封禁重复执行也不变 → 上游去重有效）；
  标记保留 `GRACE=10` 分钟再撤（≥2× 哨兵 60s 轮询，保证一定被读到）；顺带把被封 IP 写进 `banned`。
- **本地侧**（`tools/attack_sentinel.py`）：去重键换**内容签名**（封禁 IP + 各计数，与 time 无关）
  并加 30 分钟冷却窗口（双保险）；**单次 SSH 封禁按噪声档**处理 → 只写日报、不弹窗、也不调模型
  （顺带省掉一次 API 调用）；模型输出为空/异常时走**本地兜底**，`need_user` 不再恒为 True。
- **回归测试**：新增 `tests/test_attack_sentinel.py`（22 项，纯本地不连服务器），
  把「同封禁不同时间戳必须同签名」「噪声档边界」「空分析兜底」钉死。
- **生效**：本地常驻哨兵已重启（旧 PID 22044 → 新 23268；`--once` 自检 1.4s 静默退出）。

**教训（值得记）**：告警的**去重键选了每次都变的字段**（时间戳）＝ 没有去重；
「检测到什么」与「报几次」是两件事，阈值宽不代表不会刷屏。

### 四、语音条贴紧自己的消息（同日追加，用户真机反馈）

用户：「**语音应该再贴紧点（现在语音的前端样式和文本分太远了，消息之间反而太近了）**」。

实测（写了个逐行内容块分割的量尺 `.tmp_test/measure_chat_spacing.py`）证实了这条感受，
而且**两者正好反了**：

| | 改前 | 改后 |
|---|---|---|
| 气泡 ↔ 自己的语音条 | **17.0px** | **4.3px** |
| 相邻消息之间 | **10.3px** | **16.3px** |

**根因**：可见间距 = `.msg-row` 的 `row-gap`（`clamp(8px,3vw,12px)`→10.8）**加上**
`.voice-bar` 自己的 `margin-top: 6px` = 16.8px —— 两处叠加，谁也没错，合起来就过了。
**修法**：`.msg-row.has-voice { row-gap: 0 }`（换行行的间距归零，完全交给条自己的 margin-top
`6px→4px` 决定）；`#messages` 的 gap `clamp(8px,2.8vw,12px)` → `clamp(12px,4.5vw,18px)`（→16.2px）。
→ 层级变成 16 vs 4，语音条明显属于它上面那条消息。

新增 H 组 4 条守卫（`test_chat_ui_geometry.py` 升到 28 项），核心是
**断言「气泡↔语音条」严格小于「消息间距」** —— 这条不变量比具体数值重要，
以后谁调间距都不会把层级关系调反。
