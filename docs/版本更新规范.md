# 版本更新规范（v1.0）

> 目标：保证任何用户（含 0.6 老版本、跳版本如 0.7→0.9）都能稳定升级，自动更新链路不因发布疏漏而失效。

## 一、版本号规则

### 格式
- 只用 `x.y.z` 纯数字点分（语义化版本）：`0.7.0`、`0.8.1`。
- **禁止后缀**（`-beta`、`-rc`、`-test`）：Gitee 无 prerelease 概念，带后缀的 release 会污染 `releases/latest`，导致正式用户被引导到预发布版。
- 预发布只发 GitHub（draft 或 prerelease 标记），Gitee 永不发。

### 单一权威源
`app/core/config.py` 的 `APP_VERSION` 是唯一权威。发版必须同步改 5 处：

| 位置 | 用途 |
|------|------|
| `app/core/config.py` → `APP_VERSION` | 后端检测/下载接口（权威） |
| `app/static/app.js` → `CURRENT_VERSION` | 前端降级对比 |
| `android/app/build.gradle.kts` → `versionName` | 安卓系统显示 |
| `android/app/build.gradle.kts` → `versionCode` | 安卓升级判定（映射规则见下） |
| `package/firefly.iss` → `AppVersion` | PC 安装器显示 |

> ⚠️ 2026-09-13 更新（阶段 2.1 拆分）：`APP_VERSION` 随职责从 `app/modules/app_config.py`
> 迁到 **`app/core/config.py`**；`app/modules/app_config.py` 现为兼容层（只 re-export），
> `tools/check_version.py` 的校验路径已同步改指 `app/core/config.py`。

> ⚠️ 2026-08-23 更新：`CURRENT_VERSION` 已从 `app/static/app.js` 移至 **`app/static/js/panels.js`**（0.9.0 起前端拆分为 js/ 模块）；实际发版同步清单以 `check_version.py` 的 7 项校验为准（含 `server/frontend/js/panels.js`、`server/version.json` 的 `tag`）。

**versionCode 规则（2026-08-14 起，兼容历史装机）**：versionCode 只要求**大于 `tools/check_version.py` 里的 `PREV_VERSION_CODE`**（历史 0.8.0 整合版曾用 800，0.7.2 系列已用到 804，不能再按 major×10000+minor×100+patch 回退）。本次 0.8.0 使用 805；发版后按需更新 `PREV_VERSION_CODE` 并在下一次发版时保证严格递增。

**发版前必须跑**：`python tools/check_version.py`（版本号不一致直接失败，禁止发布）。
> ⚠️ 2026-09-19 更新（0.9.0 发布，公告通道 + 首次真机验证）：
> ① 第 5 门禁 `check_hotupdate.py` 查的东西**变多了**，且**与本次有没有补丁无关**：
>    验签公钥两份副本逐字节一致（`HotUpdateKeys.kt` ↔ `app/hotupdate/pubkey.py`）、
>    Python 侧能解析出 RSA 参数、公告清单验签通过、**客户端校验器接受该清单**、
>    公告引用的图片齐备且 sha256 匹配。**公告没发过也会查**（缺发布区就是 FAIL）。
> ② 测试新增 `tests/test_frontend_boot.py`（Node + DOM 桩把**产物 bundle 真跑一遍**）——
>    见 `docs/错误总结.md` #15：bundle 是单作用域拼接，跨模块顶层调用会撞 TDZ 把整块打死，
>    只有产物级冒烟能抓到。发版前的"全量测试"里必须包含它。
> ③ **APK 必须 ≤ 100MB**：Gitee 单个附件上限 100MB（官方配额），而它是下载优先级第一的通道。
>    `libonnxruntime.so` 单 ABI 就 31–37MB ⇒ **发布包只带 `arm64-v8a`**
>    （`android/app/build.gradle.kts` 的 `defaultConfig.ndk`；x86_64 只在 debug 变体里）。
>    实测：双 ABI 132.6MB（**会被 Gitee 拒**）→ 单 ABI **81MB**。
> ④ Gitee release 用它：`python tools/publish_gitee_release.py --apk android/firefly.apk …`
>    （幂等：已存在的 release/资产不重复建；建完**必须**确认"id 最大的 tag 就是本 tag"，
>    因为整包兜底取的就是 id 最大者）。附件上传用 **`curl -F`** 实测可用
>    （早前"必须用 requests 库"的说法不再必要，`publish_hotupdate.py` 一直用的是 curl）。
> ⑤ 热更/公告的 Gitee 镜像根是 `.../releases/download/v{base}` ⇒ **base 版本必须存在对应 tag**，
>    否则镜像 404（本次为此建了 v0.9.0）。
>
> ⚠️ 2026-09-19 更新（热更新上线）：门禁扩为**五件**，缺一不可。新增
> `python tools/check_hotupdate.py`（若本次有补丁要发；无补丁时该步跳过并显式打印"本次无热更"）。
> 热更的规范、契约与可行性依据见 `docs/热更新规范.md`、`docs/热更新/02_实现契约.md`、
> `docs/热更新/01_可行性依据.md`。
>
> **发版时必须同时想清楚两件事**：
> ① 本次改动**能不能热更**（前端/Python 可以；Kotlin/权限/pip 依赖不行）；
> ② **底座内容变没变** —— 变了就必须升版本号，否则客户端上的旧补丁会与新整包混在一起
>    （见《热更新规范》§5.4 的反向铁律：内容进整包 ⇒ 作废补丁线 + 重建基线）。

> ⚠️ 2026-09-13 更新（R-03 收尾）：发版门禁已扩为**四件**，缺一不可：
> `python tools/check_version.py`、`python tools/sync_frontends.py --check`、
> `python tools/build_frontend_bundle.py --check`、`python tools/check_backend_sync.py --check`。
> 前三者管版本号与三端前端副本，第四者管安卓内嵌后端副本（`android/.../python/backend/`）——
> 它此前不在任何门禁里，漂移会导致"看仓库代码做的判断"系统性偏差。
> `check_version.py` 现对**文件缺失**记 SKIP（干净 clone 可跑），文件在而版本不一致才 FAIL。

## 二、发行版资产命名（固定不变）

| 平台 | 资产名（必须固定） | 检测匹配 |
|------|------------------|---------|
| Windows | `firefly-setup.exe` | 按 `.exe` 扩展名 |
| Android | `firefly.apk` | 按 `.apk` 扩展名 |

- 资产名**不携带版本号**（不要 `firefly-0.8.1-setup.exe`）——检测逻辑按扩展名匹配，跳版本天然兼容。
- 每个 release **恰好一个 exe + 一个 apk**。多个会匹配到错误资产。

## 三、发布流程（每次发版照此执行）

1. **改版本**：4 处同步（`APP_VERSION` / `CURRENT_VERSION` / `versionName` / `AppVersion`）
   > ⚠️ 2026-08-23 更新：实际是 **6 处**按 `tools/check_version.py` 校验（该脚本检查 7 项：`app_config.APP_VERSION` / `app/static/js/panels.js` 的 `CURRENT_VERSION`（**不是 app.js**，0.9.0 起拆分为 js/ 模块）/ `android/app/build.gradle.kts` 的 `versionName`+`versionCode` / `package/firefly.iss` 的 `AppVersion` / `server/frontend/js/panels.js` / `server/version.json` 的 `tag`）。发版以 `check_version.py` 输出为准。
2. **校验**：四门禁全绿（`check_version.py` / `sync_frontends.py --check` / `build_frontend_bundle.py --check` / `check_backend_sync.py --check`）
3. **测试**：全量测试通过（`tests/` 全部；当前 36 个 `test_*.py` 脚本，以目录实际文件数为准）
4. **打包**：
   - PC：`python -m PyInstaller firefly.spec --noconfirm` → 确认 `dist/firefly/user_data` 被清空（`Remove-Item -Recurse -Force dist/firefly/user_data`）→ `ISCC.exe package/firefly.iss` 产出 `firefly-setup.exe`
   - 安卓：`gradlew.bat assembleRelease`（syncBackend 自动同步）→ 复制 `app-release.apk` → `android/firefly.apk`
5. **冒烟**：分别启动 PC/安卓，`GET /config` 正常、`POST /check-update` 返回新版本号
6. **打 tag 并 push**：`git tag vX.Y.Z` → push GitHub（origin）+ Gitee（gitee）两个远程
7. **GitHub Release**：`gh release create vX.Y.Z` 上传两个资产（正式版，非 draft）
8. **Gitee Release**：API 或网页创建（tag 已存在则直接传资产），上传 `firefly-setup.exe` + `firefly.apk`
   > ⚠️ 2026-08-23 更新（实测）：
   > - Gitee API **创建 release**：`POST /api/v5/repos/{owner}/{repo}/releases`，body 需含 `target_commitish`（缺则 400）；tag 已存在则幂等复用（list 按 `id` 最大取最新）。
   > - **上传资产**：`POST /api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files`——**必须用 requests 库** `files={"file": (name, f, "application/octet-stream")}`；**urllib 手拼 multipart 会 404**（本人在 0.8.1 实测踩坑）。Gitee 无此 API 的可靠替代，网页手动上传亦可。
   > - **Gitee 没有 `/releases/latest` 端点**（404）：`download_server.py` 的"最新 tag"逻辑必须用**列表 API** `releases?per_page=10` 按 `id` 最大取（0.8.1 已修，见部署记录）。
9. **验证**：`POST /check-update` 返回 `tag: vX.Y.Z`；`GET releases/latest` 两平台均可见
   > ⚠️ 2026-08-23 更新：**Gitee 无 `/releases/latest` 端点**（仅 GitHub 有）。Gitee 侧验证 = GET release 列表 API，确认 `tag_name` == vX.Y.Z 且含两个资产：`firefly-setup.exe` + `firefly.apk`；GitHub 侧 `GET /releases/latest` 正常。
10. **更新文档**：README 版本号

## 四、跳版本更新保证

### 检测
- 版本对比是**数值逐段比较**（`compareVersions`），0.7.0 → 0.9.0 直接判定更新，无需中间版本。
- 前端落后多个版本（0.7.0 用户直接收到 0.9.0 提示）→ 正常，直接下载最新。

### 数据迁移（关键）
- 每个版本的迁移函数必须**幂等 + 按文件状态判断**（不是按版本号判断）：
  - 例：`_migrate_legacy_layout()` 用 `move` + `目标不存在才移`，重复执行无副作用。
- **新增迁移规范**：跳版本时旧数据只经过"它自己的迁移链"——每个迁移独立检查"目标文件是否存在"，不存在才执行。这样 0.7.0 用户升 0.9.0 时，0.8.0 的迁移也会被 0.9.0 的代码执行（因为检查的是文件状态不是版本号）。
- 迁移必须**先于默认文件拷贝**执行（防默认文件占位挡住用户数据）。
- 迁移只 move 不删除（旧位置保留备份语义，防误删）。

### 安装覆盖
- PC：安装器固定 `AppId` + 固定目录 + `CloseApplications=yes`（自动关运行中的旧版，解决文件锁）→ 覆盖安装，`user_data` 被 iss `Excludes` 排除 → 数据保留。
- 安卓：`install -r` 覆盖安装，系统保留 `files/` 数据。

## 五、自动更新链路（用户视角）

```
用户点"检查更新"
  → POST /check-update（本地后端）
      → GitHub releases/latest（失败降级 Gitee）
      → 对比 APP_VERSION（后端权威）→ 返回 {tag, current, html_url}
  → 前端 compareVersions(tag, current) > 0？
      → 否：显示"已是最新版本 x.y.z ✓"
      → 是：显示 [自动更新] [发行说明]
  → 用户点"自动更新"
      → POST /update-download {kind}
          → 资产 URL：Gitee 优先（国内快），GitHub 降级
          → 下载到临时目录
      → PC：静默启动 setup.exe /VERYSILENT → 2s 后自动关闭本服务 → 安装器接管
            （CloseApplications 关旧 exe → 覆盖安装 → user_data 保留 → 用户手动重启新版）
      → 安卓：提示去发行版页面下载（系统限制需手动确认安装）
```

### 降级保障
- 后端接口不可用 → 前端直连双源检测（`UPDATE_SOURCES`）
- GitHub 不可达 → Gitee；Gitee 也不可达 → "检查失败（网络或仓库不可达）"
- 下载失败 → 错误信息展示，不自动重试（用户可重试）
