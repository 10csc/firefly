# 热更新规范（v2.0-draft）

> **与《版本更新规范》的关系**：`docs/版本更新规范.md` 管**整包**（APK/exe）的版本号与发布；
> 本文管**补丁**（无需重装的修复）。两条链路**并行且互不替代**，冲突时以整包为准
> （整包包含全部修复，装上整包即作废所有补丁）。
>
> **本文的目的是纪律，不是功能**。热更本质是"下载并执行代码"，没有纪律就是给自己开一个后门。
>
> **v2（2026-09-21）**：`py/` 层已实现 —— 前端与 Python 两层同属一个 serial，
> 但生效方式不同（web 刷新页面、py 重启进程）。**真机验证未做，不许发布**（见契约 §十一）。

## 〇、可行性依据

**已实测确认（2026-09-18，勿再重新论证）**：前端与 Python 层可热更、Kotlin/native 不可热更、
Chaquopy 的 Python 解释器同进程只能启动一次。完整实测数据见 **[热更新/01_可行性依据.md](热更新/01_可行性依据.md)**。

**实现字段与 URL 形态以 [热更新/02_实现契约.md](热更新/02_实现契约.md) 为准**（本文只管纪律）。

## 一、适用范围（铁律，不许越界）

| 层 | 热更 | 说明 |
|----|------|------|
| 前端 `app/static/**`（html/css/js/资产指纹） | ✅ | 纯数据 |
| Python `app/**/*.py`（业务逻辑，不含数据） | ✅ | 走覆盖层 + `sys.path` |
| 角色包数据 `app/assets/character/**`、`database/**` | ⚠️ **禁止** | 属用户数据域，走原有资源下发链路，不混进热更 |
| Kotlin/native、`AndroidManifest`、权限、`applicationId` | ❌ | 只能整包 |
| Python 版本、`pip` 依赖、Chaquopy 配置 | ❌ | 只能整包 |
| **删除文件** | ❌ **禁止** | 删除不可逆；需要删就发整包。补丁只允许"新增/覆盖" |
| **发新功能** | ❌ **禁止** | 热更只用于**修复**。功能走整包，保证"APK 版本 ↔ 功能集合"一一对应 |

## 二、版本标识体系

**三元组**（客户端必须能完整上报，排障全靠它）：

```
base_version   = APP_VERSION + versionCode       例：0.8.1 / 806
hot_serial     = 该 base 下的补丁序号（从 1 单调递增）  例：3
patch_hash     = manifest.json 的 sha256 前 16 位      例：a1b2c3d4e5f60718
```

**展示口径（用户 2026-09-25 拍板）**：`0.9.0_hot1` —— 下划线后缀，`hot` 是热更新的英文缩写、
数字是第几个热更版本。没打补丁时**只显示 `0.9.0`**（不显示 `_hot0`：后缀的含义就是"打过补丁"）。

- **`APP_VERSION` / `versionCode` 永不被热更改变**。热更只推 `hot_serial`。
- **serial 是 per-base 的**：换 base（装新整包）→ 覆盖层**立即清空**、serial 归零。
- **用户可见 + 可上报**：设置页显示 `0.9.0` / `0.9.0_hot1` 并给**一键复制**，
  复制出来的是 `0.9.0_hot1 · <patch_hash>`（两个用户都报 hot1 时靠指纹区分）；
  `GET /config` 的 `running` 与诊断包 `summary.json` 的顶层 `running` 都带同一份三元组。
  > 用户 2026-09-25 的原话："热更新是需要变更版本号的（不然无法确定用户处于哪个版本）"。
  > 这里的答案是：**不改版本号，但让用户能一句话说清自己在跑哪份代码** ——
  > 版本号一旦被热更改写，"补丁针对哪个底座"的契约就失效了（见 §5.4 反向铁律）。
- 已知未做：每个 API 请求带 `X-Firefly-Running` 头（原设计有、当前未实现）。

## 三、补丁包格式（纪律）

字段级定义见 **[实现契约 §三](热更新/02_实现契约.md)**，这里只定不许动的四条：

- **累积式**：serial N 的包 = `base → serial N` 的完整差异。客户端不管当前是 0 还是 3，
  下最新的一个即可到位（**不做"必须按序应用"的状态机**——那是用户中断时最先坏掉的地方）。
- **格式固定 zip**：Python 侧 `zipfile`、Kotlin 侧 `java.util.zip`，两端标准库，**零新增依赖**。
- **只增/只改**：清单里不允许出现"删除"语义。
- **单包管两层**：`web/` 与 `py/` 同属一个 serial，避免"前端已更、Python 没更"的中间态。

## 四、签名与信任根

- **算法**：RSA-2048 / SHA-256（或 ECDSA P-256）。**验签在 Kotlin 壳做**（`java.security`），
  公钥**硬编码在 APK**（`BuildConfig` 或 `res/raw`）。**Python 侧不重复实现密码学**——它只信任"壳已验过"。
- **签名对象**：`manifest.json` 的**规范化字节**（UTF-8、键序固定、无尾随空白）→ `manifest.sig`。
  ⚠️ 只签补丁内容不签清单 = 没签（可改文件同时改哈希）。
- **私钥**：只在发布机、离线保存、**绝不进仓库/服务器**。轮换办法：先用旧钥发一版带新公钥的**整包**，再用新钥签补丁。
- **应用必须原子**：下载到临时目录 → 验签 → **逐文件校验 sha256** → 全部通过才 `rename` 成正式覆盖层。
  防 TUF 的 **mix-and-match**（新旧文件拼一起）。
- **防回滚**：客户端持久化 `(base_version, applied_serial)`；同 base 下**拒绝 serial ≤ applied**。
  例外只有一种：服务端签名的**显式回滚指令**（本身也是一次发布）。

## 五、客户端行为（下载 → 验签 → 应用 → 生效）

### 5.1 时机
- 每天一次 + 冷启动后 30 秒 + 用户手动点「检查更新」时，拉 `latest.json`（**必须 `Cache-Control: no-store`**）。
- 用户开关关闭时：**不下载、不应用**；但**吊销指令（`min_safe_serial`/`revoked_serials`）无条件生效**（安全例外）。

### 5.2 生效（★ 用户已定：下载后立即生效，但**只在空闲时**）

| 补丁内容 | 生效方式 | 用户感知 |
|---------|---------|---------|
| 只含 `web/` | 覆盖层替换 → 空闲时 WebView `location.reload()` | 几乎无感（草稿会保留，见 5.2.2） |
| 含 `py/` | 覆盖层替换 → 空闲时**自动重启 App 进程**（AlarmManager + PendingIntent 自拉起，无新依赖） | 约 1 秒闪一下，回到原页面 |

> **为什么含 `py/` 必须重启**：Chaquopy 的 `Python.start()` 一个进程只能调一次、且无 `restart()`；
> 即便能重启解释器，`importlib.reload` 也救不了模块级单例（`PRESETS`/`SITES`/缓存/锁）与
> HTTP handler 里已绑定的引用。重启进程是唯一可靠路径（CodePush/EAS 的 immediate 安装同理）。

#### 5.2.1 「空闲」的判定（必须逐条实现，不许各自理解）

**只要下列任一为真，就不是空闲 → 推迟，绝不打断：**

| # | 占用状态 | 判据来源 |
|---|---------|---------|
| 1 | 输入框有未发送内容 / 正在打字 | 前端上报（含 hint 续期中的合并窗口） |
| 2 | 正在播放语音 | 播放器状态 |
| 3 | 回复流水线在跑（分析/回复/组织/合成中） | 后端活动标志 |
| 4 | 模型下载中（语音插件） | `plugin._DL["running"]` |
| 5 | 已有一个补丁在应用/待重启 | 覆盖层的 `pending` 标记 |

**流程**：补丁就绪 → 每 5 秒探测一次 → 连续 **3 秒**无活动即视为空闲 → 执行生效。
**长时间不空闲** → **推迟到下次冷启动**（新进程本来就会带上覆盖层，无需再重启一次）。
**冷启动时补丁已在覆盖层 ⇒ 直接生效，不触发任何重启**。

> **补一条 v2 实测口径（两层同时变更时）**：若一个补丁同时含 `web/` 与 `py/`，
> **只走 py 那条路（重启进程）**，不要去 reload 页面 —— 重启之后新前端自然一起生效，
> 先 reload 一次纯属白闪一下。客户端已把 `reload_pending` / `restart_pending` 分开报（契约 §五）。

> **再补一条（v2 生效性判定）**：`py/` 层只对**尚未 import** 的模块生效。
> 若补丁改的是本进程早已加载的模块，重启也换不掉 —— 客户端会如实上报
> `restart_pending=false` + `restart_note`，**不许**为了"看起来生效了"而反复重启用户。
> 判定细节见契约 §7.1。

#### 5.2.2 前端 reload 不许吞掉用户草稿

`location.reload()` 会清空输入框。生效前必须把「输入框内容 + 滚动位置」暂存到 `sessionStorage`，
reload 后恢复。**这是硬要求**：一个会吃掉用户正在打的字的"静默修复"，比不修复更让人恼火。

### 5.3 `sys.path` 注入时序（实测结论，写错就静默失效）
```
Python.start(AndroidPlatform)        ← Chaquopy 在这里整体重写 sys.path
  → 我们 insert(0, {FIREFLY_DATA_DIR}/hotupdate/py)   ← 必须在这之后
  → 再 import 后端入口
```
**只对"当时尚未 import 的模块"生效** ⇒ 注入要尽可能早。

### 5.4 覆盖层位置与整包升级的清理
- 位置：`{FIREFLY_DATA_DIR}/hotupdate/`（与 `user_data` 平级：卸载清空、升级保留、不进备份/同步）。
- **每次启动检查 `APP_VERSION`/`versionCode`**：与上次记录不同（＝装了新整包）→ **整个 `hotupdate/` 清空**。
  ⚠️ 安卓覆盖安装**不会**清 app 私有目录，不主动清就会出现"旧补丁盖住新 APK 代码"的灾难。

**⚠️ 反向的同一条铁律（2026-09-19 演练时踩到）**：**把某个补丁的内容又打进了整包之后，
必须作废该补丁线并重建基线**（删发布区、`build_hotupdate.py --init`、serial 归零）。

为什么：`base_version` 是"底座内容"的标识符。一旦底座内容变了而版本号没变，基线就与真机
实际内容不一致 —— 后续补丁会基于**错误的底座**生成，症状是"补丁应用成功、但有些文件还是旧的"。
**根治法只有一条：底座内容变了就升版本号**；万不得已（同版本重出包）必须重建基线 + 作废旧补丁线。

### 5.5 安全模式（坏补丁不能把用户钉死）
1. 应用补丁时写 `pending` 标记（含 serial）。
2. **启动成功判据**：内嵌后端 `/config` 返回 200 **且**前端上报一次 `boot_ok`（首帧渲染完成）。
3. 判据满足 → 清除 `pending`；不满足 → 计数 +1。
4. **连续 2 次**带着同一 `pending` 启动失败 → **禁用全部补丁、回落 base**、上报一次。
5. 回落是静默的（用户只看到"变回旧版"），但必须在「关于」页留痕："上次修复已回退（原因）"。

## 六、服务端与发布

- **托管**：服务器 `/opt/firefly/hotupdate/`（主）+ Gitee/GitHub release 附件（兜底镜像）。
  整包仍走 release（不变）。
- **入口**：`GET /hotupdate/latest.json`（`no-store`）→ 含当前 base 的最新 `serial` + 包 URL + sha256 + 签名。
  鉴权：公开只读（匿名可下，与模型分发同策略）；**不得**要求登录（否则离线用户永远拿不到修复）。
- **发布流程（只有维护者用发布机脚本执行）**：
  1. 在 `base` 对应的 commit 上改代码 → 跑**五门禁** + 全量测试
  2. `tools/build_hotupdate.py` → 产出累积补丁 + 签名 + `CHANGELOG` 条目
  3. `git tag hot-<base>-<serial>`（**代码本体留 git，可精确 diff**）
  4. 传服务器 `hotupdate/<base>/` + 更新 `latest.json`（**已发布文件永不覆盖**）
  5. **灰度**：先 `rollout_percent=10`，24h 无异常 → 100
  6. 归档：补丁 zip 也附到 GitHub/Gitee release（公开可审计）
- **kill switch 是 v1 必做项**：出问题 5 分钟内把 `revoked_serials` 加上 → 所有客户端下次拉清单即自动回退。
- **禁止**：修改已发布的补丁包；用热更发新功能；跳过门禁"先发再补"。

## 七、兼容性矩阵

| 客户端 base | 服务端最新补丁 base | 行为 |
|------------|------------------|------|
| 0.8.1 (806) | 0.8.1 | 正常热更 |
| 0.8.1 (806) | 0.8.2 | **拒绝热更**，提示"需下载新版安装包" |
| 0.8.0 (805) | 0.8.1 | 同上（老 base 不再产出补丁，强制整包收敛版本） |
| 任意 | 有更高 `min_safe_serial` | 按 kill switch 处理 |

**策略**：只为**当前最新整包**产出补丁；新整包一发布，旧 base 的补丁线即冻结。

## 八、可追溯性（用户报 bug 时怎么精确定位）

1. 用户念「关于」页的三元组 → 你得到 `(base, serial, patch_hash)`。
2. 服务器 `hotupdate/<base>/` 保留了**不可变**的 1..serial 全部补丁 + `CHANGELOG`。
3. `git tag hot-<base>-<serial>` → 精确 checkout / diff。
4. **运行版 = base commit + 依次应用补丁 1..N**，逐字节可重建（**不需要在仓库里放"运行版副本"**）。
5. `CHANGELOG.md` 每条必填：`serial / 日期 / 改了哪些文件 / 为什么 / git tag / 谁发的`。

> **为什么不在仓库开"运行版文件夹"**：现在已有三份前端副本（`app/static`、`android/.../assets`、
> `server/frontend`），四门禁里两条就是防它们漂移。再加一份"按定义就会漂移"的副本 = 自找麻烦。
> 运行版要的是**可重建的坐标**，不是第四份副本。

## 九、测试与门禁

**四门禁 → 五门禁**，新增第 5 条 `tools/check_hotupdate.py --check`，对每个待发布补丁校验：

- [ ] manifest 签名可验证、字段完整
- [ ] 包内文件与 `files` 清单**完全一致**（不多不少）
- [ ] 每个文件 sha256 匹配；路径**不越界**（禁止 `..`、绝对路径）
- [ ] **无删除语义**；`base_version` == 产出时的 base
- [ ] serial 单调递增且**累积正确**（N 的包必须包含 1..N-1 的全部文件差异）
- [ ] 不引入新依赖、不改 `AndroidManifest`/Kotlin/权限
- [ ] （v2）**`layer` 字段与 `files` 前缀互相印证**；`py/` 里只有 `.py`，
      且不含 `hotupdate/`（补丁链路的加载器只能走整包）
- [ ] （v2）**py 层注入点仍在**：`app/core/paths.py::STARTUP_PATH_INSERTS` 登记的每个文件
      确实在启动早期挂了 `overlay_py_dir()`。这条防的是"补丁装上了、重启后代码没换、零报错"

**补丁级回归**：`tools/apply_hotupdate.py --patch <zip> --base <干净 checkout 的 app/> --out <临时目录>`
→ 应用后跑**全量测试 + 冒烟**，绿了才允许签名发布。**不需要新代码树**（临时目录即可）。
（v2 起该工具同时支持 `web/` 与 `py/`，并对打进补丁的 py 文件做语法自检。）

**端到端**：`tools/e2e_hotupdate.py`（真私钥签名 + 真 HTTP + 真覆盖层）。
其中 **K 组专测 py 层**：产出 → 应用 → `restart_pending` → 覆盖层插 `sys.path` 首位后
**真的 import 到补丁内容**。这一段是"py 层热更到底成不成"的唯一自动化判据。
