## 2. 验证发现：「先查后扣」是刻意设计，不是 bug

`server/server_app.py:77-83` 的 docstring 原文：「放行即记账（先查后扣：调用失败套餐也计次，**与计费口径一致**）」。

即：失败照扣额度是运营者有意为之（与上游套餐按调用计费的口径对齐）。方案 A3/B3 的「成功后扣费」改动会改变计费口径——上游波动期间服务器替用户承担失败调用的成本。

**需用户决策**（三选一）：
1. 维持先查后扣（现状）——用户体验差但成本零风险；
2. 改成功后扣费（方案原提案）——体验好，上游波动期运营者净亏失败调用费；
3. 折中：**失败调用记账但不占用户额度，单独记 `proxy_usage_failed` 表**——用户无感，运营者保留成本观测与防刷数据。推荐 3。

在决策前，A3/B3 对应条目标记为「待定」。

## 3. 规划补充

### 3.1 前端心跳合并范围修正（补充 05 B 档）

05 文档只提了合并 `/chat-stage` 与 `/proactive-status` 两路轮询。全量核验确认还有第三路：`relay.js:139` 的 1s relay 轮询（`main.js:33` 确认仅服务器模式激活）。`/events` 心跳应五合一：`{stage, proactive, sync, upstream, relay}`。relay 是延迟敏感路径（每跳省 1s），合并时保留其 1s 档，其余退到闲时 10s（proactive）/ 按需（stage）。

### 3.2 B0 客户端 sync.db 的 Chaquopy 可行性标注

方案 B0 客户端实体镜像用 Python 标准库 `sqlite3`（底层 `_sqlite3` C 扩展）。全量核验确认：**本项目安卓端目前无任何 sqlite3 使用先例**（`android/app/src/main/python` 与 `app/` 全 grep 零命中；`server/db.py` 只在 Linux 跑过）。`sqlite3` 属标准库，Chaquopy 通常随解释器内置，但未实测。

行动项（B 第二期开工第一步）：在安卓上跑 `import sqlite3; sqlite3.connect(':memory:')` 冒烟验证；若不可用，降级方案 = 实体镜像用 JSONL 文件 + 内存索引（数据量小，性能可接受）。此不确定性不影响 B0 的实体模型设计本身。

### 3.3 模型锁差异是双端产品决策（补充 01 §3.4）

全量核验确认服务器版模型锁有三道（`app_config.py:275-278`、`:347-350` 配置层 + `api_client.py:192` 客户端层），锁 `mimo-v2.5`；本地版用 `deepseek-v4-flash/pro`（`app_config.py:130-132`）。即双端**人设表现可能不一致**（不同模型跑同一套 prompt）。三套方案均未触及此点，但它影响「本地↔服务器同步后体验一致」的用户预期。

**需用户决策**：双端模型策略是否对齐（对齐到同一模型族 / 接受差异 / 按模式声明差异）。建议在 B 第三期（网关层）落地时一并处理——网关层正是做模型路由与别名的正确位置（逻辑模型名 → 各端实际模型）。
