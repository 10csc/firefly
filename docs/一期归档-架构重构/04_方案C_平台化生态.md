# 04 · 方案 C：平台化生态

> 定位：长期形态参考。**现阶段不推荐直接上**——运维组件翻倍、引入外部计费/停服风险，与小团队维护能力不匹配。
> 诚实说明：C 的价值是「B 落地后，当用户量/角色生态真的长出来时的演进方向」，不是当前开工项。

## C1. 同步：PowerSync（或 ElectricSQL 的新形态）

- PowerSync：后端 Postgres → 设备 SQLite 的成熟同步引擎，冲突规则、断线重连、部分复制全内建；客户端 SDK Apache 2.0，服务端可自托管，托管版 $49/月起（06 主题 1，powersync.com/pricing）。
- 代价：数据模型绑定其 schema、服务器多跑一个 sync 服务、安卓端绕开 Chaquopy 用其 Kotlin SDK——**打破「三端同一套 Python」的本项目最大资产**（01 §1）。
- 排除项（时效核查，06 主题 1）：Realm Device Sync 已于 2025-09-30 EOL 关服；ElectricSQL 旧写路径产品已搁置；one-api 停维护有未修 CVE。C 方案不选它们。

## C2. 数据层：Postgres + 对象存储

- 账号/实体/审计进 Postgres（JSONB 存 payload，保留 B0 的实体模型——C 是 B0 的换底而非另起）。
- 表情包/图片走本地存储 + 哈希寻址，**用户媒体不进对象存储**（媒体本地策略，01 §4）；对象存储只服务运营基础包与未来官方图包。实体表只存文字描述与引用。
- 触发条件（何时从 B 升 C）：单服务器 SQLite WAL 扛不住（实测并发 >~50 活跃）、或多服务器部署需求出现。

## C3. LLM 网关：LiteLLM Proxy 或 new-api

- LiteLLM Proxy：重试/冷却/fallback/多 key/预算全是配置项，自带 health check 与 spend tracking（06 主题 2，docs.litellm.ai/docs/routing）。
- 要 Web 管理面板 + 按用户额度管理 → new-api（one-api 的活跃分支，渠道内多 key 轮询、连续失败自动禁用）。
- 与 B3 的关系：B3 自研网关的接口设计成 LiteLLM 兼容（OpenAI 格式 + 按部署路由），升 C 时是「换实现」不是「改协议」。

## C4. 角色生态：chara_card_v2 + 世界书引擎

- 角色卡直接兼容 `chara_card_v2` 规范（`spec/data` 包裹、`alternate_greetings` 多开场白、`character_book` 内嵌世界书、`extensions` 命名空间扩展位）——可无缝导入 Chub.ai 等社区卡片，白捡内容生态（06 主题 3）。
- 世界书引擎照搬 SillyTavern World Info 核心三元组：`关键词(支持正则) → 内容 → 注入位置/深度` + `constant / scan_depth / token_budget / insertion_order` 四字段；中文默认关闭整词匹配（官方明确警告）。递归扫描/概率触发/互斥分组作为二期。
- 与本项目现状的映射：现有「知识库整体注入」（`llm_retriever.py:49-52`）演进为「常驻条目」；LLM 子代理检索保留为「向量相似度触发」档的等价物。注意红线：注入机制只能从 organizer 工具协议进，不动 ①②③ 阶段（01 §4）。

## C5. 前端：多角色 + 桌面三栏

- 多角色 → 首页轮播变「角色列表/发现页」；聊天页加会话列表侧栏（桌面三栏：会话列表/消息流/角色详情抽屉）。
- 剧情分支：消息级 swipe 重生成 + 从某条消息分叉新会话（UI 成本最低，天然适配 append-only 实体模型）。

## C 的进入条件（写死，防过早过度设计——CLAUDE.md 已犯错误 #5）

满足任一才启动评估：
1. 日活 > 100 或单服务器实测撑不住；
2. 出现「用户想要第二个角色」的真实需求积压 > 10 条；
3. 托管成本 > LiteLLM/PowerSync 托管费 × 3。
