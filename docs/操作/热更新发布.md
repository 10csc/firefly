## 发布前检查

1. 确认用户已明确授权本次热更新发布。
2. 确认本次修改是当前底座上的 bugfix，且没有改变底座内容。
3. 确认 `hotupdate_declare.json` 声明本次 serial，而不是依赖目录存在性猜测。
4. 确认 key 只在发布机，公钥的两份副本一致。

## 产出候选

```powershell
Set-Location F:\CodeFile\firefly
$env:PYTHONUTF8 = "1"
python tools\build_hotupdate.py --note "<修复内容>"
python tools\check_hotupdate.py --all --declare hotupdate_declare.json
python -B tests\test_hot5_release_pipeline.py
```

检查至少覆盖：

- `latest`、manifest、RSA 签名、zip SHA-256 和逐文件 SHA-256。
- 累积包包含此前 serial 的差异，serial 单调且已发布文件不被覆盖。
- `web/` 与 `py/` 的路径合法，没有删除语义和路径穿越。
- Python 顶层包完整；不能只带新子模块而漏掉祖先 `__init__.py` 或兄弟模块。
- 灰度晋级只增加比例，文件集合和哈希不变。
- 干净底座应用后，新进程真的导入到覆盖层代码。

## 发布

以下命令是 S2 外部发布；必须获得用户明确授权，失败时停止后续步骤。
获得授权后，使用发布工具推送主源与 Gitee 镜像：

```powershell
python tools\publish_hotupdate.py --serial <N>
python tools\publish_hotupdate.py --verify-only --serial <N>
```

发布器只处理 HTTP 资产，不代替 git tag 或手工部署。必须确认：

1. 主源与 Gitee 都能回读 `latest`，返回同一个 base/serial。
2. `patch-N.json`、`patch-N.zip` 与本地字节完全一致。
3. Gitee 不新建会改变“最新整包 tag”判定的 Release；补丁附属于已有底座 Release。
4. 服务端日志出现真实客户端拉取，而不是只有发布机自检。

## 真机验收

发布成功不等于设备已生效。真机必须验证：

1. 冷启动后版本显示 `base_hotN`，`pending_serial=0`。
2. 含 Python 层时 PID 必须改变；`logcat` 必须出现独立交接进程按旧 PID 销毁进程的证据，
   且页面不能出现 Android 14 的 `BAL_BLOCK`。
3. `/auth/state`、`/sync/manifest`、图片和公告链路正常。
4. 开启灰度时，未命中的设备保持旧 serial 且不被强制应用。
5. 回滚或安全模式不会删除用户数据。

## 失败与回滚

- 签名、哈希、路径、Python 包闭包或干净底座导入任一失败：整包拒绝，不发布。
- 已发布后发现坏包：先停止继续扩大灰度，再发布带 `revoked_serials`/`min_safe_serial` 的新清单。
- 回退只回到 base 覆盖层不能解决的问题，发新整包；不要覆盖已发布补丁来“修复历史”。
- 任何发布失败都保留退出码、清单哈希、源回读结果和真机状态，写入部署或事故记录。

## 不做的事

- 不通过热更新发布新功能。
- 不修改 `app/hotupdate/` 自身；它属于补丁加载器，只能随整包升级。
- 不删除文件；需要删文件就发整包。
- 不用本地 `latest` 文件代替线上回读。
