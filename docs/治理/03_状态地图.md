# Firefly 状态地图（执行稿 v2）

> 目的：规定“谁可以写什么、谁读什么、何时更新”，避免把本地候选、已发布事实、线上实际和证据混成一个状态。
> 标记：【现行】当前文件/代码已存在；【规划】尚未实现，不得当成已完成；【外部】只能实际回读。

## 1. 四个不可混用的层次

1. **源**：代码、声明、用户批准的变更输入。
2. **生成物/投影**：bundle、version.json、发布清单、部署 manifest，可由源再生，不得手改成第二真相。
3. **外部实际状态**：主源/镜像附件、生产文件与进程、设备 applied serial，只能回读证明。
4. **证据**：命令输出、哈希、测试日志、真机记录；证据支持结论，但不自动变成外部实际状态。

## 2. 权威文件与读写权限

| 状态 | 权威载体 | 写入者 / 更新触发 | 读取者 | 禁止与备注 |
|---|---|---|---|---|
| 开发/候选版本【现行】 | `app/core/config.py::APP_VERSION` 及登记的本地投影 | DeepSeek；仅用户批准 bump 时 | 本地后端、构建、check_version、热更 base | 不表示最新已发布，不证明 APK/EXE 身份 |
| 最新已发布整包【现行】 | `server/update.json` | 发布执行者；批准发布后更新并签名 | `server/update_manifest.py`、server/app、客户端、check_version | 是最新发布语义，不是线上当前回读；修改后必须验签 |
| 老客户端兼容投影【现行】 | `server/version.json` | 由 update.json 生成；发布时 | 老客户端、fallback、check_version | 禁止手写第二套版本；update_manifest 可用时运行路由动态投影 |
| 已发布产物身份【现行】 | `release_manifests/release_manifest_<ver>.json` | release_manifest 工具；每版本首次登记 | check_version、下载验收、发布审核 | 发布后同版本不可改字节；旧 `_harden` 只作历史证据 |
| 当前热更意图【现行】 | `hotupdate_declare.json` 的 version/hotupdate 字段 | DeepSeek；本次补丁意图变化且获批准 | check_hotupdate、publish、审核者 | note 仅注释，不得与机器字段形成另一结论；冲突先停 |
| 热更候选包【现行】 | `hotupdate_dist/prod/<base>/` | build_hotupdate；候选构建时 | check_hotupdate、发布器、本地发布测试 | 目录存在不等于已发布；旧 serial 资产不可原地覆盖 |
| 主源/镜像实际 latest【外部】 | 服务器与 Gitee 实际回读 | 仅批准的发布动作 | 客户端、publish verify、Kimi/用户 | 主源与镜像必须分别取证；一个为 5 不能证明另一个为 5 |
| 生产业务代码【外部】 | 线上文件哈希和进程实际加载 | 仅批准的同批部署 | 部署审核、线上 probe、事故指挥 | 不用本地 server/ 或发布包推断线上 patch 级别 |
| 设备实际补丁【外部】 | 真机 running base/serial/hash、pending、冷启动行为 | 设备应用补丁或回滚后 | 真机验收、事故指挥 | 版本显示只是其中一项；还需 pending、同步、图片与业务行为 |
| 发布/部署证据【现行】 | `_harden/` 下只读留档及测试输出 | 执行者；每次检查/部署 dry-run | Kimi、用户、Codex 审查 | 证据不是权威状态；不得用旧日志证明当前线上 |
| 部署 dry-run 清单【现行】 | `_harden/deploy/<change_id>/manifest.json` | deploy_manifest；每批候选文件确定后 | verify-local、审核者 | 只证明本地清单与字节；不证明远端，不含用户数据/密钥 |
| 当前待办【现行】 | `docs/未完成事项清单.md` | DeepSeek 提证据；独立 verified 后销行 | 所有 Agent | implemented 不得直接销账；报告不替代销行 |
| 文档规则【现行】 | `docs/文档治理.md` 与对应 ADR | 用户批准治理变更后 | 文档 writer、审核脚本 | 内容分型保留；执行契约需与源码/链接检查同步 |
| 事故历史【现行】 | `docs/错误总结/` | 有新证据时追加/纠正明确错误 | 规划与审查者 | 不用事后推断改写当时事实；当前状态仍以源码/实测为准 |
| 单变更执行状态【规划】 | `delivery/<change_id>.json`，每卡一份 | DeepSeek 写 implemented/证据；独立批准后才能记 verified | 用户、Kimi、DeepSeek、Codex 只读 | 当前目录不存在；不得宣称已实施，不另设全局可变 delivery_state |

## 3. implemented / delivered / verified 权限

| 状态 | 含义 | 谁可判定 | DeepSeek 权限 |
|---|---|---|---|
| implemented | 白名单实现和要求的本地检查已完成，附 diff 与原始输出 | DeepSeek 可自报，Kimi 审查证据是否齐全 | 可以标记；不得销待办、不得宣称交付完成 |
| delivered | 已执行批准的外发/部署动作，并有动作记录 | 用户批准动作；DeepSeek 只记录实际执行结果 | 可记录；不能由 scp/upload 成功推出用户已收到 |
| verified | 指定验收者确认实际对象满足验收，且证据对应当前版本 | Kimi 可验本地/只读项；生产、真机、发布、公开内容由用户或用户明确授权的验收者判定 | 不能自证；只能凭 `verified_by + approval_ref` 代记独立结论 |

Codex 只能只读审查，不能直接写 verified。全局 done 要求当卡所有声明交付物均 verified；缺一项即 blocked。

## 4. 四条更新链

### 整包

`APP_VERSION/投影` → 构建候选 → `release_manifests/<候选>` → 用户批准 → 上传资产 → 更新并签名 `update.json` → 生成兼容投影 → 回读双通道和生产 → 真机 verified。

同版本已发布资产不可替换；当前本地 0.9.1 APK 与清单不一致，只能保留为未发布候选或进入新版本。

### 热更新

`hotupdate_declare` → `hotupdate_dist/prod` 候选 → 包闭包/签名/干净底座检查 → 用户批准 → 先 patch 后 latest → 主备回读 → 真机 applied/pending/行为 verified。

hot5 双源发布不等于 hot3/hot4 已恢复，也不等于服务端业务代码同级。2026-10-27 实测生产仍为 patch4。

### 部署

变更白名单 → deploy manifest → 本地 verify → 用户批准 → 同批备份/单文件部署 → 线上哈希与进程/路由验证 → 独立 verified。

dry-run 只能验证工具和计划；未执行远端动作时，状态必须保持“未部署”。

### 文档与待办

代码/行为变化 → 同步对应概念/参考/操作页 → 链接与命令检查 → 独立审查 → verified 后销待办。

文档与代码冲突时，当前行为以源码和可复现实测为准；先纠正错误描述，不为迁就旧文档改回代码。
