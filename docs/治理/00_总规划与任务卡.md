# Firefly 架构与治理总规划（执行稿 v1）

> 日期：2026-10-27。本文是任务编排入口，不是现行产品规范。所有发版、生产、数据、协议和铁律变化仍由用户拍板。
> 配套：[01 架构与覆盖矩阵](01_架构与覆盖矩阵.md) · [02 企业级规范差距](02_企业级规范差距.md) · [03 状态地图](03_状态地图.md) · [04 文档治理执行契约](04_文档治理执行契约.md)

## 1. 目标与边界

- **T0 事故收口独立**：hot3/hot4 恢复、数据安全和线上状态独立验收，不能随 0.9.2 开发自动销账。
- **0.9.2 只纳入审过的架构卡**：用户负责 UI；Kimi 负责规划/审核；DeepSeek 负责实现与证据；Codex 仅抽查冻结 diff。
- **治理做减法**：不新增服务、数据库、付费 CI、大企业审批或新文档体系；优先复用现有脚本、harness、manifest 和《文档治理》。
- **核心冻结**：不重写对话流水线，不改变正常产品语义，不把架构变化塞进热更，不用全仓重构解决局部问题。

## 2. 角色、权限与 WIP

| 角色 | 做什么 | 不能做什么 |
|---|---|---|
| 用户 | 产品/UI、范围与优先级、发版/生产/协议/数据/铁律拍板、终端验收 | 不需要替执行者补证据或传递整段聊天状态 |
| Kimi | 调研、ADR、任务卡、证据审查、抽查命令、维护规划与阶段 | 不写业务实现、不跑生产、不把 DeepSeek 自报直接记 verified |
| DeepSeek | 白名单实现、测试/门禁、证据包、文档与待办更新 | 不扩范围、不自证 verified、不擅自部署/发布、不与其他 writer 同改一文件 |
| Codex | 对冻结 diff 做只读审查，引用文件:行 | 不写文件、不改状态、不做开放全仓审计 |

同时最多两张未关闭卡：**执行中 1、待审查 1**；实际 writer 始终只有 1。每次交接以任务卡、盘上证据和 `verified_by/approval_ref` 为准。

## 3. 分阶段路线图

## 4. 首批任务卡

### C0 四方版本与生产只读基线（P0）

- **目标**：得到客户端补丁、主/备 latest、服务端代码、服务端能力及整包资产的当前事实表。
- **范围**：只读命令、公开/授权只读 probe、现有 manifest；不读聊天正文和用户数据内容。
- **禁止**：scp、重启、写 latest、改 user_data、上传资产、修改版本。
- **步骤**：①记录本地候选与声明；②分别回读主备 latest/包体；③回读线上代码哈希和 mode 能力；④整理证据与待核实。
- **验收**：每项有实际值、来源、时间、命令关键输出/退出码；缺证据明确标待核实；生产零写入。
- **回滚**：纯只读，无回滚动作；若发现权限或数据边界越界，立即停止并报告。
- **完成后**：只更新证据和待办，不因“看起来最新”销任何事故项。

### A0 架构未覆盖矩阵与 ADR 输入（P0，只读）

- **目标**：补齐对话、认证、迁移、备份、平台及新治理脚本的风险→源码→现有测试→缺口矩阵。
- **范围**：相关源码、活动测试和当前文档；不恢复归档测试充当证据。
- **禁止**：实现性修改、全仓无目的通读、把“未测”直接判为“有 bug”。
- **步骤**：①按六条链列关键失败；②定位源码与现有 oracle；③区分缺陷/未测/待核实；④提出 A1/A2 ADR 选项。
- **验收**：每个 P0/P1 都有文件:行、影响、已有防线、独立 oracle；A1/A2 给出兼容与回滚选项。
- **回滚**：只读，无代码回滚；错误结论从规划稿撤下并记录原因。

### T1 mode 寻址与能力协商（P0，ADR 批准后）

- **目标**：任何不可寻址 mode 和响应错包都在副作用前明确失败。
- **白名单**：`app/routes_common.py`、`app/api/data_sync.py`、必要的协议响应与活动测试；其他模块须先申请。
- **禁止**：自动复制客户端包到服务端、改变 story/haruno 正常语义、顺手重构同步全链。
- **步骤**：①写入口策略矩阵；②服务端写路径拒绝；③客户端 state/ops/manifest 先验；④补 unknown×版本×入口测试。
- **验收**：文件、epoch/rev、outbox 和服务器状态在负例下逐字节不变；`sync_now` 不再把非法输入改 story；同步四套与既有回归不退化。
- **回滚**：恢复当卡 diff；保留显式错误测试证明旧风险，不动用户数据。

### T2 clear 与远端状态持久化（P0）

- **目标**：清理文件、epoch/rev、outbox、服务器提交不再出现不可解释的部分成功。
- **白名单**：`app/api/chat_ops.py`、`app/modules/sync_state.py`、必要的 `app/modules/sync_server_state.py` 与活动测试。
- **禁止**：引入新数据库、改变用户清理范围、用大范围锁包住网络请求。
- **步骤**：①先写失败矩阵；②收束直接 HTTP 与 save 失败；③收束 apply_remote_state 两方向；④故障注入和恢复复验。
- **验收**：begin/文件/save/commit 各失败点无虚假 ok；重试幂等；清理失败与状态未存两条都覆盖；既有恢复测试不退化。
- **回滚**：代码按卡恢复；测试夹具不接触真实 user_data，生产数据不在本卡操作。

### T3 存量设备与修复候选的受控恢复验收（P0，分两段）

- **目标**：分别证明 hot5 当前恢复状态，以及后续包含 T1/T2 的候选在真实设备上的安全性，二者不得混写版本。
- **范围**：有备份的测试设备/账号、只读快照、非破坏性先行检查；后续候选须另行批准。
- **禁止**：未备份直接测 robin/自建包 clear、触碰其他用户数据、为通过而改现象、把未含修复的 hot5 当新候选。
- **步骤**：①记录当前 serial/pending/文件快照；②做 hot5 冷启动、登录、同步、图片的非破坏性验收；③T1/T2 形成独立候选后记录其实际 base/serial/hash；④再验 unknown 与 clear 零串写。
- **验收**：hot5 段要求 `0.9.1_hot5`、`pending_serial=0` 和业务正常；修复候选段要求版本与候选一致、负例零副作用、前后数据可解释。任一段失败都不得关闭相应事故项。
- **回滚**：只恢复测试环境快照；生产/其他设备恢复由用户另行批准。

### G1 部署 dry-run 与回滚独立验收（P1）

- **目标**：部署工具能证明清单、漂移和真实回滚语义，且不再把本地 deploy 当线上。
- **白名单**：`deploy_manifest.py`、相关新测试、`docs/参考/版本与发布.md` 的必要说明。
- **禁止**：scp/ssh/systemctl、生产写入、借 dry-run 宣称已部署。
- **步骤**：①分离备份/恢复计划；②处理路径与缺备份；③v1→v2→v1 沙箱；④补 version/release/deploy 新脚本负例。
- **验收**：恢复后是 v1 而非 v2；缺备份/漂移/旧进程均失败；文档不再称本地检查为线上验证。
- **回滚**：只回退工具与文档变更；生产未触碰，无生产回滚。

### D1 三页文档执行化试点（P1）

- **目标**：版本发布、热更新、生产服务器三页能被正确执行，并被机械检查发现旧错误。
- **范围**：三页、现有《文档治理》、轻量链接/CLI/常量/结构检查。
- **禁止**：全仓重写、语义猜测、执行 S2/S3 示例命令。
- **步骤**：①只读问题清单；②用户确认迁改；③修三页；④跑检查与一次 dry-run 审读。
- **验收**：deploy 不再冒充线上；443/端口、§4.5、MD5/SHA-256 冲突消除；检查有实际条数且非零退出能抓反例。
- **回滚**：恢复三页文档 diff；若检查误报高，退回链接/CLI/常量三类，不扩规则。

### R1 0.9.2 独立发版卡（ blocked，用户另行放行）

- **目标**：只发布已审架构卡和用户 UI，身份、下载、设备与回滚均有证据。
- **进入条件**：S1/S2 退出、当前 APK 差异有新版本归属、用户明确版本号和范围。
- **禁止**：覆盖 0.9.1、夹带 M3/未审功能、先 bump 后讨论、以旧测试/旧线上结果代替当前证据。
- **验收**：新 manifest；release、包内、签名、活动测试通过；双通道实际字节一致；真机与回滚独立 verified。
- **回滚**：未发布撤候选；已发布按批准恢复上一更新指针和资产，并复测；不得改写旧 manifest。

## 5. 统一回报与审核

DeepSeek 每卡必须回传：卡号、完成/部分/阻塞、diff 文件、原始命令关键行与退出码、测试对象、偏离、未验证项、拍板项。Kimi 对验收逐项判通过/不通过；每 2~3 卡抽查一条只读命令。

状态权限：DeepSeek 只能自报 implemented；Kimi 验本地/沙箱；生产、真机、发布和公开内容由用户或指定验收者 verified。缺证据不得销待办。

## 6. 指标与停止条件

- unknown-mode/错包副作用：目标 0；clear 虚假成功与不可恢复部分提交：目标 0。
- 发布四平面当前证据覆盖：目标 100%；部署沙箱回滚通过后才允许生产。
- 新 P0/P1 独立 oracle 覆盖：目标 100%；活动文档试点失效引用/错误 CLI：目标 0。
- 治理维护 ≤30 分钟/周；同时执行卡不超 1；连续两周指标不动则删/改机制，不加机制。

**立即停止并上报**：需要触碰真实用户数据、改变协议/数据布局、扩大文件白名单、线上状态与预期不一致、同类阻塞连续两次、发现可能继续扩大影响的热更或部署动作。
