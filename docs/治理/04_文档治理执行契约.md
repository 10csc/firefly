# 文档治理执行契约（规划稿 v1）

> 本文补充现行 `docs/文档治理.md`，不另立一套文档体系。内容分型、单一事实源、归档和 ADR 规则继续有效。
> 目标：活动文档能正确指导开发；写的人知道必填什么，执行的人知道怎么做，审核的人能机械发现失效内容。

## 1. 试点前的当前基础与缺口

现行规范已经有 Concept/Task/Reference/Decision 分型、200 行限制、单一事实源和生命周期，**全部保留**。

以下问题在 2026-10-27 三页试点中已被修订，保留作启动依据：

- `docs/参考/版本与发布.md:33` 把本地 deploy 预检写成“线上 update.json”。
- `version_truth.py`、`deploy_manifest.py` 引用过不存在的 `docs/治理/03_状态地图.md`，说明“必须检查链接”尚未形成可靠执行点。
- `docs/操作/生产服务器.md` 同时写 443 TLS 与“公网只开 22+8787”，并引用不存在的“§4.5”；同一页还有 MD5 与 SHA-256 两种资产验收口径。
- P1-2 曾同时出现“公告无冷却”与源码已有 60 秒冷却，说明代码变化时只更新结论、不核对源码仍会失真。

## 2. 每类页面的必填结构

| 类型 | 必填内容 | 不应包含 |
|---|---|---|
| 概念 | 当前边界、数据/控制流、权威源码、非目标、已知限制 | 长命令、实施流水账、未标来源的“当前已实现” |
| 操作 | 适用场景、前提、权限、步骤、副作用、验收、失败停止点、回滚 | 只列命令不说写哪里；历史事故全文 |
| 参考 | 字段/命令、默认值、合法范围、权威代码、验证方式、兼容边界 | 无源码依据的默认值、与代码重复的大段实现 |
| 决策/ADR | Context、Decision、Consequences、Status、superseded_by | 每次小改动、事后篡改旧决定 |
| 错误总结 | 已证实事实、推断、未知项、时间线、影响边界、恢复与防复发 | 把推测写成原因、把补丁发布写成恢复完成 |
| 使用指南 | 用户前提、可见步骤、可见结果、排障、数据风险 | 内部脚本参数、源码路径、Agent 术语 |
| 治理规划稿 | 证据边界、选项、决定点、任务与验收、退出条件 | 冒充现行规范、无 owner 的开放讨论 |

“当前状态”页另需 `verified_at + evidence_ref`；概念/ADR 不机械要求频繁改日期，避免制造无意义维护。

## 3. 强制规则的登记格式

操作和参考页中的关键 MUST 使用稳定 ID：

`[域-序号] 规则句｜权威源码｜执行者｜验证者/命令｜失败处置`

示例（仅说明格式，不新增规则）：

`[REL-001] 同版本已发布产物不可替换｜release_manifest.py｜发布执行者｜build --dry-run 应拒绝差异｜停止发布并进入新版本`

- MUST：必须有脚本检查或明确人工验收者；没有则降级为 SHOULD/说明。
- SHOULD：写明何时可以不遵循及谁批准。
- MAY/兼容回退：写明是否允许副作用，禁止把“可以读”推成“可以写”。
- 同一规则只在一个页面定义，其他页面引用 ID，不复制不同版本。

## 4. 命令与证据安全合同

| 级别 | 例子 | 命令块必须附带 |
|---|---|---|
| S0 只读 | 查文件、哈希、HTTP GET、--check | 工作目录、预期关键输出、退出码；不得泄露令牌/用户内容 |
| S1 本地写入 | 生成 manifest、构建候选、改文档 | 写入路径、输入前提、覆盖行为、如何撤销、预期结果 |
| S2 构建/外部发布 | 打包、上传 Release、热更发布 | 用户批准、目标版本/资产、不可变规则、失败停止点、回读验证 |
| S3 生产/数据风险 | scp、重启、迁移、恢复、删除 | 明确授权、备份、白名单、生产目标、回滚、线上复验；不得伪装成普通示例 |

“验证通过”必须说明验证对象是本机源码、候选产物、沙箱、真机还是生产。旧输出只能证明当时，不能证明当前。

## 5. 文档与代码冲突的处理

1. 先用当前源码和可复现命令确认实际行为，不直接采信任何一侧的描述。
2. 文档过时则修文档；代码缺陷则开代码卡，不能为迁就旧规范改回错误行为。
3. 行为变化的任务卡必须列 `doc_effects`：受影响页面、段落、需更新的命令/默认值、验收方式。
4. 完成时同时提交代码证据和文档 diff；只有口头“已同步”不算完成。
5. 无法确认的内容写“待核实＋核实方法”，禁止用“应该、正常、已修复”填空。

## 6. 机械检查（先做能确定判断的项目）

| 检查 | 通过标准 | 当前反例 / 防误报 |
|---|---|---|
| 相对链接 | 活动页相对链接目标存在；历史链接必须标明历史 | 状态地图失效引用应失败；http 外部链接不做联网全扫 |
| 源码/文件引用 | 显式 `source/evidence` 字段中的路径存在 | 只解析登记字段，不把所有反引号当路径，减少误报 |
| CLI 形状 | 白名单脚本的命令与子参数存在于当前 `--help` | 只读调用 help；不执行发布/部署命令 |
| 默认值/常量 | 登记的端口、目录、版本字段与源码一致 | 通过规则 ID 建立映射，不用模糊全文搜索猜常量 |
| 操作页结构 | 前提、验收、失败停止、回滚齐全 | S0 小命令可合并说明，不强迫所有页面同长 |
| 归档引用 | 活动页不得把归档材料当当前依据 | 明确“历史对照”的链接允许存在 |
| 证据时效 | release/deploy/线上结论必须有当前 evidence_ref | 语义真实性由 reviewer 判断，脚本不假装理解自然语言 |

第一版不做“AI 判断文档是否正确”。链接、CLI、常量、结构可机械检查；事实与语义仍需源码 reviewer。

## 7. 三页试点

| 页面 | 已发现问题 | 迁移动作与验收 |
|---|---|---|
| `docs/参考/版本与发布.md` | deploy 被写成线上语义；本地/线上证据边界不够明确 | 改为本地 preflight＋独立线上回读；用当前 APK 差异验证 release 会失败，任何线上措辞必须有 evidence_ref |
| `docs/操作/热更新发布.md` | 总体流程较完整，但 hot5 当前结果容易被未来会话复用 | 保留包闭包/真机要求；把 hot5 事实改成带日期的证据引用，发布命令全部标 S2，验收区分主备、服务端和设备 |
| `docs/操作/生产服务器.md` | 443 与公网端口表述冲突、§4.5 引用失效、MD5/SHA-256 混用、备份口径待核对 | 先修结构和引用，再统一 SHA-256；备份实际 cron/位置标待核实并给只读核对法，所有生产命令标 S3 |

试点顺序：只读审查 → 用户确认迁改 → 修改三页 → 机械检查 → DeepSeek 按页执行一次 dry-run → Kimi 对源码抽查。通过后才推广到其他页面。

2026-10-27 试点结果：三页已修订，`python tools/check_docs_execution.py` 检查 3 页、
10 个相对链接、13 个脚本引用、4 组 CLI 和 26 项页面常量，结果为 PASS。
`python tools/check_docs_execution.py --self-test` 用旧端口、失效章节、MD5、坏链接等反例验证
检查器会失败（本次命中 8 项），不是空扫通过。语义结论仍需 reviewer 对照源码。

## 8. 文档完成定义（DoD）

- 内容类型正确，权威事实只有一个来源，未复制另一页的动态表。
- 强制规则有 ID、源码、执行者、验证和失败处置。
- 命令有安全级别、预期输出和退出码；S2/S3 有批准与回滚。
- 链接/CLI/常量/结构检查退出码为 0，并附实际检查条数，不接受空扫 PASS。
- reviewer 已对照当前源码核验关键事实；无法核实项明确标注。
- 相关待办只有在独立 verified 后销行；过程记录不替代活动页更新。

## 9. 成本与退出条件

- 每个行为变更卡只点名相关页面，不做全仓文档审查；规划稿评审目标 ≤10 分钟/页。
- 若机械检查连续两周误报多于真实问题，退回到链接/CLI/常量三类，不扩展语义规则。
- 若某模板导致重复抄写，删除字段，不允许为了“显得规范”增加维护量。
- 若未来文档系统原生提供同等检查，迁移后退役本地脚本，不保留两套结果。
