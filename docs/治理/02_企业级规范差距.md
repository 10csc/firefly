# 最小企业级控制差距（执行稿 v2）

> 目标不是模仿大企业流程，而是让单人＋多 Agent 项目做到：变更有主、执行有界、结果独立可验、失败可退、事故可关闭。
> 判断分三档：**有效**＝当前证据足够保留；**部分**＝已有机制但覆盖/执行不完整；**不足**＝关键控制缺失或语义错误。

## 1. 控制差距矩阵

| 控制域 | 当前 | 证据与真正缺口 | 最小补强及执行点 |
|---|---|---|---|
| 变更所有权与分级 | 部分 | 热更/整包规则存在，但修复、发布、服务端部署和架构改造仍能混卡 | 每卡唯一 owner、change_type、track、交付物；热更只修 bug，架构只走整包 |
| implemented / verified | 不足 | DeepSeek 能给出实现与输出，但“自己完成、自己验收”仍可能变成最终结论 | DeepSeek 只报 implemented；Kimi 验本地，用户验生产/真机/发布；verified_by 必须独立 |
| 数据安全不变量 | 本地有效，生产未部署 | T1/T2 已让 unknown-mode 写前失败、clear 走可恢复事务；生产仍是 patch4，真机未验 | 独立复核 diff 与故障日志；部署与真机验证前不得标 delivered/verified |
| 产物来源与不可变 | 有效（本地） | release_manifest 已拦当前 0.9.1 APK 差异；远端实际资产仍需回读 | 保留现有工具；发布卡必须附双通道字节证据，禁止同版本替换 |
| 四平面发布 | 部分 | 热更双源为 serial 5，生产业务代码仍 patch4，设备未验证；整包投影正常 | 每次发布/事故验收都填四平面表；当前 P0-4 保持 blocked |
| 部署与回滚 | 本地部分有效 | G1 沙箱 v1→v2→v1 与 11 项负例通过；生产回滚未执行 | 生产按同批备份+单文件部署+线上哈希/进程/行为复验，且需用户另批 |
| 测试治理 | 部分 | 同步四套 153 项与 G1 11 项有活动 oracle；聊天、认证、迁移、备份、平台、公告仍无活动测试 | 风险→oracle 矩阵；新 P0/P1 无独立 oracle 不得 verified，不追求旧测试数量 |
| 事故指挥 | 部分 | #36/#37 时间线和边界明显改善，但遏制、恢复、关闭仍易混用 | 统一 detected→contained→recovered→verified→closed；每阶段证据不可互相替代 |
| 密钥与签名 | 有效 | RSA 验签、公钥一致性、更新清单签名、secrets hook 已有实测 | 保留；新增发布路径必须复用同一信任根，不另造凭证体系 |
| 生产数据与隐私 | 部分 | 实际 cron、备份路径/保留期已只读核实；下载兜底仍指向 v0.8.1 | 修复兜底并做恢复演练；任何高风险操作先 pre_ 备份，不下载用户数据 |
| 文档生命周期 | 试点有效 | 三页现由 `check_docs_execution.py` 检查 10 个相对链接、13 个脚本引用、4 组 CLI 与 26 项常量；自测反例命中 | 推广前保持误报可接受；代码变化必须登记 doc_effects |
| 成本与 WIP | 部分 | 主会话执行成本低，但连续救火会并行扩大改动面 | 同时执行≤1、待审≤1；同卡两次同类阻塞即缩卡/升级，不靠多 Agent 抢进度 |

## 2. 变更与发布的最低状态合同

每卡只声明实际需要的交付物：`code / apk / exe / server / hotupdate / notice / docs`。每项分别记录：

`pending → implemented → delivered（如适用）→ verified`，异常进入 `blocked` 或 `rolled_back`。

- **implemented**：实现者本地完成，证据包括 diff、原始命令、退出码、测试对象。
- **delivered**：经批准的外发或部署动作已执行；scp/upload 成功只到这一层。
- **verified**：独立验收者针对当前实际对象确认；本地、线上、真机证据不可互换。
- **done**：所有声明交付物 verified；未声明交付物不得顺手外发。
- **销账**：只有 verified 才能删除待办；事故遏制、补丁发布、设备恢复是三条不同状态。

## 3. 事故指挥协议

| 阶段 | 必须回答 | 不得冒充 |
|---|---|---|
| detected | 何时、何物、什么证据、影响谁 | 用户反馈不等于根因已查明 |
| contained | 如何停止扩大：停灰度/停发布/冻结写路径/保留现场 | 停止扩散不等于设备恢复 |
| mitigated | 是否已有候选修复，覆盖哪个故障层 | 本地测试绿不等于线上已修 |
| recovered | 主备指针、服务端、设备是否回到可用状态 | 版本号显示不等于数据链路恢复 |
| verified | 独立验收是否覆盖版本、pending、业务、数据完整性 | 执行者自报不等于独立验收 |
| closed | 遗留风险已入待办、回归 oracle 存在、回滚可用 | 关闭事故不等于删除历史或风险 |

事故期间只设一个协调入口：用户拍板，Kimi 维护阶段与证据，DeepSeek 单 writer 执行；不允许三个 Agent 分别修不同层再拼结论。

## 4. 发布与部署放行清单

### 整包/热更

- 版本、候选 manifest、不可变检查、包闭包、签名、活动风险测试均有当前证据。
- 主源与镜像分别回读 latest、清单和包体；热更还需真机 applied/pending/行为。
- 同版本已发布资产不可变；任何差异必须进入新版本，不得改写历史证据。

### 生产部署

- 变更文件白名单、同批备份、部署 manifest、回滚计划先经 dry-run。
- 部署后回读文件哈希、进程加载、严格 surface、关键 API 和版本投影。
- 回滚后也跑同一组检查；不能只汇报“文件已恢复”。

### 独立验收

- Kimi 可复核本地命令与沙箱；生产、真机、公开发布由用户或其指定验收者确认。
- 每 2~3 张卡抽查一条原始验收命令；证据与当前 manifest 不符即退回。

## 5. 指标与复核节奏

| 指标 | 当前基线 | 目标 |
|---|---|---|
| unknown-mode 造成写副作用 | 本地负例全部零副作用；生产仍 patch4 | 部署与真机负例全部零副作用 |
| clear/远端合并部分提交 | 本地故障矩阵通过；生产仍 patch4 | 部署与真机故障矩阵可恢复，无虚假 ok |
| 四平面都有当前证据的发布次数 | 当前证据齐全，并明确显示服务端 patch4、设备未知 | 每次发布/事故验收四平面一致或显式 blocked |
| 可执行回滚的部署批次 | 沙箱 v1→v2→v1 通过；生产未演练 | 生产回滚逐批有备份、哈希与业务复验 |
| 独立 verified 比例 | 执行者自证风险仍存在 | 生产/发布/真机 100% 独立确认 |
| 活动文档失效引用与错误 CLI | D1 三页检查为 0，自测能抓反例 | 随后活动树为 0 |
| 新 P0/P1 风险有独立 oracle | 多项缺失 | 新增/修改风险 100%，不恢复旧测试充数 |
| 治理人工维护 | 当前未测 | ≤30 分钟/周；连续超标先减机制 |

每两周只复核这些指标。指标不动就修改或删除机制，不增加新会、新表、新角色。

## 6. 不引入的“伪企业级”负担

- 不引入 Jira/新平台、每日站会、多层审批、专职运维或必须付费的 CI/设备服务。
- 不要求每次小改都全量构建、全量真机或全仓文档审查；按风险选择验证。
- 不以文档篇数、测试数量、提交数量、门禁数量作为成熟度。
- 不为形式统一而重写有效签名、真实 HTTP harness、现有发布清单和单文件部署规则。

## 7. 机制退出条件

- 独立状态文件若连续三次只增加抄写、未拦住漏项，退化为任务卡固定字段。
- 文档检查若连续两周误报高于真实问题，缩小到链接/CLI/常量三类，不硬做语义判断。
- 部署 manifest 若未来由可证明来源的自动部署完全替代，删除手工清单，不保留双真相。
- 任一机制连续两次发布没有提升可核验性，先停用复核，禁止再叠加一层流程遮盖。
