## 3. 0.9.2 必须守住的架构不变量

| ID | 不变量 | 独立验收 |
|---|---|---|
| A-I1 寻址 | 每个请求都保留 requested_mode、resolved_mode、capability；有副作用操作不得静默改写成另一 mode | unknown-mode 对所有写入口均在副作用前失败，story/haruno 行为不变 |
| A-I2 先验后写 | 任何 state、ops、manifest、文件、outbox 副作用之前，先验证响应 mode、协议和对象归属 | 错包/错 mode/旧协议响应下，本地与服务器字节、rev、outbox 均不变 |
| A-I3 持久化成功 | 破坏性操作只有在规定状态成功落盘后才可报告成功；失败不得产生半提交 | 每个失败点都能说明哪些步骤允许前进、哪些必须回退或留 PREPARED |
| A-I4 四平面一致 | 客户端补丁、主/备发布指针、服务端代码、服务端可用能力分别记录，禁止用一个版本号代替全部 | 同一验收表列出四项实际值；任一项不符即不能 verified |
| A-I5 产物不可变 | 同版本已发布资产及哈希不得替换；本地重建差异只能作为候选或进入新版本 | 当前 0.9.1 不同 APK 继续被 release 拒绝；0.9.2 必须走新 manifest |
| A-I6 本地/线上分离 | 本地 preflight 不得命名为线上 verified；线上结论必须来自实际回读和加载行为 | 审核证据明确来源为本机、沙箱、真机或生产，不混用 |
| A-I7 独立 oracle | 关键测试不得由被测实现自己生成期望值，不得只查函数名 | 固定期望、真实 HTTP、另一进程、干净底座或可执行不变量至少一项 |
| A-I8 可回退 | 每个结构改造卡都有上一行为恢复方式；回滚后必须重新验证，而非只恢复文件 | dry-run 真能从 v2 回 v1；涉及数据时同时证明数据语义可恢复 |

## 4. 目标改造包（ADR 后才开实现卡）

### A1 mode 寻址与能力协商

- **方案边界**：优先扩展现有 state/manifest 响应和 mode 解析结果，不默认新增服务或重写协议。
- **必须覆盖**：`_query_mode/_body_mode`、`_sync_mode_root`、`sync_now` 的入口 fallback、state/ops/manifest/import/export。
- **兼容原则**：无副作用读取可保留明确降级；写操作和可能改变代际的操作必须失败关闭。旧客户端得到可识别错误，不得落到 story。
- **验收**：unknown×各入口×各版本矩阵；响应错包零副作用；四套同步检查与既有回归不退化。
- **不做**：不自建第二套 mode 注册表，不要求服务端自动拥有全部客户端自建包。

### A2 clear 与远端状态的持久化边界

- **方案边界**：复用现有 txn/outbox/pending，不引入新数据库；先写清直接 HTTP、recover、apply_remote_state 三条路径的失败矩阵。
- **必须覆盖**：begin 失败、每个文件副作用失败、状态 save 失败、outbox commit 失败、进程中断、重试。
- **验收**：任一失败都不产生虚假 ok 或不可解释的部分成功；两个方向（清理失败/状态未存）都有独立 oracle。
- **不做**：不试图用一次大锁包住所有网络与文件操作，不改变正常清理的产品语义。

### A3 发布控制面

- **方案边界**：复用 update.json、release_manifests、hotupdate_declare 和现有门禁；per-change 文件只记状态，不建平台。
- **必须覆盖**：candidate/published、主备 latest、服务端业务代码、mode capabilities、实际下载字节、设备 applied serial。
- **验收**：一张四平面证据表能指出不一致发生在哪一层；本地 preflight 与线上 verified 分开签字。
- **不做**：不新增“总版本号”掩盖各层差异，不自动推送或自动部署。

### A4 部署与回滚

- **方案边界**：保留单文件 scp；先修 dry-run 的备份/恢复语义，再考虑任何真实部署。
- **必须覆盖**：同批文件、部署前备份、线上哈希、进程加载、严格 surface、关键 API、回滚后同组检查。
- **验收**：v1→v2→回滚 v1 的沙箱证据；缺备份、字节漂移、旧进程均失败；生产操作另获用户批准。
- **不做**：不把 `check_version --profile deploy` 当线上探针，不引入 CI 才能使用的流程。

### A5 风险驱动测试与观测

- **方案边界**：保留现有六份 Python 测试程序、共享 harness 和 JS 合约，按事故缺口新增，不恢复旧测试数量。
- **优先补**：unknown-mode、响应错包、clear 直接 HTTP、release/deploy 新脚本、平台/备份/认证/迁移。
- **验收**：每个 P0/P1 风险至少一项独立 oracle；测试报告包含真实覆盖对象和未覆盖项。
- **不做**：不以测试数量、pytest 收集数或 AST 函数名作为质量目标。

## 5. 0.9.2 实施顺序与依赖

| 顺序 | 工作 | 进入条件 | 退出条件 |
|---|---|---|---|
| 0 | 四方版本与数据安全基线 | 只读，不触碰生产数据 | 每项都有实际值或“待核实”，无凭空推断 |
| 1 | A1/A2 ADR 与故障矩阵 | 当前事故时间线和源码证据齐全 | 用户批准协议/行为变化；验收用例先于实现确定 |
| 2 | A1、A2 小步实现 | 一次一张卡，白名单明确 | 本地 implemented；生产与真机另验 |
| 3 | A3/A4 发布与部署 dry-run | 不发布、不部署 | 四平面证据齐全；G1 沙箱回滚通过；生产未执行 |
| 4 | 用户 UI 与接口联调 | 数据形状和错误码稳定 | UI 不需要绕过协议或猜 mode；前端 bundle/包内检查通过 |
| 5 | 0.9.2 独立发版卡 | 用户明确放行版本与范围 | 新 manifest、全部门禁、实际下载、真机和回滚证据齐全 |
| 6 | 后续 M3/其他架构项 | 0.9.2 候选产物已确认 | 不夹带未审功能，不借新包自动销掉旧事故 |

## 6. 明确不在本轮架构承诺内

- 不承诺重写核心对话流水线、前端 UI、服务器平台化或数据库替换。
- 不把“全量文档整理”“全仓测试恢复”当成 0.9.2 前置条件；只处理风险相关部分。
- 不在未核实前声称认证、迁移、备份、语音或安装器存在新缺陷；它们先进入覆盖矩阵。
- 不用 0.9.2 的版本号替代 hot3/hot4 设备的恢复证据。
