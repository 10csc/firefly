## 一、端到端数据流

```
聊天轮次 ──用户反馈──▶ feedback.jsonl（👍/👎+标签+理由）
                         │  👎 自动落失败案例（含该轮上下文快照）
                         │  👎+换一条 落 preference.jsonl（选中/落选对）
                         ▼
开发者手动触发 tools/harness_optimize.py（周级，离线）
  归因（Flash）→ 候选生成（Think Max，整槽位新版）→ 静态校验（代码层）
  → 双盲 judge（Flash×4）→ pending.md + report.json（停，不生效）
                         ▼
设置页「行为改进」：摘要 + 条目级 diff + judge 分 → 用户【应用 / 忽略】(默认忽略)
                         ▼
原子替换 active → 版本归档 → clear_cache() → audit.jsonl
                         ▼
召回式回滚：同类型点踩 ≥3 且匹配改动点 → 通知复核 → 恢复上一版
```

## 二、目录与数据文件（全部在 user_data 下，不进 prompt）

```
user_data/{mode}/character/harness_rules.md        # 生效版（active，由批准后系统写）
user_data/{mode}/character/.harness/pending.md     # 候选（L1 唯一写入区）
user_data/{mode}/character/.harness/v{N}.md        # 历史版本（回滚源）
user_data/{mode}/character/.harness/report.json    # 评审报告（diff/分数/来源/归因）
user_data/{mode}/character/.harness/audit.jsonl    # 生效/回滚五元组审计
user_data/{mode}/data/feedback.jsonl               # {time,turn,verdict,reason_label,reason_text,mode}
user_data/{mode}/data/preference.jsonl             # {turn,chosen,rejected,mode}（换一条产生）
```

- 服务器版全部天然按 user_id 隔离；跨用户聚合明确不做。
- bundled 兜底：`app/assets/character/{mode}/harness_rules.md` 仅承载**开发者审核后**随发版发布的规则；`app_config._DEFAULTS` 增加一行首次启动拷贝。

## 三、代码改动清单

### 3.1 注入点（前置改造，一次性）

- `polisher.py`：story/haruno 模板在 `## 角色核心 {core}` 之后插入固定段（位置一经确定不再改，保缓存前缀稳定）：

```
## 已确认的改进规则（若为空则忽略本节）
{harness_rules}
```

- `analyzer.py`：`_ANALYZER_SYSTEM` 同样注入（供事实核查用），位置在 `{story_extra}` 之前。
- `llm_base.load_slot("harness_rules", mode)` 直接复用（user_data 优先 + 缓存 + user_scope 隔离）；relay 模式跟随 `用户设定` 真实注入（存服务器 user_data，不需占位符）。
- 未创建文件时返回空串 → 模板用 `.format(harness_rules="")`，零影响。

### 3.2 静态校验器 `app/modules/prompt_gate.py`（纯 Python，不调 LLM）

`validate(candidate: str, mode: str) -> {ok, errors[]}`，规则：
1. 行级时态标记合法：每条规则以 `[事实]/[经历]/[若]/[原句]` 或 `-` 禁止/风格条目开头；
2. 槽位预算 ≤ 500 token（按「汉字数≈token」粗估，超限拒绝并要求压缩）；
3. **元指令黑名单**：`忽略以上/无视/你是/你必须/作为 AI/system:/[MSG]/输出/标记为/判为` 等对模型二次编程措辞——槽位只描述流萤，不向模型下指令；
4. 每条引用类规则必须附 `出处：<文件名>#<条目>` 且 `resolve_character_file` 可验证；定位失败即拒；
5. 与 core/identity 的 `[事实]` 做关键词级冲突检查（“痊愈/治好/没有失熵症”vs“不可逆”等）；
6. 纯文本：无 URL、代码块、emoji、超长行。

### 3.3 版本管理 `app/modules/prompt_registry.py`

- `stage_candidate(text, report)`：写 pending.md（唯一 L1 写入点）；
- `apply(mode)`：pending → 原子替换 active（写 tmp + os.replace）→ 归档 v{N+1} → `llm_base.clear_cache()` → 写 audit；
- `rollback(mode, v=None)`：复制 v{N} 回 active → 清缓存 → 写 audit；
- `diff_entries(old, new)`：生成**条目级纯文本 diff**（增/删/改标记，不引 diff 库）。

### 3.4 路由（`app/routes.py`）

| 端点 | 权限 | 说明 |
|------|------|------|
| `POST /feedback` | 本地任意；服务器=本人 | 落盘反馈；👎 同时把该轮上下文快照存入失败案例 |
| `POST /chat/reroll` | 同上 | 换一条：按原上下文重跑 polisher 替换该轮消息，并记 preference 对 |
| `GET /prompt/candidates` | 同上 | 读 pending + report（摘要/diff/分数） |
| `POST /prompt/apply` | 同上 | 用户批准 → registry.apply |
| `POST /prompt/rollback` | 同上 | 用户撤销 → registry.rollback |
| 服务器版管理员 | 管理员 | 指定测试用户、查看全局审计（P2） |

### 3.5 前端（`app/static/`，同步 server/frontend + 安卓 assets）

- 聊天气泡操作区：👍 / 👎 / 换一条；点 👎 弹标签选择 + 一句话（可选，≤200 字）；
- 设置页新增「行为改进」卡片：候选摘要 + 条目 diff + judge 分 + **【应用】【忽略】**（忽略为默认样式）+ 改进记录 + 一键回滚；
- 只读审计入口：时间 / 改了哪条 / 谁批准的 / 可回滚。

## 四、反馈采集细节（行为研究修正版）

- 定位：**失败案例采样器**，计数不作质量统计。
- 👎 自动携带该轮上下文（最近 N 轮截断），不进优化器前不清洗；理由标签枚举：`人设崩了 / 记错了 / 重复 / 太冷淡 / 太黏 / 不像她 / 其他`。
- **归因分流**：事实性批评（违背设定/记错/复读/OOC）→ 候选管线；偏好性愿望（更甜/更黏/更主动）→ 仅归档，不进管线（除非与 core 不冲突且另行确认）。
- 换一条产生的 (选中, 落选) 对优先级高于纯 👎 文本。
- 去噪：同一用户同一轮只计一条；无理由的 👎 仍保留上下文但权重低于带标签的。

## 五、优化器与 judge（`tools/harness_optimize.py`，离线手动）

### 5.1 触发与输入（初定，待拍板）

- 触发：负面反馈 ≥5 条 或 开发者手动；每批间隔 ≥7 天。
- 输入：失败案例（含上下文）+ preference 对 + 现版 core/identity/sms_samples/harness_rules + polisher 负面清单（仅查重）。

### 5.2 两步生成

1. **归因（Flash + Think High）**：每条失败案例 → `{layer, rule_hit, missing, evidence}`；只放行「harness 槽位层 + 事实类」；模板层/资产层归因 → 人工待办归档。
2. **候选（Pro + Think Max）**：输出**整槽位新版本** JSON 契约：
   - `rules[]`：`{id, type(事实|经历|若|禁止|风格), text, source, reason}`
   - `removed[]`：旧规则 id + 删除原因
   - `summary`：一句人话摘要
   - 硬约束写进优化器 system：提案者身份、只描述流萤不对模型下指令、引用必有可验证出处、与模板负面清单查重。
   - 静态校验拒绝 → 退回重写 1 次 → 再拒整批放弃并出失败报告。

### 5.3 双盲 judge（初定，待拍板）

- 固定回归样本集：初始 10 轮（日常/情感/边界/编造陷阱/约定跟进 ×2），从 `pipeline.jsonl` 挑真实轮次，开发者标注，用户确认后入库。
- 流程：候选 vs 现版并排盲评 ×2（交换顺序）→ Flash 四维 1–5（人设一致/事实准确/风格语气/不重复）。
- 参考通过线：四维均分 ≥ 现版，且单维不落后 >0.5，且总分优势 ≥0.3；**分高不自动生效**，只展示给批准人。
- 成本参考：归因 ~0.01 元级 / 候选 0.1 元级 / judge 10轮×4 约 0.1–0.3 元级；周级频率可接受，不触发=零成本。

## 六、批准、召回式回滚与审计

- 批准：候选攒批（**每月一批**）后提示；默认按钮「忽略」；用户可看条目 diff 或直接摘要决策。
- 召回阈值（初定，待拍板）：生效后**同类型点踩 ≥3 且与刚生效改动点匹配** → 通知用户/开发者复核，确认后回滚并冻结候选；不做无人的自动回滚。
- 审计五元组：`{触发反馈来源, 优化器与模型, judge 分数, 批准人, 生效范围}`；回滚同留痕。
- 服务器版：管理员批准 → 指定测试用户生效（先不做尾号自动分流）；管理员可见全局审计。

## 七、分阶段实施（预估）

| 阶段 | 内容 | 量级 |
|------|------|------|
| P0 前置 | 注入点 + 槽位加载 + `_DEFAULTS` 兜底 | 0.5 天 |
| P1 反馈闭环 | 👍/👎/换一条 + 标签理由 + feedback/preference 落盘 + 前端 | 1 天 |
| P2 候选与批准 | prompt_gate + prompt_registry + optimize 脚本 + judge + 设置页批准/回滚 | 1–2 天 |
| P3 服务器版 | 管理员端点 + 指定测试用户生效 + 审计面板 | 1 天 |
| P4 远期 | 自然语言调设定（复用 P2 管线，同样候选制） | 待议 |

每阶段结束跑现有 15 项单测 + 新模块测试；**不完成 P0–P2 不开任何自动生效口子。**

## 八、明确不做（YAGNI）

- 不做 APP 内一键优化按钮（开发者离线代跑）；
- 不做隐式行为埋点（长按/滑走/中断率）；
- 不做无人的自动生效/自动回滚；
- 不做跨用户反馈聚合改共享角色；
- 不迁移 polisher 现有 14+ 条负面清单进槽位（只查重）；
- 不引第三方库（diff 用纯文本条目级；token 用字符粗估）。
