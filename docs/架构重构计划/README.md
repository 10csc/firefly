## 一、总则

1. **渐进式，行为不变**：阶段 0-2 不允许任何用户可感知的行为变化；阶段 3 起的变化必须逐条列在任务卡中。
2. **先测试后重构**：没有保护网的任务不许开工（阶段 0 存在的意义）。
3. **小步提交**：每张任务卡 = 一个本地 commit；**禁止 push、禁止 bump 版本号**（提交≠发版，见 `docs/部署与发布约定.md`）。
4. **中文注释与文档**；注释解释"为什么"，不复述代码。
5. **禁止新增第三方依赖**（唯一例外：阶段 4 语音插件的 onnxruntime，且需用户拍板后单独批准）。
6. **禁止子代理**：全部工作在主会话顺序完成（CLAUDE.md 硬约束）。
7. 改前端只改 `app/static/`，改完跑 `tools/sync_frontends.py`（含 `--check`）；改后端注意安卓构建期 `syncBackend` 拷贝。

## 二、DeepSeek 的自主权边界（重要）

**以下事项可自行判断，不必请示**：
- 变量/函数命名、函数拆分粒度（在任务卡约束内）；
- 测试代码的具体实现方式；
- 文档与代码冲突时**以代码为准**并在执行日志记录冲突点；
- 任务卡未覆盖到的明显笔误/注释漂移的顺手修正（写入日志）。

**以下事项必须停止并上报（这些是规划者无法确认或涉及拍板的点，不允许自行发挥）**：
- 任何会触碰生产服务器数据的操作（SSH 只读盘点除外，且需用户授权）；
- 任何删除用户数据的逻辑变更；
- API 端点语义/返回结构变更（新增字段可以，改/删字段不行）；
- 版本号、发行资产、git push、安装器配置；
- 新增依赖、UI 布局大改；
- 标注「需拍板」的任务（阶段 4 大部分）。

**任务卡未明确的细节**，按"最小改动 + 与邻代码风格一致"处理；拿不准且影响超出单文件时，停下来问。

## 三、任务卡模板（每阶段文件内的统一格式）

```
### 任务 X.Y：<名称>
- 级别/来源：P? / 问题 ID（见 architecture-refactor.html 视图⑫）
- 目标：一句话
- 证据：文件:行号（现状）
- 改动范围：允许触碰的文件清单
- 禁止：明确不许动的
- 步骤：1…n
- 验收：测试名 + 门禁命令 + 手工确认点
- 回滚：如何退
```

## 四、完成定义（DoD，每张卡都必须满足）

1. 验收项全过；2. 全量测试绿：`Get-ChildItem tests\test_*.py | ForEach-Object { python $_.FullName }`；
3. 涉及前端时 `python tools/sync_frontends.py` 且 `--check` 一致；
4. 涉及版本相关文件时 `python tools/check_version.py`；
5. `docs/架构重构计划/执行日志.md` 追加一条（任务号/改动文件/测试结果/遗留问题）；
6. `git status` 中无任务卡范围外的改动。

## 六、阶段顺序与暂停点

- 阶段 0 → 1 → 2 → 3 严格顺序执行；**阶段 3 完成后停下汇报**（这是行为开始变化的分界）。
- 阶段 4 每项独立排期，含「需拍板」标记的不经确认不开工。
- 任何阶段出现验收不过且 30 分钟内定位不了原因：回滚该任务卡，日志记录，继续下一张。
