# 阶段 5 · 旧版数据迁移专项

> 目标：迁移机制成体系——统一注册、必带备份、可校验、用户可见。优先迁移重组，兼容旧版兜底。
> 前置：阶段 3 完成（packs.json 与快照 manifest 已就位）。
> 依据：architecture-refactor.html 视图⑦、`docs/版本更新规范.md`。

---

### 任务 5.1：迁移注册表统一
- 证据：全仓 10 处迁移散在各模块（视图⑦存量表）；仅 `server/db.py` 有版本号驱动
- 步骤：
  1. `core/migrations.py`（阶段 2 落位）定义迁移协议：`{name, detect() -> bool, backup() , run(), verify()}`；
  2. 现有迁移逐条登记（平铺→分目录、providers、conversation 旧路径、memory 旧路径、表情包默认集、陈旧副本清理），不改其逻辑只收口；
  3. 启动链统一执行：detect → backup（pre-migrate zip）→ run → verify → 汇总日志；
  4. 每条迁移保持"按文件状态判断"哲学（docs/版本更新规范.md:67），不引入版本号驱动（db 除外）。
- 验收：测试——逐条迁移的幂等性（连跑两次结果一致）；备份失败即中止
- 回滚：revert（迁移逻辑本体未动）

### 任务 5.2：setting_fix.cleanup_legacy 加备份
- 证据：`app/modules/setting_fix.py:146-162`——全仓唯一 rmtree 用户数据且无备份
- 步骤：删除前把目标目录打 zip 到 `{mode}/.setting_fix/backups/`；失败即跳过清理
- 验收：测试——清理后备份存在且可还原

### 任务 5.3：迁移结果用户可见
- 步骤：迁移汇总写入 `{mode}/data/pipeline.jsonl`（type=migration）；前端数据面板显示「启动迁移：已迁移 N 项/跳过 M 项」（读最近一次记录）；无迁移则不显示
- 验收：手工——旧布局副本启动后数据面板可见迁移行

### 任务 5.4：老版本数据副本升级演练
- 步骤：
  1. 构造（或从 git 历史 tag 取）v0.7.2 / v0.8.0 / v0.8.1 三个时代的 user_data 布局副本到 `.tmp_test/`（平铺 character/、单 Key config、旧表情包注册表）；
  2. 用当前代码逐个启动演练：数据齐全（对话条数/手账/memory 一致）、config 迁移备份产生、 packs.json 自愈含 story；
  3. 每时代演练结果记录进执行日志。
- 验收：三个时代全部零丢失
- 回滚：演练本身只读副本，无回滚需求

### 任务 5.5：服务器端迁移盘点与演练【需用户授权 SSH】
- 不可见信息（规划者标注）：生产 /opt/firefly 实际数据量、是否已有真实自建包、downloads 目录与 version.json 一致性
- 步骤（授权后）：只读盘点（`ls/du/find` 类，不改任何东西）→ 盘点报告 → 在 /tmp 副本上演练 db v3 与 packs.json 自愈 → 正式执行窗口另行约定
- 禁止：未授权前不得 SSH；生产直接执行迁移

### 任务 5.6：旧客户端兼容闸门复核
