## 任务 2.1 备注（app_config → core/ 五文件，纯移动，2026-09-13）

**做法**：写了一次性拆分脚本（`.tmp_test/split_app_config.py`，不入库）按**行范围**机械切片，
避免手抄 1000 行出错；再用 pyflakes 抓未定义名、用"84 个顶层名字清单"做纯移动 oracle。

### 三个必须显式解决的坑（都会导致真实故障，不是理论风险）

1. **可变全局量不能按值 re-export**。测试普遍用 `cfg.USER_DIR = tmp` / `cfg.CONFIG_FILE = tmp`
   注入沙箱（约 20 个测试文件）。若兼容层写 `from core.paths import USER_DIR`，
   `cfg.USER_DIR = tmp` 只会在兼容层新增属性，`core.paths.USER_DIR` 不变 ->
   **测试会写进真实 user_data**。故兼容层用 `ModuleType` 子类转发**读与写**，
   且 core 内部一律经 `paths.USER_DIR` 属性访问（不按值 import）。
2. **monkeypatch 语义要一致**。`cfg.get_client = stub` / `cfg.get_api_key = ...` / `cfg.config = ...`
   在拆分前与函数同处一个命名空间，补丁会**连带影响模块内部调用**；拆分后若只写兼容层，
   `core.config.get_client` 内部的 `get_api_key()` 就吃不到补丁。故写操作先落到真正持有它的
   core 模块（多个测试依赖这条）。
3. **`APP_DIR` 在安卓模式下原本就不存在**（原 `if FIREFLY_ANDROID` 分支只赋 ROOT/USER_DIR）。
   兼容层若按值 import 会让**整个 app_config 导入失败 = 安卓端全站起不来**。
   已把 `APP_DIR` 改为惰性访问（缺名抛 AttributeError，与拆分前逐字一致），
   并在 `test_core_split` F 段用子进程实测（`FIREFLY_ANDROID=1` 下导入成功且 APP_DIR 仍缺失）。

### 两处必须打破的模块级循环（都在 def/import 期触发，不是随便延迟就行）

- `paths ↔ presets`：`mode_root(mode: str = DEFAULT_MODE)` 的**默认参数在 def 期求值** →
  import 期就需要 presets。改为默认 `None` 哨兵 + 函数内 `_resolve_mode()` 延迟解析
  （逐条等价：None/未传 → DEFAULT_MODE；非法值仍回退默认包；`bundled_character_dir`

- `inherited`：正在用包自带内容，但**副本存在过**（删除副本 / 启动清理陈旧副本后回落）
- `customized`：用户副本与包自带内容不同（或自建包无内置对应物——那种包的文案本来就是用户写的）

**记录优先规则**（本卡的关键）：`refresh_slots` 只在"没记录"或"副本已消失"时推导；
**有记录且副本仍在 → 一律照旧**。所以内置内容更新不会翻转 `inherited`。
`test_slot_states` 的 B 段把这条钉死，并给了**反证**（同一状态用旧口径会判 customized）。

**内置包怎么办（与 3.2 的定论不打架）**：3.2 定"内置包不入 `packs`"（清单只描述用户区）。
但内置包的槽位同样需要记录（story 的 core.md 正是用户最常改的），故 `packs.json` 顶层另开
`bundled_slots` 键存放——清单语义不变，`all_ids()`/`heal()` 都不看它。

**顺手修掉的两个隐患**
1. `pack_root(pid)`：`mode_root()` 对不在 MODES 的 id 会静默回退默认包，而槽位/归档操作要按
   包 id 定位目录 —— 用 `mode_root(归档包)` 会读写**默认包**的目录（3.8 在同步链路上已踩过同一个坑）。
2. `_EDITABLE_FILES` 改为取自 `PACK_SLOT_FILES`：API 能写的文件与能被标记的槽位从此**同一份口径**
   （原来两处各写一份，加一个提示词段就会漂移）。

**未做（有意）**：`/pack-files` 的 `customized` 字段仍原样返回（前端零改动），只多给一个
`slot_state` 供后续 UI 用；卡片说的"UI 改读清单"落在**数据源**上（API 从清单读并下发）。

## 任务 3.4 备注（快照 `_manifest.json`，2026-09-13）

**为什么值得做**：恢复是**破坏性覆盖**，而旧快照 zip 只有数据、没有清单 —— "这份备份里有哪些包、
是否完整、有没有被改过"只能靠解压猜。清单把这三件事变成可核对的事实。

**实现分工**：哈希口径（`_sha256_file`/`_pack_digest`）放在 `infra/sync/restore.py`（数据层），
打包端 `routes_snapshot` 直接 import 它 —— 打包与核对**共用同一实现**，不会各写一份悄悄漂移
（结构守卫 G1 断言 `routes_snapshot` 里没有 hashlib）。

**三个刻意的口径选择（都写进了测试）**
1. **清单只用于核对与上报，不做过滤**：手改过的 zip 里多出来的目录仍按现逻辑恢复
   （"宁可多恢复，不可因为清单缺一条就静默丢数据"）。`extra_in_zip` 报出来但照恢复（F2/F3）。
2. **`verified=False` 不中止恢复**：用户有权改自己的备份，此时"照旧恢复 + 明确告知不可信"
   比"直接拒绝"更符合备份工具定位。真正的安全审查（zip slip/炸弹/大小）在 `_zip_safe_entries`
   与 `_validate_snapshot_zip`，与本核对无关。
3. **返回值仍是 3 元组**，摘要走**可选 `summary` out-param** —— 既有调用方与测试按 3 元组解包，
   改返回结构会连带打碎一大片。`test_snapshot` L 段的桩函数同步补了 `summary=None` 形参
   （否则"补丁生效但调用即 TypeError"，L 段会变成假绿/假红 —— 这是本次真实踩到的一处）。

**超出卡片的一处补充**：清单里加了 `stickers{files,sha256}`。卡片只写了 `packs`，但快照确实包含
用户表情包，清单不提它就不完整（少一个包和少一批表情包是同一种"漏"）。

**旧 zip 兼容**：实测"手工删掉 `_manifest.json` 的 zip"仍被 `_is_snapshot_zip` 认作快照、
仍可恢复，且摘要里没有 manifest 键（D1-D3）。

## 任务 3.5 备注（删除两级化，**行为变化卡**，2026-09-13）

**核心行为变化**：删包不再一次灭失数据。`delete_pack` 从"一次 confirm → `rmtree` 连数据"
改为**两级**：`/pack-archive`（归档：数据与清单条目都留，只是从列表/聊天里隐藏）→
`/pack-delete`（抹除：仅归档包可删，且删除前强制备份）。用户手滑一次不再等于永久丢角色卡与聊天记录。

**四处关键实现**

| 点 | 做法 | 为什么 |
|---|---|---|
| 归档 | `set_state(archived)` + `reload_presets()`，并**输出验证**"归档后确实不在 MODES" | 状态与投影必须一致；不一致宁可报错也不假装成功 |
| 贴纸 | `picker.detach_pack(pid)` 把 `pack=该id` 的条目 `pack` 置空 | 贴纸是**用户资产**，包没了不该连带销毁；`pack` 本来就是弱引用。降级失败只告警不阻断（包状态已改，别让整个操作回滚） |
| 抹除前的保险 | `_force_pack_backup()`：`build_full_snapshot_zip()` 落 `backups/pack-erase-{id}-{ts}.zip`，**失败即中止删除**（数据一个字节不动） | "没备份成功就不许抹除"。用**全量快照**而不是单包 zip：单包 zip 的恢复入口要求该包存在（mode 合法），而包刚被抹除恰恰不满足；全量快照走"按包分发恢复"，空环境也能恢复 —— 这才是能用的保险 |
| 备份命名的讲究 | 前缀 `pack-erase-` 既不被 `/backups` 列表收录（只列 `{mode}-*.zip`），也不被 auto-/pre-restore 的滚动裁剪命中 | 这份保险**不会被自动淘汰**，与"滚动保留 N 份"的普通备份区分开 |

## flaky 修复说明（`test_fault_tolerance.py` J 段，2026-09-13）

**根因（已定位，非猜测）**：J 段设 `deadline = t0+2.5`，指望随机 Full Jitter 抽到的 sleep
把预算耗掉从而抛 `code=timeout`；但 jitter 抽到小值时，几次重试能在预算内全部跑完，
循环正常结束 → 抛 `code=network` → J1 断言失败。**整套连跑 3 次复现 2 次，单跑 3 次全绿**，
与"高负载"无关，是纯随机性。

**改法**：`patch("modules.api_client._jitter_delay", return_value=10.0)` + `deadline = t0+2.1`
→ delay 必被截断到剩余预算(≈0.1s)，预算耗尽必抛 timeout，与随机数无关。
**顺带增强**：J2 现在真的守住了"截断"——若不截断会睡 10s 而超时失败（旧写法下 J2 恒真）。
**零生产代码改动**，属 README 划给执行者的「测试代码具体实现方式」自判范围。

## 任务 1.11 备注（knowledge_dirs 越界校验，2026-09-13）

按任务卡实现 `_clean_knowledge_dirs()`：逐项拒绝绝对路径（前导 `/` 或 `\`、盘符）、`..` 穿越、
resolve 后不在仓库内的路径；非法项**逐项跳过并告警**，不整包拒绝。

**实测证据（本次的真实坑，值得留给后续）**——Windows 下 pathlib 拼接会"吞掉"左侧：
```
ROOT / "/etc/passwd" => F:\etc\passwd     ← 逃出仓库
ROOT / "C:/Windows"  => C:\Windows        ← 逃出仓库
ROOT / "etc/passwd"  => 仓库内
```
旧实现先 `strip("/")` 把 `/etc/passwd` 变成 `etc/passwd`，**靠这一步"碰巧"安全**。
本卡实现时第一版把顺序写反（先 strip 再判绝对），被测试 E4 当场抓出；现改为
**先判绝对、再归一化**，并把 resolve-in-repo 作为第二道防线。
