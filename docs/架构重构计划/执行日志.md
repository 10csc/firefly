## 任务 2.1 备注（app_config → core/ 五文件，纯移动，2026-09-13）

**做法**：写了一次性拆分脚本（`.tmp_test/split_app_config.py`，不入库）按**行范围**机械切片，
避免手抄 1000 行出错；再用 pyflakes 抓未定义名、用"84 个顶层名字清单"做纯移动 oracle。

### 三个必须显式解决的坑（都会导致真实故障，不是理论风险）

1. **可变全局量不能按值 re-export**。测试普遍用 `cfg.USER_DIR = tmp` / `cfg.CONFIG_FILE = tmp`
   注入沙箱（约 20 个测试文件）。若兼容层写 `from core.paths import USER_DIR`，
   `cfg.USER_DIR = tmp` 只会在兼容层新增属性，`core.paths.USER_DIR` 不变 ->
   **测试会写进真实 user_data**。故兼容层用 `ModuleType` 子类转发**读与写**，
   且 core 内部一律经 `paths.USER_DIR` 属性访问（不按值 import）。
2. **monkeypatch 语义要一致**。`cfg.get_client = stub` / `cfg.get_api_key = ...` / `cfg.config = ...`
   在拆分前与函数同处一个命名空间，补丁会**连带影响模块内部调用**；拆分后若只写兼容层，
   `core.config.get_client` 内部的 `get_api_key()` 就吃不到补丁。故写操作先落到真正持有它的
   core 模块（多个测试依赖这条）。
3. **`APP_DIR` 在安卓模式下原本就不存在**（原 `if FIREFLY_ANDROID` 分支只赋 ROOT/USER_DIR）。
   兼容层若按值 import 会让**整个 app_config 导入失败 = 安卓端全站起不来**。
   已把 `APP_DIR` 改为惰性访问（缺名抛 AttributeError，与拆分前逐字一致），
   并在 `test_core_split` F 段用子进程实测（`FIREFLY_ANDROID=1` 下导入成功且 APP_DIR 仍缺失）。

### 两处必须打破的模块级循环（都在 def/import 期触发，不是随便延迟就行）

- `paths ↔ presets`：`mode_root(mode: str = DEFAULT_MODE)` 的**默认参数在 def 期求值** →
  import 期就需要 presets。改为默认 `None` 哨兵 + 函数内 `_resolve_mode()` 延迟解析
  （逐条等价：None/未传 → DEFAULT_MODE；非法值仍回退默认包；`bundled_character_dir`
  对非空值仍**不校验**，保持既有语义）。
- `config ↔ migrations`：`_load_config` 内的迁移调用改为函数内延迟导入。

### 其它

- **门禁跟实现走**：`APP_VERSION` 随职责迁到 `app/core/config.py`，
  `tools/check_version.py` 的版本源路径同步改指（否则"文件在而模式找不到"=FAIL，门禁会正确拦住）；
  `docs/版本更新规范.md` 的权威源路径表同步更新。
- **副产品**：`FIREFLY_SERVER=""` 那条链路（1.2 的安卓/子进程测试）顺带覆盖了本次拆分的环境差异。
- **`README.md` 的模块表**仍写着 `app/modules/app_config.py`（现在是兼容层）——
  按计划书，文档对齐属阶段 6（`07_阶段6_治理收尾.md`），此处不改，避免阶段 2 扩散。

## 任务 2.2 备注（routes_data → api/ + infra/sync/，纯移动，2026-09-13）

**目标结构**：`api/data_export.py`（导出/导入/本地备份）、`api/data_sync.py`（增量同步）、

**踩到并修掉的两个坑（都会真出错）**：

1. **`restore ↔ data_export` 环**：`_EXPORT_EXCLUDE_DIRS`（导出/备份要排除的内部目录）
   原本被两边共用。把常量归到 `restore.py`（它才是"用户数据布局"的归属方），
   依赖方向变成单一 `data_export → restore`，环消失。
   教训：**跨模块共享的常量要放在依赖图的下游**，否则纯移动也会撞环。
2. **monkeypatch 语义（比 2.1 更细一层）**：测试打桩的是 `routes_data.time`（**模块级 import**），
   而 `_backup_current_mode` 已搬到 `restore.py`。兼容层若只把写转发给"第一个持有该名字的模块"
   （`time` 在三个新模块里都有），假时钟就到不了 restore → 1.3 的自动备份裁剪断言（G1-G5/G7）全红。
   修法：**写转发给所有持有该名字的模块**（这才等价于"拆分前同一个命名空间"），
   并把 2.1 的 `core` 兼容层一并改成同一规则（保持一致，避免另一处潜伏同类问题）。

**纯移动证据（比"测试绿"更硬）**：`pyflakes` 报告拆前 9 条、拆后 9 条，**逐条对应**

故意**不清**它们——清理属行为外的改动，留给阶段 6 的死代码批次，也让这条对照证据成立。

**兼容层的作用面（记录备查）**：`routes.py` 顶部分发表静态导入 10 个端点名、

### 本次最值得记的一条：**"顺带 import" 的名字也是对外契约**

`routes.py` 顶部 import 了 ~88 个项目内名字，其中 8 个在 routes.py 内部**根本没被用到**
（pyflakes 一直报"imported but unused"）。但它们**不是死导入**——tests 直接经 `routes.*` 取用：
`routes.auth_proxy`（test_auth_proxy）、`routes._IMG_ID_RE`（test_security_hardening）、
`routes._fetch_json` / `_match_asset` / `get_latest_release` / `_get_asset_url`（test_update，共 30+ 处）、
`routes.parse_multipart`（多份测试打桩）。第一版兼容层只 re-export 了"定义名"，
`test_routes_split` 的 A2 段（88 个名字逐条断言）当场抓出问题。
结论：**旧模块的命名空间 = 定义名 ∪ 导入名，两者都是契约**。

`chat()` 拆分的行为保持细节：空消息+hint 路径原本**不触发**后台通知，为逐字一致给

## flaky 修复说明（`test_fault_tolerance.py` J 段，2026-09-13）

**根因（已定位，非猜测）**：J 段设 `deadline = t0+2.5`，指望随机 Full Jitter 抽到的 sleep
把预算耗掉从而抛 `code=timeout`；但 jitter 抽到小值时，几次重试能在预算内全部跑完，
循环正常结束 → 抛 `code=network` → J1 断言失败。**整套连跑 3 次复现 2 次，单跑 3 次全绿**，
与"高负载"无关，是纯随机性。

**改法**：`patch("modules.api_client._jitter_delay", return_value=10.0)` + `deadline = t0+2.1`
→ delay 必被截断到剩余预算(≈0.1s)，预算耗尽必抛 timeout，与随机数无关。
**顺带增强**：J2 现在真的守住了"截断"——若不截断会睡 10s 而超时失败（旧写法下 J2 恒真）。
**零生产代码改动**，属 README 划给执行者的「测试代码具体实现方式」自判范围。
