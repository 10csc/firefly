## flaky 修复说明（`test_fault_tolerance.py` J 段，2026-09-13）

**根因（已定位，非猜测）**：J 段设 `deadline = t0+2.5`，指望随机 Full Jitter 抽到的 sleep
把预算耗掉从而抛 `code=timeout`；但 jitter 抽到小值时，几次重试能在预算内全部跑完，
循环正常结束 → 抛 `code=network` → J1 断言失败。**整套连跑 3 次复现 2 次，单跑 3 次全绿**，
与"高负载"无关，是纯随机性。

**改法**：`patch("modules.api_client._jitter_delay", return_value=10.0)` + `deadline = t0+2.1`
→ delay 必被截断到剩余预算(≈0.1s)，预算耗尽必抛 timeout，与随机数无关。
**顺带增强**：J2 现在真的守住了"截断"——若不截断会睡 10s 而超时失败（旧写法下 J2 恒真）。
**零生产代码改动**，属 README 划给执行者的「测试代码具体实现方式」自判范围。

## 任务 1.3 备注（自动备份统一裁剪，2026-09-13）

按任务卡实现，两处按代码事实收紧了口径（不改行为方向，只是把范围写明确）：

1. **裁剪按 (前缀, 模式) 定位，不是全局 `auto-*`**。`backups/` 是**各模式共用**的一个目录
   （`_backup_dir(mode) = mode_root(mode).parent / "backups"`），若按 `auto-*.zip` 全局裁剪，
   story 频繁导入会把 haruno 的备份删掉。卡里写的 "auto-* 留 10 份" 落实为
   `auto-{mode}-*.zip` 每模式 10 份——与同文件里手动备份的 `{mode}-*` 裁剪口径一致。
2. **配额表 `_AUTO_KEEP = {"auto": _BACKUP_KEEP(10), "pre-restore": 3}`**，未登记前缀**不裁剪**
   （将来新增前缀时不会误删，已加断言 G7）。

测试要点：`_backup_current_mode` 的文件名是**秒级**且无 `_N` 去重，同一秒连写会覆盖同一文件，
所以测试用**可控时钟**（临时替换 `routes_data.time`）造出跨秒累积，否则"15 次→≤10 份"恒真等于没测。

**顺带确认的既有行为（本次不改）**：`_backup_current_mode` 的"空目录跳过"判据是
`not any(root.rglob("*"))`，**空子目录也算非空** → 只删了文件、留着空 `data/` 目录时仍会
打出一个空 zip。属既有语义，阶段 1 不动；如果阶段 3 做数据所有权时想收紧，请单独开卡。

## 任务 1.6 备注（REGISTRY 通配项匹配，2026-09-13）

但当前读的是 `cfg.get_user_overlay()`——那是**请求入口** `_setup_user_context` 装进本请求
contextvar 的**旧快照**。只加锁、基准仍用它，后到的请求会拿旧快照整份覆盖回去（丢更新照旧）。
故新增 `_load_overlay_file(uid)`，**锁内重新读盘**取基准。实测口径：本地版无覆盖场景不受影响；
服务器版语义仍是"只改请求里带的字段，其余保持磁盘现状"（测试 D2 钉死）。

**鉴别力验证（不是自证清白）**：`.tmp_test/old_impl_check.py` 把这两个函数打桩回旧实现
（无锁 + 旧快照基准）后复跑同一交错，磁盘只剩 `{"analyzer_model": "model-from-A"}`，
B 的字段确实丢失——说明该回归测试不是恒真断言。

**遗留**：同账号跨进程并发（未来多 worker 部署）需要文件锁而非进程内锁；当前部署是单进程
ThreadingHTTPServer，进程内锁已足够。若阶段 5/6 考虑多 worker，请单独开卡。
