# 0.9.0 升级回归：服务器 × 客户端（2026-09-20）

> 触发背景：**前后端同时大版本跨越** —— 服务器 app 层 9-15 → 9-20、服务器前端 0.8.1 → 0.9.0；
> 客户端 0.9.0 刚发布。要回答的问题不是"接口能不能返回 200"，而是：
> **真实用户在升级这一刻会不会被打断、会不会丢数据、会不会静默失败。**

## 一、结论（先说结果）

| # | 检查项 | 结果 | 证据 |
|---|---|---|---|
| 1 | **新客户端（0.9.0）× 新服务器** 契约面 | ✅ **0 缺口** | 客户端 74 个 (方法,路径) 对全部可达；`/auth/login` 公网 200 拿到 token |
| 2 | **老客户端（v0.8.1）× 新服务器** 契约面 | ✅ **0 真实缺口** | 从 Gitee 取 v0.8.1 真产物（57.8MB，`CURRENT_VERSION=0.8.1`），54 个调用对逐个打线上：仅 `/shutdown` 404 —— 那是**本地引擎专用**端点，老客户端只在本地模式调它 |
| 3 | 真实流量里的失败 | ✅ 无 | 主服务日志近 3 小时：**0 个 5xx、0 个 404** |
| 4 | 老账号数据仍在 | ✅ 在 | uid=1 对话 7392B + 手账 1231B；uid=13 对话 49127B。**没有数据被清空/搬走** |
| 5 | uid 隔离 | ✅ 正常 | 新建测试号（uid=16）只见自己的空数据（`favorites=[]`、`sync/manifest files={}`），看不到他人数据 |
| 6 | 服务健康 | ✅ | 双服务 active、`/health` 200、`/opt/backups/` 三份备份齐 |

**判定：这次双端升级在 API 契约层与数据层没有造成破坏，老客户端继续可用。**

## 二、为什么这么测（方法论）

用户的手点是"一次性"的，不可复现；这次要的是**可复现的回归**。采用：

1. **消费方驱动的契约比对**（consumer-driven contract）：从客户端产物里抽出它真正会发的
   `(方法, 路径)` 对，与**线上服务器**注册表/实测响应逐条比对 —— 而不是我猜它调什么。
   - 关键教训：第一轮我用 GET 盲扫，误报 9 个 404（`/favorite`、`/pack-*`、`/check-update`、
     `/hotupdate/status` 都是 **POST-only**）。代码注释早就写过"GET 会 404，曾长期被前端双源兜底
     掩盖" —— 所以**必须按客户端真实方法**比对。
2. **用真老产物测老客户端**：不靠"看代码推测 0.8.1 行为"，而是下载 Gitee 上 v0.8.1 的 APK，
   抽出它自己的 `bundle.js` 再抽调用面。
3. **真实流量 + 数据核对**：日志里的 5xx/404 是"静默失败"的直接证据；老账号数据文件是
   "没丢数据"的直接证据。

## 三、属"设计如此"的 404/403（不是 bug，别再当问题修）

| 端点 | 行为 | 原因 |
|---|---|---|
| `/shutdown` | 404 | 本地引擎关机端点，服务器版不需要（老客户端只在本地模式调） |
| `/hotupdate/*` | GET 404 / POST 403「服务器版不提供热更新」 | 热更只服务端侧覆盖层；`routes_hotupdate._deny()` 明确拒绝，且"避免任意登录用户触发联网下载" |
| `/export-diagnostics` | 403 | 诊断包只在用户自己设备上生成（本轮新加的设计） |
| `/metrics`、`/requests` | 403 | 多用户共享计数器/缓冲，不下发给单用户 |
| `/voice/status` | 200 但 `engine_ok=false` | 语音引擎只接了安卓 Kotlin 侧，服务器无引擎 |
| `/auth/state` | 403「服务器版请用 /auth/me」 | 服务器版鉴权态查询走 `/auth/me` |

## 四、未覆盖的部分（如实标注，别当成"已测"）

1. **没有跑真实 UI 端到端**：本轮只验了 API 面与契约，**没有**用无头浏览器把 0.9.0 前端在
   服务器模式下点一遍（登录 → 首页 → 同步 → 各面板）。所以"前端在服务器模式下的渲染/交互"
   仍未验证。
2. **没有做语义级字段比对**：契约比对只能发现"端点不存在"，发现不了"字段改名/结构变化"。
   老客户端若依赖某个被改名的字段，仍可能静默失效。
3. **没有真机验证**：手机被带走，本轮全部从 PC 侧完成。
4. **老账号数据只看了存在性**：没有解析内容（也不该把用户数据拉到开发机，规范 §6.1）。

## 六、遗留风险与建议

1. **建议补一条自动化**：把"客户端 (方法,路径) ⊂ 线上服务器注册表"做成发布前门禁
   （放到 `tools/` 里，与 `check_apk_frontend.py` 并列）。这次的 9 个误报说明**必须带方法**，
   否则门禁会天天假警报。
2. **语义级兼容仍需人工抽检**：`/config`（providers 迁移）、`/sync/*`、`/modes` 的字段结构
   是历史踩坑区，发版前建议对这三个端点做一次"老客户端期望字段 vs 新服务器返回字段"的核对。
3. **老客户端迟早要退役**：本次老客户端能跑，但它拿到的是 **0.9.0 的前端**（前端由服务器下发），
   而老壳/老缓存能否吃下新前端，属于第四节的未覆盖项。
