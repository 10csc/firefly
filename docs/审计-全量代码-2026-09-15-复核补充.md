## 三、新发现的两处残留

### 残留 1：`local_origin_ok`「三标记全缺 → 放行」可被主动撕标绕过

`app/shared_http.py:119-120`

```python
if not origin and not sfs and not ref:
    return True   # 非浏览器客户端（urllib 探测/安装器/白盒测试）
```

这条回退是为了兼容 urllib/curl/测试，但它同时给了攻击者一条**主动撕掉来源标记**的路径：

```html
<img src="http://127.0.0.1:8765/shutdown" referrerpolicy="no-referrer">
```

- `<img>` 属 no-cors，**不发 Origin**；
- 攻击者显式 `referrerpolicy="no-referrer"` → **不发 Referer**；
- 若浏览器**不支持 `Sec-Fetch-Site`**（Safari < 16.4、Firefox < 90）→ 三标记全缺 → `return True` → **进程被杀**。

现代 Chrome/Firefox/Safari 16.4+ 会发 `Sec-Fetch-Site: cross-site`，会被拦住；所以这是**窄窗口**（老浏览器 + 攻击者主动撕标），但确实存在。

**建议（低成本、不破坏现有兼容性）**：三标记全缺时，再补一条 UA 判据——

```python
ua = (handler.headers.get("User-Agent") or "")
if re.search(r"Mozilla|Chrome|Safari|Firefox|Edg/", ua):
    return False   # 三标记全缺却带浏览器 UA = 主动撕标，拒
return True        # urllib / curl / 测试脚本
```

urllib 的 UA 是 `Python-urllib/3.x`、curl 是 `curl/x.y`，都不匹配；59 个测试无一受影响。

### 残留 2：`save_config` 未检查 `atomic_write_json` 返回值（B1 只修了一半）

`app/core/config.py:423`

```python
from modules.storage import atomic_write_json
atomic_write_json(_paths.CONFIG_FILE, {...})   # 返回 bool，未检查
```

`atomic_write_json` 按 storage 约定**失败只 logger.warning 不抛**（`app/modules/storage.py:53-59`）。于是：写盘失败（磁盘满/权限）时 `save_config()` 静默返回，调用方照常回 `{"ok": true}` → **用户在设置页改完 Key 看到"保存成功"，实际没落盘**，下次启动又回到旧值。

这正是 B2 那条教训（检查原子写返回值），B2/B5 都改了，**B1 的写路径漏了**。

**建议**：`save_config()` 改为返回 bool，路由层按返回值决定回 `ok` 还是报错。顺带：本地分支仍无写锁（C14，你已列在遗留里），两个请求并发保存会互相覆盖字段。
