# 设定纠错助手设计（v1.2）

> 状态：**已按本设计实施**（后端 + 前端 + 测试 + 纯代码引导教程完成；v1.2 新增全屏页状态指示、当前模式最近聊天记录、去重清空入口并修复 AI 回复需重进页面才刷新的 bug；待服务器部署）。
> 目标：替代旧「消息 👍/👎 反馈 + harness_rules 优化器」路线。用户遇到“回复不合理/设定不对”时，用一句话描述问题，AI 以聊天 + 选择题的方式与用户**多轮对齐**，用户点「开始修改」后 AI 生成修改清单（不生效），用户看 diff 点「应用」后才原子写入，可一键回滚。
> 核心原则：**AI 只提案，人批准，系统生效；核心文件只纠正不追加；不新建任何文件；AI 逻辑永远跑在 Python 后端，前端只做 UI。**

---

## 一、为什么这样做

1. 用户来用这个产品，多数时候是发现“她说的和设定不一致”，但用户不知道问题在哪个文件，也不该知道。
2. 旧反馈页让用户逐条 👍/👎，把“归因工作”推给了用户，门槛高、信噪比低。
3. 核心设定错了不能靠追加规则压制——规则越堆越多，冲突和内耗会降低角色一致性。正确做法是**原位纠正**。
4. 世界知识/关键记忆体量太大，AI 直接改知识库不可靠；用户已拍板**不新建文件**。因此世界知识类问题落进现有 `用户设定.md`（分析器和回复器都已加载，且与核心设定同等权威），个人记忆/约定类问题落进 `memory.md` 或 `手账.md`。
5. 沿用项目已确立的安全哲学：AI 永不直接生效，修改必须经人批准 + 自动备份 + 可回滚。

## 二、允许 AI 修改的文件（共 6 个，不新增）

| 文件 | 路径（`{mode}`=story/haruno） | 语义 | 当前注入点 | 允许的操作 |
|------|------|------|------|------|
| `core.md` | `user_data/{mode}/character/core.md` | 她是谁：身份/身体/经历/价值观 | analyzer + polisher | 仅 `replace`（原位纠正） |
| `identity.md` | `user_data/{mode}/character/identity.md` | 她与谁：关系/习惯/认知边界 | analyzer + polisher | 仅 `replace` |
| `sms_samples.md` | `user_data/{mode}/character/sms_samples.md` | 她怎么说：节奏/样例/避免项 | polisher | 仅 `replace` |
| `用户设定.md` | `user_data/{mode}/character/用户设定.md` | 用户补充的剧情/世界设定（与核心同等权威） | analyzer + polisher | `replace` / `append` |
| `memory.md` | `user_data/{mode}/data/memory.md` | 跨会话记忆（头部概括 + 承诺/偏好/事件） | polisher（头部）+ proactive | `replace` / `append` |
| `手账.md` | `user_data/{mode}/journal/手账.md` | 流萤第一人称的重要对话与约定 | polisher + proactive | `replace` / `append` |

### 归因规则（AI 必须遵守，写进 prompt）

| 用户抱怨的类型 | 落点 |
|------|------|
| 官方人设/经历/价值观错了（如“她还在医疗舱”） | `core.md` |
| 人际关系/习惯/认知边界错了 | `identity.md` |
| 说话方式/短信节奏/样例错了 | `sms_samples.md` |
| 世界知识、剧情事实、用户自己的剧情补充 | `用户设定.md`（注明这是用户补充，不硬改官方知识库） |
| 她记错了真实发生过的对话/约定 | `memory.md` 或 `手账.md`（优先手账=约定，memory=事实） |
| 描述不清，无法定位 | 继续问，不急着改 |
| 不需要改，或该问题应由对话本身解决 | 明确告诉用户“不用改” + 原因 |

## 三、两阶段交互流程（用户新要求）

### 阶段一：对齐（聊天 + 选择题，AI 不生成修改）

```
用户在首页卡片输入问题，例如：
“她总说自己在医疗舱，但设定里已经恢复得不错、能开机甲了”

→ AI 回复一段人话 + 0~4 个选择题（或开放问题）
  例：“我看了 core.md，恢复状态确实已经更新。你说的这种情况，
       是最近聊天里出现的吗？[最近聊天出现 / 不是，是我听别人说的 / 我需要补充]”
→ 用户点选项或自由输入
→ 继续追问，直到信息足够或达到上限
→ 最多追问 6 轮；仍不明确时，AI 停止追问并给出一份“我的理解”摘要，
   告诉用户“你可以直接开始修改，我会按这个理解生成，也可以再补充”
→ stage=ready：前端亮起【开始修改】按钮
```

### 阶段二：生成清单（不生效）→ 用户应用（才生效）

```
用户点【开始修改】
→ AI 读取对齐对话 + 6 个文件 + 最近对话（可选），生成 proposal
→ 静态校验 → pending.json
→ 前端展示：
   诊断一句话 + 每个文件的 before → after diff + 每处修改的人话理由
   【应用修改】（主按钮）【放弃】
→ 用户仍可继续补充：“第二条先别改，她喜欢橡木蛋糕卷那段保留”
   → 该消息追加进对齐对话，AI 重新生成 proposal（仍然不生效）
→ 用户点【应用修改】
   → 重新校验（防 stale）→ 备份 → 原子写 → 清缓存 → 审计
→ 应用/放弃后清空当前对齐对话与 pending，修正历史保留；新问题重新开始
```

### 状态机

```
aligning → ready → proposal → applied
             ↑        ↑
             └─用户补充可退回重生成
任何阶段可【放弃并重新开始】（清空 conversation + pending，不动历史版本）
```

## 四、后端 API（新增）

> 全部按 `mode` + 服务器版用户上下文隔离；本地版行为不变。

| 端点 | 方法 | 入参 | 返回 | 说明 |
|------|------|------|------|------|
| `/setting-fix/status` | GET | `?mode=` | `{ok, stage, messages[], proposal?, active_version, history[]}` | 恢复/初始化卡片状态 |
| `/setting-fix/message` | POST | `{mode, text}` | `{ok, stage, text, options[], can_start}` | 对齐阶段对话；`text` 可为自由文本或选项文本 |
| `/setting-fix/start` | POST | `{mode}` | `{ok, stage:"proposal", diagnosis, changes[]}` | 从对齐对话生成修改清单并落 pending |
| `/setting-fix/apply` | POST | `{mode, session_id?}` | `{ok, version, applied[]}` | 用户批准后应用 |
| `/setting-fix/dismiss` | POST | `{mode}` | `{ok}` | 放弃当前方案 |
| `/setting-fix/rollback` | POST | `{mode}` | `{ok, version}` | 回滚到上一版本 |
| `/setting-fix/reset` | POST | `{mode}` | `{ok}` | 清空当前对话与 pending（历史保留） |

- 对齐全过程不是调现有 `/chat`（那是流萤本人），而是独立的“设定诊断助手”小 Agent，共用 `llm_base / api_client / 错误分类` 基建。
- `text` 上限 1000 字；空/非法拒绝。
- 同一 `(mode, 用户)` 同时只存在一个对齐会话。
- 服务器版 relay 模式下，本功能的 LLM 调用由现有 relay 客户端统一承载；分析请求只注入 6 个文件与对齐对话，不注入全量知识库。

### 修改项 JSON 结构（LLM 输出契约）

```json
{
  "kind": "proposal",
  "diagnosis": "人话总结：她说的是……实际应是……",
  "changes": [
    {
      "file": "core.md",
      "op": "replace",
      "old": "原文片段（必须与当前文件逐字一致，且全局唯一）",
      "new": "替换后的文本",
      "reason": "为什么改，一句话"
    }
  ]
}
```

- `op=append` 时额外给 `anchor`（可选）：追加到该锚点所在小节末尾；不填则按文件默认位置追加（见下）。
- `old` 必须**唯一精确匹配**；不唯一直接判失败，AI 收到校验错误后允许重试一次，要求给更长上下文。
- 一次 proposal 最多 4 个 change；同一文件最多 2 个 change。
- 对齐阶段 LLM 输出为 `{stage, text, options[]}`，不属于 proposal。

## 五、六个文件的默认追加位置（append 语义）

| 文件 | 默认追加位置 |
|------|------|
| `用户设定.md` | 文件末尾 |
| `memory.md` | 对应分节（`## 承诺` / `## 偏好` / `## 事件`）末尾；AI 必须在 new 中自带 `- [日期] 内容` 格式 |
| `手账.md` | 对应栏目（“聊了什么” / “想做的事/约定”）末尾，单条不超过 1000 字符总长 |

- `core.md / identity.md / sms_samples.md`：**禁止 append**。确有“新增事实”需求时，必须通过 replace 扩写既有条目或小节——保证核心文件永远处于“纠正后的一致版本”，而不是增量补丁。

## 六、静态校验（代码层，失败即拒）

1. **文件白名单**：只允许上述 6 个文件名，路径由服务端公式生成，绝不接受前端传路径。
2. **锚点校验**：`replace` 的 `old` 必须逐字存在且唯一；`append` 的 `anchor` 若给了必须存在。
3. **结构守卫**：改完后的文件必须保留既有顶级标题与关键分节：
   - story `core.md`：`# 第一层：核心上下文`
   - haruno `core.md`：`# 春日手信 · 核心设定`
   - `identity.md`：`# 次级核心`
   - `sms_samples.md`：`# 流萤短信风格速查`
   - `memory.md`：`# 核心记忆头部` 与 `# 事实与任务`
   - `手账.md`：`# 流萤的手账` 与两个 `##` 栏目标题
4. **预算**：单 change 的 `new` ≤ 2000 字；全部 `new` 合计 ≤ 4000 字；改后文件 ≤ 50KB。
5. **元指令/注入防护**（沿用旧 prompt_gate 的有效思路，重写进新校验器）：
   - 禁止 `忽略以上/无视/你是AI/你必须/system:/[MSG]/[SYSTEM]` 等对模型二次编程的措辞；
   - 禁止 URL、代码围栏、控制字符；
   - `new` 里引用“说过/约定/记得”类内容时，reason 必须说明依据（用户反馈原话或文件原文）。
6. **冲突检查**：关键词级防“修 A 坏 B”。例如 new 含“失熵症已痊愈”而当前文件仍含“不可逆”→ 拒绝；含“能再次入梦”而 core 含“无法再进入”→ 拒绝。规则表随版本维护。
7. **去重**：append 的新条目若已逐字存在于目标文件 → 拒绝（防重复记忆/重复设定）。
8. **pending 唯一**：同 `(mode, 用户)` 同时只允许一个 pending；已有 pending 时必须先 apply、dismiss 或 reset。

## 七、本地运行还是服务器运行？（研究结论）

### 7.1 结论：数据在哪，Agent 就跑在哪，AI 逻辑只在共享 Python 后端

| 版本 | 设定纠错 Agent 运行位置 | LLM Key | 数据流向 |
|------|------|------|------|
| Windows 本地版 | 本机 `app/server.py`（Python） | 用户本机 Key 直连 DeepSeek | 本地 6 文件 → DeepSeek 分析 → 写回本地（与现有聊天一致） |
| 安卓本地模式 | 手机内嵌 Chaquopy Python | 用户本机 Key 直连 DeepSeek | 同上，App 私有目录 |
| 服务器模式 | 服务器 `server/server_app.py`（Python） | 用户 Key 走 relay / 托管额度走 proxy | 服务器上该账号的 6 文件 → LLM → 写回该账号目录 |
| 浏览器 / WebView | **不跑 AI 逻辑** | — | 只做 UI：收发消息、渲染选项与 diff、发起 apply |

**不在浏览器 JS 里实现**。理由：浏览器拿不到完整文件的权威版本，备份/原子写/缓存清理都要服务端做；在 JS 里重复实现会再次制造“前端三副本逻辑漂移”，违背 0.8.0 收敛前端为薄 UI 的方向。

### 7.2 维度对比

| 维度 | 本地后端（本地模式） | 服务器后端（服务器模式） | 浏览器 JS 直连（被否） |
|------|------|------|------|
| 六文件位置 | 就在本地 | 就在服务器 | 只能经 API 取，存在副本不同步风险 |
| 隐私增量 | 无：与现有聊天一致 | 无：与现有服务器模式一致 | 会把全部设定内容拉进浏览器内存，无收益 |
| Key 归属 | 用户本机 Key | relay 不落服务器 / 托管额度 | 用户 Key，但绕过现有 relay 审计 |
| 多轮会话状态 | `user_data/{mode}/.setting_fix/` | `user_data/{user_id}/{mode}/.setting_fix/` | localStorage，清缓存即丢 |
| 原子写/备份/回滚 | 本地 Python 完整实现 | 同一套 Python 模块复用 | JS 无法安全做文件事务 |
| 网络延迟 | 直连 DeepSeek | 服务器 + relay（与聊天同链路） | 直连 DeepSeek，但 UI 与文件操作还是要回服务器 |
| 维护成本 | 一套 `app/modules` 代码 | **同一套** | 三处前端逻辑，漂移风险高 |

### 7.3 业内同型产品的做法（外部参考）

- [SillyTavern 中文指南](https://raw.githubusercontent.com/sillytavern-zh/sillytavern-chinese-guide/main/data/markdown/what-is-sillytavern.md) 的形态是本地程序 + 自选 API：设定、角色卡、世界书都在本地，AI 服务只负责推理——本项目的本地模式与之一致。
- [开源 AI 助手 Local-First 架构分析](https://developer.baidu.com/article/detail.html?id=5888952) 强调状态与数据本地持有、服务端只做计算/推理或完全由用户 API 驱动；多轮状态落盘在本地是 local-first 的常规做法。
- [本地模型 vs 云端 API 的角色扮演选择](https://blog.meganova.ai/the-best-ai-models-for-roleplay-and-storytelling-local-llms-vs-cloud-apis/) 的共性结论：决定本地/云的不是“模型能力强弱”，而是**数据归属、Key 归属与断网可用性**——本项目两个模式的数据归属不同，所以 Agent 运行位置自然不同。

### 7.4 落地含义

1. 新增模块放 `app/modules/`（本地版与服务器版天然共用，安卓构建 `syncBackend` 自动带过去）。
2. 服务器版零额外部署改造：多用户隔离沿用 `contextvars` 用户上下文，relay/proxy 沿用 `get_client()`。
3. 前端三副本只同步一份 UI，不含任何修正逻辑。
4. 若将来要做“云同步设定修正”，直接复用同一套端点，只换数据目录上下文，不需要新架构。

## 八、版本、备份与回滚

目录：`user_data/{mode}/.setting_fix/`（服务器版在 `user_data/{user_id}/{mode}/` 下）

```
.setting_fix/
├── conversation.jsonl   # 阶段一对齐对话（多轮，带 stage 与选项，重启可恢复）
├── pending.json         # 阶段二待批准方案（complaint、诊断、changes、gate 结果、时间）
├── manifest.json        # {version, active, history:[{v,time,action}]}
├── audit.jsonl          # 每次 apply/rollback/dismiss/reset 留痕
└── backups/
    └── v{N}/            # 该次应用前被改文件的完整快照（保留相对路径）
```

- 首次 apply：把当前 6 个文件中被改的那几个完整备份为 `v0`，应用后成为 `v1`。
- 每次 apply：备份上一状态为 `vN`，新状态版本 `vN+1`。
- rollback：恢复到 `vN-1`；不删除历史版本（保留审计）。
- 写入顺序：全部先写 `.tmp` → 全部成功后逐个 `replace`；若中途失败，用刚生成的 backups 尽力恢复，并把失败写 audit。
- `clear_history` 不清除 `.setting_fix/`（设定修正历史独立于聊天历史）。
- 导出备份 `GET /export-data` 会包含 `.setting_fix/`（可随数据整体迁移）。

## 九、LLM 分析器设计（`setting_fix`）

- 两个 Prompt 角色：
  1. **对齐 Agent**：只提问、复述理解、给选项；**不生成修改**。输出 `{stage, text, options[]}`。
  2. **提案 Agent**：基于完整对齐对话 + 6 文件生成 proposal。输出第三节的修改 JSON。
- 模型：默认 `deepseek-v4-flash`，思考档位 `high`（与 analyzer/polisher 默认一致）；先用 `polisher_model/polisher_effort` 配置驱动，不新增设置面板字段。
- 对齐 Agent 约束：
  - 一次只问一个问题，选项 ≤4，且允许自由输入；
  - 不重复已问过的问题；
  - 最多追问 6 轮；到上限给“我的理解”摘要并置 `ready`；
  - 用户说“没问题/对/就这样” → 立即 `ready`。
- 提案 Agent 约束：
  1. 你只提案，不生效；
  2. 官方设定错 → 改 core/identity/sms_samples；世界知识/用户剧情补充 → 用户设定.md；记忆约定 → memory.md/手账.md；
  3. core/identity/sms_samples 禁止 append，只准 replace；
  4. `old` 必须从给定文件里逐字复制，不得凭记忆改写；
  5. 一次最多 4 处改动；拿不准就不改，输出 no_fix 或把疑问带回对齐阶段；
  6. 不要为了“显得有产出”而改风格/个人偏好。
- 提案校验失败时，把校验错误回喂提案模型重试**一次**；仍失败返回友好错误并回到 `aligning`，不落 pending。

## 十四、风险与取舍（明确记录）

1. **AI 可能改坏核心设定**：缓解 = 提案制 + 多轮对齐 + 用户看 diff + 自动备份回滚 + 结构守卫 + 锚点唯一 + 冲突检查。不接受的残余风险：用户批准了错误修改但没发现。
2. **世界知识纠正只能进 `用户设定.md`**：这是“不新建文件”决策的代价；它依赖现有“与核心设定同等权威”的注入位置。若未来发现覆盖力不足，再讨论是否回退到“补充文件”方案。
3. **多轮对齐会增加用户操作步数**：用“选择题为主、自由输入为辅、最多 6 轮、随时可直接开始”控制成本；不追求 AI 无限追问。
4. **对齐会话不经过流萤本人**：设定纠错助手是独立小 Agent，避免“流萤聊设定”的角色混淆与 OOC。
5. **分析只读 6 个文件，不读全量知识库**：成本低、快；AI 对“官方知识对不对”的判断依赖用户描述，必要时继续追问而不是硬改。
6. **服务器 relay 模式**：分析与对齐请求走 relay，首次可能稍慢；后续与聊天共享机制，不新增架构。
