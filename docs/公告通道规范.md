# 公告 / 更新说明通道 · 规范

> **这是什么**：服务端向每个客户端**下发公告与更新说明**的通道 —— 与热更新共用同一个
> 信任根（RSA 签名）与同一套更新源，但**风险面完全不同**：公告不是代码。
> **为什么要有它**：热更新只能修 web 层代码，"这次修了什么、为什么修、用户要注意什么"
> 得有个能立刻送到每台设备的地方。APK 里的公告是**静态 HTML**，改服务端用户看不见；
> 已发布的旧客户端更是连"公告"这个概念都没有。
> **代码**：端侧 `app/notice.py` + `app/routes_notice.py` + `app/static/js/notice.js`；
> 网关 `server/download_server.py::_serve_notice`；产出/发布 `tools/build_notice.py`、
> `tools/publish_notice.py`；内容源 `notice_src/`。

---

## 一、与热更新的关系（一张表说清）

| 维度 | 热更新（`/hotupdate`） | 公告（`/notice`） |
|---|---|---|
| 传的东西 | zip → **覆盖端侧代码** | 结构化 JSON + 图片（**不执行任何东西**） |
| 信任根 | RSA-2048 / SHA-256 签名 | **同一个密钥**、同一个验签实现 |
| 更新源 | 热更的 `url_roots` | **由热更源翻译而来**（见 §三） |
| 防回滚 | `serial` 单调 + `min_safe_serial`/`revoked_serials` | 同左（语义一致，便于记忆） |
| 失败后果 | 可能白屏 → 安全模式 + 自动回退 | 少看一条公告 → **静态兜底照常显示** |
| 服务器版 | **403 禁用**（改端侧文件对服务器无意义，且是联网下载口子） | **两端都开**（读下发内容 + 端侧缓存） |
| 门禁 | 第 5 门禁 `check_hotupdate.py` | 同一门禁（新增「公告通道」小节） |

**一句话**：能复用的（密钥、源配置、serial 语义、门禁）全部复用；**不能复用的（风险模型）
明确分开** —— 所以公告**不接受 HTML**（见 §四）。

## 二、信任与降级模型

```
        ┌──────────── 端侧（手机 / PC）────────────┐
源 ① 网关 /notice/latest ──► 索引（未签名，只是提示"有新东西"）
   /notice/notice-N.json ──► 签名清单（manifest_b64 + sig）
                              │  验签：Kotlin（安卓）/ 标准库自实现（PC）
                              ▼
                          结构校验（§五）→ 版本定向（§六）→ 落缓存
   /notice/img-*  ─────────► 图片：**独立 URL**、逐张 sha256 对账后才落盘
        └───────────────────────────────────────────┘
源 ② Gitee release 资产（同一批扁平文件）—— 主源失败自动降级
```

降级三级，**任何一级都不影响用户用 App**：

1. **联网失败** → 用缓存（localStorage 镜像 + 端侧 `state.json`）；
2. **无缓存/首次安装** → 只显示 APK 内置的使用指南（`index.html` 的 `#notice-static`）；
3. **验签/格式/图片校验失败** → 整份丢弃（**绝不"降级成信任"**），保留上一份可信缓存。

## 三、更新源：一个配置，两条通道

公告源不是独立配置，而是从热更源**翻译**出来的（`app/notice.py::_to_notice_root`）：

| 热更源形态 | 公告源 | 理由 |
|---|---|---|
| `http://<host>:8787/hotupdate` | `http://<host>:8787/notice` | 自己的网关：换掉最后一段路径 |
| `http://<host>:8787`（无路径） | `http://<host>:8787/notice` | 必须按 URL 结构解析，**不能字符串 rpartition**（`//` 会被当分隔符 → 翻成 `http://notice`） |
| `https://gitee.com/o/r/releases/download/v{base}` | **原样** | release 资产目录是扁平的，公告文件与补丁放同一目录 |

用户/运维只需要维护 **一处** `url_roots`（`hotupdate/state.json`），两条通道同时生效。
**新增源形态时必须同时写这个函数的用例**（`tests/test_notice.py` A 组）。

## 四、安全线：公告的敌人是"注入"，不是"执行"

热更的敌人是"跑恶意代码"，所以那里的规则是"整包要么全信要么全丢"。
公告**不执行任何东西**，所以真正的风险是 **XSS / 内容投毒 / 资源耗尽**：

1. **不接受 HTML**：清单只允许 `p / h / li / tip / img` 五种块，其余一律丢弃；
2. **端侧只用 `textContent` 写文本**（`js/notice.js` 里没有任何 `innerHTML` 参与服务端数据）
   —— 即使签名密钥泄露、服务端被投毒，也**注入不进来**，这是结构保证而不是编码纪律；
3. **XMLHttpRequest 之外的图片**：图片走 `<img src>`，所以端点必须公开可读
   （`img` 标签不带 `Authorization`）——它读的是 `notice_root()`（与 `user_data` 平级、
   全站一份、不含任何用户数据），且**端侧先按清单 sha256 校验才落盘**；
4. **所有上限都在**（`app/notice.py` 顶部的常量表）：清单 256KB / 40 条 / 单条 120 块 /
   正文 4000 字 / 单条 6 图 / 单图 1.5MB / 总图 8MB；
5. **索引与清单的 `serial` 必须一致**（否则"索引说 3、清单说 2"可被用来回放旧公告）。

## 五、结构校验（审查约束）

| 阶段 | 做什么 | 不合法的处置 |
|---|---|---|
| 验签前 | 清单字节 ≤ 256KB | 丢弃（`validate` 抛异常） |
| 验签后 | `schema == 1`；`entries` 是数组 | 抛异常 → 保留旧缓存 |
| 逐条目 | `id` 命中 `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`、`title` 非空 | 丢该条 + 记日志（**一条坏条目不毁整份公告**） |
| 逐块 | 类型在白名单内；文本非空 | 丢该块 |
| 逐块（img） | 名字合法、sha256 是 64 位十六进制、size ∈ (0, 1.5MB] | 丢该块 |
| 图片下载后 | sha256 + size 与清单一致 | 丢**该图**（图块一并消失，宁可不显示也不显示裂图） |

**"丢条目/丢块"而不是"整份拒绝"是有意的**：公告是运营内容，一条写错不该让所有人的
公告全黑。反过来，**清单级**（schema/大小/serial/签名）的问题一律整份拒绝。

## 六、版本定向

条目可带 `min_app_version` / `max_app_version`（半开区间：`min ≤ 本端 < max`，空 = 不限）。
端侧在 `validate()` 里过滤，**过滤发生在缓存之前** —— 定向掉的条目不会占用户的已读位。

用途：给 0.9.0 及以上写的"新功能说明"不要打扰还在 0.8.1 的用户；
需要旧版用户看到的"请升级"提示则反过来写。**默认留空 = 所有版本都看**。

## 七、已读与撤回

- **已读**：`POST /notice/action {action:"read", ids:[...]}`（或 `all:true`）。
  面板打开 1.5 秒后自动标记 —— 延迟是为了让"新"标记真的被眼睛扫到。
- **撤回一条公告**：改 `notice_src/source.json` 去掉它，再发一版。
  serial 递增 → 端侧重拉 → 条目消失；`read_ids` 里那条**同时被清掉**（不留死 id）。
- **撤回一个坏 serial**：新清单的 `revoked_serials` 填上旧号 → 端侧清掉那份缓存。

## 八、发布流程（不可跳步）

```bash
# 1. 改内容（人写）
notepad notice_src/source.json          # 图片放 notice_src/images/
python tools/build_notice.py --check    # 只审查 + 报告与上次的差异
python tools/build_notice.py --note "0.9.0 更新说明"   # serial+1、打包、签名、自检
# 2. 门禁（与热更同一个门禁，会验签 + 用**客户端自己的校验器**再验一遍）
python tools/check_hotupdate.py
# 3. 发布（服务器主源 + Gitee 兜底），并逐 URL 拉回来比 sha256
python tools/publish_notice.py --serial 1
```

**铁律**：
- `serial` **只增**、产物**不可覆盖**（文件名带 serial，内容不可变 → 客户端可长缓存）；
- 内容没变时 `build_notice.py` **拒绝白出一版**（serial 是"发布事件"的编号）；
- 图片必须**与清单同批上传**，否则端侧会把对应图块丢掉（不是错误，是设计）；
- **Gitee 不新建 release**：公告文件挂到已有的整包 release 资产上
  （新建 release 会让"取 id 最大 tag"的整包兜底取到错 tag → APK 下载 404）。

## 九、门禁与测试

- **门禁**（`tools/check_hotupdate.py`，与热更共用）：
  公钥两份副本逐字节一致 + Python 侧能解析出 RSA 参数 + 公告清单验签通过 +
  **客户端校验器接受** + 引用图片齐备且 sha256 匹配。
- **回归**（`tests/test_notice.py`，43 项，全离线）：源翻译 / 验签拒绝 / 结构校验 /
  版本定向 / 图片对账 / 缓存与降级 / kill switch 与回放防护 / 已读与撤回 / payload 形状。
- **验签实现一致性**（`tests/test_hotupdate_verify.py`，20 项）：固定向量正例 +
  10 种篡改必须全拒 + 与 `canonical_bytes` 口径一致 + 注入优先级与异常兜底。

## 十、已知边界（写清楚，别当成 bug）

1. **PC 端验签是自实现的**（`app/hotupdate/verify.py::_py_verify`）：安卓走 Kotlin。
   两份公钥的一致性由门禁钉死；实现在 `tests/test_hotupdate_verify.py` 用固定向量钉死。
   **签名（带私钥）绝不自己写** —— 只在发布机用 openssl。
2. **公告不带已读同步**：已读状态在端侧（localStorage + `state.json`），换设备会重新提示。
   公告不是消息，重新看到一次的成本可以接受。
3. **图片没有端侧清理策略**：当前只在覆盖时按 sha256 命中跳过。
   图总量受 `MAX_TOTAL_IMG_BYTES` 与"每条 6 张"约束，实际不会失控；
   若将来公告图变多，需要在 `check()` 里加"删除不再被引用的图"。
4. **旧客户端（≤0.8.1）收不到任何公告**：它们既没有公告通道也没有热更新，
   唯一触达方式是发一个 **versionCode 更高**的整包。
