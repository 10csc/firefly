# 开发规范 · 扩展接入协议（v1）

> 配套 `docs/开发规范.md` §3/§4/§5。实现任何新工具（语音/游戏/识图/其他）前先读本文件。
> 本协议未覆盖的问题：停下来问，不自行扩写协议。

## 1. 目录与命名

- 代码：`app/tools/<tool_id>/`（多文件）或 `app/tools/<tool_id>.py`（单文件）。
- `tool_id` 必须匹配 `^[a-z][a-z0-9_]{1,31}$`，且不与现有模块/路径冲突。
- 工具设计文档：`docs/工具/<tool_id>.md`（≤200 行）；简单工具可只写在模块 docstring。

## 2. 工具清单 TOOL_INFO（注册必填）

```python
TOOL_INFO = {
    "id": "tts",                 # 唯一 id，注册表键
    "name": "语音朗读",           # 日志/监控显示名
    "version": "0.1.0",
    "message_types": ["voice"],   # 该工具会产出的消息 type（决定渲染/回灌）
    "modes": ["story", "haruno"], # 支持的模式；空列表 = 全模式
    "max_per_turn": 1,            # 每轮最多调用次数（游戏=1，TTS 按方案定）
    "needs_llm": False,           # 执行时是否要 LLM；默认必须 False
    "heavy": False,               # 重型（模型加载/大计算）工具，调度前先 available()
}
```

- 字段只增不减；任何字段语义改动视为协议修订，需用户批准。

## 3. 注册表与生命周期

- 统一入口：`get_tool(tool_id)` / `list_tools(mode)` / `tool_available(tool_id, mode)`。
- 调度器只能通过入口取工具，不允许 import 具体工具后自行调用。
- 生命周期：`available()` 检查（配置启用 + 模式支持 + 资源就绪）→ `dispatch()` 执行。
- 重型工具资源未就绪时 `available()=False`，调度器直接跳过，不阻塞聊天。

## 4. 输入输出契约

```python
@dataclass
class ToolInput:
    user_input: str
    reply_texts: list[str]      # 流萤本轮文本回复
    recent_history: list[dict]  # 与 OrganizerInput.recent_history 同源
    mode: str
    client = None               # 仅 needs_llm=True 且获批准时使用，必须走 llm_base 记账

@dataclass
class ToolResult:
    message_type: str           # 必须在 TOOL_INFO.message_types 中
    render: dict                # 前端渲染字段（自包含、可 JSON 化、无大对象）
    ctx: str                    # 上下文摘要，≤100 字，必填非空
    error: str = ""             # 非空 = 该结果作废，只记日志
```

规则：

- 每个 dispatch 最多返回 2 条 ToolResult；需要更多表现时复用 text/narration 并在方案中说明。
- `error` 非空时 render/ctx 必须为空，按失败计数，聊天继续。
- dispatch 内部必须遵守模块铁律四段：审查 params → 执行 → 验证输出 → 返回。

## 5. 调度器（organizer）扩展契约

现状：

- story：`{"sticker": "label原文" | "无"}`
- haruno：`{"narrations": [{"text","style","after"}]}`

扩展后允许并列新增（旧字段继续有效）：

```json
{"sticker": "比心", "tools": [{"id": "tts", "params": {"text": "……"}}]}
```

- 解析顺序：parse_json → sticker/narrations 旧逻辑 → tools 列表。
- 逐条校验：id 在注册表？`available()`？本轮到次数上限？params 交给工具自身审查。
- 任一条非法：只丢弃该条（warning 日志 + 计数器），继续执行其余工具。
- 执行顺序 = tools 数组声明顺序；一条失败不影响下一条。
- 任何情况下 polisher 的文本回复照常返回。

## 6. 结果进历史 / 上下文契约

### 6.1 三件套

每个结果同时产出：渲染记录（前端）、jsonl 记录（持久化）、ctx 摘要（上下文）。

jsonl 记录示例：

```json
{"seq": 101, "time": "2026-08-16 23:10:05", "who": "firefly",
 "type": "voice", "src": "data/voice/v101.webm", "ctx": "语音念了：今天早点休息。"}
```

规则：

- `type` 必须先注册（= 某工具 `TOOL_INFO.message_types` 成员）。
- 每行必须自包含；只存标量/短文本/路径。
- 音频/图片/存档等二进制或大文件：写入 `user_data/{mode}/data/` 对应子目录，jsonl 只记相对路径。
- `ctx` 必填 ≤100 字；后端 `append_message` 从硬编码 type 白名单改为按注册表校验（旧 text/sticker/narration 三种保留硬兼容）。

### 6.2 上下文（ContextManager）

- 每结果一条：`ctx.add_action(<工具显示名>, <ctx>)` → system 消息 `[行为: 工具名] <ctx>`。
- 同一轮多条结果按顺序各写一条。
- 每轮工具 ctx 总量 ≤300 字；超限按结果顺序截断并打点，完整内容看外置文件。
- 已有先例：`[行为: 表情包] 比心`、`[行为: 旁白] ...`。

### 6.3 回灌（hydrate_context）

- 旧 text/sticker/narration 分支原样保留。
- 新 type 走通用分支：读 `ctx` 字段，`ctx.add_action` 同一条；无 ctx 的异常记录跳过 + 日志。
- 禁止在 hydrate 里为具体工具写 if 分支。

### 6.4 前端

- 注册了新 type，就同时提供渲染分支；否则走统一 fallback：有 ctx 显示小字说明，无 ctx 忽略；任何路径禁止 throw。
- 现有 `renderMessages` / `renderHistoryMessage` 按 type 分派；新增分支后必须同步三个前端副本（`tools/sync_frontends.py`）。

## 7. 语音工具补充协议（TTS）

- 目标：超轻量本地模型/方案。引入前先报：模型名+版本、体积、推理延迟、内存、Android 兼容性（Chaquopy / 资产打包方式）。
- 调用在文字回复完成后异步/缓存执行；任何同步阻塞主回复都是违规。
- 产出 type 建议 `voice`；render 至少含 `{src, text}`。
- 失败（无模型/生成超时）→ 静默降级纯文字 + 日志计数，不做重试风暴。
- ctx 只记「语音念了什么」的文本内容（≤100 字），不记音频路径/时长/格式。
- 禁止为语音引入任何云端 API（本地可离线是目标；确有云方案必须单独报批）。
- 音频文件放 `user_data/{mode}/data/voice/`，命名 `v<seq>.<ext>`；清理策略在方案中写明。

## 8. 游戏工具补充协议（格斗/RPG/galgame）

- 游戏引擎是纯代码确定性模块（随机数可指定种子），**游戏循环内禁止调 LLM**。
- 每用户轮最多一次 dispatch；params 必须是有限枚举（如 `{"cmd":"attack"}`），不得接受自由文本当代码逻辑。
- 状态/存档存 `user_data/{mode}/data/games/<tool_id>/`；每步落盘可恢复；jsonl 不存完整状态。
- 结果表现优先复用已有 type：text / narration / sticker；确需新 type（如 `game`）才注册，render 必须简单（标题/结果文本/可选小图）。
- 战斗/回合结果、好感/剧情分支变化 → 必须写 ctx（如「游戏《xx》第3回合：胜，HP 70/100」≤100 字）。
- 支持随时退出/存档，不因游戏状态卡死聊天。
- galgame 剧情文本走 polisher 或预写剧本；新增 LLM 调用必须单独报批。

## 9. 识图工具补充协议

- 触发方式、图片上传入口在方案中确定；图片先落 `user_data/{mode}/data/images/`（服务器版按 `user_scope_key` 隔离）。
- 识别结果必须转成文本（谁/什么/在做什么/要点），**原图与原始像素不进提示词**。
- ctx 示例：「[工具: 识图] 图中是两人在甜品店，流萤拿着菜单」≤100 字。
- 本地模型优先；服务器模式若用云端识图：必须先明确告知用户并获同意，不得静默调用、不得把用户图片传到第三方存储。
- 识图失败 → 无该条工具记录 + 日志，聊天继续。

## 10. 服务器模式约束（扩展必须逐条核对）

- 用户数据隔离：所有写盘用 `user_scope_key()`；工具不得有跨用户可变全局状态。
- 服务器模型已锁 Flash：扩展不得新增绕过锁的 LLM 调用；任何新增调用都要先报批。
- 重型本地模型（语音/识图）在服务器上默认不可用（`available()=False`），除非方案明确通过。
- 资源获取遵守 Gitee 优先；不给服务器增加带宽负担。

## 12. 每个工具的测试最低要求

- [ ] 输入审查：非法 params 拒绝，不抛未捕获异常。
- [ ] 正常路径：ToolResult 的 message_type 已注册、ctx 非空 ≤100 字、render 可 JSON 序列化。
- [ ] 失败路径：error 分支返回空结果，调度器仍返回文本回复。
- [ ] 调度集成：organizer 输出含该工具时被正确分发；未知 id 被跳过。
- [ ] 历史集成：jsonl 记录可写可读；hydrate 回灌后 ctx 进入 ContextManager。
- [ ] 前端：新 type 正常渲染；未知 type 不报错。
- [ ] 回归：全量 tests 通过；动前端后 `sync_frontends.py --check` 一致。
