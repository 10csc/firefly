# 部署与发布约定（通用规则 v1）

> 本文件是项目级的硬约束。任何会话执行「提交 / 推送 / 发布 / 部署 / 归档」前必须先读本文件。
> 更细的发布步骤见 `docs/版本更新规范.md`。

## 1. 版本号：提交 ≠ 发版

1. **没有用户明确发版指示时，绝不自动升级版本号**，包括：
   - `app/modules/app_config.py` 的 `APP_VERSION`
   - `app/static/app.js` 的 `CURRENT_VERSION`
   - `android/app/build.gradle.kts` 的 `versionName` / `versionCode`
   - `package/firefly.iss` 的 `AppVersion`
   - `server/version.json` 的 `tag`
2. 即使代码已提交甚至推到 GitHub/Gitee，**用户可见版本号也保持不动**，避免无谓占用版本号。
3. 只有用户明确说「发布 / 更新版本到 X.Y.Z」时，才允许 bump 并同步全部版本位置；改完必须 `python tools/check_version.py` PASS。
4. `versionCode` 只在发版时递增，且必须大于 `check_version.py` 中的 `PREV_VERSION_CODE`（覆盖安装前提）。

## 2. 下载优先级：Gitee 第一，服务器第二

1. 大文件下载**永远优先走 Gitee**，服务器只做轻量处理脚本：
   - 前端请求 `/download/resolve?file=firefly.apk|firefly-setup.exe`
   - 服务器只返回 Gitee foruda 直链（几 KB 的 JSON），不传文件流；
   - 浏览器 fetch + Blob + `a.download` 强制保存为 `.apk/.exe`（绕开 Gitee 把 APK 当 zip MIME 下发的问题）。
2. 只有当 Gitee resolve/foruda 不可用时，才允许回退服务器本地文件或 Gitee 302。
3. 服务器 `/opt/firefly-downloads/` 保留 `download_server.py`、`version.json`、`firefly.apk` 和 `firefly-setup.exe`（兜底直连副本，供不支持 blob 下载或反馈下载成 zip 的浏览器走正确 MIME）；其余大文件放 `local_bak_*` 备份目录，不主动占带宽。
4. 每次改动下载逻辑后，必须实测 `/download/resolve?file=firefly.apk` 返回的是 `foruda.gitee.com` 直链，且 CORS `Access-Control-Allow-Origin: *` 正常。

## 3. 部署后必须汇报的四个关键点

每次服务器部署完成后，回复里必须明确写清：

1. **resolve 是否正常**：实测 URL、是否 foruda 直链、是否 CORS 可用；
2. **更新优先级是否正确**：确认「Gitee 优先 → 服务器兜底」没有写反；
3. **数据安全是否审查**：提交/部署内容里没有 API Key、SMTP 授权码、`user_data/`、`config.json`、`firefly.db`、备份包、研究草稿等敏感/无关文件；
4. **提交/发布是否成功**：GitHub 与 Gitee 的 branch、tag、release、资产上传结果逐一核实（成功就写成功，失败就写失败原因，不允许只写“已推送”而不验证）。

## 4. 提交前审查（防串改 / 防泄露）

1. `git status` 逐项核对：只提交本次任务相关文件；出现不是自己改的文件先查明，必要时 `git checkout --` 恢复。
2. 未跟踪的研究草稿、截图、临时目录、备份文件不得 `git add`；统一归入 `封装（没指定就不读）/<日期>_归档/`（该目录已被 .gitignore 忽略）。
3. `git diff --cached --check` 必须通过；并扫描 diff 中是否出现 `sk-`、`Bearer`、SMTP 授权码、密码、数据库路径等敏感内容。
4. `server/` 目录被 gitignore，不随 git 提交；服务器代码通过 scp 部署并在部署后单独说明。

## 5. 项目整理与归档

1. 过时计划、被替代的方案、无用的研究资料，**归档而不直接删除**（除非用户明确说删）。
2. 统一归档位置：`封装（没指定就不读）/<YYYY-MM-DD>_归档/`（已 ignore，不进 git）。
3. 从仓库移除的 tracked 旧文档：`git rm` 前先复制到归档目录，commit message 写清「归档」。
4. 归档后报告：归档了什么、为什么归档、保留在哪、是否已从 git 删除。

## 6. 变更顺序

1. 普通功能提交：先测试 → 提交 → 推送（版本号不动）；
2. 发版提交：先 bump + 全部测试 + check_version + 构建资产 → 单独 commit/tag/release；
3. 部署：在用户明确指示后执行，并遵守第 3 条的部署汇报；
4. 任何一步失败都要停下说明，不静默降级。
