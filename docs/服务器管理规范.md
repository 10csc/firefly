> 目的：把「服务器是什么状态、怎么安全地改、改完怎么验收」一次写死，任何会话动服务器前先读本文件。

> 配套：`docs/部署与发布约定.md`（部署后四关键点汇报）、`docs/部署说明.md`（历史部署手册，个别细节已过时以本文件为准）。

## 0. 总纲（五条铁律）

1. `server/` 目录被 gitignore，**永不进 git**；服务器代码只走 scp，本地 `server/` 是唯一正式源。
2. 生产环境任何变更前先备份 `user_data`；高风险改动（表结构/迁移/删数据）先手动打 `pre_` 命名备份。
3. API Key / SMTP 授权码 / 运营者 Key / admin token **绝不出现在聊天、文档、git、日志**；服务器上只存在于 systemd 环境变量或受限文件。
4. 服务器托管模式已锁 `mimo-v2.5`（OpenCode Go 运营套餐）：任何新增 LLM 调用、改模型、改额度参数都必须先报用户批准。
5. 部署后必须按 `docs/部署与发布约定.md` 第 3 条汇报四个关键点（resolve / 更新优先级 / 数据安全 / 推送验证）。

## 3. 服务与关键配置

- `firefly-server`：`User=www-data`、`WorkingDirectory=/opt/firefly`、`Restart=always`；systemd `Environment` 注入 SMTP 与运营者 Key（**查配置只 `grep ^Environment= | cut -d= -f1` 看键名，不输出值**）。
- `firefly-downloads`：`/usr/bin/python3 /opt/firefly-downloads/download_server.py`，8787，www-data。
- 认证与会话（A7）：`POST /auth/verify`（token 校验 + 滚动续期——剩余 <7 天续到 30 天，`auth.py:verify_and_renew`）；本地版/安卓本地模式经本地后端 `/auth/*` 代理到本站（`routes.py:auth_proxy`，地址取 `auth_server_url`，默认公网 8787）。
- 环境变量（改前必须报用户）：
  - `FIREFLY_SMTP_USER` / `FIREFLY_SMTP_AUTH`（发信）
  - `FIREFLY_PROXY_KEY`（托管模式运营者 Key）
  - `FIREFLY_PROXY_DAILY`（默认 5000 次/天）与 `FIREFLY_PROXY_REQS_PER_CONV`（默认 4）→ 约 1250 轮/天；**当前按用户要求不做单账号防刷**
  - `FIREFLY_IMAGE_QUOTA_MB`（2026-08-22 新增，可选；每用户图片存储上限，默认 200MB——图片=压缩图正式消息数据，落 `{uid}/{mode}/images/`，上传与同步导入都检查）
- 服务器启动时 `server_app.py` 强制 `FIREFLY_SERVER=1`，app_config 四模型强制 `mimo-v2.5`、proxy 走 `QuotaClient`（内部硬编码 `mimo-v2.5`，`api_client.py`）——这是安全锁，不是可选项。
- 图片链路（2026-08-22 用户修订口径）：**服务器只存压缩图**（前端 Canvas 预压缩：单边 ≤1024px/≤300KB，GIF 不动），原图不出用户设备；proxy 托管识图（desc + polisher 首轮 image block）走 QuotaClient 正常记账——每条图片消息 = 1 次 desc 调用 + 1 次 polisher 调用（单图 ≤384 token，已报用户批准）；relay 走用户 Key。
- 备份口径（2026-08-22 起）：**手动云端备份端点（/sync/upload、/sync/download）已下线**——数据同步靠自动同步（/sync/manifest|import|export|now，登录/回前台/进聊天页触发）；用户备份在**本地** `{用户目录}/backups/`（/backup/create|list|restore|delete，每模式留 10 份）。服务器侧每日 cron 备份 user_data 不变，但内容现在含压缩图（体积上限 ≈ 用户数 × 200MB），部署时留意磁盘。

## 4. 标准部署/更新流程

1. 本地先完成全部测试 + `sync_frontends.py --check`（动前端时）。
2. 登录后先备份（高风险时手动带前缀）：
   `tar -czf /opt/backups/user_data_pre_$(date +%Y%m%d-%H%M).tar.gz -C /opt/firefly user_data`
3. scp 更新（只传变更部分，**绝不传 `user_data`、`venv`、备份包**）：
   - 代码/资料：`scp -i C:\Users\FANGL\.ssh\id_rsa -r app knowledge database root@101.200.14.126:/opt/firefly/`
   - 服务器入口：`server/server_app.py`（及 db/auth/mail 等）→ `/opt/firefly/server/`
   - 前端：先跑 `sync_frontends.py`，再传 `server/frontend/` → `/opt/firefly/server/frontend/`
   - 下载服务：改 `server/download_server.py` 才传 `/opt/firefly-downloads/`；`version.json` 两处都传
4. 重启：
   `systemctl restart firefly-server`；改过下载服务再 `systemctl restart firefly-downloads`。
5. 验证：
   `systemctl is-active firefly-server firefly-downloads`（两个都要 active）；
   `curl -s http://127.0.0.1:8765/health`；`ss -lnt` 确认 8787 公网、8765/8766 仅 127.0.0.1；
   下载链路：`/download/resolve?file=firefly.apk` 返回 `foruda.gitee.com` 直链且 CORS `*`。
6. 部署后按部署约定汇报四关键点，其中**推送/发布验证必须逐项核实**（GitHub/Gitee branch/tag/release/资产），失败就写失败。

## 5. 下载通道（不可写反）

- 优先级：**Gitee（resolve 直链）→ 服务器兜底**；大文件主备份在 `local_bak_20260816/`。
- `/opt/firefly-downloads/firefly.apk` 与 `firefly-setup.exe` 是**兜底活动副本**（约 58MB / 23MB），给微信/QQ/Edge 等不支持 blob 或反馈下载成 zip 的浏览器走服务器直连（APK=`application/vnd.android.package-archive`，EXE=`application/vnd.microsoft.portable-executable`，均带正确文件名）。**不要当冗余大文件删除**。
- `download_server.py` 的 `FALLBACK_TAG` 与两处 `version.json` 的 `tag` 要同步；只改 tag 不动 exe/apk 链接格式。
- Gitee 下载 APK 按 zip MIME 下发：前端 fetch + Blob + `a.download` 强制改名，这套逻辑不得移除；UA 命中不靠谱浏览器时自动改走服务器直连。
- 下载量统计（2026-08-16 起）：`/opt/firefly-downloads/downloads.db`（SQLite：ts/file/channel，**不记录 IP**）。计次点：`/download/resolve` 成功=channel `gitee`；服务器直发=`server`；Gitee 302 兜底=`gitee-302`。公开接口 `/download/stats` 返回 `{total, by_file, by_channel}`，其中 `total` 只统计 firefly.apk + firefly-setup.exe；下载页顶部显示该 total。
- 最近请求日志（2026-08-17 起）：同一 `downloads.db` 新增 `requests` 表（ts/ip/method/path/status/ua，滚动保留 2000 条），记录到达 8787 网关的全部请求（含反代），仅供管理台「最近请求」面板排障/安全监测；主服务侧另有内存环形缓冲（300 条，含管理操作留痕），经 `/admin/api/requests` 一并返回。

## 6. 数据与密钥红线

1. `user_data/`（对话、记忆、firefly.db）只在服务器内使用；除备份外不下载到开发机，更不进 git/聊天附件。
2. SMTP 授权码 / `FIREFLY_PROXY_KEY` / admin token：只存在于 systemd 单元文件或 `/opt/firefly/.admin_token`，任何操作不得把它们 echo/打印/写日志。
3. 删除用户账号走管理后台 `/admin/api/users/delete`（先二次确认）；手动 rm 前先备份该用户目录。
4. 每日 3 点 cron 已保留 7 份备份；升级/表迁移前必须额外打一份 `pre_` 备份再动手。
5. 从服务器拷回本地的唯一常见内容是 `version.json` 这类公开文件；其它文件拷回前先想清楚数据安全。

## 7. 模型锁与额度（红线中的红线）

- 托管模式只有 `mimo-v2.5`；用户操作不可能切换模型（A8 重分层：`QuotaClient` 运行时锁 `api_client.py` + `/set-config` proxy 请求头分支强制；配置层已放开给 BYOK 用户自由模型名）。
- 托管配额口径（A3 默认拍板）：**成功调用记账**（proxy_usage），**失败调用单独记 `proxy_usage_failed`、不占用户额度**；每日池检查在调用前（放行后成功才消耗）。
- 任何新功能想引入额外 LLM 调用：先报用户，写明用途/模型/token 预算/额度影响，批准后实现；**服务器上绝不静默新增调用**。
- 改额度：只改 systemd `Environment` 并 `daemon-reload && restart`，改前报用户。
- 用户自带 Key 模式：Key 走 `X-API-Key` 头，内存即弃，服务器不落盘——新增代码不得改变这一点。

## 8. 安全监测（已有设施，不要动坏）

- `attack_watch.sh` cron 每分钟跑：扫描 fail2ban 封禁、主服务 429、SSH 爆破、网关 429，命中写 `/opt/firefly/user_data/attack_flag.json`，平静自动清除。
- 管理服务：127.0.0.1 + `X-Admin-Token` 双因子；`/shutdown` 限本机。管理台接口：`/admin/api/users`（分页用 `?page=N` 查询参数）、`/admin/api/users/ban|unban|delete`、`/admin/api/requests`（最近请求：网关 requests 表 + 本服务内存环）。
- 8765/8766 只监听回环；公网只开 22 + 8787。若发现监听变化立即报告。
- `_harden/harden_server.sh` 为幂等加固脚本；root authorized_keys 只保留 PC 主密钥，手机端走 `dsh-tunnel`。
