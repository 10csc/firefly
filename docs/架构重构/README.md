## 三套方案一句话对比

| 维度 | A · 演进式加固 | B · 服务化重构（推荐） | C · 平台化生态 |
|---|---|---|---|
| 核心思路 | 现有骨架上打补丁，问题逐点消灭 | 数据层与同步推倒重来，业务流水线保留 | 全面接入成熟生态组件 |
| 数据同步 | 文件级双向同步（哈希清单 + 新者胜，**仅文字类；媒体元数据随行、本体留本机**） | 实体级增量同步（服务器序列号游标 + oplog + tombstone；`scope` 字段执行媒体本地策略） | PowerSync / 托管同步服务 |
| 服务器数据管理 | 统一存储层模块收口 | 实体注册表 + 版本化 migration + 按用户加密域 | Postgres + 对象存储 |
| 上游托管容错 | 基于真实调用链：error_code 透传止血 + 分类重试/冷却/分档超时/relay 活性快速失败 | 独立 LLM 网关层（同一契约 + 冷却熔断 + 健康探针 + 配额治理） | LiteLLM Proxy / new-api 现成网关 |
| 前端 | 入口收敛，安卓底部 tab 化 | IA 重构：对话/角色/我的三区 + 同步中心 | 多角色生态 + 桌面三栏 |
| 风险 | 低 | 中（数据层迁移需谨慎） | 高（运维组件翻倍） |
| 预估工期（1 人） | 2-3 周 | 6-8 周（可分四期） | 3 个月+ |
| 关系 | **是 B 的第一期** | 主体 | B 完成后再评估 |

**推荐路径：A 先行（即 B 的第一期），数据层与同步直接按 B 的实体模型设计，避免 A 的临时方案变成第二次迁移。C 的组件在 B 落地后按需引入，不预先承诺。**

## 各方案对硬性需求的覆盖（4 + 3）

用户需求 → 各方案落点：

1. **安卓双模式自动同步**：A=文件级双向同步；B=实体级增量同步引擎（本地/服务器模式共用一份同步客户端代码，因为安卓本地模式跑的就是同一套 Python 后端，`android/app/src/main/python/start_server.py:28-52`）；C=PowerSync。
2. **服务器数据管理（扩展性/安全/稳定）**：A=统一存储层收口路径与原子写；B=实体注册表（任何新数据类型 = 注册一行）+ 版本化 migration + HTTPS；C=Postgres schema + 对象存储。
3. **上游托管控制力**（已出线上 bug）：A=修 `api_client.py` 最小四件套；B=独立网关层 + 后扣费 + 状态指示；C=LiteLLM/new-api。
4. **前端页面重设计**：`05_前端信息架构重设计.md`，三档深度。

2026-08-21 新增三条（落点已写入对应方案）：

5. **登录基本操作化**（使用前提 + 本地优先 + 本地后端不可用时自动连服务器 + 删切换按钮）：A=A7；B=B1 登录态常驻同步（实体模型天然承接）。
6. **多供应商模型配置**（默认 DeepSeek 预填、SK 自动迁移、OpenAI 兼容、官方英文名 + 一键模型列表）：A=A8；B=B3 第 9 条（网关按供应商路由 + 能力声明）。
7. **图片消息与媒体铁律强化**（DeepSeek 识图上线；服务器只传输不保存、最多存 AI 文字结果）：A=A9；B=B0 `image_meta` 实体 + B2 服务端执行细则。
