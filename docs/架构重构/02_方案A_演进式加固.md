## A0. 两条全局数据策略（用户确立，贯穿所有条目）

1. **媒体本地策略**：服务器只保留运营方基础表情包包；用户自有图片（表情包、未来的图片功能）只存用户本地，服务器只是"经过"并保留**文字描述**。同步/备份/传输方案必须区分「文字类（可上服务器）」与「媒体类（永不上服务器）」。

## A3. 上游托管容错（按本项目真实调用链设计，见 01 §3.3）

**核心洞察：本项目不是通用 LLM 网关场景——每轮聊天是 4 次（story）/3 次（haruno）串行调用，任一失败整轮降级；且 error_code 链路在模块层被吞，用户永远看不到真实原因。容错设计必须围绕这个事实。**

1. **修 error_code 透传（止血第一刀）**：四模块的 `except Exception` 降级保留（流水线不断），但降级输出**携带被吞的 error_code**（`{degraded: true, error_code}`）上抛 orchestrator，首轮第一个非空 code 进 /chat 响应 → 前端现有 toast 映射（`chat.js:367-378`）即刻生效。`quota_exhausted` 终于能提示用户切自带 Key。setting_fix 路径补 `fix.js` 读 error_code。——这一步就把"上游波动=用户眼中的 bug"变成"上游波动=用户看到的明确提示"。
2. **分类重试**：429/5xx/网络错误 → Full Jitter（base=1s、cap=30s、最多 3 次，AWS 官方推荐，06 主题 2）；401/400/余额类不重试；429 有 `Retry-After` 则遵守。**relay 链路补重试**（现状零重试，`api_client.py:315-324`）。
3. **冷却（简化熔断）**：按上游端点维度，连续失败冷却 60s，期间快速失败走降级话术（LiteLLM cooldown 同款）。
4. **超时预算对齐现实**：现状 story 单轮最坏 968s（proxy）/480s（relay），而网关 600s、前端 4 分钟中止（`chat.js:531`）都会先断。改为**按阶段分预算**（retriever/organizer 是 non-think 小任务给 30s，analyzer/polisher 给 90s）+ 单轮总预算 210s 硬顶，与网关/前端对齐；**前端消费已有的 `waited` 字段**（`routes.py:917-918`）做"等待偏久"预警。
5. **relay 活性快速失败**：`/relay/pending` 的 1s 轮询本身就是心跳——服务器记录每用户最近轮询时刻，超过 30s 无轮询则 relay_submit 立即失败降级，不再每阶段干等 120s。
6. **配额口径（待定，见 07 §2 三选一）**：现状按调用次扣（story 一轮 4 次），可选改按轮扣/失败单独记账。无论选哪个，管理台把主动消息与 rest 的消耗也纳入展示（现状只按 4 次/轮折算，`server_app.py:460-461`）。
7. **失败后扣费**：`server_app.py:79-83` 先查后扣 → 依决策结果改（推荐：失败调用单独记 `proxy_usage_failed` 不占额度）。

零代码项：前端按 `error_code` toast 已有；新增「上游服务波动中」状态条（读 `/health` 扩展字段）。

## A7. 登录基本操作化 + 后端自动选择（2026-08-21 新需求 1）

登录从「服务器版专属」变成全端使用前提，同时消灭「local/server 双态」维护成本（现状实证见 01 §3.8）。

- **本地版引入账号**：账号体系仍在服务器（`server/auth.py` + `server/db.py` 不动）。本地版首次启动 → 注册/登录引导（复用 QQ 邮箱验证码流程）→ token 缓存本地（`user_data/auth.json`，与 config.json 分离）；此后启动凭缓存放行。**离线宽限**：缓存 token 在宽限期内（已定 30 天，与服务器会话有效期一致；决策 9 已关闭）完全离线可用本地后端；超期要求联网续期一次。
- **后端自动选择（删切换按钮）**：
  - 安卓：启动照常起内嵌 Python 后端；`/health` 健康检查连续失败 → 自动改连服务器后端，界面只显示「云端连接中」。删除 SharedPreferences 手动模式与杀进程切换逻辑（`MainActivity.kt:59-72,489-506`），`FireflyMode` JS Bridge 同步移除。iOS/鸿蒙等无本地后端的平台天然走服务器。
  - PC：本地后端端口被占且无法释放等失败场景，前端自动改连服务器地址并提示。
  - 前端收敛单态：`config.js` 两份合并为一份（运行时由后端 `/config` 告知当前形态）；`api.js` 恒带 Bearer token；relay 引擎激活条件从「server 模式」改为「当前后端是服务器」（`relay.js:139`、`main.js:33`）。
- **同步联动**：登录态下本地后端同样向服务器账号同步文字类数据（A1 引擎常驻）——「数据默认在本地」与「登录支持自动同步」由此兼得。
- **关键路径风险与修复（决策 10 已关闭）**：注册成为使用前提后，注册漏斗（QQ 邮箱验证码 + 群号 + 安装码）就在首次启动第一屏。安装码「一个安装只能注册一次」机制**不动**——重装会产生新安装码，注册通道始终可用；真正要修的是流程：首次启动引导把「登录已有账号」置于「注册新账号」之前，换机/重装默认走登录，忘记密码走邮箱重置。如此「重装 ≠ 不能用」。

## A9. 图片消息与视觉理解（2026-08-21 新需求 3，铁律：服务器只传输不保存）

- **消息模型**：新增 `type=image` 消息 `{seq, time, who, img_id, desc}`；图片字节本地存 `user_data/{mode}/images/{img_id}.<ext>`，conversation.jsonl **只存 img_id + desc 文字**（`conversation_store.py:243-254` 校验表加 image；`hydrate_context`/`format_quote_for_llm` 同步支持，图片在 LLM 上下文中以 `[图片：desc]` 文本出现，对齐 sticker label 现有机制 `routes.py:366`）。
- **首轮直接识图（主路径，决策 12 已确认可行）**：用户发图 → 若 polisher 模型识图（如 `deepseek-v4-flash-vision-exp`，其纯文本能力与 v4-flash 持平，06 主题 5），图片字节**首轮直接进 polisher** 的 user 消息（OpenAI `image_url` block）——流萤首轮就"看到"图；同时由 vision 模型（独立 `vision_model` 配置项，默认同为 vision-exp）生成 1-3 句客观描述 desc 落盘。若 polisher 模型不识图 → 降级为 desc 文字化（流萤"看"描述）。
- **后续轮次纯文本**：所有模块只见 `[图片：desc]` 文本，图片字节不再进任何 prompt——上下文体积、缓存命中、服务器传输面全部可控。每图 ≤384 token（06 主题 5）；首轮 desc 是一次额外小调用，与现有「按调用次」记账口径天然一致。
- **上传路径**：图片不走 `/chat` body（1MB 上限 `routes.py:74-93` 不动）——先 `POST /upload-image`：本地版落盘返回 img_id；服务器版分两种——relay 模式图片由 APP 本地持有（见下，服务器无此端点）；proxy 托管模式开放**经过式上传**（字节进内存 TTL 队列、随当次 LLM 调用发出后即弃、全程不落盘）。
- **relay 链路（铁律执行点）**：prompt 中图片位置放占位符 `__IMG_{img_id}__`，APP 端填充时从本地读图转 data URL 填入——复用现有资产占位符机制（`llm_base.py:121-137`、`relay.js:52-64`）。**服务器 payload 全程无图片字节**。
- **proxy 托管链路（决策 11 已关闭：托管允许传图）**：图片经服务器内存中转直发 LLM。执行：禁写盘；pipeline.jsonl 落盘前剥离图片 block 只留 desc（`orchestrator.py:372-409`）；请求日志本就不记 body（已核实 `server_app.py:112-126`、`download_server.py:70,130`）。识图能力由服务器内部路由到的模型决定——所路由模型不识图时，服务器侧自行改走 desc 路径，客户端无感（客户端不固定任何供应商，见 A8）。
- **导出/同步/备份**：`images/` 目录不进任何传输清单（同 stickers 媒体本地策略）；导出包含 image_meta（img_id+desc+内容哈希）供换机占位提示。
- **降级**：vision-exp 是实验模型，desc 生成失败时降级为用户手填描述或 `[图片]` 占位。
- **前端**：输入区加发图按钮（安卓 WebView 文件选择器扩展 accept，`MainActivity.kt:441-456` 现为 zip 专用）；气泡渲染本地图片；`chat.js` 渲染分支（`:345-347,757-759`）、长按快照（`:152-174`）、引用预览（`:67-72`）加 image 分支。

## A 方案不解决什么（诚实清单）

- routes.py 上帝文件、延迟导入循环依赖——只治标，不拆。
- 文件级同步在「两端同时改了 memory.md/手账.md」时会丢一边（有备份可找回，但要手动）。
- 无实时性，同步靠冷启动触发。
- 媒体本地策略下，换设备后自传表情包只能靠元数据占位提示，无法自动找回图片本体（策略本身的代价，需用户知情接受）。
- 多供应商放开后，各模块在同一份人设 prompt 下的表现差异（人设一致性）需按供应商实测——方案只保证协议通，不保证味道对；图片消息同理：首轮可直达识图（模型支持时），但后续轮次流萤「看」的是 desc 描述不是画面。
- 这些正是 B 的动机。
