# 03 · 方案 B：服务化重构（推荐）

> 定位：数据层与同步推倒重来，业务流水线（retriever→analyzer→polisher→organizer）一行不动（红线见 01 §4）。
> 分四期，每期独立可交付。第一期 = 方案 A。已并入 2026-08-20 精读修正（媒体本地策略、单会话记忆定位、真实调用链）。
> 2026-08-21 修订：并入三条新需求——登录前提化（B1 触发改写）、多供应商（B3 新增第 9 条，网关按供应商路由）、图片消息（B0 image_meta 实例化 + B2 服务端细则）。平台事实见 06 主题 5。

## B0. 核心决策：实体化数据模型（扩展性的根）

现状 10+ 种数据类型散在 JSONL/JSON/Markdown/二进制四种格式（01 §2），每加一种就新写一套读写+迁移+备份。B 方案统一抽象为**实体（Entity）**：

```
entity = {
  id:         UUIDv7,            # 客户端生成，幂等与排序兼得（06 主题 1）
  type:       注册类型名,          # message / summary / config / sticker_meta / favorite / ...
  scope:      synced | local_only, # ★ 媒体本地策略的执行点（见下）
  payload:    类型自有 JSON,      # 各类型 schema 自描述
  updated_at: HLC 时间戳,         # 混合逻辑时钟，不信设备时钟（06 主题 1）
  deleted:    tombstone 标记,     # 软删除，保留 90 天
  device_id:  来源设备            # LWW 平局决胜：rev → updated_at → device_id
}
```

- **`scope` 字段服从媒体本地策略（A0）**：`synced` = 纯文字，参与同步并在服务器持久化；`local_only` = 媒体类，**实体本体（含 payload 里的文字描述/label/内容哈希）参与同步，但引用的二进制文件永不离开设备**。服务器端同步服务收到 local_only 实体时只存元数据，不存在接收二进制的端点。服务器容量因此只随文字增长，媒体成本恒为零——这正是"项目一直处于扩张阶段、后面还有图片功能"需要的结构性保障：未来图片功能注册为 `type=image_meta, scope=local_only` 即完成接入，AI 看图生成的文字描述放 payload（服务器"经过"时生成/保存描述、丢弃字节）。
- 服务器侧实体表：`entities(user_id, type, entity_id, scope, payload_json, updated_at, deleted, seq)`，**`seq` 服务器侧全局单调序列号做同步游标**——不用裸时间戳（同事务共享时间戳会永久丢行，06 主题 1）。
- 客户端（PC+安卓同一套 Python）：`user_data/sync.db`（sqlite3 标准库；Chaquopy 可用性待冒烟验证，不行则降级 JSONL+内存索引，见 07 §3.2）存本地实体镜像 + outbox + 游标。
- **类型注册表** = 扩展性答案：新数据类型只需注册 `{类型名: {校验函数, 冲突策略, scope, 同步开关, 备份策略}}`。冲突策略按实体定：message=append-only 无冲突；config=字段级 LWW；summary/文档类=整文档 LWW+版本快照（06 主题 1）。
- 现有格式的映射（不动业务代码读法，存储层适配）：
  - `conversation.jsonl` → `type=message, scope=synced`，每行一实体，`seq` 沿用；**配套加归档策略**：单会话无限增长（现状无轮转，`conversation_store.py:269-270`），实体化后按「90 天前且已入摘要」归档冷数据，同步只带热数据；
  - `memory.md` → 改名定位「会话压缩摘要」：`type=summary, scope=synced`（头部一条文档实体 + 事实区逐条目实体），渲染回 Markdown 供 `wake()` 读口（`memory_manager.py:368-385`）——签名不变；
  - `手账.md`、角色设定 4 文件 → 文档型实体 `scope=synced`；
  - 表情包 → `type=sticker_meta, scope=local_only`（元数据实体同步，webp 二进制按内容哈希寻址、仅本地）；运营基础包走 bundled 资产分发，不进同步；
  - 聊天图片消息 → `type=image_meta, scope=local_only`（2026-08-21 新需求 3 实例化）：`{img_id, desc, 内容哈希}` 参与同步，图片字节仅存设备 `user_data/{mode}/images/`；`desc` 由 vision 模型首轮生成（A9），后续轮次 prompt 只用 desc 文本；
  - `config.json` → 字段级实体（顺带解决按用户隔离）。

## B1. 增量同步引擎（安卓双模式自动同步的正式答案）

协议 = WatermelonDB 简化版（06 主题 1），三端同一套 `app/modules/sync/`：

- **Pull**：`GET /sync/pull?cursor=N` → `WHERE user_id=? AND seq>N` 实体批次 + 新游标；游标超窗 → 全量重同步信号（数据量小）。
- **Push**：本地 outbox 有序队列 + 幂等 `op_id`；服务器按序应用、去重、分配 seq。
- **媒体边界**：push/pull 只过实体 JSON；local_only 实体的二进制由设备自管，换机时按元数据清单提示「N 个表情包仅存于旧设备」。
- **触发**：登录态常驻（2026-08-21 起登录是使用前提，不再有「服务器模式才同步」）：冷启动 + 回前台 + 发消息后闲时后台推，本地后端运行期间同样向服务器账号同步。首次登录自动「本地全量 push → 服务器 merge」。
- **UI**：设置里「同步中心」（最后同步时间、各端数据量、冲突处理、手动同步、媒体本地策略说明）。

## B2. 服务器数据层重构

- **版本化 migration**：`schema_version` 表 + `server/migrations/NNN_name.py`，替换 `db.ensure_auth_columns()`（`server/db.py:97-134`）。
- **连接与并发**：每请求连接 + WAL；限流计数落 `settings` 表。
- **按用户配置隔离**：`/set-config` 只写 `user_data/{uid}/`（修 `routes.py:128-210`）。
- **媒体策略服务端收尾**：`/add-sticker` 改经过式不落盘（同 A2）；`/assets/` 只服务内置/公共池；未来图片功能的"经过式描述生成"挂 organizer 工具协议（红线内唯一扩展点，01 §4）。
- **图片铁律服务端执行细则（2026-08-21 新需求 3）**：聊天图片字节只允许两种过路形态——relay 模式走占位符 `__IMG_{img_id}__`（服务器 payload 全程无图，APP 端填充，复用 `relay.js:52-64`）；proxy 托管模式内存中转直发 LLM，**禁止落盘**，pipeline.jsonl 落盘前剥离图片 block 只留 desc（`orchestrator.py:372-409`），请求日志本就不记 body（已核实 `server_app.py:112-126`、`download_server.py:70,130`）。「服务器最多保存 AI 返回的文字结果」= 只有 desc 进实体表。托管模式允许传图（决策 11 已关闭），识图能力由服务器内部路由到的模型决定，客户端无感、不因此禁用图片。
- **备份**：实体表每日 SQLite 在线备份 + 现有 tar 打包双轨；恢复演练写进 `docs/服务器管理规范.md`；先统一备份口径（07 §3.4 决策 5）。
- **HTTPS**（强制前置）：Caddy 反代 8787。
- **审计**：管理端（8766，`server_app.py:418-506`）加实体变更审计只读视图。

## B3. LLM 网关层（按本项目真实调用链设计，不是通用模板）

本项目托管的特殊性（01 §3.3）：**每轮聊天 = 4/3 次串行调用，配额按调用次计，error_code 链路断裂**。网关层 `app/modules/llm_gateway/`（三端共用，托管模式受益最大）按此设计。**2026-08-21 新增多供应商维度（新需求 2）**：BYOK 场景用户可自定义 OpenAI 兼容供应商，网关不再是「锁死 mimo-v2.5 单 provider」假设，必须按 provider 组织配置、能力声明与冷却维度（见第 9 条）：

1. **错误透传契约（最高优先级）**：模块降级照旧，但降级结果携带 error_code 上抛，网关聚合成响应字段 → 前端 toast 生效。同时补 `fix.js` 读 error_code。**这是"上游波动=用户眼中的 bug"的根治。**
2. **重试归一**：网关独占重试（Full Jitter，仅 429/5xx/网络；401/400/余额不重试），调用方零重试，避免 (1+N)²（LiteLLM 教训，06 主题 2）。relay 链路纳入同一策略。
3. **冷却熔断**：按 `provider+模型` 维度冷却 60s、失败率阈值摘除、到期探测恢复。本项目单 provider，冷却的直接收益是**上游抽风期间整站快速失败走降级话术，而不是每个用户各挂 16 分钟**。
4. **超时预算分档**：non-think 小任务（retriever/organizer/动机决策）30s、think-high（analyzer/polisher）90s、单轮总预算 210s 硬顶——对齐网关反代 600s（`download_server.py:649`）与前端 4 分钟中止（`chat.js:531`）；前端消费 `waited` 做预警。
5. **relay 活性快速失败**：`/relay/pending` 轮询即心跳，>30s 无轮询 → relay_submit 立即失败降级（现状每阶段干等 120s）。
6. **健康探针 + 状态条**：每分钟探活 OpenCode Go 端点，写 `/health` 扩展字段；前端聊天页顶栏状态点（绿/黄/红）。
7. **配额治理（口径待定，07 §2）**：按轮 vs 按调用、失败记账方式、主动消息/rest 消耗进管理台展示。单账号防刷启用 `proxy_usage` 的 user_id 维度（预留注释在 `server_app.py:53`）。
8. **备用链路**：主 OpenCode Go（mimo-v2.5 锁定）。备用 = 运营者 DeepSeek Key 直发 flash（成本/人设一致性权衡，与双端模型策略同属待决策，07 §3.4 决策 3）——无备用时冷却+降级话术已是完整闭环。

9. **多供应商与能力声明（2026-08-21 新需求 2 落地）**：provider 注册表 `{id, name, base_url, api_key, models[], caps}`；`caps` 声明 `vision / thinking / prompt_cache / models_endpoint` 能力——DeepSeek 预设全开，自定义供应商默认全关（最保守 OpenAI 兼容），调用报 unknown param 时自动剥离 `extra_body` 重试一次并回写 caps。DeepSeek 私有字段（`thinking`/`reasoning_effort`/`reasoning_content`/缓存计数，`api_client.py:67-68,145,152-153`）全部移到 caps 分支后。`VALID_MODELS` 与端点白名单（`app_config.py:127-132` 等五处，清单见 01 §3.8）废除，改为内置建议清单 + 用户自由输入。模型锁只存在于服务器侧路由配置（现状指向 mimo-v2.5，但属服务器内部实现：运营方可换上游；**客户端不感知、不硬编码任何供应商细节**，只有「是否托管」一个开关——07 §5.3 架构约束）；relay/direct（BYOK）走用户 provider。逻辑档位→实际模型的映射收在网关层，双端跑同一份配置逻辑（07 §5.3 决策 3 因此关闭）。

**不引入 LiteLLM/new-api**：项目依赖敏感铁律 + BYOK 场景自研四件套已够用（多供应商能力声明见第 9 条）；网关接口设计成 LiteLLM 兼容（OpenAI 格式 + 按部署路由），为 C 预留「换实现不改协议」空间。
