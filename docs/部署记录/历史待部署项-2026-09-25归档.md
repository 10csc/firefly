### 线上实测发现的两件事（2026-09-25，`tools/probe_live_server.py`）

**① `/update-manifest` 线上返 401 —— 检查更新的主通道是坏的**（P0-11）

```
curl -s -o /dev/null -w '%{http_code}\n' http://101.200.14.126:8787/update-manifest
→ 401（3/3 次稳定；body = {"error":"未登录或登录已过期"}）
curl -s -o /dev/null -w '%{http_code}\n' http://101.200.14.126:8787/version.json → 200（对照）
```
客户端 `app/routes_update.py::fetch_manifest()` 是 **`urllib` 无凭证**请求 ⇒ 本地版"检查更新"
每次都 401 → 静默降级到 GitHub/Gitee 双源。功能没坏成"不可用"，但**主通道形同虚设**。
**仓库里的 `server/app.py` 已经是对的**（`do_GET` 内 `/update-manifest` 在公开区，鉴权闸在其后）
⇒ **部署第 3 项即可修好，不需要改代码**。

**② 真实部署缺口只有 7 个端点**（P0-8 的收窄）

```
python tools/probe_live_server.py      # 复现证据（不带任何凭证）
→ 缺：/hotupdate/{status,action,activity,boot-ok,restart}、/notice/action、/notice-image
```
⇒ 这 7 个随第 3/7/10 项部署补齐；**不再需要"整体对齐线上 app 层"**。

### 发版前的两道新门禁（2026-09-25 新增）

```bash
python tools/check_server_contract.py   # 离线：客户端会调的端点 ⊆ 服务器注册表（防 P0-8 类漂移）
python tools/probe_live_server.py       # 在线：线上注册表 vs 仓库路由表（部署前后各跑一次）
```

**私钥的正确走法**（唯一一次"传密钥"）：
```bash
scp -i ~/<SSH 私钥路径> ~/.firefly/session_priv.pem root@<服务器>:/opt/firefly/keys/
ssh root@<服务器> "chmod 600 /opt/firefly/keys/session_priv.pem; chown www-data:www-data /opt/firefly/keys/session_priv.pem; ls -l /opt/firefly/keys/"
```
公钥已经在 `app/static/js/session_crypto.js` 里（随前端走），**不需要**单独传。
