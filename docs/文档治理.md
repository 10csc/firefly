# 文档治理

本项目采用精简版 docs-as-code：文档跟代码一起评审，活动页描述当前事实，历史过程单独归档。

## 采用的行业实践

- [GitLab Documentation topic types](https://docs.gitlab.com/development/documentation/topic_types/index.md)：区分 Concept、Task、Reference、Troubleshooting；页面先解释概念，再给任务或参考。
- [Kubernetes page content types](https://kubernetes.io/docs/contribute/style/page-content-types/)：Concept、Task、Tutorial、Reference 各有固定结构，不把解释和操作混写。
- [Google timeless documentation](https://developers.google.com/style/timeless-documentation)：产品文档描述当前能力，避免用“现在、最新、即将”等会快速失真的词。
- [GitLab documentation style guide](https://docs.gitlab.com/development/documentation/styleguide/index.md)：文档规范只有一个来源；链接使用同仓库相对路径，控制每页链接数量。
- [ADR](https://adr.github.io/)：重要决定记录 Context、Decision、Status、Consequences；被取代时新增决定，不改旧记录。

本项目不照搬大厂的多层审批或站生成器。规模不需要那套成本，只采用内容分型、单一事实源、链接校验、过期下线四件事。

## 目录映射

| 目录 | 内容 | 不应包含 |
|---|---|---|
| `概念/` | 产品目标、架构、数据模型、边界 | 长命令清单 |
| `操作/` | 前提、步骤、验收、回滚 | 历史设计和审计过程 |
| `参考/` | 协议、字段、命令、门禁、测试基线 | “我觉得应该”式讨论 |
| `决策/` | 不可逆或高成本决定及其后果 | 每次小改动 |
| `错误总结/` | 事故复盘和防复发规则 | 未经证实的推断 |
| `使用指南/` | 用户操作与排障 | 内部实现细节 |

## 硬规则

1. 一类事实只保留一个权威载体；其他页面链接过去，不复制整表。
2. 活动页写当前事实；日期只用于事故、发布记录和 ADR，不用“最新”代替版本号。
3. 已实施方案、交接单、审计过程移入归档，不留在活动树里伪装成规范。
4. 错误总结保留原事故语境；只修明确的事实错误，不把事故记录改写成事后设计。
5. 新文档默认不超过约 200 行；超长先拆主题，不继续堆在同一页。
6. 移动或删除活动页前先搜索引用；活动文档的相对链接必须能解析。
7. 代码行为变化时同步更新对应概念、参考和操作页；不能只补一份新报告。
8. 任务完成必须在 [未完成事项清单](未完成事项清单.md) 销账；过程记录不替代销账。

## 生命周期

```text
提案/调查 → ADR 或归档资料
当前事实 → 概念/参考
可执行流程 → 操作
用户可用功能 → 使用指南
事故与教训 → 错误总结
被替代内容 → 归档并从活动索引移除
```

归档不删除，保证审计线索可恢复；归档内容不再参与“当前系统是否正确”的判断。
