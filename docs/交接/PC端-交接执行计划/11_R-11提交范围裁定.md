## 3. `server/` 版本化：裁定 = **方案 B（tar 归档 + sha256），不纳入 git**

**为什么不采纳"纳入 git"（你的推荐）**

1. **不入库是既定策略，不是疏漏**。`.gitignore` 里那行原文带注释：
   `# 服务器后端（四部分之一，不提交 git/github，**防泄露**）`。
   改它属于**项目级策略变更**，不该在发版收尾时顺手做；要做也该单独提案。
2. **09 清单 R-11 的验收判据原文就允许二选一**：「`server/` 的版本化归档（**tar 或纳入 git**）」⇒ 选 tar **满足验收** ✓。
3. 纳入 git 的代价：服务器侧含部署配置与运维脚本，仓库一旦外泄等于把网关与运维面一起交出去。

**方案 B 已执行（本轮，纯复制、零风险、可随时删）**

```
封装（没指定就不读）/2026-10-03_归档/server_src_20261003_0.9.1.tar.gz
    size = 197,750 B   sha256 = fa12af57b5aad41ed2666e46552a20b2f8f2cdc963c1e371a6ec7cc1fc134860
    内容 = server/ 下 24 个文件（排除 __pycache__ / *.pyc / *.log），含 frontend/ 与 update.json、version.json
封装（没指定就不读）/2026-10-03_归档/server_src_20261003_0.9.1.sha256.txt
    → 24 个文件的逐文件 sha256 + size（便于逐文件追溯，而不只是整包哈希）
```

⚠️ 该归档目录本身已被 `.gitignore` 忽略 ⇒ **归档不入库**（否则又绕回"server 进 git"）。
⚠️ 归档的是**源码**，不是部署动作；R-14 部署仍单独批准。

**制度化建议**（写进 R-12 清单）：每次发布冻结后，同时归档「产物字节」+「server 源码」两份。
