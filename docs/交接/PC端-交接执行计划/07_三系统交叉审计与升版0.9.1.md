## 二、任务 V-A：三系统交叉审计（**只出报告，不改功能**）

审计对象（三个 0.9.1 主力功能）：
- **① 公告系统**（`notice_src/` 内容源、运行期 `notice/` 缓存、下发接口、`refreshing` 先回缓存后台刷新、
  只接受结构化块 p/h/li/tip/img、端侧一律 `textContent`）；
- **② 完整热更新系统**（五道门禁含 `tools/check_hotupdate.py`、热更只修 bug 不发新功能、
  **底座内容变了必须升版本号** §5.4 反向铁律、`CURRENT_VERSION` 单一来源）；
- **③ 角色卡开放平台**（`app/plaza/**` 客户端与平台 API + `server/frontend/platform.*` 平台页 +
  角色卡广场/制卡/我的卡/治理台/安装配额/官方标记/改编通道 derive）。

**A1 依赖与共享面盘点**：给一张表 —— 三者各自的**入口 / 存储位置 / 路由 / 前端面板 / 生命周期**，
并标出**共享的东西**（文件+行号当证据）。特别关注共享枢纽：**版本号**、`app/static/**` 三副本同步、
鉴权令牌、公告缓存目录、热更清单、`server/frontend/` 平台白名单。

**A2 两两交叉（3 对）+ 三向交叉（1 组）**，每组必须回答"**会不会互相造成 bug**"并给证据：
1. **公告 × 热更**：热更后前端产物变了，公告缓存/版本文案是否会过期或指向失效入口？
   `refreshing` 在后端刷新期间是否可能给用户看到与当前前端版本不匹配的内容？
2. **公告 × 平台**：平台页（服务器侧）是否也走公告通道？若共用通道，**令牌与缓存键是否隔离**？
   结构化块在平台页的渲染路径是否仍是 `textContent`（**XSS 红线**）？
3. **热更 × 平台**：热更范围是否覆盖平台页（服务器资源）？平台页的资源是否会被热更或三副本同步误改？
   升版本号后，旧热更补丁与新整包是否会混用（§5.4）？
4. **三向**：以**版本号**为枢纽，列出"改一处会导致哪几处不一致"的**具体路径**
   （例如：`CURRENT_VERSION` 改了，而 `server/frontend` 副本 / `build.gradle.kts` / `update.js` /
   `firefly.iss` / 热更清单 / 公告版本文案 未同步 ⇒ 后果是什么）。

**A3 与原有功能的冲突面**（至少覆盖，逐条给"无冲突证据"或"冲突点"）：
启动与登录鉴权（`/auth/me` 与 `/auth/state` 的差异）、下载与更新（`/download/*`、`/update-manifest`）、
数据同步与恢复（`app/infra/sync/**`）、对话与记忆主链路（`app/api/chat.py` 等）、诊断与导出（`app/api/diag.py`、`data_export`）、
安全加固（令牌桶、越权、账号隔离）、**手机端**（`sync_frontends` 三副本 + `app/static/style.css` 共用）。

**A4 每条发现的必备格式**（**禁止**只给结论不给证据 ✗；**禁止**把"没测"说成"没问题" ✗）：
严重度（阻断/高/中/低）｜证据（文件+行号，或可复现步骤）｜影响面（哪个端/哪条链路）｜
是否会真的触发（触发条件）｜建议修法｜是否本轮已改（应为"未改"）。

**A5 尽量真跑**：能写成脚本或断言的交叉场景就真跑（例如：模拟"热更后公告刷新"、
"升版本号后三副本一致性"、"平台页不受 App 热更影响"、"公告块注入尝试被 `textContent` 拦住"）；
跑不动的**写明原因与缺什么条件**。审计报告放 `docs/设计/0.9.1三系统交叉审计.md`（≤200 行；
