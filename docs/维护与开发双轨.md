# 维护与开发双轨（v1，2026-09-20 立）

> 背景：0.9.0 已发布（客户端 APK + 服务器 app 层 + 服务器前端同时跨越）。
> 从这一刻起，**已发布版本**与**正在开发的功能**必须分开对待 ——
> 否则"在线修 bug"会与"新功能未完成代码"混在一起，发出去的东西没人能复现。

## 一、两轨的划分

| | **维护轨（release/*）** | **开发轨（master）** |
|---|---|---|
| 起点 | tag `v0.9.0`（本次冻结） | `master` 最新 |
| 只接受 | **bug 修复**、安全修复、文案/样式修正 | 新功能、重构、架构调整 |
| 禁止 | 新功能、数据布局变更、协议变更 | 直接上线、直接打进热更补丁 |
| 产出 | `0.9.x` 补丁（APK/安装器 + 热更补丁） | 下一个次版本（0.10 / 1.0） |
| 上线方式 | 走 `docs/服务器管理规范.md` §4 + 热更通道（**热更只用于修 bug**，见热更规范） | 走发版流程，一次性 |
| 版本号 | `0.9.1`、`0.9.2`…（`check_version.py` 管） | `0.10.0` 起 |

**硬规则**：
1. 维护轨的每一次产出，必须能追溯到 `release/0.9` 上的一个 commit + 一个 tag；
2. 开发轨的代码**不得**直接进维护轨的补丁；要修 bug 就在 `release/0.9` 上改，再
   `git cherry-pick` 回 `master`（方向只允许这一边）；
3. **数据兼容**：维护轨不许改数据布局；若必须改（例如修一个数据 bug），按
   `docs/版本更新规范.md` §四 三条铁律（幂等 + 按文件状态判断 + 先于默认拷贝 + 只 move 不删）。

## 二、本次冻结了什么（快照内容）

位置：`封装（没指定就不读）/2026-09-20_0.9.0发布快照/`（该目录 gitignore，不进仓库）

| 子目录/文件 | 内容 | 为什么 |
|---|---|---|
| `client/firefly.apk` | 已发布的 Android 0.9.0 产物 | 客户端交付物本体（sha256 记录在 `hashes.txt`） |

| `server/app/` | 线上实际运行的 app 层（服务器版跑的那份） | 同上；客户端与服务器共用 app 层，但部署时点不同 |
| `deployed/` | systemd 单元键名（**不含值**）、DB schema、`version.json`、下载服务状态 | 可复现"线上是什么状态"，且不泄漏任何密钥 |
| `hashes.txt` | APK/安装器 sha256、git commit + tag、服务器侧文件 md5 | 追溯"这个产物到底是哪份代码" |

**不放进去**（红线）：`user_data/`、`firefly.db` 内容（只放 schema）、任何 Key/token/授权码、
systemd `Environment=` 的值（只留键名）。

## 三、维护轨的日常操作

```bash
# 从冻结点开维护分支（只做一次）
git checkout -b release/0.9 v0.9.0

# 修一个 bug（例）
git commit -m "fix(0.9.1): ..."
python tools/check_version.py            # 版本号一致性
python -m pytest tests/ 或逐个跑 tests/*.py   # 全量
cd android && gradlew.bat --no-daemon clean assembleRelease   # ★ 必须 clean（见错误总结 #16）
python tools/check_apk_frontend.py       # 包内前端与源一致（防增量构建给旧前端）
python tools/check_apk_manifest.py android/firefly.apk allowBackup usesCleartextTraffic
# 服务器侧改动再加：单文件挑传 + §4.5 六项验证
git tag -a v0.9.1 -m "..." && git push gitee release/0.9 --tags
```

热更补丁（只修 bug）：按 `docs/热更新规范.md` 出补丁 → 客户端自动收到；
**底座内容变了必须升版本号**（否则旧补丁会与新整包混，热更规范 §5.4）。

### 3.3 已知偶发（留给以后加固，不是阻断项）

`tests/test_diag_export.py` 在**全量连跑**时偶发失败，单跑与复跑均全绿：

| 观测 | 结果 |
|---|---|
| 单跑 | 3/3 PASS（22/22 断言） |
| 全量重跑 | 2 次 FAIL、6 次 PASS（其中一次连跑 5 轮全绿）|
| 失败时的输出 | 抓到过 `统计: PASS=22 FAIL=0`（退出码非 0）与一次未捕获的 X 行 |

**已经排除的原因**：该测试不碰端口、不起子进程、无 sleep/计时断言；
`routes_common._is_server()` 每次读 `os.environ`（无缓存）⇒ 不是"环境变量被上一个测试改脏"。

**判断**：低频、非确定性，怀疑是**资源/临时目录层面的瞬时失败**（全量时几十个 python 进程
交替创建/清理临时目录）。**没有复现就不改代码** —— 盲改会把一个偶发变成一个稳定但错误的测试。
下次再现时**先记下当时那条 `X` 的文案**（现有扫描脚本已经把失败输出抓下来了），再决定怎么加固。

## 四、开发轨的日常操作

- 正常在 `master` 上开发；每个里程碑打 tag（`v0.10.0`…）；
- 维护轨的修复要**定期并回**：`git checkout master && git cherry-pick <release/0.9 的修复 commit>`；
- 开发轨**不许**为了"顺便修一下"去动维护轨的文件 —— 同一个 bug 改两次很容易只改一边。
