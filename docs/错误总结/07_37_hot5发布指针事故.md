## 37. hot5 已构建不等于已发布：默认目录与 Gitee 同名 `latest` 让线上停在 patch4（2026-10-27）

**现象**

本地生产候选已经是 `0.9.1/serial 5`，hot5 门禁和真机也显示新代码可用，但主源与 Gitee 的
`latest` 实际都返回 `{"base":"0.9.1","serial":4}`。这意味着新安装、未应用补丁或回退到 base
的设备检查更新时，仍可能拿到 hot4，而不是包含后续修复的 hot5。

**根因一：发布工具默认目录与实际发布区不一致**

- 发布规则和生产候选都在 `hotupdate_dist/prod/<base>/`。
- `publish_hotupdate.py`、`check_hotupdate.py` 的默认目录仍是 `hotupdate_dist/`；
  同族排查还发现热更构建、公告构建和公告发布的默认目录也停在旧的根目录布局。
- 因此不带 `--dist` 的默认命令直接判定 `latest / patch-N.json / patch-N.zip` 不存在；
  发布没有发生，但本地声明文件和候选目录仍然看起来正常。
- 这是“本地候选存在”被误当成“线上已发布”的直接来源。

**根因二：Gitee 允许同名附件，下载 URL 会命中旧 `latest`**

- 首次推送时，patch5 JSON/ZIP 已上传，主源也已切到 serial 5。
- Gitee 原有的 `latest`（serial 4）没有被替换，而是又挂了一个同名 `latest`（serial 5）。
- `releases/download/.../latest` 仍解析到旧附件，所以两端没有一起收敛。
- 发布器的逐字节回读正确抓到了这个问题：主源 5、Gitee 4，判定整体发布失败。

**修复**

1. 热更构建/审查/发布与公告构建/发布的默认目录统一改为 `hotupdate_dist/prod` 生产区。
2. 发布器在 Gitee 上传新 `latest` 前，先列出 release 附件并删除所有旧同名 `latest`；
   旧补丁的 patch JSON/ZIP 仍保持不可变，不做原地覆盖。
3. 若旧 `latest` 清理失败，发布器跳过新 `latest` 上传，宁可暂时回落到主源，也不制造
   “两个同名索引指向不同 serial”的歧义。
4. 保持既定发布顺序：先传 patch JSON/ZIP，最后切 `latest`。

**验证证据**

- hot5 发布门禁：`PASS=127 FAIL=0`。
- hot5 真实发布链路：`PASS=31 FAIL=0`，包含 72 文件签名、源码一致性、完整包闭包、
  干净底座导入、攻击包拒绝和 192 次并发下载 soak。
- 修复前：主源与 Gitee 的 `latest.serial` 都是 4。
- 修复后：主源、Gitee、服务器本地文件的 `latest.serial` 都是 5。
- 两端 patch5 JSON/ZIP 与本地 SHA-256 一致；`publish_hotupdate.py --verify-only` 为
  `PASS=9 FAIL=0`。
- Gitee release 中 `latest` 附件数量为 1，下载重定向到新附件。

**影响边界**

- 此修复关闭了“用户再次检查更新仍被送到 hot4”的发布指针问题。
- 它不能证明已经卡在 hot3/hot4 的存量设备一定能自行恢复，也不能修复服务端仍是 patch4
  业务代码、未知 mode 回退或 clear 持久化风险。
- 真机 `pending_serial=0`、同步与图片链路仍按 [未完成事项清单](../未完成事项清单.md) 验收。

**教训**

- **本地有包 ≠ 已发布。** 必须回读主源和每个镜像的 `latest`、清单和包体字节。
- **可变索引不能靠追加同名附件更新。** 对 `latest` 这类可变指针，发布前要清理旧同名项；
  对 patch JSON/ZIP 这类不可变资产，禁止覆盖。
- **验证必须同时看指针、清单和包体。** 只看到“上传成功”不够，只看到主源 5 也不够。
- **发布工具本身也要有真实回归。** 默认目录、镜像同名附件和回读失败都应在发布前暴露，
  不能让操作者凭路径存在性推断线上状态。
