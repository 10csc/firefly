## 36. hot3→hot5：热更包、Python 覆盖层与同步寻址叠成一次复合事故（2026-10-25～10-27）

**结论先行**

- 本次可复现的大面积故障**确实从 hot3 开始**：成功应用 hot3 的设备在 Python 包闭包处导入失败，
  后端与依赖它的网络、图片链路一起不可用。
- 但现在看到的问题**不只属于 hot3**。至少叠加了四层：hot3 包闭包、hot4 覆盖层路径、
  hot5 客户端与线上 patch4 的版本错配、同步接口对未知 `mode` 的静默回退。
- 清理历史还有一条尚未复现但代码允许的持久化失败链：文件已经清掉，本地 epoch/rev 却没成功落盘，
  之后 clear op 仍可能进入 outbox。它会把“单次清理”恶化成客户端与服务端代际错配。
- 截至本文记录时，hot5 只在客户端真机运行，线上同步服务仍对应 patch4；因此不能把 hot5 客户端
  通过测试等同于“整条链路已经修复”。

**证据边界**

- 本文使用热更产物时间、真机文件时间、服务日志和当前源码做交叉核验，不记录账号、邮箱、令牌或聊天正文。
- 04:17 服务器明确处理的是 `mode=story` 的 clear。**不能据此声称当时 UI 一定处于 robin**。
- 手机 `robin` 目录在快照里没有可恢复的 conversation、journal、memory、pipeline、outbox 或 txn；
  这只证明“快照时没有这些文件”，不能反推 robin 之前一定有多少有效内容。
- `robin` 被服务端回退到 story 有日志和代码路径证据；某一次具体数据消失是否由此导致，
  仍要结合当时的请求与落盘日志，不能把所有现象归给单一 bug。

**故障层次与覆盖面**

| 层次 | 触发条件 | 实际/潜在后果 | 当前状态 |
|---|---|---|---|
| hot3 Python 包闭包 | 所有成功应用 hot3 的设备 | 后端启动导入失败，网络与图片不可用 | hot4 已补包；仍需 hot3/hot4→hot5 真机恢复证据 |
| hot4 覆盖层路径 | 应用 hot4 的设备 | `BASE_DIR` 与 Chaquopy `AssetFinder` 路径假设不兼容 | hot5 客户端已改；服务端未同步该包 |
| 客户端/服务端版本错配 | hot5 客户端连 patch4 同步服务 | 客户端行为不能只按 hot5 解释；发布与真机结论不一致 | 未消除 |
| 未知 mode 静默回退 | 服务端没有 robin 或其他自建/归档包 | story 的状态和操作可能被写进本地 robin 的同步上下文 | 未修，高风险 |
| clear 状态持久化 | clear 时事务创建、状态保存或进程中断 | 本地文件已清、本地代际未落盘，服务器却已推进代际 | 代码允许，尚未复现具体写失败 |
| 测试盲区 | 继续只测 story/haruno 的 happy path | 上述跨版本、未知 mode、响应错包不会被测出 | 未覆盖 |

按生产目录快照，`story` 有 30 个账号目录、`haruno` 有 15 个、`robin` 为 0 个
（这是目录计数，不是用户人数）；服务端内置包也只有 `story` 与 `haruno`。
因此 `robin` 不是“偶尔解析失败”，而是当前服务端根本没有这个可寻址模式。

**最危险的同步路径**

`app/api/data_sync.py` 的 `_sync_one_mode_body()` 当前顺序是：

1. 请求 `/sync/state?mode=<本地 mode>`；
2. **立即**把响应里的 state 应用到这个本地 mode；
3. 读取并发送该目录的 outbox；
4. 之后才请求 `/sync/manifest`；
5. 在 manifest 响应里检查服务端是否把 mode 回退。

所以“检查到 robin 被回退”只保护了后面的文件清单同步，**保护不了前面已经应用的 state 和 ops**。
当本地请求 robin、服务器按 story 返回更高 epoch 时，客户端可能先在 robin 本地目录执行
story 的清理语义。manifest 随后报错，只会让用户看到同步失败，不能撤销已被应用的状态。

`app/routes_common.py` 的 `_query_mode_ex()` 和 `_body_mode_ex()` 已经知道发生了回退，
但兼容包装 `_query_mode()` / `_body_mode()` 丢弃了 `fell_back` 标记。
`sync_state`、`sync_ops`、`sync_manifest`、`sync_export` 等入口都有机会静默按 story 执行。

**清理历史的次生风险**

1. `app/api/chat_ops.py` 的 `clear_history()` 在事务创建发生普通异常时把 `_root/_txn` 设为 `None`，
   但随后仍继续清理物理文件；最终整体 catch 只记日志，HTTP 仍返回 `ok: true`。
2. `app/modules/sync_state.py` 的 `clear_history()` 增加 epoch/rev 后调用 `save()`，
   却忽略其布尔返回值；`merge_server_state()` 也忽略保存失败。
3. 因此代码允许“对话、记忆和手账已删除 → 本地代际标记未保存 → clear op 仍进入同步”。
4. 这不是已证实的本次数据丢失原因，但它是必须消除的结构性风险；只比较文件时间不能替代事务日志。

**多轮修复为什么让问题更复杂**

1. **hot3 把发布层问题变成运行时全断**：一个缺包错误同时打断后端、同步和图片，前端报错只是表症。
2. **hot4 修对包闭包，又暴露运行层假设**：文件补齐以后，`BASE_DIR` 和虚拟底座解析才成为下一层故障。
3. **hot5 修客户端，却没有同步服务端发布面**：真机版本已经向前走，线上协议实现仍停在 patch4，
   同一时刻观察到的行为来自两个不同版本。
4. **新 mode 与旧服务端能力表碰撞**：客户端能识别 robin，服务端不认识；旧的“兼容回退”在普通页面
   也许只是显示成 story，放进带 clear/epoch 的同步接口就成了写错目录风险。
5. **清理、outbox、自动全包同步与进程重启相互叠加**：本地文件、同步标记、待发送队列、
   服务器代际各自可能前进，恢复时很难再判断哪一个动作先成功、哪一个只成功了一半。
6. **测试把“两个正常 mode 能收敛”误当成“同步协议安全”**：现有活动测试覆盖 story/haruno、
   并发和恢复，但没有把“未知 mode 返回默认 mode 且客户端先应用 state”作为必须失败的真实链路。

**当前处置**

- 2026-10-27 已纠正发布指针：主源与 Gitee 均从 patch4 切换到 serial 5，两个源的
  `latest`、patch5 JSON/ZIP 已逐字节回读一致；这关闭了“新检查更新的用户仍拿到 hot4”的问题。
- 发布指针修复不等于线上服务端业务代码同步到 patch5，也不代表存量 hot3/hot4 设备已经自动恢复。
- 暂按用户决定保留手机上的 hot5，不再推送新的热更版本、不触碰生产 `user_data`。
- 保留 hot5 不等于确认事故关闭；`robin`、自建/归档 mode、清理历史、跨版本同步仍应视为高风险条件。
- 在下一步修复前，发布与测试需要同时回答三件事：
  服务端是否显式拒绝不可寻址 mode；客户端是否在任何副作用前校验响应 mode；
  clear 的状态保存失败是否会阻止成功响应与 outbox 提交。
- 未完成状态已登记到 [未完成事项清单](../未完成事项清单.md)，后续不能只凭“页面暂时正常”销账。

**教训**

- **故障起点不等于完整根因。** hot3 是事故开关，但后续症状横跨发布包、运行底座、协议寻址和持久化。
- **兼容回退只能用于无副作用读取。** 一旦接口会推进 epoch、删除文件或提交 op，未知参数必须显式拒绝。
- **输入合法性检查必须发生在任何副作用之前。** 先应用响应、后检查响应 mode，顺序本身就是漏洞。
- **破坏性操作的“成功”必须以状态落盘成功为前提。** 清文件成功、写状态失败不能返回业务成功。
- **发布版本必须按客户端、热更层、服务端代码和可用 mode 清单四项对齐。** 只核验 App 版本会漏掉服务端错配。
- **真实链路测试要包含错误能力协商。** 至少要构造“客户端认识、服务端不认识”的 mode，
  并断言没有 state、ops 或本地文件被默认包污染。
