## 31. 清理脚本的「引用检查」gate 被变异自检抓出 **4 个** bug（2026-10-01，孤儿文件清理）

**背景**：清理线上孤儿前端文件时，我在脚本里写了一条判据「**去注释后仍有引用 ⇒ 拒绝清理**」，
并在注释里写着「任一文件被引用就跳过」。verifier 看完说了句关键的话：**"有判断"不等于"判断正确"，
得给这条判据做变异验证**（故意造一处引用，脚本必须拒绝）。我照做了，结果抓出 4 个 bug：

| # | bug | 后果 |
|---|---|---|
| 1 | `c=$(grep -c ... \|\| echo 0)` —— `grep -c` 无匹配时**退出码 1**，`\|\|` 又执行 `echo 0` ⇒ 计数变成 `"0\n0"` | `[ "$c" != "0" ]` 恒真 ⇒ **所有文件都被判"有引用"，清理全部被拒**（脚本第一版连判断都没有，是"注释里的承诺"） |
| 2 | 只过滤**整行注释**（`^\s*//`），漏了**行尾注释** | 线上 `bundle.js:9094` 的真实形态 `window.showHome = ...; // 供 pc_nav.js 使用` 被当成真引用 ⇒ 假阳性 |
| 3 | `sed -E 's\|...\|...\|'` —— 定界符用 `\|`，而模式里含 `\|` 交替 | `sed: unknown option to 's'` ⇒ 该步**静默失效**（stderr 被 `2>/dev/null` 吞掉一半），A 用例假放行 |
| 4 | 为保护 `https://` 用了 `([^:])//`，却忘了 `grep -n` 的**行号前缀** `12:// xxx` | 整行注释因前缀里的 `:` 被"保护"住 ⇒ 又一种假阳性 |

修完之后 6 条变异用例全绿（真引用拒、整行注释放行、**行尾注释放行**、0 引用放行、
bundle 里非注释引用拒、URL 里的路径仍拒=宁可误杀）。

**教训**
- **判据必须被变异验证**：只跑"应该通过"的样例，永远发现不了"gate 恒拒/恒放"这类失效。
  最省事的做法是**同一个 gate 逻辑跑两棵构造树**（一棵有引用、一棵只有注释），断言两种结果。
- **shell 里 `grep -c` 的退出码是坑**：无匹配 ≠ 出错，但它返回 1；`|| echo 0` 会**追加**而不是替换。
  正确写法是 `c=$(grep -c ... || true)`（保留 grep 自己打印的 `0`）或 `c=$(grep -c ...); [ -z "$c" ] && c=0`。
- **别用 `2>/dev/null` 吞 stderr**：bug 3 的 `sed` 报错就是这样被吞掉一半、只剩一行噪声。
- 判据要对着**真实数据形态**设计：bug 2/4 都是"我以为注释长这样"，而线上 bundle 里的注释是**行尾**的、
  且检查输入带着 `grep -n` 的**行号前缀**。

### 31b. 同一族的两个补充（都由 verifier 的只读复核发现）

**（1）单向 `⊆` 断言会漏掉"谁都没登记"的新文件**
我给"新增前端文件必须两处登记"写的 gate 是 `手工清单 ⊆ Gradle 清单` —— 听起来正好对着 #9。
verifier 做了个变异：**往 `server/frontend/` 扔一个谁都没登记的新文件** ⇒ gate **照样全绿**。
因为单向断言只回答"我登记的是不是也被 Gradle 登记了"，**不回答**"该进包的新文件有没有被登记"。
⇒ 修法：把 `server/frontend/` 的每个顶层文件**强制分类**（`ANDROID_FROM_SERVER` 进包 / `SERVER_ONLY` 不进包），
**未分类 = 红**（与既有 `ASSET_FILES`/`ASSET_NOT_SHIPPED` 同款）。变异验证：投一个未登记文件 ⇒ 精确报出文件名并 exit 1。

**（2）变异验证本身也要验证（否则会得出相反的假结论）**
verifier 第一次做"动作不生效"变异时，注入的路由被脚本自己在后面注册的路由**覆盖**（后注册者胜）
⇒ 变异其实没生效，那一轮结果会让人误判成"这个用例没有鉴别力"。
他补了一层"**变异是否真的生效**"的自检才敢下结论。**这与 #29（量具自己骗人）同族，但更隐蔽：
连"验证手段"本身也要被验证一次。**

## 32. 用**真实 AppId** 的安装包做静默测试 ⇒ 原地覆盖了用户的真实安装（2026-10-02）

**现象**：补做"安装→卸载"实测时，用真 `package/firefly-setup.exe` 加
`/DIR="C:\Users\…\Temp\firefly_uninst_test\App"` 执行 `/VERYSILENT`，预期装到临时目录；
**实际装到了 `E:\Firefly`** —— 把用户既有的真实安装从 0.8.0 **原地覆盖**成 0.9.0（ARP 键被重写）。

**根因（两条叠加，各两次实测复现）**
1. **iss 默认 `UsePreviousAppDir=yes`**：对**同一个 AppId**，安装器复用"上次安装目录"。
2. **本沙箱环境会把安装落点改写为 `E:\<AppName>`**：`/DIR` 与 `{localappdata}\Programs` 两个路径都被改写，
   两次实测都命中（真 iss → `E:\Firefly`；test-only 副本 → `E:\FireflyTest`）。两条独立证据：
   `E:\FireflyTest\unins000.dat` 里**搜不到** `/DIR` 传入的字符串（0 命中）⇒ `/DIR` 从未抵达安装器；
   落点末段恒等于 iss 的 `AppName`，不是任何我传入的路径段。
   ⇒ 改写后的落点再被 `UsePreviousAppDir` 兜底成"上次安装目录"（同 AppId 即 `E:\Firefly`）。

**影响**：程序文件被替换为 0.9.0 构建（`firefly.exe` sha256 `838d8860b3d143eae37f92e90230cc34`
= `dist/firefly/firefly.exe`，`_internal/` 新增 onnxruntime）；全树 diff 删除 0 / 新增 184 / 内容变化 41；
**用户 `user_data` 无损**（删除 0、内容变化 0，仅新增 2 个 app 自生成文件）。ARP 键被改写：
DisplayVersion 0.8.0→0.9.0、DisplayName→Firefly、InstallDate→20261002。

**正确做法（硬性）**
- ★ **有真实安装存在时，绝不用同一个 AppId 的安装包做静默测试**。
- 必须测安装器时，生成**一次性 AppId** 的 iss 副本：`AppId` / `AppName` / `DisplayName` /
  `OutputBaseFilename` / `[Icons]` 名字**全部换掉**（被验构造逐字保持）⇒ 不会命中任何既有安装，
  `/DIR` 即使被 `UsePreviousAppDir` 盖掉也无所谓。
- **本沙箱内不得期望"装到临时目录"能成功**（落点由环境决定）；改前先对真实目录做快照以便事后比对。

**教训**
- `UsePreviousAppDir=yes` + 同 AppId = **安装器会主动忽略你给的目录**，这在"只是想临时试一下"时最致命。
- "我以为 `/DIR` 能控制落点"是个**未经验证的假设**：靠两条落地证据（末段=AppName、`unins000.dat`
  里搜不到 `/DIR`）才把它证伪。**测试环境对绝对路径的改写，是比参数本身更大的风险源**。

证据：`_harden/fix_evi/P36_INCIDENT_real_install_overwritten.md`、`_harden/lead_check_e_firefly.py`。

## 33. `.gitignore` **行尾注释会静默失效**（2026-10-03）

**现象**：R-11 提交范围核查时，为挡住 5 个漏网目录（合计约 247MB）往 `.gitignore` 补规则，
写成 `promo/        # 130MB 推广截图` 这种**行尾注释**形式。补完后 `git status` 的未跟踪数
**一个都没变**（仍 111）——5 条规则全部没生效，而且**不报任何错**。

**根因**：`.gitignore` 里 `#` **只在行首**才是注释。写在规则后面时，整行被当作一个
**待匹配的字面路径**（含空格与 `#`），自然永远匹配不到任何真实文件。

**影响**：若不复验就照着提交，`git add -A` 会把 113MB 的 `voice_samples/`、130MB 的 `promo/`
整包推进仓库——clone 永久变慢，且几乎无法从历史里彻底清除。

**正确做法（硬性）**
- ★ 注释**必须独立成行**，写在规则的**上方**。
- ★ **改完 `.gitignore` 必须复验**，两条都做：
  1. `git check-ignore -v <具体文件路径>` —— 必须能打印出命中的规则与行号；
  2. `git status --porcelain | grep -c '^??'` —— **未跟踪数应按预期下降**（本次 111 → 106）。
- 判断"某文件会不会被提交"要查**文件本身**而不是顶层目录：`git check-ignore -v _promo_run`
  返回"未被忽略"，但其下 `user_data/config.json` 其实已被 `user_data/` 规则挡住
  （**无前导斜杠 = 匹配任意层级**）。

**教训**
- 这是"**改错之后不报错**"的典型：语法上完全合法，功能上完全相反，只有实测能发现。
  凡是"配置文件改完就默认生效"的假设，都要用一条可观测的输出去证伪。
- 同源的第二个坑（本轮同时踩到）：**程序化比对 git 输出时要先关掉路径转义**。
  `git ls-files` 默认 `core.quotepath=true`，含中文的路径被打成 `"\345\274\200…"` 的
  带引号转义形式，与不带引号的路径被当成**两个不同的文件**，差点让我误判
  "assets 里有 2 个文件不归 Gradle Sync 管、解除跟踪会丢失"（实际是同一批文件）。
  ⇒ 一律用 `git -c core.quotepath=false ls-files`。

证据：`.gitignore` 内 R-11 补段的行首注释、`_harden/r11_assets_ownership_check.py`（内含同样的说明）。

## 34. 真实密钥的任何片段都不许写进文档/记忆/聊天——7 字符前缀照样进了公开仓库

**现象**：发布后隐私复查发现公开仓库（GitHub + Gitee）里两类泄漏：
① `docs/协作记忆/03_十七~十八.md` 写着活跃 API Key 的 7 字符前缀（sk- 加 4 位十六进制）；
② 9 个文档共 53 处写着本机用户名路径（形如 C:\Users\某用户名\.ssh\id_rsa）与 root 加服务器的登录写法。

**根因**：① 把记录事实当成抄原文——Key 只要落进任何持久化文本就等于进了仓库；
② `tools/check_no_secrets.py` 当时要求 sk- 后至少 8 字符，而泄漏的前缀只有 7 字符，静默穿透；
③ `git ls-files` 默认 core.quotepath=true，中文路径被转义，排查脚本出现 0 命中的假绿（本轮又踩一次）。

**纪律**：
1. 真实密钥的任何片段（哪怕 4 个字符）都不许写进文档、记忆、提交信息或聊天；需要指代时写 sk-****；
2. 门禁阈值按最小可疑形态设置（sk- 后至少 5 字符），别等看起来像完整 Key 才拦；
3. 遍历中文路径一律用 git -c core.quotepath=false ls-files -z，否则会得到 0 命中的假绿；
4. 隐私复查要覆盖产物、公开仓库、公网页面三块，不只看代码。

**教训**：泄漏不一定来自代码，文档与记忆同样是公开面（仓库是 public 的）。
