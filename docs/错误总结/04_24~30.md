## 24. 加了缓存却没变快 —— 说明真凶还没找到，别急着交付（2026-10-01）

**背景**：规模压测（`tests/test_plaza_scale.py`）测出 480 张卡时广场列表 p95 **451ms**（设计验收 300ms），
趋势 **4.58× / 4× 规模** ⇒ 纯线性扫描。于是加缓存。

- **第一版**：缓存 `iterdir` + 读 `meta.json`。重测 → 热路径**仍 474ms**（几乎没动）。
- **第二版**：发现 `list_cards` 里还有"每卡每请求 `stat(card.zip)`"（同秒排序的 mtime 次级键），
  把它也纳入缓存。重测 → **仍 553ms**。
- **第三版（真凶）**：`_public_view()` 每张卡要查 `cover` + `avatar` 两个槽位，而 `_find_asset()`
  **每个槽位都 `iterdir` 一遍 `assets/<id>/`** ⇒ 480 张卡每请求约 **960 次目录列举**。
  把它也缓存后 → **p95 24ms（≈18 倍）**，且 120→480 张几乎不变（27ms→33ms）。

**教训**
- **"改了但没变快"就是强信号：瓶颈在别处，继续量，别交付。** 前两版改动本身都"讲得通"，
  但数字没动就说明命中的不是瓶颈 —— 如果当时收手，就会留下一个"看起来优化过了"的假结论。
- 缓存要按**最内层的 I/O 调用点**去包，而不是按"我以为最贵的那一步"。这次的真相是
  "投影函数里藏着一个按卡的目录列举"，它不在扫描循环里，纯读代码很容易漏。
- 尾巴要**如实报**：TTL 过期后的第一个请求仍要付一次全量扫描（120 张 162ms、480 张 431ms）。
  只报热路径 p95 等于把尾巴藏起来 ⇒ 压测里**冷启动与热路径分开报**
  （`cold_ms()`；剩余项见 `docs/未完成事项清单.md` P4-11）。

## 25. 网关"一次性申请整包额度"⇒ 大响应被整段丢掉，线上登录页白屏（2026-10-01 部署当天暴露）

**现象**：把共创平台上到服务器后，**登录页白屏**。浏览器控制台：
`Failed to load resource: net::ERR_CONTENT_LENGTH_MISMATCH`（`/js/bundle.js`，490KB）。
**直连主服务 8765 一切正常**（`curl` 收到完整 489960 字节），**只有经网关 8787 才坏**。
极具迷惑性：`style.css`（gzip 后 ~15KB）能过，`bundle.js`（gzip 后 ~120KB）挂掉。

**根因**（`server/download_server.py::_proxy`，M4 引入）：为了顺手 gzip，网关对
"200 + 已知 Content-Length ≤4MB"的响应会**先缓冲整包**，然后
`GOV.take(cls, len(整包), timeout=30)` 一次性申请额度。而令牌桶的**容量只有
`类速率 × burst`**（默认 ≈ 该类每秒额度的 0.25 秒，api 类约 55KB）——
**任何大于桶容量的响应永远拿不到额度** ⇒ `take` 超时返回 False ⇒ 整段跳过写入
⇒ 响应头声称 N 字节、实际 0 字节 ⇒ 浏览器拒收整包。

**修法**：把"已缓冲的正文"改成**分块写**（每块单独 `take`），见 `_write_throttled()`；
并把"上游截断"如实报 502（不再发出自相矛盾的响应）。
守卫：`tests/test_gateway_proxy_body.py` 新增"**开限速**（`FIREFLY_BW_KBPS=2800`）+ 426KB 响应"两例
—— 原来的用例全都把限速设成 0，所以**从没走过这条被限速的缓冲写路径**。

**教训**
- **测试把被测量的机制关掉了，等于没测**：`FIREFLY_BW_KBPS=0` 让所有既有反代用例都绕开了限速。
  凡是"被测行为依赖某个开关"的，至少要有**一例把开关打开**。
- **"小文件能过、大文件挂"是典型的容量/阈值症状**，别去怀疑内容（编码、类型），先量阈值。
- **多客户端对照能快速二分**：`curl 直连 8765` 完整 vs `经网关` 0 字节 ⇒ 一口咬定网关，
  省掉大量猜测。

## 26. UTF-8 文件被按 GBK 读写 ⇒ 登录页 JS 整整一个半月没执行（2026-08-14 造成，2026-10-01 发现）

**现象**：线上 `/login.html` 能打开、表单也在，但**点「登录」毫无反应**（JS 全不执行）。
真浏览器抓到的报错是 `pageerror: Invalid or unexpected token`（**解析期**错误，无堆栈）。

**根因**：文件在 **2026-08-14 15:30** 被整体写坏——所有中文变成"UTF-8 字节按 GBK 解码"的乱码
（459 行里 52 行），其中 **6 处字符串的闭合引号被吃掉的字节连带吞掉**（例如
`showErr(..., "验证码已发送，请查收邮箱")` 变成 `"…请查收邮锛?);`）⇒ 内联 `<script>` 解析失败
⇒ **整段 JS 不执行**。`server/` 不在 git 里，所以**没有任何历史版本可回滚**，
这份坏文件就这样在线上躺了一个半月（含 9-20 的发布快照）。

**怎么修**：这类乱码是**确定性**的 ⇒ 逐行 `gb18030 → utf-8` 反解（30 行无损还原）；
当初被替换成 `?` 的少数**单个丢失字符**按上下文补全（37 行，含那 6 处闭合引号）。
修完必须过三道自检：① 无 U+FFFD/私用区；② 无"中文旁的 ?"；③ **`node --check` 内联脚本通过**。

**教训**
- **`Get-Content -Raw` / `-replace` / `Set-Content` 改 UTF-8 文本会写坏文件**（协作记忆 #15④）——
  这次是这条纪律的**代价实证**：一次写入 = 一个半月登录不可用。
- **"页面能打开"不等于"功能可用"**：curl 200、表单可见都骗过了；**只有真浏览器跑一遍**
  才能看到"点按钮没反应"。这就是本项目坚持真浏览器验证的理由。
- **没有版本控制的目录（`server/`）必须靠备份兜底**：这次能找到并修回来，靠的是
  `login.html.broken.bak` + 逐行反解；如果连坏文件都被覆盖，就只能凭记忆重写页面。
- **排查同类污染要用"判定性检验"而不是猜字**：我把"`gb18030→utf-8` 反解成功"当判据，
  扫 137 个前端文件 ⇒ **只有 login.html 中招**；若靠"含某些怪字"去猜，`pinyin.json`
  这类字典文件会大面积误报。

## 28. 缓存文件的**写入位置**反馈到它自己的失效判据 ⇒ 自激重扫（2026-10-01，P4-11 持久索引）

**现象**：给广场加 `_index.json` 持久索引后，**热路径反而从 p95 24ms 崩到 490ms**（480 张卡），
120 张的 p50 也从 20ms 涨到 235ms —— 等于每个请求都在全量重扫。

**根因（自激）**：索引的失效判据之一是「`cards/` 目录 mtime 变了 ⇒ 重扫」，
而我把索引文件放在了 **`cards/_index.json`** —— **写索引这个动作本身就会更新 `cards/` 的 mtime**
⇒ 每次"扫描 → 写索引"之后，下一次请求立刻发现"目录变了"⇒ 再扫 ⇒ 再写 ⇒ 循环。
**缓存把自己写脏了。**

**修法**：索引文件挪到**扫描根之外**（`plaza_root()/_index.json`，扫描根是 `plaza_root()/cards/`）。
一行位置调整即断环。

**第二个坑（同一处代码）**：修完自激后冷读仍有 **283ms**。查服务端日志（加了受环境变量门控的
`FIREFLY_PLAZA_INDEX_DEBUG` 打印）发现索引**一直在命中**——慢的不是扫描，而是
**资源名**：投影每张卡要查 `cover`+`avatar`，每个槽位都要 `iterdir` 一遍 `assets/<id>/`
⇒ 480 张 = **960 次目录列举 ≈ 260ms**。也就是说"把一半的数据缓存起来"照样会露馅
（前两版缓存漏 mtime、漏 `_find_asset`，错误总结 #24 记过一次，这次是**第三处**）。
把资源名一并写进索引并在加载时**预热** `_ASSETS` 后，480 张冷读 **24ms**。

**教训**
- **缓存文件的存放位置是它自己的输入**：一旦失效判据依赖某个目录的 mtime，就别把缓存写进那个目录。
- **"缓存了"要问清"缓存了几件东西"**：投影链上每一处 O(n) 查找都得覆盖（meta / zip mtime /
  cover / avatar …），漏一处就等于没缓存 —— 这正是 #24 的复发版。
- **压测必须同时报冷热**：只报热路径，这次的自激（热路径 490ms）反而会被当成"没优化"；
  只报冷路径，自激根本看不见。两个一起报，改动的真实效果才无处躲。
- **调试开关要有**：`FIREFLY_PLAZA_INDEX_DEBUG=1` 让服务端把"命中/拒①/拒②/拒③"打到 stderr，
  否则"索引为何没吃到"只能靠猜（这次就是靠它一眼定位）。

## 27. 网关吞掉主服务的路由命名空间（`/hotupdate/*`）—— 前端永远拿不到热更状态（2026-10-01 部署当天发现）

**现象**：线上真浏览器冒烟里，前端调用 `/hotupdate/status` 得到 **404**，而该端点明明注册在
`app/api/router.py:187`。curl 直连 8765 正常，经 8787 就 404。

**根因**：网关把**整个 `/hotupdate/*` 命名空间**当成自己的补丁分发路径
（`_serve_hotupdate` 只认 `/hotupdate/<x.y.z>/<latest|patch-N.json|patch-N.zip>`），
形状不匹配就**直接 404，从不转发** ⇒ 主服务上同前缀的路由（`/hotupdate/status`）被整段遮住。

**修法**：网关只接管"补丁形状"（`_is_hotupdate_patch()` 判据与 `_serve_hotupdate` 的审查一致），
**其余 `/hotupdate/*` 一律反代给主服务**。修复后线上 `/hotupdate/status` 返回
**401（未登录）**——证明请求真的到达了主服务。守卫：`tests/test_gateway_proxy_body.py` ⑨/⑨b/⑨c。

**教训**
- **反代网关"按前缀接管"时，必须给主服务留出同前缀的出口**：要么精确匹配后接管、
  要么把不匹配的**转发**（绝不能 404 吞掉）。否则主服务新加一个同前缀路由就静默失效。
- 这类问题在**单元测试里看不见**（两边各自都对），只有"经网关的真实端到端"才暴露 ⇒
  又一条"真环境验证不可替代"的实例。

## 29. 量具自己骗人：`sar` 的 12 小时制列位、PS 5.1 不让改 `Range` 头（2026-10-01，P4-4 交叉验证）

做"`sar` 采样 vs 网关字节记账"的互校时，**两次都先得到"零"**，都不是被测系统的问题：

1. **`sar -n DEV` 在 en_US 下时间是 12 小时制**（`05:55:46 PM`）⇒ 我按"第 1 列=时间、第 2 列=网卡"
   写的 awk 正则，把 `PM` 当成了网卡名 ⇒ **样本数 0**，程序却"正常"输出 0 字节。
   修：`LC_ALL=C sar -n DEV …` 强制 24 小时制，并把匹配放宽为 `$1 ~ /^[0-9]/ && $2 == iface`。
2. **PowerShell 5.1 的 `Invoke-WebRequest` 不允许设置 `Range` 头**（报"必须使用适当的属性或方法
   修改 Range 标头"）⇒ 下载 0 字节。修：改用 `curl.exe -r 0-4194303 -w "%{size_download}"`
   （顺带更像真实客户端，也能拿到 206 与耗时）。
   另：`-w "%{size_download}"` 这类 `%{...}` 在 PS 里不会被展开，安全；但**脚本文本里的中文**
   会被 PS 5.1 按 ANSI 解码 ⇒ 测量脚本一律**写纯 ASCII**（协作记忆 #15④/#17 的同族）。

**教训**：**"测量结果为零"要先怀疑量具，再怀疑被测对象**（这与 #23「测量代码自己的 bug」同族）。
两条自保动作：① 量具先做一次**已知输入的冒烟**（比如先量一个 1KB 请求，非零才继续）；
② 采样类工具的**样本数**要一起打出来（`sar_samples=0` 一眼就能看出根本没采到）。

**最终结果（验收通过）**：客户端实收 `4,194,304` B；网关记账增量 `4,194,304` B；
令牌桶 `bulk` 增量 `4,194,304` B；`sar` eth0 出向 `4,063,119` B ⇒
**偏差 3.1%（验收线 <20%）**；且 4MB 用时 11.9s = **352 KB/s ≈ 满 2800kbps**
⇒ 空闲时单流吃满带宽、有竞争才让路，符合 04 文档的设计意图。

## 30. 令牌桶的**发放单位大于桶容量** ⇒ 永远拿不到额度（2026-10-01，单连接限速暴露出来）

**现象**：新写的单连接限速集成测试用 `FIREFLY_CONN_MAX_KBPS=400`（生产默认是 1400）时，
下载**卡满 60 秒**然后连接被截断；客户端 `TimeoutError: timed out`。
把上限调回 1400 一切正常 ⇒ 典型的"只在特定参数下才现形"。

**根因**：`take(nbytes)` 的判据是"桶里攒够 `nbytes` 才发"，而**桶的上限就是容量**（`速率 × burst_seconds`）。
当 `nbytes > 容量` 时，攒到天荒地老也到不了 `nbytes` ⇒ 每次调用都等到 `timeout` 才返回 False。
- 400kbps 时桶容量 = 50000×0.25 = **12500B < 16384B（写出块）** ⇒ 死等；
- 生产 1400kbps 时容量 43750B > 16384B ⇒ 侥幸正常。

**同一 bug 还藏在类级限速器里，只是被"空闲池"掩盖了**：`bulk` 桶容量仅 **10937B**，而块是 **16KB**
——单看类桶永远不够，但 `take()` 有"空闲池"这条第二通路（87500B）兜着，所以平时看不出来；
**一旦链路繁忙、空闲池被高优先级抽干**，bulk 就会卡到超时再截断下游。也就是说：**这个 bug 一直在生产里，
只是被另一条通路遮住了**（"掩盖"比"没有"更危险 —— 它在最需要限速的时候才发作）。

**修法（两层，缺一不可）**：
1. **发放单位不得大于桶容量**：`Governor.chunk(cls)` 现在返回 `max(1024, min(MIN_CHUNK, 桶容量))`
   —— bulk 自动收窄到 ~10.9KB；1024 是"别把块切太碎"的地板。
2. **赤字法**：`take()` 的判据改为 `tokens >= min(nbytes, burst)`，取出时允许**余额为负**
   （下一次自然多等）。这样即使地板块仍大于极小桶（80kbps 时 bulk 桶只有 312B），也能正常推进而不是死等。

**教训**
- **限速器的"发放单位"与"桶容量"必须一起设计**：任何"等到足够多再发"的实现，都要回答
  "我能等到吗？"——上限 < 单位就等于永久饥饿。
- **被次要通路掩盖的 bug 最危险**：空闲池让默认参数下完全正常，于是它只会在**压力最大**时爆发。
  测限速必须测**极端参数**（很低的上限）和**冲突场景**（空闲池被抽干），不能只测默认值。
- 断言也要跟着改：原来 `test_server_traffic.py` 里"限速时恒用 16KB 块"这条**编码了错误假设**
  （块可以大于桶容量）；正确的不变式是 **块 ≤ max(1KB, 该类桶容量)**，并另有一条"地板大于桶容量时
  靠赤字法仍能拿到"的正面用例。
