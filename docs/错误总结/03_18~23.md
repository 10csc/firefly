## 18. 真机专属的两个坑：系统会拦你的"自重启"，前端会伪造"启动成功"（2026-09-25）

**背景**：热更新 v2（py 层）代码写完、80 项单测全绿、五门禁 PASS，然后在真机（704c2441 /
Android 15）上连炸两处 —— **单测里永远抓不到**，因为没有 ActivityManager，也没有真实 WebView 生命周期。

**坑 A：`AlarmManager` 自拉起在后台被系统拦掉，而代码已经把界面结束了**

真机日志：
```
I FireflyHotUpdate: 含 py 层的补丁就绪且空闲 → 壳重启 App 进程
W ActivityTaskManager: Background activity launch blocked … (BAL_BLOCK) result code=102
```
Android 10+ 禁止后台应用启动 Activity。原实现无条件 `finishAffinity()` ⇒ 闹钟被拦、
界面已被结束 ⇒ **补丁永不生效且每 8 秒重试一次**（实测循环十几分钟）。用户视角是"App 打不开"。

**坑 B：前端页面 reload 会重跑 `boot()`，于是"启动成功确认"被自己伪造**

重启被推迟后，前端轮询触发 reload → 页面重跑 `boot()` → **无条件** POST `/hotupdate/boot-ok`
⇒ `pending_serial` 被清。真机证据：进程 PID 始终没变，日志却打印"新进程已完成启动确认"。
后果比 A 更隐蔽：**安全模式（坏补丁连续两次启动失败 ⇒ 自动回滚）被彻底绕过** ——
坏补丁会被标记为"启动成功"。

**为什么单测抓不到**
- 单测里没有 ActivityManager，`finishAffinity()` 只是个空动作，"闹钟被拦"不存在；
- 单测里没有 WebView 生命周期，`boot()` 只在测试里被显式调一次，看不出"reload 会再调一次"；
- 两处的失败都是**状态被静默改对**（`pending` 从 1 变 0），没有任何报错。

**正确做法**
- **"要动系统能力"的分支必须问系统当前状态**：能不能启动前台 Activity（`isAppForeground`）、
  有没有精确闹钟权限（`canScheduleAlarm`）——别假设"我调了就会生效"。
- **"确认类"信号必须带身份**：`boot-ok` 原设计只有"我起来了"，无法区分"新进程"与"同进程的页面 reload"。
  加一个进程号（`os.getpid()`）就够。凡是"收到某个信号就认为某件大事已完成"的设计，
  都要问一句：**这个信号能被伪造吗？**
- **后台推迟不是失败**：覆盖层已经落盘，下次冷启动天然生效（规范 §5.2.1 本来就允许），
  所以"什么都不做"是正确行为，不是降级。
- 回归钉在 `tests/test_android_install.py` E2 组（源码不变量）+ `tests/test_hotupdate_py.py` M 组（语义）。

**同轮顺带的两条小教训**
- 我在真机上反复点不中"设置"按钮，根因是 **WebView 从 y=120 开始**（`bounds=[0,120][1080,2244]`），
  我用 DOM 坐标去点，全部偏移了 120px —— **先量容器边界再算点击坐标**。
- 我用 PowerShell `Set-Content -Encoding UTF8` 还原被临时改过的文件，**写进了 BOM**
  （`git diff` 显示 `+//`）—— 项目早就写明"改文本一律用 Edit/Write 工具"，我又犯了一次。
  BOM 会污染三端同步副本，靠 `git diff --numstat` 才发现。

---

**表现**：给 `app/static/js/diag.js` 删一个函数时写了 `s = s[:i] + s[j:]`，
其中 `j = s.find("/** 一键清理", i)` 实际返回 **-1**（锚点没匹配上）
⇒ `s[-1:]` 只剩最后一个字符 ⇒ **文件尾部被整段截断**，
`clearDiagnostics()` 与它的 `window` 挂载一起消失。而脚本照样打印了 `V 已删除 diagSendAgain()`。

**用户看到的现象**：点「清理」**毫无反应** —— 连兜底提示都不出现，因为内联
`onclick="clearDiagnostics()"` 抛 `ReferenceError`，清理前后两张截图**逐像素相同**。
（对照：同一排的「导出并发送」正常，所以我一开始误判成"坐标点偏了"，白试了三轮。）

**根因**：把"找不到"当成了"找到了"。`find()/indexOf()` 用 -1 表示失败，
而切片语法对负索引是**合法**的（`s[-1:]` = 最后一个字符）⇒ 失败被伪装成成功。

**怎么防**：
- `find()/indexOf()` 的结果**只要用于切片或删除**，下一行必须 `assert i != -1`
  （或 `if i < 0: raise`），**不允许**直接进切片。
- **改完立刻断言目标关键字仍在文件里**（如 `assert "function clearDiagnostics" in t`），
  不要只打印一句 "V"。
- 语法检查**不足以**发现这类问题：截断后的 JS **语法仍然合法**，只有运行时才炸。

## 19. CSS 属性选择器找的是 HTML 属性，而代码设的是 JS 属性——封面一张都不会加载（2026-10-01）

**背景**：角色卡广场前端交付时，假 DOM 测试 31 项全绿、静态守卫（bundle / pack_view / pc_shell）也全绿。
我用 Playwright 在**真浏览器**里跑 21 项端到端时，第 8b 条暴露：列表里 3 张卡的 `<img>` 的 `src`
**轮询 6 秒仍是空字符串**（截图里只有占位字）——**一张封面都没加载**。

**根因**：`app/static/js/panels/plaza.js` 用 JS 属性标记待懒加载的图片：
```js
img._pzLive = true;                        // 设的是 **JS 属性**
root.querySelectorAll("img[_pzLive]")      // 找的是 **HTML 属性** → 永远空集
```
选择器返回空集 ⇒ IntersectionObserver 一个都没 observe ⇒ 没有一条 fetch 发出 ⇒ `src` 永远为空。
**全程没有任何报错**：渲染、事件绑定、面板切换全都"正常"。

**为什么假 DOM 测试抓不到**：它断言的是"**没有**直接写 `src`"（安全性：不绕过鉴权），
而没断言"最终**真的**取到了图"（功能性）。两者之间隔着"观察器 → fetch → blob → src"整条链路。
子代理在交付说明里诚实写了"只经假 DOM 与 CSS 复核，**未真浏览器确认**"——**这句话本身就是风险信号**。

**怎么防**
- 前端行为改动**必须有一次真浏览器端到端**（`tests/manual_*.py` 惯例 + 沙箱数据根），
  且断言要落在**可观测结果**上：`src` 变成 `blob:`、磁盘上真的出现文件、DOM 里真的出现目标节点，
  **而不是**"调用了某个函数/没写某个字符串"。
- 属性选择器只匹配 **HTML 属性**；标记用 JS 属性时，取全集再过滤
  （`root.querySelectorAll("img")` + `if (!img._pzLive) return;`），或统一改用 `setAttribute`。
- **harness 自己也会骗人**：本轮同一个脚本先后报出两类假失败——① "删引导节点"导致产品代码
  去给已移除的元素挂 `onclick` 而抛异常（改成用 CSS 隐藏而非删节点后消失）；
  ② init script 在 `documentElement` 存在之前就 `MutationObserver.observe(null)`。
  所以测试脚本要把失败**归因到具体阶段**（给错误打 `[阶段]` 前缀、用 `elementFromPoint` 打印真正的
  拦截者），否则"产品 bug"与"测试写错"会混在一起。

## 20. 调用处从不看返回值 —— 失败被推后三步、报成另一个断言（2026-10-01）

**现象**：`tests/test_hotupdate_py.py` 在全量套件里偶发两红：`D1 layer=py`、`D2 restart_pending 为真`。
但**真正的失败发生在这两步之前**：组 D 先调 `HU.check()`，它偶尔失败 ⇒ `_RT["available"]` 留空 ⇒
紧接着的 `apply_available()` 走"没有已就绪的补丁"**早退** ⇒ 返回的 dict 里**没有 `layer`** ⇒ D1 红；
`restart_pending` 自然仍是 False ⇒ D2 红。更隐蔽的是 **D3/D4 反而"假过"**：
`reload_pending=False`、`web_files=0` 在"什么都没应用"时恰好也成立 ——
**一次真失败被两条假通过掩盖了**。

**代价**：这个 flaky 挂了三轮（P4-5）。前两轮都在猜"是不是时序/负载"，因为报错信息只有一个
`layer=None`，指向的是**症状**而不是**病因**。第三轮先让失败自己开口（拿到断言名），才顺着
`apply_available()` 的早退分支反推到 `check()`。

**怎么防**
- **被测函数的返回值要么断言、要么至少打印**。12 处 `HU.check()` 全都只调用不看返回值 ——
  这就是"失败点被推后"的根源。改法：包一层 `check_update()`，失败即打印错误文本。
- 看到"莫名其妙的两红 + 旁边的断言反而绿"，先怀疑**上游某步静默失败了**，
  去查**第一个**可能有返回值的调用，而不是盯着报红的那两条。
- 断言设计上：`X is False` / `== 0` 这类断言在"前置步骤没执行"时**天然成立** ⇒
  关键前置要单独断言（本例应在组 D 开头断言 `check_update()["ok"]`）。
- 相关：#21（断言比了会变的字段，也是"报错指向症状"）。

**同族再现（同一天内，第二个文件）**：`tests/test_hotupdate.py` 的 `D2 serial 不大于已应用 → 不重复提示`
以**完全一样的机制**偶发（单跑 3 次全绿、全量偶发）：D2 之前那次 `HU.check()` 从不被断言，
它失败 ⇒ `apply_available()` 空转 ⇒ `applied_serial` 仍是 0 ⇒ 复查必然报"不是最新" ⇒ 红在 D2。
**一次性把两处一起修**，并把两个假更新源从**单线程** `socketserver.TCPServer` 改成
`ThreadingTCPServer` —— 单线程假源在负载下会让取数抖动，而**假源不该成为被测路径上的不确定因素**。
教训升级：这不再是"某个测试写差了"，而是**一类写法**（"调用不看返回值 + 关键前置不断言"）
在同一个仓库里会成对出现 ⇒ 修一处时**顺手 grep 同族**（`grep -n 'HU\.check()' tests/`）。

## 21. 断言把"按设计会变"的字段也比进去了 —— 高负载下必然偶发（2026-10-01）

**现象**：`tests/test_diag_export.py` 的「每个成员内容一致（同一份数据）」在**全量套件**里偶发红
（实测全量 3 次红 1 次），**单独跑 3 次全绿**。因为它逐成员比字节，而 `app/api/diag.py:124`
会写 `generated_at = time.strftime("%Y-%m-%d %H:%M:%S")` —— 两次导出只要**跨过 1 秒**就不相等；
全量套件有负载时这个窗口必然被跨过。

**怎么防**
- 比对"同一份数据"时，先问一句**哪些字段是按设计会变的**（时间戳、耗时、随机 id、mtime），
  **把它们归一化成占位再比**，而不是整块比字节。
- 这类失败的特征很好认：**单跑绿、全量红**，且失败点总落在"两次快照应相同"的断言上。
  遇到就先怀疑断言，别先怀疑产品。
- 同类已登记：`test_hotupdate_py.py`（`docs/未完成事项清单.md` P4-5）。

## 22. 只在**部分客户端**上现形的响应 bug：正文已缓冲读走，却走了"流式"分支（2026-10-01）

**现象**：网关（8787）对业务 API 的响应，用 `urllib` 请求时报
`IncompleteRead(0 bytes read, 33 more expected)`——**声明了 N 字节却一个字节都没写**。
浏览器访问一切正常。

**根因**（`server/download_server.py::_proxy`）：为了顺手 gzip，代码对"200 + 已知
Content-Length ≤4MB"的响应**先把正文缓冲读走**，然后 `gzip_if_worth()` 判断值不值得压。
原实现只在**压缩成功**（`packed is not None`）时使用缓冲内容；否则**落到流式转发分支**——
可流已经被读干了 ⇒ 写出 0 字节，而响应头里还带着上游的 `Content-Length: N`。
触发条件只要一条成立：客户端没发 `Accept-Encoding: gzip`、体积 <1KB、类型不在白名单、压缩没更小。

**为什么线上一直没事**：浏览器都会发 `Accept-Encoding: gzip`，于是总走压缩分支。
`curl`（不带 `--compressed`）、Python `urllib`、Go 等**不发 gzip** 的客户端才会踩中。
**发现方式**：新写的抢占压测用 `urllib` 当客户端 → 当场暴露。

**怎么防**
- **"要么 A 要么 B"的分支，必须确认每条路径都能处理同一份状态**：这里正文已经被消费，
  却有两处出口（压缩/流式），只有一处接住了它。修法是显式记住 `buffered` 并让它自己走一条出口。
- **`except Exception: raw = b""` 之后继续走正常路径** = 静默损坏：宁可如实报 502
  （上游截断就该 502），也不要发出自相矛盾的响应。本次也顺手把"上游截断"改成 502。
- **测试要用不同客户端各打一遍**（带/不带 `Accept-Encoding`、有无 `Content-Length`、上游截断），
  这类差异是 HTTP 层 bug 的通用藏身处。守卫：`tests/test_gateway_proxy_body.py`（9 项）。

## 23. 测量代码自己有 bug：单位乘了两次、窗口由样本数决定（2026-10-01）

**现象**：新写的抢占压测打印「基线 p50=**30353ms**、p95=44153ms」（即 30 秒），
而阈值也同步放大，所以**10 项断言全绿**——差点据此去改限速器（当时怀疑"低预算把 api 类饿死了"）。

**根因有两处，都在测试自己身上**
1. **单位二次换算**：`api_ping()` 已把耗时算成毫秒，`pct()` 又 `× 1000` ⇒ 打印值放大 1000 倍。
   真值是 **30.4ms**。"30 秒恰好等于 `take(timeout=30)`"这个巧合是我当时的误判线索。
2. **断言的量不是要证的性质**：有一条写"窗口 ≥1s 证明下载被限速"，但**窗口长度由请求条数决定**
   （25×18ms≈0.45s），与下载无关 ⇒ 随机红。改成断言"窗口内**下载只推进了 128KB**"。

**怎么防**
- **看数字不合常识就先怀疑测量代码**，别先怀疑被测系统。30 秒的 API 延迟、
  恰好等于某个超时常数——这种"整数巧合"是测量错误的高发信号。
- **单位写进函数名或注释**（`pct_ms` 优于 `pct`）；`pct()` 这类工具函数必须有单位契约。
- **断言的量必须就是你要证的性质本身**：要证"限速生效"，就断言"单位时间内传输了多少字节"，
  而不是"循环跑了多久"。
- 已在同一测试里把两条都注释留档，防止后人重犯。
