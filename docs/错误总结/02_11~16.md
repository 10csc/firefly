## 11. 告警去重键选了"每次都变"的字段——一次封禁弹 4-5 次窗

**表现**：用户报「服务器频繁提示我遭到攻击」。日报显示 `2026-09-18 22:03/04/06/07` 四条告警、
`2026-08-28 16:01-16:05` 五条告警，而每次**其实只有同一个来源 IP**，其余计数全 0
（主服务 429=0 / 网关 429=0 / SSH 失败=0 / 服务全 active）。

**根因**：两头各错一半，叠起来把**一次**封禁放大成 4-5 次打扰。
1. `server/attack_watch.sh` 统计「**最近 5 分钟** fail2ban 日志里的 `Ban` 行数」，阈值 `>= 1`
   → 一次封禁在 5 分钟窗口里**每分钟都命中** → cron 每分钟重写了标记文件，
   而标记里的 `time` 字段是 `date` 取的**当前时间**，每次都变；
2. `tools/attack_sentinel.py` 的去重键正是 `flag["time"]`
   → 「同一攻击不重复处理」这行注释从来没生效过。

**教训**：
- **去重键不能选会随时间自然变化的字段**。判断"是不是同一个事件"要用**事件本身的特征**
  （来源 IP、计数、类型），时间戳只能做**冷却窗口**，不能做等值比较。
- **"检测到什么"与"报几次"是两件事**。阈值宽 ≠ 不刷屏；上报链路的去重是独立的一环。
- **告警要能被证伪**：本例里"If the trigger is `fail2ban_bans`, then it must be inbound SSH,
  which my test never touched"一句话就能排除嫌疑——先看**触发字段**，别先怀疑自己刚做过的事。
- 附带：模型返回 `{"analysis":"","need_user":true}` 时照样弹了窗（空的"分析"+ "需要你行动：是"），
  **LLM 输出必须有本地兜底**，否则最烦人的那次恰好最没信息量。


## 12. 测试里写死"会随产品变更而变化"的数字——每次合理变更都报假失败（2026-09-19）

**表现**：同一天里，因为**加功能**而失败的断言出现了 4 次，全不是 bug：
| 位置 | 写死的东西 | 变更原因 |
|---|---|---|
| `tests/test_routes_split.py` | `"OK 70 39"`、`72 POST / 41 GET` | 新增 4 个公告端点 |
| `tests/test_snapshot.py` | 教程步骤 `nums[:9]` | 引导加了"公告""自动修复"两步 |
| `tests/test_core_split.py` | 字面量 `"VER 0.8.1"` | 版本升到 0.9.0 |
| `tools/check_hotupdate.py` | 「无补丁」直接 `return 0` | 新增了"公钥一致性/公告"两项必查 |

**根因**：断言写的是**当前状态的快照**，而不是**应当成立的性质**。
"端点数是 70"不是性质，"端点集合与 oracle 一致"才是。

**怎么防**：
- 门禁/测试里的数字**必须有一处真相源**，别处**读**它（本轮的修法：
  `test_routes_split` 用 `ast` 解析 `test_routes_oracle.py` 的集合字面量；
  `check_hotupdate` 把与补丁无关的检查提到早退之前）。
- 写断言前先问：**"产品正常演进时，这条断言该不该变？"** 该变的就不是断言。
- 版本号这类"必然会变"的值一律**现读**（`config.py`），绝不写进断言。

## 13. "先回缓存、后台刷新"的接口，前端不跟第二次 = 功能像没做（2026-09-19）

**表现**：真机装上 0.9.0，后端 `/notice` 明明 `serial=1`、`unread=1`，
但公告面板只显示内置指南、首页也不亮小圆点 —— 看起来"公告通道根本没生效"。

**根因**：`GET /notice` 的设计是**先回缓存、后台联网刷新**（为了不阻塞面板），
首次安装时这一次返回的是**空 payload + `refreshing: true`**；
前端 `notice.js` 拿到空结果就渲染空、然后**再也不请求** ⇒ 刷新结果没人取。
后端每处都对，错在**两端对"异步"的约定**。

**怎么防**：
- 只要接口有"`refreshing`/`pending`/`async` 之类字段"，消费方就**必须**处理它
  （重试、订阅、或下次进入时强制拉）。**返回了字段却没人读，等于没设计**。
- 这类 bug **单测抓不到**（单测里后端是同步的），**必须真机/真链路跑一次首装路径**。
  本轮正是"真机截屏"抓到，而不是 52 项单测。

## 15. bundle 是**单作用域拼接**，跨模块在顶层调用会撞 TDZ，把整块代码静默打死（2026-09-19）

**表现**：0.9.0 真机装上后，**公告功能整体不存在** —— 首页不亮未读小圆点、公告面板只有内置指南。
同时：后端 `/notice` 一切正常（`serial=1 unread=1`）、52 项公告/热更单测全绿、
APK 里也确实有 `notice.js` 与渲染代码。**唯一能看出问题的地方是真机界面**。

**根因**：`templates` 说清了 —— `bundle.js` 不是模块系统，而是把 `js/*.js`
**按 ORDER 拼进同一个作用域**（`import`/`export` 行被删掉）。ORDER 是
`… guide, main, hotupdate, notice`，而我在 `main.js` 顶层写了 `initNotice();`
⇒ 执行到那一行时，`notice.js` 顶层的 `let _payload = null;` **还没执行** ⇒
`ReferenceError: Cannot access '_payload' before initialization`（TDZ）⇒
**main 的顶层从这里中断，`notice.js` 整块再也没执行**（连末尾
`window.noticeOnOpen = …` 都没跑到），于是 `views.js` 里
`typeof window.noticeOnOpen === "function"` 恒为假 → 面板打开什么都不做。
后端的异步错误全被 try/catch 吞掉了，所以**没有任何日志**。

**为什么老的单测抓不到**：源码逐行都对，错在**拼装后的执行顺序**；
后端测试碰不到 JS；真机只是"看起来没功能"，不报错。

**怎么防**：
- **跨模块引用只允许发生在事件/函数调用期**（本项目 `build_frontend_bundle.py` 的注释里
  早就写了这条，我违反了它）。模块顶层只注册事件，不调别的模块的函数。
- 需要"启动即运行"的模块，**自己挂 `DOMContentLoaded` 自启动**（顺带保证 DOM 已就绪），
  不要指望别人在顶层调你。
- 新增 **`tests/test_frontend_boot.py`**：用 Node + 极简 DOM 桩把**产物 bundle 真跑一遍**，
  断言"顶层不抛异常 + 关键入口已注册"。它当场复现了这条 bug
  （`THREW:ReferenceError:Cannot access '_payload' before initialization`），
  也在修好后转绿 —— **产物级的冒烟测试是这类问题的唯一有效防线**。


## 14. 字符串切 URL / 切文件 = 早晚出错（2026-09-19，两处都被自己的测试抓住）

**表现 A**：`_to_notice_root("http://127.0.0.1:12345")` 返回 `"http://notice"`
（把 `//` 里的斜杠当成了路径分隔符）→ 公告源指向一个不存在的主机。
**表现 B**：`_pem_body()` 比对两份公钥时，把整份源文件当成了 PEM 正文
（Kotlin 的 `package` 行、Python 的 docstring 全进来了）→ 门禁报"公钥不一致"。

**根因**：对**有结构的东西**用了字符串操作。URL 有 scheme/netloc/path；
PEM 有 BEGIN/END 边界。`rpartition("/")`、`replace(标记)` 都懒得管结构。

**怎么防**：
- URL 一律 `urllib.parse.urlsplit/urlunsplit`（或等价的结构化解析），
  别用 `split("/")` / `rpartition("/")` —— 主机端口写法里"没有路径"是常态。
- 有边界标记的文本，先按标记**抽出块**再做后续处理；不要"删掉标记当成正文"。
- 这两处都是**写测试时当场抓到的**（`test_notice.py` A 组、`check_hotupdate.py` 公钥项）——
  说明"给新写的解析函数配一条边界用例"的成本远低于事后排查。

## 16. Gradle **增量**构建 → APK 里的前端是旧的（2026-09-20，已造成一次对外事故）

**表现**：改了 `app/static/js/*` 后跑 `assembleRelease`（增量）→
`BUILD SUCCESSFUL`、全量 72 项测试与五门禁全绿、`adb install` 也是 `Success`，
但**装到手机上的还是旧前端**：界面是新按钮、提示语却是上一版的

| 位置 | 是否含新代码 |
|---|---|
| `app/static/js/bundle.js`（源） | 有 |
| `android/app/src/main/assets/js/bundle.js`（`syncFrontends` 目标） | 有 |
| **APK `assets/js/bundle.js`** | **没有** |

**根因**：`syncBackend` / `syncFrontendAssets` 是 Gradle 的 **`Sync` 任务**，
其产物未被判定失效，打包环节读到的是**上一轮的中间产物**。
源与同步目标都是新的，**只有包里的旧**。

**后果（严重度所在）**：
- 它是**静默**的 —— 构建、门禁、装机三个信号全部正常，唯一异常是"包里的内容"；
- 我据此**误报过"已修复并验证通过"**：前几轮真机实测里，有几轮验的是旧前端；
- 直接导致一个陈旧 APK 被发到 **Gitee + 服务器**（公网可下），事后只能撤回，
  下载被迫钉回旧版 v0.8.1。

**怎么防**：
- **发版/装机前校验包内实际内容**：新增 `tools/check_apk_frontend.py`，
  比对同一份前端文件在 **源 / `assets/` / `app.imy` 内** 三处的 sha256，不一致退 1。
  判据已被本次事故本身验证（撤回那个包里 `__diagResult` 缺失，而源里有）。
- 前端一有改动就 **`clean assembleRelease`**；增量构建只用于"确定没动前端"的迭代。
- 这条与 #9（把资产放进 `Sync` 的输出目录）是**同一类**：`Sync` 的输入/输出关系
  看不清楚，文件就会以"成功"的姿态消失或过期。
