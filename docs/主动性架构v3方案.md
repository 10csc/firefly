## 一、信号量模型

两个独立信号量，作用域不同，重启行为不同。

### 1.1 REPLY（回复通道锁，全局）

| 属性 | 值 |
|---|---|
| 实现 | `threading.Lock`，模块级（`proactive.py` 或 `routes.py`） |
| 获取方式 | 响应式：**阻塞**（用户消息不可丢）；主动式/概率式：**非阻塞**（空闲才触发，忙则放弃） |
| 消耗时机 | 响应式（/chat 入口）/ 主动式或概率式（生成开始前） |
| 恢复时机 | 回复流程完成时（`finally` 保证释放，防 LLM 异常锁死） |
| 重启后 | 自动空闲（进程内锁，无并发必然为 1） |

### 1.2 ACTIVE（主动性互斥锁，会话级）

| 属性 | 值 |
|---|---|
| 实现 | `session["proactive_semaphore"]`，0/1 整数 |
| 作用 | 主动式与概率式互斥——触发后归 0，同一周期内另一个不可触发 |
| 消耗时机 | 主动式或概率式生成成功后 |
| 恢复时机 | a) 用户发送消息（/chat 入口复位 = 1）；b) 距上次主动 ≥10 分钟自动恢复（懒检查） |
| **重启后** | **从 proactive_log.jsonl 重建**（见第五节） |

## 二、前端↔后端交互协议

### 2.1 轮询

- 间隔：**10 秒**
- 两种触发路径走同一个 `checkProactive()`：
  - **路径 A**：响应式回复完成后，`setTimeout(checkProactive, 1000)`（≥1s 防抖）
  - **路径 B**：`setInterval(checkProactive, 10000)`（兜底轮询）

### 2.2 前端锁（预占用）

```
checkProactive() 调用：
  _idleOk() 通过
  → 立即锁输入框（状态："对方正在输入..."）  ★ 请求发出即锁
  → POST /proactive-status
     ├─ 返回空 → 解锁（耗时 <0.5s，用户无感知）
     └─ 返回消息 → 保持锁（思考 2-5s）→ 渲染动画 → 解锁（≈10-16s）
```

### 2.3 空闲判定 `_idleOk()`

```js
function _idleOk() {
    if (waiting) return false;        // 响应式等待中
    if (_rendering) return false;     // 主动消息渲染动画中（新增）
    if (_pending.length > 0) return false;  // 预提交窗口中
    if (inputEl && inputEl.value.trim()) return false;  // 正在打字
    return _chatVisible();
}
```

### 2.4 输入锁的完整时机表

| 状态 | 锁？ | 理由 |
|---|---|---|
| 用户自由输入 | ❌ | |
| 预提交窗口（_pending 5s） | ❌ | 用户可以继续补发多条消息 |
| 响应式 /chat 请求飞行中 | ✅ | waiting=true（已有） |
| 主动/概率 /proactive-status 请求发出→渲染完成 | ✅ | 预占用（本次新增） |
| 主动消息思考延迟（2-5s） | ✅ | 已有 |
| 主动消息动画渲染中 | ✅ | 新增，防 DOM 乱序 |

## 三、服务端统一入口

`POST /proactive-status` 内部做主动式 + 概率式串联判断，一次请求完成：

```
服务端流程：
1. 非阻塞获取 REPLY → 失败返回空
2. ACTIVE 检查（<10min 且未复位 → 返回空）
3. 主动式（gate_open：硬约束轮次+软约束概率+动机决策+生成）：
   触发 → ACTIVE=0 → 返回消息
4. 未触发 → 概率式（ACTIVE>0 → 掷概率 → 动机决策 → 生成）：
   ★ 概率掷骰放服务端（读 config prob_reply_value），前端滑条可视化保持
   触发 → ACTIVE=0 → 返回消息
5. 都不触发 → 返回空
6. finally: 释放 REPLY
```

**去掉的**：概率式的服务端时间门控（`prob_gate_open` 的"距最后 user 消息 ≥10min"检查）、前端 `_PROB_QUIET` 静默窗口。

## 四、重启兜底：ACTIVE 从持久化重建

重启后 ACTIVE 不从 0 开始，而从 proactive_log.jsonl + conversation.jsonl 重建：

```python
def _restore_active_semaphore(mode) -> int:
    rows = [r for r in _load_log(mode) if r.get("sent")]
    if not rows:
        return 1  # 从未主动过 → 空闲
    last_ts = rows[-1].get("_ts", 0)
    last_user_ts = _last_user_msg_ts(mode)
    if last_user_ts > last_ts:
        return 1  # 用户回应过 → 复位
    if time.time() - last_ts >= 10 * 60:
        return 1  # 超时恢复
    return 0      # 锁定中（防"退出重进刷主动"）
```

## 六、PC 端多开限制

`server.py` 启动时：

```
1. socket.bind(127.0.0.1:8765) 尝试
   ├─ 成功 → 正常启动（唯一实例）
   └─ 失败 → 旧实例存在
2. GET /health 探测旧实例
   ├─ 有响应 → POST /shutdown（优雅关闭）→ 等端口释放 → 正常启动
   └─ 无响应（卡死）→ 兜底 taskkill
```

新增 `/shutdown` 端点：flush 所有文件 → HTTP 服务停止 → 进程退出。

## 七、Android 后台概率触发

### 7.1 原理

| 环节 | 实现 |
|---|---|
| 前后台感知 | `MainActivity.onPause/onResume` 通过静态标志通知 `KeepAliveService` |
| 后台定时器 | `KeepAliveService` 内 `Handler.postDelayed`，每次随机 10-30 分钟延迟 |
| 前台时 | 定时器暂停（前端 10s 轮询已覆盖） |
| 消息生成 | Chaquopy 直调 `proactive.backdoor_proactive_check(mode)` → 写盘 |
| 通知 | Kotlin `NotificationManager` 发送（需 `POST_NOTIFICATIONS` 权限） |
| 点击通知 | Intent → MainActivity → 聊天页，消息已写盘 hydrate 可见 |

### 7.2 可行性

全部用户设备本地完成，**零服务器依赖**：
- 前台服务（KeepAliveService）不被系统杀死 → Handler 定时器可靠
- Chaquopy `Python.getInstance()` 进程内全局可用 → Service 中直调
- DeepSeek API 走用户本地网络 → 不是"需要服务器"
- 通知走 Android 系统 API → 纯本地

### 7.3 竞态安全

- 前后台切换时：`onResume` 先停定时器，再恢复前端轮询
- REPLY 锁保证**同进程内只有一个回复流程在跑**（前台请求 vs 后台定时器）
- ACTIVE 共享——后台触发也消耗，前台 hydrate 后可见

### 7.4 通知权限

`AndroidManifest.xml`：`<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>`

首次启动时 MainActivity 动态申请（Android 13+），用户同意后可用。
