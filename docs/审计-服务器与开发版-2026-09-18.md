## 二、安全漏洞（按危害从高到低）

### 2.1 【严重·结构性】全站明文 HTTP，凭证在网络上裸奔

**问题是什么**
服务器只有 HTTP（`http://101.200.14.126:8787`），没有 HTTPS。安卓 APP 的清单里写着 `android:usesCleartextTraffic="true"`，也就是允许明文。于是：

- 用户的**登录凭证**（Bearer token，有效期 30 天）每次请求都在网络上明文传输；
- 用户的**自己的 DeepSeek API Key**（`X-API-Key` 请求头）同样明文传输。

**为什么危险**
同一个 WiFi 下的人（咖啡厅、宿舍、公司网络）、或者链路上任何一跳，都能直接抓包拿到这两样东西。

- 抓到 token = 可以冒充这个用户，看他的对话、改他的设定、删他的数据。
- 抓到 API Key = 可以花这个用户的钱。

这不是理论风险，是抓包工具装好就能复现的。

**为什么现在还这样**
因为不想买域名、不想申请证书——这是现实约束，我理解。所以下面给的都是**零成本**方案。

**怎么修（按性价比排序）**

1. **立刻能做的（改代码，零成本）**：应用层加密敏感请求头
   - 在 APP 里内置一个服务器公钥；客户端把 `Authorization` 和 `X-API-Key` 这两个头的值用公钥加密后再发；服务器用私钥解密。
   - 能挡住"链路偷看"，挡不住"攻击者重放"（要防重放得加时间戳+nonce，属于第二步）。
   - 改动面：前端两个头 → 服务端入口解密一处；不需要域名、不需要证书、不需要花钱。

2. **同时做的（改配置，零成本）**：把 30 天的 token 缩短到 7 天
   - 现在已有滚动续期机制（`server/auth.py: verify_and_renew`，剩余 <7 天自动续到 30 天）。把 `SESSION_DAYS` 从 30 改成 7、`RENEW_BEFORE_DAYS` 从 7 改成 2 即可，用户体验几乎不变，但凭证被盗后的可用窗口从 30 天缩到 7 天。

3. **中期可选（自签证书，零成本但要改客户端）**
   - 自己生成一套证书（自签 CA），服务端上 TLS，APP 里内置该证书做校验。
   - 好处：传输层真正加密，且能防中间人。
   - 代价：要改客户端、要处理安卓 WebView 对自签证书的告警。建议放在 1+2 之后。

4. **不建议**：让用户"不要在公共 WiFi 用"——用户不会照做的。

**修完怎么算通过**
- 抓包工具在链路上看不到明文 token / Key（能看到密文）。
- token 有效期显示为 7 天，且长期使用的用户不会被动退出。

### 2.2 【高·已修未部署】下载页的直链没做信任校验（A4）

**问题是什么**
下载页有个"加速通道"：点击下载时，浏览器先问服务器要一个真实下载地址（`/download/resolve`），然后直接从 Gitee 的 CDN 拉文件。这个"要地址"的响应是 JSON，走的是明文 HTTP。

中间人可以把 JSON 里的地址改成自己的服务器，用户就会下载到一个**假的安装包**（exe 或 apk），装上就是木马。

**在哪**
- 线上运行的是：`/opt/firefly-downloads/download_page.py`（旧版，MD5 `9f78c3b4`）
- 仓库里已经修好了：`server/download_page.py`（新版，MD5 `554a0918`，多了 `trustedDl()` 函数，只放行 https + Gitee/GitHub 官方域名）

**怎么验证**
```bash
md5sum /opt/firefly-downloads/download_page.py   # 应为 554a0918...（现在是 9f78c3b4...）
grep -c trustedDl /opt/firefly-downloads/download_page.py   # 应为 1（现在是 0）
```

**怎么修**
把仓库的 `server/download_page.py` 传到**两个地方**（这是文档里写过的坑，别只传一个）：
```bash
scp -i C:\Users\FANGL\.ssh\id_rsa server/download_page.py root@101.200.14.126:/opt/firefly-downloads/
scp -i C:\Users\FANGL\.ssh\id_rsa server/download_page.py root@101.200.14.126:/opt/firefly/server/
ssh -i C:\Users\FANGL\.ssh\id_rsa root@101.200.14.126 'systemctl restart firefly-downloads'
```
（下载页是模板文件，改动后重启服务即可生效，不用重编前端。）

**修完怎么算通过**
- 两个路径下的 `download_page.py` MD5 都等于仓库版（`554a0918...`）。
- 打开下载页能正常显示版本号和文件大小（没有白屏）。

### 2.3 【中】服务器的 version.json 把更新链接指向了自己（明文）

**问题是什么**
`/opt/firefly/server/version.json` 和 `/opt/firefly-downloads/version.json` 里的 exe/apk 地址写的是：
```json
{"tag":"0.8.1","exe":"http://101.200.14.126:8787/download/firefly-setup.exe","apk":"http://101.200.14.126:8787/download/firefly.apk"}
```
仓库里同文件写的是 `https://gitee.com/...` 的 https 地址。

**为什么危险**
用户点"检查更新"拿到的是明文 HTTP 下载链接，中间人可以替换成恶意包（和 2.2 是同一类问题，但这条即使修了 2.2 也还在）。
另外服务器带宽只有 3Mbps，让用户从服务器下载 26MB 的安装包也很慢。

**怎么修**
优先方案：改回 https 的 Gitee 地址（仓库里已经是这样了，直接同步过去）。
保留方案：如果因为安卓浏览器把 Gitee 的 apk 存成 .zip 而必须走服务器直连，那就在 version.json 里**加一个 sha256 字段**，让客户端下载后校验；前端加一段校验逻辑。
```json
{"tag":"0.8.1","exe":"https://gitee.com/cpt-asymmetry/firefly/releases/download/v0.8.1/firefly-setup.exe",
 "apk":"https://gitee.com/cpt-asymmetry/firefly/releases/download/v0.8.1/firefly.apk",
 "sha256":{"exe":"...","apk":"..."}}
```

**修完怎么算通过**
- 浏览器打开 `http://101.200.14.126:8787/version.json`，链接是 https 开头（或带正确 sha256）。
- 服务器版 APP 点"检查更新"能正常显示版本。

### 2.4 【中】登录接口没有按 IP 的失败限制

**问题是什么**
现在的防护是"同一个邮箱连续失败 5 次，锁这个邮箱 15 分钟"（`server/auth.py: login_locked`）。
但**没有**"同一个 IP 失败多少次就拒绝"这一层。网关只有 300 次/分钟/IP 的粗限流。

**为什么危险**
攻击者手上如果有用户邮箱列表（注册要求 QQ 邮箱+群号+安装码，门槛不低，但不是零），可以对每个邮箱只试 4 次密码，就不会触发邮箱锁定。300 次/分钟的额度对撞库来说太宽松了。

**怎么修**
在 `auth.py` 里加一层 IP 维度计数（复用现成的内存/DB 计数写法）：
- 同一 IP，15 分钟内失败 ≥ 20 次 → 直接拒绝登录请求（返回"尝试过于频繁，请稍后再试"）。
- 成功登录后清掉该 IP 的计数。
- 注意：真实 IP 要从 `X-Forwarded-For` 取（网关已经会透传，`server/app.py: _real_ip` 已经处理了信任边界），不要用 socket 地址，否则所有请求看起来都来自 127.0.0.1。

**修完怎么算通过**
- 用脚本从同一 IP 连打 25 次错误密码 → 第 20 次之后开始返回"频繁"，而不是继续返回"邮箱或密码错误"。
- 正常用户输错 1-2 次不受任何影响。

### 2.5 【中低】邮箱验证码用的是可预测的随机数

**在哪**
`server/mail.py:86`
```python
code = f"{random.randint(0, 999999):06d}"
```

**为什么危险**
`random` 用的是可预测的伪随机算法。攻击者如果能观察到足够多的验证码（比如反复给自己的邮箱申请验证码），理论上可以推算出别人的验证码。

**补充说明（防止过度紧张）**：当前的验证码校验是"一次性弹出生效"（`verify_code` 里 `_codes.pop`），猜错一次验证码就作废，所以**实际爆破难度很低**。但这个生成方式本身不该用在安全凭证上。

**怎么修**
```python
import secrets
code = f"{secrets.randbelow(1000000):06d}"
```
顺手把 `verify_code` 里的 `item["code"] != ...` 改成 `not hmac.compare_digest(item["code"], (code or "").strip())`。

**修完怎么算通过**
- 发送验证码功能正常，注册流程能走通。

### 2.6 【中低】SSRF 防护有一个 DNS 时间差可以利用

**问题是什么**
服务器托管/中转模式允许用户填一个 API 地址（`X-API-Base`），服务器会替用户去请求这个地址。为了防止用户拿它探测内网（比如云服务器的元数据地址 `169.254.169.254`），代码做了一个检查：解析域名 → 判断 IP 是不是公网 → 是才放行。

**漏洞在哪**
检查用的是"解析一次 DNS"，真正发请求时 `requests` 会**再解析一次 DNS**。攻击者控制自己的域名服务器，第一次返回公网 IP（通过检查），第二次返回内网 IP（真正的请求就打到内网了）。这是典型的"检查与使用不一致"。

- 检查处：`app/modules/api_client.py: is_public_endpoint`
- 使用处：`app/routes_relay.py: relay_proxy` 里的 `requests.post`

**为什么危害不高**
需要攻击者：①有登录账号；②自己控制一个域名的 DNS；③能稳定命中那个时间窗。属于"有点技术才能用"的漏洞，但确实存在，而且这类漏洞在云环境里后果很严重（能读云主机元数据 = 拿临时凭证）。

**怎么修**
两个办法任选：
1. 校验通过后，把连接**锁定到已校验的那个 IP**（自定义 `HTTPAdapter` 或在 URL 里直接用 IP，同时把域名放进 `Host` 头）。
2. 更简单：解析出 IP 后，用一个 `session` + `urllib3` 的连接池覆盖 `socket.getaddrinfo`，让它在本次请求内只返回已校验的 IP。

**修完怎么算通过**
- 构造一个控制 DNS 的域名做两段解析，服务器只允许第一次校验通过的公网 IP，拒绝内网。

## 四、会导致数据丢失的地方（重点）

这一部分比"漏洞"更贴近用户实际会遇到的痛苦：数据莫名其妙少了、同步完发现对话不对了。

### 4.1 【高】同步写文件不是"原子"的，中途失败会写坏正式文件

**问题是什么**
"原子写"的意思是：先把内容写到一个临时文件，写完整了再一次性改名覆盖原文件。这样即使中途断电，原来的文件还是完好的。

现在的问题是：**同步链路是直接往正式文件上写的**。

- 服务器侧：`app/api/data_sync.py` 的 `sync_import()` 里多处 `fp.write_text(merged, encoding="utf-8")`
- 客户端侧：`app/api/data_sync.py` 的 `_sync_one_mode()` 里同样多处 `fp.write_text(...)`

**为什么危险**
同步过程中断电 / 磁盘写满 / 进程被杀 / 手机清理后台，正在写的那个文件会**被截断**——对话历史（`.jsonl`）少一截，用户看到的是"最近的聊天记录没了"。因为写的是正式文件，没有回滚的可能。

**对比：项目里其实已经有正确做法了，只是同步链路没用上**
- 导入/恢复：`infra/sync/restore.py: _swap_dir_into_place()` —— 临时目录 + 整体改名，失败自动回滚 ✅
- 上传图片：`modules/storage.py: atomic_write_bytes()` ✅
- 同步：❌ 直接写

**怎么修**
把同步链路里的所有 `write_text` / `write_bytes` 换成 `modules/storage.py` 里现成的原子写函数（如果没有文本版本就补一个 `atomic_write_text`）。涉及 `data_sync.py` 里大约 6 处写入点（`sync_import` 的 jsonl/favorites/文档三类分支、`_sync_one_mode` 的下载合并分支）。

**修完怎么算通过**
- 写一个测试：模拟"写到一半抛异常"，断言原文件内容不变、且没有残留半截内容。

---

### 4.2 【高】同步上传遇到网络异常时，用户会收到错误的提示

**问题是什么**
客户端同步（`_sync_one_mode`）里，上传文件的代码只接住了"HTTP 错误码"这一种异常：

```python
try:
    with urllib.request.urlopen(req, timeout=120) as r:
        rp = json.loads(r.read().decode("utf-8"))
    ...
except urllib.error.HTTPError as e:      # ← 只接住这个
    return f"上传失败（{e.code}）"
```

如果发生的是**连不上 / 超时 / 连接被重置**（`URLError`），或者服务器返回的不是合法 JSON（`JSONDecodeError`），异常会直接往上抛。

**接下来会发生什么（这才是真正的坑）**
1. 异常一路上抛到 HTTP 入口（`app/server.py: do_POST`）——那里**没有兜底**（见 4.3）。
2. 连接被直接断开，前端什么响应都收不到。
3. 前端 `app/static/js/sync.js:65` 写的是：
   ```js
   const d = await r.json().catch(() => ({}));   // 解析失败 → 空对象
   ...
   const err = "同步未完成：" + (d.error || "请先登录账号");   // ← 兜底文案是"请先登录账号"
   ```
4. **用户明明登录着，却看到"请先登录账号"，然后一脸问号地来问你。**

这是本次审计里最能说明"反馈机制缺失"的实例。

**怎么修**
1. `_sync_one_mode` 把 `except urllib.error.HTTPError` 换成 `except Exception`，并返回带错误码的结构化错误；
2. HTTP 入口加全局兜底（见 4.3）；
3. 前端兜底文案改成"同步失败（错误号 XXX），请导出诊断包给我"，不要瞎猜原因。

**修完怎么算通过**
- 把服务器地址改成一个不通的地址触发同步 → 界面显示"同步失败 + 错误号"，而不是"请先登录账号"。

---

### 4.3 【高·机制性】两个 HTTP 入口都没有全局异常兜底

**问题是什么**
本地版入口 `app/server.py: do_GET / do_POST`、服务器版入口 `server/app.py: do_GET / do_POST`，调用路由处理器时都是直接 `fn(self)`，**外面没有 try/except**。

**后果**
任何路由里没被捕获的异常（磁盘满、网络异常、代码 bug、编码错误……）都会穿透到 Python 标准库的 `ThreadingHTTPServer.handle_error`。标准库的行为是：**往 stderr 打一段 traceback，然后什么都不回**。于是：

- 用户端：连接断开 → 前端显示"网络错误"或上面那个错误的"请先登录账号"。
- 排障端：服务器版还能 `journalctl` 看，**本地版（用户电脑上的 exe）根本看不到**——日志只在窗口模式下写文件，普通用户不会去翻。

**怎么修（这是第五部分机制的地基，建议先做这一条）**
在两个入口的分发函数外面包一层：
```python
try:
    fn(self)
except Exception as e:
    trace_id = new_trace_id()
    log_diag(module=..., stage=..., code=classify(e), trace_id=trace_id, exc=e)
    try:
        self._json({"ok": False, "error": "服务器处理失败", "code": classify(e),
                    "trace_id": trace_id}, 500)
    except Exception:
        pass
```
注意：响应必须能重复发送失败（可能已经开始发响应体了），所以包在 try 里。

**修完怎么算通过**
- 人为在某个路由里 `raise RuntimeError("test")` → 前端收到 JSON 错误（带错误号和 trace_id），不是断连。

### 4.4 【中】备份打包不是原子的

**位置**：`app/api/data_export.py: backup_create()` → `fp.write_bytes(data)`

**后果**：写备份的中途失败（磁盘满、进程被杀），会在备份目录里留下一个**半截的 zip**。它会出现在备份列表里，用户可能选中它去恢复 → 恢复失败或恢复出残缺数据。

### 4.5 【中】快照恢复时，表情包是直接写进正式目录的

**位置**：`app/infra/sync/restore.py: _restore_full_snapshot()` 的 stickers 分支

**问题**：其它数据（角色包）都走"临时目录 → 整体换入"，唯独表情包这段是 `open(dst, "wb")` 直接往 `stickers/` 里写，而且**没有备份**。

**后果**：恢复中途失败 → 表情包目录里留下半截文件，且没有回滚。

**怎么修**：改成和角色包同一套路（临时目录 + 换入），或者至少先备份 `stickers/`。

### 4.6 【中低】恢复过程中"备份失败"的处置前后不一致

**位置**：`app/infra/sync/restore.py: _restore_full_snapshot()`

- 阶段 1（自建包）和阶段 2b（自建包数据）：备份失败 → **中止恢复**（做法正确，注释里也写明了"宁可恢复失败，不可丢数据"）
- 阶段 2a（正式角色包）：备份失败 → `except Exception: pass` → **静默继续**

同一个函数里两套标准，容易出事。

**怎么修**：统一成"备份失败就中止并告知用户"（推荐），或者统一成"记录警告并让用户确认后再继续"。

### 4.7 【中】自动同步失败是"静默"的，用户不知道数据一直没同步

**位置**：`app/static/js/sync.js:48 / 52 / 53`

以下三种情况都是默默 return，界面上没有任何痕迹：
- 节流期内（10 分钟）跳过
- 未登录 / 登录过期
- 本地后端没就绪

**后果**：用户以为数据在同步，实际上已经几周没同步成功过。等到换手机才发现记录没了。

**怎么修**
- 记录"最近一次成功同步时间"和"连续失败次数"；
- 连续失败 ≥ 3 次，或超过 24 小时没成功同步过 → 在界面上显式提示（黄色横幅，不阻断使用）；
- 这些状态一起写进诊断包，方便排查。

## 五、异常反馈机制（要新建，这是你要求的那套规范）

### 5.1 要解决的真实问题

你原话的意思我理解为：**用户只会说"同步不了/对话坏了"，你没法判断是哪个环节坏的。** 所以需要一套机制，让系统自己把"哪个阶段、什么错、什么上下文"记下来，用户一键导出，发给你，你一看就知道。

现状的三个缺口：
1. **没有错误码**：错误信息都是给人看的中文句子，机器没法统计、也没法定位（想找"同步上传网络错误"有多少例，做不到）。
2. **没有关联标识**：用户说"刚才同步失败了"，你不知道对应日志里哪几条。
3. **服务器版用户没有可导出的数据**（`/metrics` `/requests` `/pipeline` 全部 403），本地版用户也不会自己去找日志文件。

### 5.2 设计总览

```
用户操作
   ↓
[1] 入口分配 trace_id（8 位短号，如 A1B2C3D4）
   ↓
[2] 每个阶段写一行结构化日志（JSONL）→ user_data/logs/diag-YYYY-MM-DD.jsonl
   ↓
[3] 出错时：响应里带 {ok:false, error:"人话", code:"sync.upload.network", trace_id:"A1B2C3D4"}
   ↓
[4] 前端弹窗显示："同步失败：上传中断（错误号 A1B2C3D4）"
   ↓
[5] 用户点「设置 → 帮助与反馈 → 导出诊断包」→ 下载 diag-<日期>.zip
   ↓
[6] 用户把 zip 发给你 → 你解压看 summary.json 的错误码统计 → 用 trace_id 在 diag 里定位阶段
```

### 5.3 错误码规范

格式：`模块.阶段.原因`，全部小写英文点号分隔。

| 模块 | 阶段 | 原因 | 例子 |
|---|---|---|---|
| `chat` | `retriever` / `analyzer` / `polisher` / `organizer` | `timeout` / `key_invalid` / `no_balance` / `rate_limit` / `network` / `bad_response` | `chat.polisher.no_balance` |
| `sync` | `manifest` / `upload` / `download` / `merge` / `commit` | `network` / `timeout` / `rejected` / `readonly` / `corrupt` | `sync.upload.network` |
| `backup` | `pack` / `write` / `restore` / `verify` | `diskfull` / `perm` / `corrupt` / `missing` | `backup.write.diskfull` |
| `auth` | `login` / `register` / `verify` / `mail` | `badcred` / `locked` / `ratelimit` / `smtp` | `auth.mail.smtp` |
| `http` | 任意 | `unhandled` / `badrequest` / `toobig` | `http.unhandled` |

**规则**：同一个原因在本地版和服务器版用**同一个码**（这样一张统计表能同时看两端）。

### 5.4 诊断日志（diag JSONL）要记什么

**位置**：`user_data/logs/diag-YYYY-MM-DD.jsonl`（本地版在 exe 同级；服务器版在 `user_data/{uid}/logs/`）
**滚动**：保留 7 天，单文件超过 10MB 就切分
**格式**：一行一个 JSON 对象

必备字段：
```json
{"ts":"2026-09-18 17:20:31.482","trace_id":"A1B2C3D4","platform":"android|pc|server",
 "module":"sync","stage":"upload","event":"fail","code":"sync.upload.network",
 "dur_ms":15230,"attempt":2,"detail":{"file":"data/history.jsonl","bytes":48213},
 "err":"<class 'urllib.error.URLError'>: timed out","ver":"0.8.1"}
```

**必须脱敏**（写日志前统一过滤）：
- API Key / token / 密码 → 一律不写，或只写前 4 位 + 长度
- 邮箱 → 只留 `a***@qq.com`
- 对话正文 / 记忆 / 手账正文 → **不写正文**，只写长度和 sha256 前 8 位
- 用户目录的绝对路径 → 转成相对路径（`{uid}` 占位）

### 5.5 一键导出诊断包（要新建的端点 + 按钮）

**端点**：`POST /export-diagnostics`（服务器版需登录；服务器版必须按 user_id 过滤）

**产出一个 zip，内容：**

| 文件 | 内容 | 为什么要 |
|---|---|---|
| `summary.json` | 版本号、平台、运行时长、配置摘要（**无 Key**）、错误码计数 TOP20、最近一次成功同步时间、数据目录总大小 | 一眼看全局 |
| `diag-*.jsonl` | 最近 7 天诊断日志 | 用 trace_id 精确定位阶段 |
| `requests.jsonl` | 最近 200 条请求（时间/方法/路径/状态码/错误码）。**服务器版要按 user_id 过滤** | 看是哪些请求在失败 |
| `pipeline.jsonl` | 最近 20 轮对话各阶段的输入长度/模型/耗时/降级情况 | 排查"答非所问""没回复" |
| `state.json` | 数据目录树（文件相对路径 + 大小 + 修改时间 + sha256 前 8 位）、同步状态、备份列表（名字/大小/时间） | 看数据完整性 |
| `env.txt` | 系统版本、Python 版本、关键依赖版本、是否配置了 Key（是/否，不含值） | 排除环境问题 |

**关键设计要求**
1. **服务器版必须按用户隔离**。绝不能像现在这样直接把全局计数器打包（那是把所有人的数据给一个人）。实现上：`requests`/`pipeline` 都按 user_id 过滤，`diag` 读该用户目录下的文件。
2. **导出本身要限流**（比如每用户每小时 3 次），防止有人拿它刷磁盘和带宽。
3. **zip 里不含任何原始对话内容**，只含元数据 —— 这样用户可以放心把文件发给别人。
4. 导出成功后，界面上直接提示"请把这个文件发给我"，并显示文件名。

**界面位置**：设置 → 帮助与反馈 → 「导出诊断包」
**顺带加的**：设置页显示"最近一次错误：`sync.upload.network` @ 2026-09-18 17:20（错误号 A1B2C3D4）"，用户截图给你也能定位。

### 5.6 服务器管理员侧（你可以主动查）

管理台（8766）加一个入口：**按 user_id 拉取该用户的诊断包**。
好处：用户懒得导出时，你自己就能查。实现上复用同一个打包函数，只是换成从服务器目录读、由管理员触发。

### 5.7 用户上报流程（写进用户可见的文档）

**给用户的说明（放到设置页帮助里）**：

## 附录 C：新增的发版验收工具 `tools/check_apk_manifest.py`

**为什么需要它**：本次审计发现"发出去的 APK 是 3 周前的旧构建、`allowBackup` 还是 `true`"，而当时**没有任何快速核验手段**——每次都得靠人装真机看，于是漏了 3 周。这个工具让"包内安全属性"变成一条可自动化的检查。

**它能做什么**（标准库实现，不需要 aapt/apktool，不装真机）：
- 直接解析 APK 里的二进制清单，读出属性真实值；
- 对照发版基线自动判定合格/不合格（退出码 0/1，可接 CI 或发版脚本）；
- 顺带检查包内是否含 `sync.js`（漏跑 `sync_frontends.py` 的典型症状）。

**用法**
```bash
python tools/check_apk_manifest.py android/firefly.apk allowBackup usesCleartextTraffic
```

**验收基线**
| 属性 | 期望值 | 理由 |
|---|---|---|
| `allowBackup` | **`false`** | `user_data` 含 API Key，不允许被云备份 / `adb backup` 带出设备 |
| `usesCleartextTraffic` | `true` | 服务器暂无 HTTPS，客户端必须允许明文（见 2.1；将来上 TLS 后改 `false`） |

**当前线上 APK 的实测结果（不合格）**
```
allowBackup = true ✗（期望 false）
usesCleartextTraffic = true ✔
包内前端：sync.js=❌ 没有（旧构建！）  panels.js(旧结构)=有
```

**建议接进流程**：把这条命令加进 `docs/构建规范.md` 的发版步骤与《上线前检查清单》，作为**上传安装包之前**的必过项。

## 附录 D：更新影响评估 —— 会不会影响旧版用户？

**这是部署前必须回答的问题。以下是逐项实测结论（2026-09-18）。**

### D.1 三种更新方式，影响完全不同

#### 方式 A：只补那 4 个文件（推荐，影响面最小）

| 文件 | 对旧客户端 | 对线上服务 | 依据（实测） |
|---|---|---|---|
| `server/download_page.py` | **无影响** | 需重启下载服务 | 它只影响"下载页"（浏览器打开的那个页面）；旧 APP 不经过它。新增的 URL 校验若不通过会**降级为服务器直连下载**，是更保险的方向，不会导致下载失败 |
| `app/shared_http.py` | **无影响** | 需重启主服务 | 新版是旧版的**超集**：旧版 4 个导出名（`ResponseMixin`/`_SERVER_REF`/`preload_knowledge`/`setup_stdio_utf8`）全在，另多出 `local_origin_ok`/`_local_allowed_origins`/`shutdown_server`。服务器模式走 `FIREFLY_SERVER` 分支，CORS 仍是 `*`，**与现状完全一致** |
| `app/server.py` | **无影响** | **零影响** | 这是**本地版入口**，服务器不导入它（全仓 grep 确认 `server/` 下无任何 `from server import`）。传过去只是保持代码一致，传不传都行 |
| `app/infra/sync/restore.py` | **无影响** | 需重启主服务 | B6 给 `_backup_current_mode` 加了**带默认值 `None`** 的 `root` 参数 → 旧调用点行为不变；新旧代码算出的备份目录经核对是**同一个**（`user 根/backups`）。B7 是纯新增函数 |

**结论：方式 A 对旧版用户零影响。** 唯一动作是重启服务（几秒）。

#### 方式 B：重建并发布新安装包

| 对象 | 影响 |
|---|---|
| **旧版用户（不升级）** | **不受影响**。继续用旧包，功能照旧 |
| 新版用户 | 拿到增量同步、本地备份等新功能 |
| 服务器 API | **纯增量**：线上 85 个端点、本地 89 个，**新增 4 个（`/pack-file*`、`/pack-structure`）、删除 0 个** —— 旧包调用的端点全部还在 |
| 额外保障 | 旧包（8-23）**根本没有 `sync.js`**，所以它不会调用 `/sync/*` 新链路，不存在"旧包遇到不认识的新接口"这种情况 |

**结论：方式 B 对旧版用户也无影响**，属于"多发一个新版本供自愿升级"。

#### 方式 C：全量部署那 19 个"方向待定"的文件 + 新前端 ⚠️ 有风险

- 本地工作区混着未完成的新工作，`app/routes_*.py` 可能改了响应结构 → 旧前端解析可能出错；
- **新前端 + 旧服务 = 坏**：所以如果非要一起上，**顺序必须是先代码、后前端**，绝不能反过来；
- 影响面澄清：`server/frontend/` 只影响**用浏览器直接打开 `http://IP:8787` 的人**（含 `/login` 登录页）。**旧 APP 的界面是打包在 APK 里的**（`file://` 加载，已核实旧包 assets 里没有 `login.html`，登录是应用内置面板）→ 服务器前端更新**不影响旧 APP 的界面**。

### D.2 两个必须知道的坑

**坑 1：B7 那个修复，只传 `restore.py` 等于白修**

`recover_swap_leftovers` 全仓**只有一个调用点**：`app/server.py:147`（本地版启动链）。
而**服务器入口 `server/app.py` 的 `main()` 从不调用它**（实测：它只调 `db.init_db` / `ensure_auth_columns` / `migrate_sticker_seed` / `preload_knowledge`）。

后果：**服务器上如果恢复/导入中断在换目录中途，用户数据目录会缺失，读取链静默回退到内置包 → 用户看到"对话/记忆消失了"，而且永远不会自愈。**
要真正修好，得**同时**给 `server/app.py` 的启动链加一行调用。

**坑 2：旧客户端兼容机制已经存在，别动坏**

服务器对旧客户端调用已下线的端点有专门处理：`server/app.py` 的 `_OLD_CLIENT_PATHS`（`/sync/upload`、`/sync/download`）→ 返回可读文案（不是裸 404 白屏）+ 对该账号发**一次**升级提醒邮件（`db.mark_notice` 去重）。这套机制是旧用户不被打断的关键，改动时别碰。

### D.3 建议的部署顺序（把影响面压到最小）

1. **先传 2 个纯服务器文件**：`download_page.py` + `shared_http.py` → 重启双服务 → 验证（对旧客户端零影响，风险最低）
2. **再传 `restore.py`，并同时给 `server/app.py` 启动链加 B7 调用**（否则白传，见坑 1）
3. `app/server.py` 可以不传（服务器不用它）
4. **最后**才考虑重建安装包、发布新版（旧用户不受影响，可自愿升级）
5. 那 19 个待定文件：**必须先提交 + 跑测试 + 做接口回归**，再单独评估；不要混进本次部署
