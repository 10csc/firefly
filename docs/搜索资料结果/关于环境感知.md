在Harness工程范式中，第一步确实是环境感知。它取代了传统流程中简单的“审查违规”或“调用记忆”，成为Agent可靠运行的基石。下面我将为你详细解释什么是环境感知、为什么它是第一步，以及如何具体实现。
🌍 一、什么是环境感知？
环境感知是指智能体在执行任何任务前、中、后，通过观察外部环境和内部状态，构建一个当前环境的表示，这个表示既准确又足够紧凑以适应上下文预算。
简单来说，它让Agent从“只看用户文字”升级为“理解自己处于什么场景、用户是谁、当前任务进度如何、有哪些可用工具和约束”。
flowchart LR
    A[用户输入] --> B[环境感知层]
    subgraph B [环境感知：构建当前上下文表示]
        B1[环境状态<br>时间、地点、设备、网络]
        B2[任务状态<br>当前目标、进度、历史步骤]
        B3[用户状态与意图<br>用户画像、情绪、即时意图]
        B4[内部状态<br>Agent记忆、情绪、可用工具]
    end
    B --> C[决策规划层<br>基于感知结果规划下一步]
    C --> D[执行层<br>调用工具或生成回复]
    D --> E[反馈与记忆更新<br>结果回写，更新内部状态]
    E --> B
🔍 二、为什么环境感知是Harness工程的第一步？
在传统流程中，“审查违规”和“调用记忆”是两个独立的、割裂的步骤，容易导致信息不完整和OOC。而环境感知作为统一的上下文构建层，能从根本上解决这些问题。

2. 如何“感知” - 技术实现路径
感知的实现并非让模型自己去“看”，而是通过Harness工程为模型构建一个“感官系统”。
显式状态注入：
短期记忆：当前对话的最近几轮，直接放入Prompt。
中期记忆（会话摘要）：由一个独立的摘要Agent实时生成，如“流萤带开拓者吃了橡木蛋糕卷，去了秘密据点，正在看星星”。
长期记忆（向量数据库）：根据当前感知到的环境状态和任务意图，语义检索相关记忆片段。例如，感知到“开拓者提到虫子”，就检索所有关于虫群、AR-214、失熵症的记忆。
环境API接入：通过工具调用获取实时信息，如get_current_location()、get_user_emotion()（可能基于用户输入文本分析）。
隐式环境感知：
渐进式披露：不一次性加载所有信息，而是按需引导。根目录的AGENTS.md只作为索引，当感知到需要了解“格拉默铁骑”时，才动态加载对应的docs/grammer.md。
可观测性接入：为Agent接入“感官”，如读取日志、查询性能指标、模拟浏览器操作（CDP），让它能“看到”自己的运行环境。
3. 感知“后”如何处理 - 状态检查与决策
感知到状态后，需要进行状态检查，决定下一步行动。这通常通过一个决策推理层实现，其核心是LLM根据状态推理下一步。
# 伪代码：环境感知后的状态检查与决策
def perceive_and_decide(user_input, environment_state, task_state, agent_state):
    # 1. 构建当前完整上下文表示
    context = {
        "environment": environment_state,  # 环境
        "task": task_state,                # 任务
        "user": analyze_user_intent(user_input),  # 用户意图
        "self": agent_state                # 自身状态
    }
    # 2. 基于状态进行推理和决策
    decision_prompt = f"""
    你是流萤的环境感知与决策引擎。请根据以下当前状态，决定下一步行动。
    【当前环境状态】{context['environment']}
    【当前任务状态】{context['task']}
    【用户意图分析】{context['user']}
    【自身内部状态】{context['self']}
    请严格输出JSON：
    1. "is_safe_to_proceed": "yes/no" - 是否具备继续执行的条件？
    2. "reason": "原因分析"
    3. "next_action": "下一步应采取的动作" 
       (例如: "retrieve_memory", "call_tool", "generate_response", "ask_clarification")
    4. "action_input": "动作所需参数"
    """
    decision = llm.invoke(decision_prompt)
    return decision
状态检查的核心问题：
前置条件检查：是否具备继续执行的条件？例如，当前任务是“去秘密据点”，但感知到“开拓者不在身边”，则需先询问。
意图校验：用户输入是否与当前任务一致？若偏离，是顺应还是引导回正轨？
资源检查：执行下一步需要的工具或信息是否已就绪？
约束检查：是否违反角色设定或安全规则？例如，感知到“黄泉拔刀可能”，立即触发“零点任务”分支。
🔄 四、环境感知与原有流程的融合
环境感知并非完全替代你原有的“审查”和“记忆”步骤，而是将它们整合并前置为统一的上下文构建层，其关系如下图所示：
flowchart LR
    A[用户输入] --> B[环境感知层<br>构建统一上下文表示]
    subgraph B [环境感知：核心第一步]
        direction TB
        B1[环境状态感知]
        B2[任务状态感知]
        B3[用户状态与意图感知]
        B4[内部状态与记忆检索<br>（原“调用记忆”）]
        B5[约束与规则预检<br>（原“审查违规”）]
    end
    B --> C{状态检查与决策}
    C -- 安全且条件具备 --> D[执行层<br>调用工具/生成回复]
    C -- 不安全或条件不足 --> E[异常处理<br>询问/拒绝/回退]
    D --> F[反馈与记忆更新]
    E --> F
    F --> B
关键融合点：
“审查违规”成为感知的一部分：在感知“内部状态”时，同时检查规则约束。例如，感知到“用户意图询问剧本”，同时检查“流萤绝对禁忌”规则库，直接触发拒绝回复。
“调用记忆”成为感知的子任务：记忆不再是盲目调用，而是基于当前感知到的环境状态和任务意图，通过向量检索等方式精准获取。例如，感知到“开拓者提到虫子”，才检索关于虫群的记忆。
决策规划有据可依：后续的规划不再凭空生成，而是基于感知层构建的完整、结构化的上下文表示进行，大幅降低OOC概率。
💎 总结与行动建议
在Harness工程中，环境感知是Agent可靠运行的第一步，它通过构建统一、结构化的上下文表示，解决了传统流程中上下文碎片化、无状态感知和OOC频发的问题。
立即行动：
为流萤Agent设计感知维度：参考第三节，列出流萤需要感知的5-6个核心维度（如环境、任务、用户、自身状态等）。
实现状态注入机制：优先实现“环境状态”和“任务状态”的显式注入。例如，在每轮对话开始时，将当前场景（黄金时刻/现实）、任务进度（闲聊/探索）作为系统提示注入。
构建决策推理层：实现一个简单的状态检查函数，基于感知到的状态决定是直接回复、检索记忆、调用工具还是询问用户。
逐步集成记忆与规则：将原有的记忆调用和违规审查逻辑，改造成基于感知结果的按需检索和条件触发，而非每轮必做。
通过构建强大的环境感知层，你的流萤Agent将不再是一个“无状态”的聊天机器人，而是一个真正“知行合一”、能感知环境、理解意图、可靠行动的智能体。
