# 同步协议

同步采用本地优先模型。用户操作先在本机提交，服务器负责分配权威顺序并收敛设备状态；
网络失败只能延迟同步，不能让本地数据消失或被旧副本覆盖。概念说明见
[同步与离线](../概念/同步与离线.md)。

## 身份与代际

| 字段 | 语义 |
|---|---|
| `mid` | 消息身份；新消息由客户端生成 UUIDv4 |
| legacy id | 旧消息迁移为 `legacy:<seq>:<content-sha8>`，同 seq 不同内容不能合并 |
| `epoch` | 清理历史的代际；旧 epoch 的历史行失效 |
| `history_rev` | 历史、撤回和清理的服务器版本 |
| `memory_rev` | 记忆产物绑定的服务器版本 |
| `op_id` | 破坏性或可重试操作的幂等键 |
| `base_rev` | 条件写入前提；不匹配返回冲突 |
| `base_sha` | 文件条件写入前提；禁止用 mtime 判断胜者 |
| `tombstone` | 删除标记；过滤旧设备或旧响应带回来的内容 |

服务器是 rev 和 epoch 的顺序来源。设备时钟、文件 mtime 和本地 seq 不参与最终裁决。

## 本地提交

多文件操作使用显式状态机：

```text
PREPARED
  → 数据、本地同步状态和 outbox 落盘
  → COMMITTED
  → 才允许上传
```

要求：

- 事务日志记录 `op_id`、类型、`base_rev`、目标文件和内容摘要。
- 只有 COMMITTED 的 outbox 记录可以发送。
- 进程在 PREPARED 阶段退出时，重启后重放或回滚，不能把半成品上传。
- 进程在 COMMITTED 阶段退出时，保留 outbox，用同一个 `op_id` 重试。
- outbox 只在服务器确认后删除；同一时刻只有一个写入者更新 outbox。
- 覆盖写、换入和恢复都必须使用原子写或可恢复的临时目录。
- direct clear 与同一 mode 的完整同步回合共享进程内 mode 锁，避免 clear 的
  文件/epoch/outbox 窗口与 state、上传、拉取交错。

## 服务器状态

服务器按 `(user_id, mode)` 维护：

- `history_rev`、`memory_rev`、`history_epoch`
- tombstones
- clear 栏栅
- op ledger：`op_id`、状态、结果和 `base_rev`
- 每个用户每模式的串行锁或 CAS

pending 未恢复时拒绝新 op，不能用一个新请求覆盖未完成的提交。

## 在线回合

1. 客户端读取 `/sync/state`，获得 rev、epoch 和水位。
2. 按 outbox 顺序发送 `/sync/ops`。
3. 服务器校验 `op_id` 幂等和 `base_rev`，应用后分配新 rev。
4. 客户端收到确认后删除对应 outbox 记录。
5. 普通文件通过 manifest、`state_rev` 和 `base_sha` 条件写入。
6. 版本不匹配返回 409；客户端重新读取，不能静默覆盖。

新客户端带同步协议版本头；旧客户端或旧服务器不具备破坏性语义时，降级为可读和普通追加，
并在清理、撤回或手工编辑冲突上明确提示。

## 失败语义

| 情况 | 结果 |
|---|---|
| 发送前断网 | 本地已提交，outbox 保留 |
| 请求超时 | 用同一个 `op_id` 重试 |
| 应用成功但响应丢失 | 重试返回原结果，本地不回滚 |
| 拉取失败 | 保留本地状态，从已知水位继续 |
| 服务器 pending 未恢复 | 暂停该模式的新 op |
| 旧 rev 或旧 sha 写入 | 返回 stale/409，重新读取 |
| 恢复失败 | 暂停同步并保留事务现场 |
| clear 与离线 append 交叉 | 备份到 `.sync_conflicts/` 并提示，不静默复活历史 |

## 清理、撤回与记忆

### clear

- 服务器分配新 epoch，并记录清理覆盖到的 rev。
- 历史对话、记忆、索引、手账、归档、语音索引和流水线数据同步失效。
- 基于旧 epoch 的离线 append 不直接并入当前历史，进入冲突备份或提示。

### retract

- 按 `mid` 写墓碑，只撤对话历史。
- 已经整理进记忆或手账的内容不会自动重写；需要消除时走 clear 的明确语义。
- 旧历史行不能因为设备并集合并复活。

### rest

- 记忆快照绑定生成时的 `base_history_rev` 或具体消息集合。
- 影响该基线的撤回、清理后续整理才判 stale；无关 append 不应误判。
- stale 快照不能覆盖更新后的记忆。

## 文件同步

- manifest 包含 `state_rev`、epoch、每文件 SHA-256 和 `base_sha`。
- export 在固定 `state_rev` 生成快照；manifest 与 zip 不一致时拒绝并重试。
- 服务器 import 校验 `base_sha` 和 rev，失败返回 409。
- `conversation.jsonl` 合并前过滤旧 epoch 与墓碑。
- 收藏删除使用墓碑，避免并集把已删除项带回来。
- 文档使用 CAS；冲突双方内容进入 `.sync_conflicts/`，不只保留本地文件。
- 批量导出不得静默截断；超过单批限制时分片并校验总数。
- 文本写入固定使用 LF，避免 Windows CRLF 造成每轮伪冲突。

## 当前实现状态

本地 T1/T2 修复后的当前语义：

- state、manifest、ops、import、export 在任何数据副作用前拒绝不可寻址 mode；
  返回 HTTP 400、`SYNC_MODE_NOT_ADDRESSABLE` 和 `requested_mode`，不再落到 story。
- 客户端先校验 state、ops、manifest、import 响应中的 `mode`，并校验 export 的
  `X-Firefly-Mode`，通过后才应用状态、清 outbox 或写文件。
- direct clear 与远端新 epoch 使用同一可恢复清理：对话、记忆、索引、手账、归档、
  pipeline、主动记录及 `data/voice/v<seq>.wav` 一起失效；语音模型等非 store 文件保留。
- 文件清理、epoch/rev 保存与 outbox 提交失败时返回 503，现场保留为 PREPARED/COMMITTED；
  重试沿同一 `op_id` 恢复，不重复推进代际。

hot5 修复的其他回归包括：

- 恢复失败时本地事务状态不再被覆盖。
- 服务器 pending 不再被新 op 抢占。
- 同一设备并发 outbox 更新不丢记录。
- 同 seq、不同 mid 的旧格式内容不再误合并。
- 200 文件量级批量导出不再静默截断。
- Windows CRLF 不再造成文档反复冲突。

本地源码已通过真实 HTTP E2E、并发压力、故障注入和规范守卫测试。生产业务代码仍为 patch4，
真机尚未验证；版本与四平面事实见 [生产只读基线（2026-10-27）](../操作/生产只读基线-2026-10-27.md)。

## 当前验证

- `test_sync_http_e2e.py`：真实 HTTP、首同步、双向收敛、图片、文档 CAS、分批、多 mode、
  unknown-mode 零副作用、clear 失败/重试与语音边界。
- `test_sync_concurrency.py`：32 并发 op、幂等重试、8 设备收敛、同设备并发同步、outbox 竞争。
- `test_sync_crash_recovery.py`：PREPARED/COMMITTED、pending、损坏文件、原子写与副作用失败。
- `test_sync_spec_guard.py`：锁、墓碑、CAS、LF、导出上限和未来重构不变量。

旧同步测试已归档，不再作为当前协议正确性的证据。
