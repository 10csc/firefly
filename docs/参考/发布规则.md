# 发布规则

本页只定义发布边界和必须保留的证据。版本号合同见 [版本与发布](版本与发布.md)，
热更新合同见 [热更新协议](热更新协议.md)，生产操作步骤见 [生产服务器](../操作/生产服务器.md)。

## 权限边界

- 提交、推送、创建 tag、发布 Release、部署服务器、发布热更新或公告，都必须有用户明确授权。
- 没有发行指令时，不修改 `APP_VERSION`、Android `versionName/versionCode`、安装器版本或线上更新投影。
- `server/` 不进公开主仓；源码同步到受控私有仓库。生产更新只能按变更清单单文件部署，禁止整目录覆盖。
- 发布、部署和热更新失败时必须停止后续步骤并报告失败项，不能把“上传命令成功”当成“用户已收到”。

## 唯一事实源

| 事实 | 权威位置 |
|---|---|
| 本地版本源 | `app/core/config.py`、`app/static/js/update.js`、Android Gradle、`package/firefly.iss` |
| 最新已发布整包 | `server/update.json` |
| 已发布产物身份 | `release_manifests/release_manifest_<version>.json` |
| 是否声明热更新 | 仓库根 `hotupdate_declare.json` |
| 热更新候选产物 | `hotupdate_dist/prod/<base>/` |
| 生产实际状态 | 线上健康、版本和资产回读结果；不能由本地文件推断 |

`server/version.json` 是 `server/update.json` 的兼容投影，不单独裁决发布状态。

## 发布前证据

发整包前至少保留以下证据：

1. `python tools/check_version.py --profile release` 退出码为 0。
2. 前端、后端镜像、热更新声明和公告门禁全部通过。
3. 当前活动测试基线通过，失败项有明确归因。
4. APK 与 EXE 的大小和 SHA-256 已写入不可变台账。
5. PC 与 Android 都实际启动过，`/config` 与更新检查可达。
6. 两个下载源能回读到同一份产物，服务器兜底副本与台账一致。

发整包后、部署前运行 `python tools/check_version.py --profile deploy`，并使用
`tools/check_update_manifest.py` 与 `tools/check_download_page.py` 核对线上投影和实际下载物。

## 热更新与整包的分界

- 热更新只修 bug，不发布新功能，不删除文件。
- 前端与 Python 可热更；Kotlin、权限、依赖、Manifest 和热更加载器本身只能走整包。
- 底座内容变化必须发布新版本；同版本不得替换已发布产物。
- 热更新发布后必须从主源和镜像逐字节回读，再由真机确认 serial、代码生效和数据链路。

## 归档

- 发布成功的身份留在 `release_manifests/`，不把临时构建日志混进活动文档。
- 被替代的发布方案和过程记录移入归档，活动文档只保留当前合同。
- 事故记录进入错误总结；不要在发布页复制整段事故经过。
