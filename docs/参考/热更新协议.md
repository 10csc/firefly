# 热更新协议

热更新用于在不重装整包的情况下修复前端或 Python bug。执行流程见
[热更新发布](../操作/热更新发布.md)。本页定义字段、信任边界和客户端语义。

## 适用范围

| 内容 | 热更新 |
|---|---|
| `app/static/**` | 允许，进入 `web/` |
| `app/**/*.py` 业务代码 | 允许，进入 `py/` |
| Kotlin、native、Manifest、权限、依赖 | 禁止，只能整包 |
| `app/assets/**`、角色包数据、数据库 | 禁止 |
| 删除文件 | 禁止 |
| 新功能 | 禁止 |
| `app/hotupdate/**` | 禁止；这是补丁加载器本身 |

## 信任模型

- 唯一信任根是签名后的 manifest 规范化字节。
- 未签名的 `latest` 只负责提示最新 serial；攻击者最多拒绝或冻结更新，不能注入代码。
- zip 由 manifest 中的整包 SHA-256 和逐文件 SHA-256 双重校验。
- 私钥只在发布机；Kotlin 与 Python 公钥副本必须逐字节一致。
- 算法为 RSA-2048 / SHA-256 / PKCS#1 v1.5。

客户端交付格式是：

```json
{
  "v": 1,
  "manifest_b64": "<规范化 manifest 字节的 base64>",
  "sig": "<RSA 签名的 base64>"
}
```

客户端先解码并验签，再解析同一串字节。禁止两端各自重新序列化对象后比较。

## 服务端布局

```text
<base_url>/
├── latest               # {"base":"x.y.z","serial":N}，no-store
├── patch-N.json         # manifest_b64 + sig，不可变
└── patch-N.zip          # 补丁内容，不可变
```

公开只读、匿名可下载。`latest` 必须 `Cache-Control: no-store`；带 serial 的文件可以长期缓存。

## Manifest

```jsonc
{
  "format": 1,
  "base_version": "x.y.z",
  "base_version_code": 901,
  "serial": 5,
  "issued_at": 0,
  "cumulative": true,
  "layer": "web+py",
  "zip": {"name": "patch-5.zip", "sha256": "...", "size": 0},
  "files": [
    {"path": "web/js/update.js", "sha256": "...", "size": 0},
    {"path": "py/api/router.py", "sha256": "...", "size": 0}
  ],
  "rollout_percent": 100,
  "promotion_of": 4,
  "min_safe_serial": 1,
  "revoked_serials": []
}
```

约束：

- `cumulative` 恒为 `true`；serial N 包含 base 到 N 的全部差异。
- `layer` 必须与 `files` 的 `web/`、`py/` 前缀一致。
- 路径不得为绝对路径或包含 `..`。
- `py/` 只能包含 `.py`，并排除 `hotupdate/`、`assets/`、`__pycache__`。
- serial 单调递增；已发布文件永不覆盖。
- 灰度晋升使用新的 serial 和 `promotion_of`；文件集合与哈希不得变化。

## Python 完整包闭包

触及 `py/<pkg>/...` 时，该补丁必须携带 `<pkg>` 当前全部 `.py` 文件。

原因：Python 在第一次导入包时确定 `__path__`。如果覆盖层只有新子模块，没有祖先
`__init__.py`，解释器会回到底座旧包，覆盖层里的新模块永远不可见。

发布器和客户端都要拒绝以下情况：

- 缺祖先 `__init__.py`。
- 同一顶层包漏掉兄弟模块。
- 试图覆盖 PC 当前进程入口。
- 试图热更新热更加载器。

## 客户端布局与状态

```text
{FIREFLY_DATA_DIR}/hotupdate/
├── web/               # 当前 web 覆盖层
├── py/                # 当前 Python 覆盖层
├── web.new/ py.new/   # 下载与校验暂存
├── web.old/ py.old/   # 换入中途的恢复副本
└── state.json
```

`state.json` 至少记录：

- `base_version`、`base_version_code`
- `applied_serial`、`applied_hash`、`applied_layer`
- `pending_serial`、`pending_boot_pid`、`pending_started_at`、`boot_fail_count`
- `applied_pid`
- `client_id`、`rollout_percent`、`rollout_bucket`
- `reload_pending`、`restart_pending`（由 state 与当前 PID 计算后对外报告）
- `last_check`、`last_error`、`rolled_back_reason`

底座版本或 `versionCode` 变化时，整个覆盖层失效并清理，避免旧补丁盖住新整包。

## 应用与生效

应用顺序固定为：

```text
下载 → 验签 → 校验 zip 与逐文件哈希
  → 两层都解到 .new/
  → 原子换入 web/ 与 py/
```

任一层失败都丢弃整包，盘上不能出现“web 已换、py 没换”的中间态。

| 层 | 空闲时的动作 |
|---|---|
| `web` | 保存输入草稿和滚动位置后刷新 WebView |
| `py` | Android 原生桥先启动独立进程中的可见交接页；交接页确认 `onResume` 后销毁旧默认进程，再由交接页拉起全新的 MainActivity。新进程在业务 import 前把 `py/` 放到 `sys.path` 首位 |

含 `py/` 的补丁只走重启路径，不先刷新页面；`finishAffinity()` 或页面刷新都不算重启，
因为它们不能销毁 JVM 中已加载的 Python 模块。重启后新前端自然一起生效。

重启交接页必须位于独立进程（`:hotupdate_restart`），并先取得真实可见窗口。它按 Intent
携带的旧 PID 直接调用 `Process.killProcess(oldPid)`，不能靠闹钟在旧进程死亡后拉起页面，
也不能把 ColorOS 可能不可见的 `/proc/<pid>` 当作旧进程退出的证据。因此新 MainActivity
一定由仍存活的交接进程启动，旧 JVM 与其中已加载的 Python 模块不会复用。

空闲判据由前端活动上报和后端状态共同决定。输入中、播放语音、流水线运行、模型下载或已有 pending
都算忙碌；持续空闲后才生效。后台不能强行拉起 Activity，覆盖层已落盘，下次冷启动生效即可。

`boot-ok` 必须带进程身份。同进程页面刷新只能确认 web 层，不能清除 Python 层的 pending。

## 安全模式

1. 应用补丁时写 `pending_serial`、`applied_layer` 和旧进程 `applied_pid`，并清空
   `pending_boot_pid`。
2. 含 `py` 的补丁在空闲后通过独立可见交接页销毁旧默认进程，并拉起新的默认进程。
3. 新进程在业务 import 之前登记 `pending_boot_pid`；`/config` 正常并由前端上报
   `boot-ok` 后才清除 pending。
4. 下一次启动发现 `pending_boot_pid` 是另一进程，说明候选进程未完成 boot-ok 就死亡：
   必须在注入覆盖层之前禁用补丁并回到 base。
5. Python 导入阶段失败时，先隔离坏层为 `py.failed-*`，记录失败并回滚状态，再从 APK
   底座重试；不能因为已隔离坏层就把 pending 当成功。
6. 回退只能删除覆盖层和临时包，不能删除用户数据。

## 更新器依赖隔离

`app/hotupdate/**` 只允许依赖标准库、自身文件和 Android 平台桥。不得导入 `core`、
`api`、`modules`、`routes`、`voice` 等业务包；业务侧只能通过注册忙碌探针等单向接口
向更新器提供信号。这样即使业务代码 import 全坏，更新器仍能在启动早期读取 state、隔离
坏覆盖层并完成回退。

## 本机 API

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/hotupdate/status` | 状态、三元组、pending、回退原因 |
| GET | `/hotupdate/restart` | 壳查询是否应重启以及当前是否空闲 |
| POST | `/hotupdate/action` | check / apply / rollback / set_enabled / set_urls |
| POST | `/hotupdate/boot-ok` | 确认启动成功 |
| POST | `/hotupdate/activity` | 上报输入、播放、流水线或下载占用 |
| GET | `/config` | 返回当前 base、hot serial 和 patch hash |

## 门禁与验收

热度门禁 `tools/check_hotupdate.py` 必须覆盖：

- manifest 验签与字段完整性。
- 包内文件集合与 `files` 完全一致。
- 整包和逐文件哈希、路径边界。
- 累积、单调、无删除语义。
- Python 包闭包与加载器排除。
- 灰度晋级可追溯。
- 公钥副本一致，公告清单可被同一客户端校验器接受。

当前全新真实链路基线是 `tests/test_hot5_release_pipeline.py`。它从发布物执行
`latest → manifest → 验签 → 下载 → 干净底座应用 → 新进程导入 → 攻击包 → 灰度 → 并发 soak`。
旧热更新测试已归档，不能作为本次通过证据。
