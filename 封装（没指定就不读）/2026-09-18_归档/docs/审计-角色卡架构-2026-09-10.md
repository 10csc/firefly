## 1. 执行摘要

**一句话结论**：角色卡从「写死的两种模式」改成「可扫描、可自建、可编辑的预设包」方向正确，但**收口没做完**——注册表、快照恢复、同步、bundled 升级四条链路上，角色包仍被当作「运行期才存在的东西」处理，导致**自建包在换机/重装场景下静默丢失**（已复现），且**内置包的后续更新永远送不到老用户**（已复现）。

- 线上稳定版是 **v0.8.1（2026-08-23，已打 tag、已推送 origin/gitee）**；`master` HEAD 领先 **37 个提交**（角色预设化 7 阶段 + 卡面重构 + 全包化）且**未推送**；另有 **20 个文件未提交**（含全包化核心实现）。角色卡全部改动**都在 v0.8.1 之后**，属未发布开发版。
- **最大隐患（P0-1）**：`import_data` / `_restore_full_snapshot` 用 `cfg.MODES`（启动期扫描结果）做白名单分发。快照内存在、但恢复端未注册的自建包会被**整包丢弃**，实测返回 `ok=False "快照里没有可恢复的数据"`。全包化的卖点就是"换机/重装恢复角色卡"，此路径对自建包直接失效。
- **次大隐患（P0-2）**：`_restore_full_snapshot` 对每个命中的包先 `rmtree(root)` 再解压，**失败即数据空窗**。快照本身无校验和、无清单、无格式版本号。
- **P1**：内置包 `core.md` 等一旦被首启拷进用户区就被永久遮蔽——新版本改了 bundled 文案，老用户**永远收不到，也无任何提示**（实测 `load_slot` 读到的仍是旧内容）。
- **P1**：仓库内 `android/app/src/main/python/backend/` 是**过期的 Python 副本**（少 4 个文件、7 个文件版本陈旧），三门禁**只校验前端**，不校验后端一致性。
- **P1**：角色包格式**没有 schema 版本号**——设计文档写了 `version` / `bans`，代码一个都没读（`bans` 是死字段）。未来任何格式变更都**无法做版本判别与迁移**。

**发布建议**：P0-1/P0-2 必须在带上「自建包」能力的版本发布前修掉；P1 的 bundled 遮蔽与 schema 版本号建议同批完成（改动小、无风险）；安卓后端副本漂移与门禁缺口需在本轮补齐校验，否则三端会持续分叉。

## 4. 角色卡架构现状

### 4.1 角色卡领域模型（[事实]）

**一个角色包 = `assets/character/{id}/` 一个目录**，字段在 `preset.json`，由 `app_config._parse_preset`（`app/modules/app_config.py:338-367`）解析并校验：

| 字段 | 必填 | 校验/默认 | 代码位置 |
|---|---|---|---|
| `id` | 是 | `^[a-z0-9_-]{1,32}$` **且必须等于目录名**，否则整包跳过 | `:346` |
| `name` | 是 | 空则跳过 | `:352` |
| `char_name` | 是 | 空则跳过（注入到所有提示词 `{char_name}`） | `:352` |
| `user_name` | 是 | 空则跳过 | `:352` |
| `presentation` | 否 | `sticker`/`narration`/`none`，非法回退 `sticker` | `:355-358` |
| `desc` / `tagline` | 否 | 首页卡文案 | `:365-366` |
| `knowledge_dirs` | 否 | 仓库相对路径清单；未声明则挂包内 `knowledge/` | `:360-362` |
| `bans` | — | **写在 story/haruno 的 preset.json 里，但代码从不读取（死字段）** | 无 |
| `version` | — | **不存在**（设计文档有、实现无） | 无 |

**内容槽位**（均为可选、有兜底）：
`core.md` · `identity.md` · `sms_samples.md` · `用户设定.md` · `opening.json` · `prompts/{polisher,analyzer_extra,organizer_sticker,organizer_narration,proactive_context,env_suffix}.md` · `assets/{avatar,cover}.png` · `knowledge/` · `stickers/`（**设计中，未落地**）

## 8. 迁移、兼容与回滚方案

### 8.1 兼容性策略（分层）

| 层 | 现状 | 目标策略 |
|---|---|---|
| 角色包格式 | 无版本号 | 加**只读** `schema` 字段（默认 1）+ 启动期统计告警；未知高版本包**跳过并日志**，不崩 |
| `preset.json` 字段 | 缺字段全有默认；`bans` 死字段 | 保留 `bans` 不读（或删除文档表述）；新增字段一律可选 + 默认值 |
| 用户数据布局 | `user_data/{mode}/{character,data,journal,images}` | **冻结**（包 id 即目录名，R-01 修复不得改变布局） |
| 快照 zip 格式 | `{mode}/… + stickers/ + _config.json` | 增加 `_manifest.json`（`snapshot_version`/`packs[]`/每包 `id,name,presentation`/条目数+sha256/生成时间/客户端版本）。**恢复端遇到无 manifest 的旧 zip 走现有逻辑**（向后兼容） |
| 单包导出 zip | 相对模式根 | 保持；未来若要支持"单包分享给他人"，需**新增** `_pack_manifest.json` 而非改现有结构 |
| API | 端点增量 | 新增端点不改语义；`/chat` 的 mode 回退要**加标记**（`mode_fallback: true`）而不是改回退方向 |
| 旧客户端 | 三端同一 bundle（升级即同步） | 服务器端**保留** `_old_client_refuse` 模式：对已下线端点返回可读文案而非 404（该机制已存在，`server_app.py:_old_client_refuse`，应作为规范沿用） |
| 旧安卓 APK | versionCode 必须单调递增（历史最大值 800，当前 806） | 发版前置检查沿用 `tools/check_version.py:70-72` |

### 8.2 迁移方案（P0/P1 专项）

**M-1（R-01，自建包快照恢复）**
1. `_restore_full_snapshot` 第一阶段：扫描 zip 顶层目录，凡 `_PACK_ID_RE` 合法且含 `character/preset.json` 者，**先写包定义**（`character/` 全量）到 `{user_root}/{id}/character/`。
2. 调 `cfg.reload_presets()`（此时新包进入 `MODES`）。
3. 第二阶段：按包解数据（`data/`、`journal/`、`images/`）。
4. `ignored_packs` 回传 UI。
- 幂等性：重复恢复结果一致；`reload_presets` 是原地重建，无副作用。
- 灰度：无字符串/格式变更，可与旧版本恢复的 zip 双向兼容（旧 zip 无自定义包，走原路径）。

**M-2（R-02，原子恢复）**
1. 解压到 `{mode_root}.restore_tmp/`。
2. 成功后 `old = {mode_root}.restore_old/; rename(mode_root, old); rename(tmp, mode_root)`。
3. 失败则删除 tmp，`mode_root` 未动；保留 `old` 一个版本供人工回退。
- 回滚：替换回 `rmtree+解压` 实现即可（无数据格式变化）。

**M-3（R-04，bundled 更新送达）**
1. 首启不再拷贝 `core/identity/sms_samples`（**去掉 `_DEFAULTS` 里三项**），改为读取时 `bundled → user` 优先级不变（用户没有副本时天然读 bundled）。
2. 对**已存在**的旧副本：启动时比对 `user_text.strip() == bundled_text.strip()`（与 `customized` 同一算法）→ 相等则**直接删除副本**（等价内容，删除无损失）；不等则保留（用户改过）。
3. 迁移必须**单向 + 幂等 + 有日志**（打印"清理 N 个未修改的副本"）。
- 风险：用户"手动删副本以恢复默认"的操作语义不变；新语义下"恢复默认"由 UI 按钮的删除动作完成（已存在 `delete_character_file`）。
- 回滚：把清理逻辑关掉即回到当前行为（但会重新产生遮蔽问题）。

**M-4（R-05，schema 版本）**
- `_parse_preset` 增加：`schema = int(data.get("schema", 1))`；`schema > CURRENT(=1)` → 记录 warning 并**仍按 1 解析**（宽进）；`schema` 写入新建包的 `preset.json`（`create_pack`/`forge_finish`）。
- 约束：内置包不改（保持向后可比）。

### 8.3 回滚方案

| 场景 | 回滚动作 | 前置条件 | 验证 |
|---|---|---|---|
| 角色卡改动引发线上问题 | 回退到 v0.8.1 tag 的 exe/APK + 服务器 `app/` 目录（scp 旧版） | `/opt/backups` 与本地发行产物齐备 | `/health` 200 + 双端各一轮对话 |
| 服务器 `app/` 回退 | `scp -r` 旧版 `app/` → `systemctl restart firefly-server`；user_data 不动 | **必须确认旧版能读新数据**（本审计未发现 0.8.x 改了 user_data 布局，[推断] 可读） | 登录 + 历史记录可加载 |
| 用户误恢复坏快照 | `/snapshot/restore` 走 `pre-restore-*.zip`；`/import-data` 路径走 `{user_root}/backups/`（每模式 10 份） | 备份未被 `_prune` 删掉 | 手账/对话条数与备份内一致 |
| 修 R-01/R-02 后要退版 | 两个改动都是**新增分支**，可单独 revert 提交 | 无数据格式变化 | 恢复旧行为后旧 zip 仍能恢复 |

**回滚能力评分**：[推断] **中等偏下**。数据侧有备份（每账号 5 份快照 + 每模式 10 份本地备份 + pre-restore 3 份），但**服务器代码无 git 历史**（R-17）、**快照无校验和/manifest**（无法判断"这份快照是否完整"）、**R-02 在恢复中途失败时旧数据已删**。

## 10. 架构替代方案与推荐

### 方案 A：最小改动（收口现有实现）

- **内容**：保留「包 = 目录 + preset.json」，只修 4 处：R-01（两阶段恢复）、R-02（原子恢复）、R-04（未修改副本自动跟随）、R-05（只读 schema 字段）。加 R-03 门禁。
- **改动量**：约 3 个文件、150-250 行；无格式破坏。
- **风险**：低。**迁移成本**：零（对旧数据只做"删等价副本"这一幂等动作）。
- **双端/双模式一致性**：与现状相同（不解决 R-07，但会加显式报错）。
- **代价**：`MODES` 仍是进程级全局 + 启动期快照；自建包与服务器模式仍互斥。

### 方案 B：兼容优先（包清单化 + 权威源单一化）

- **内容**：在 A 之上，引入**包清单（pack manifest）**作为唯一权威：
  - `user_data/packs.json`（本地版）记录所有已知包 `{id, schema, custom, source(bundled|user|imported), updated_at}`；
  - 快照/导出/同步都以该清单为白名单，**不再依赖启动期 `cfg.MODES`**；
  - `/chat` 的 mode 校验改为"清单内 + 包目录存在"，回退时返回 `mode_fallback` 标记；
  - `reload_presets` 从"原地清空全局 dict"改为"构建新快照 → 原子替换引用"，消除并发窗口。
- **改动量**：约 8-12 个文件、400-600 行；需一次幂等迁移（首次启动用现有目录生成 `packs.json`）。
- **风险**：中（多一个需要与目录保持同步的状态源，必须幂等 + 自愈：清单缺失时从目录重建）。
- **收益**：**根治** R-01/R-07/孤儿包（R-09）；为将来"包分享/导入他人角色卡"铺路。
- **双端/双模式一致性**：显著提升（服务器端可用同一清单描述"本账号可见包"，为将来服务器端自建包留门）。

### 方案 C：长期重构（包为资源、数据为外键）

- **内容**：把角色卡正式建模为**带 schema 版本的资源**：`pack.json`（含 `schema`/`version`/`capabilities`/`asset_index`/`checksum`），配 `pack_id@version` 引用；用户数据以 `(pack_id, pack_version)` 记录"这份对话属于哪个包版本"，包升级可做"数据跟随 / 提示迁移"。
- **改动量**：全链路重写（后端模块 + 三端数据布局 + 迁移工具），估 3000+ 行。
- **风险**：高（需完整迁移工具与双写期）。**收益**：解决"包更新后老对话语义漂移"这一当前**完全未处理**的问题（[事实] 现状：改 `core.md` 立即影响所有历史上下文，无版本锚定）。
- **适用时机**：出现"角色卡市场/多人共享角色卡"需求时。

### 推荐

**立即采用 A，并把 B 作为下一个版本的目标。**

理由（证据化）：
1. A 修掉的 R-01/R-02 是**数据丢失级**问题，且改动局部、可单测、可回滚——没有理由推迟。
2. R-04（bundled 遮蔽）是**每次内容迭代都会重新发生**的隐性债务：本仓库在 v0.8.1→HEAD 期间就大改过 `core.md`/`identity.md`/`sms_samples.md`（`git diff v0.7.2..v0.8.1` 显示这三个文件均有改动），继续拖会让"C 端已改好、用户端没生效"成为常态。
3. B 的核心价值是把"包的存在性"从**进程启动状态**提升为**持久化事实**——这正是 R-01/R-07/R-09 的共同根因；有了它，服务器端将来开放自建包才有地基。
4. C 在缺少 `schema` 字段（R-05）的当下无法启动，**先把 A 里的只读 schema 落地**是 C 的前置条件。

### C-2 [P0·资源/越权] 托管（proxy）额度无账号授权，全站共享

**证据（[本人核实]）**：
- `server/server_app.py:287` `proxy = (self.headers.get("X-API-Mode","") or "").strip().lower() == "proxy"` → **仅凭请求头即进入托管模式**，无任何账号授权判断。
- `server/server_app.py:77-85` `_proxy_quota_check()` 只比较**全站当日总量**与 `daily_budget`；`_proxy_quota_count()`（`:88-90`）按 `cfg.user_dir_id()` 记流水，但流水**从不出现在放行判定里**。
- `server/db.py:29` `quota_api_proxy INTEGER NOT NULL DEFAULT 0, -- API代理并发额度（0=无）`；全仓 grep 该列仅出现在 schema 与 `/auth/me` 回显（`server/server_app.py:509`）→ **从未被读取或校验**。

**触发条件**：任一登录账号在请求头加 `X-API-Mode: proxy` → 用运营者 Key（`FIREFLY_PROXY_KEY`）跑通整条流水线（一轮≈4 次调用），并可反复调用直至 5000 次/日的全站池耗尽。

**影响面**：服务器版**全体托管用户**（池被吃干后，正常用户看到"今日额度已用完"）；成本直接落在运营者账号。

**附带风险 [推断]**：`app_config.py:800` 托管 Key 回落链含 `DEEPSEEK_API_KEY`。若服务器 environment 中存在该变量，托管模式将消耗**运营者 DeepSeek 余额**（而非 OpenCode Go 套餐额度）——需核对 systemd `Environment`（本审计无权访问服务器）。

**建议（最小改动）**：
1. 托管入口加白名单：仅 `users.quota_api_proxy > 0`（或 `role='admin'`）的账号可用 `X-API-Mode: proxy`，否则返回 403 文案；
2. `_proxy_quota_check()` 增加 `cfg.user_dir_id()` 维度的日上限（`quota_api_proxy` 作为"并发/日额度"语义落地）；
3. 核对服务器是否存在 `DEEPSEEK_API_KEY`，若无则**从回落链移除**（避免运营者主 Key 可被托管模式调用）。

**验证**：普通账号带 proxy 头 → 403；管理台把该账号额度设为 >0 → 放行且只吃自己的额度。

### E-1 [**P0**·数据丢失] `backup=False` 是**无条件**的——"唯一保险"本身可能不存在

**证据（[本人核实]，`app/routes_snapshot.py:222-235` 逐行）**：
```python
222  # 恢复前自动快照当前（pre-restore- 前缀：不进列表/滚动配额，单独留 3 份；失败不阻断）
223  try:
224      pre = build_full_snapshot_zip()
...
232  except Exception as e:
233      logger.warning("恢复前自动快照失败（继续恢复）: %s", e)   # ← 失败仅告警
234  # 恢复前已打全量 pre-restore 快照（上面）→ 恢复主体不再逐包重复备份
235  ok, err, n = _restore_full_snapshot(data, backup=False)     # ← 注释把"可能失败的快照"当成"已成功"
```

**问题**：注释与实现存在**逻辑跳跃**——`backup=False`（关闭逐包备份）是**无条件**的，而它所依赖的前提（`pre-restore` 快照已成功）**在 `:232-233` 被显式允许失败**。两者组合出的最坏路径是：

> `build_full_snapshot_zip()` 失败（磁盘满 / 快照目录不可写 / 序列化异常）→ 仅 warning → 带着 `backup=False` 继续 `_restore_full_snapshot` → `rmtree` 覆盖各包 → **此时既无 pre-restore 快照、也无逐包备份** → 一旦解压中途失败，该账号数据**不可恢复**。

**对本报告第 6/8 章的修正**：本人先前把 `pre-restore` 快照称为 R-02 的"唯一保险"、并在 8.3 节把"用户误恢复坏快照 → 走 `pre-restore-*.zip`"列为回滚动作。**该表述需加条件**：保险生效的前提是快照打包成功，而代码允许它失败后继续。

**建议（最小改动）**：
1. `pre` 打包或写盘失败 → 把 `backup` 传 `True`（退回逐包备份）而不是无条件 `False`；
2. 二者都失败 → **中止恢复**并返回错误，而不是继续覆盖；
3. 恢复响应带 `backup_ok: bool`，前端在 `backup_ok=false` 时必须二次确认。

**验证**：monkeypatch `build_full_snapshot_zip` 抛异常 → 断言恢复被中止（或至少逐包备份生效）。

**[代理取证] 的同源结论**：全仓"备份失败仍继续"共 **4 处**——`app_config.py:304-305`（配置迁移）、`routes_data.py:189-190`（导入）、`routes_data.py:266-270`（快照恢复逐包）、`routes_snapshot.py:232-233`（本节）。四处共性是"**备份是最后一道防线，但防线失效不阻断破坏性操作**"，应作为一条统一整改项。

### E-2 [**P0**·服务器版] 破坏性的 `_migrate_legacy_layout()` 在 **import 期**执行 → **服务器每次启动都会跑**

**证据（[本人核实]）**：
- `app/modules/app_config.py:509` 顶层调用 `_migrate_legacy_layout()`（函数定义 `:482-506`），即**模块导入时立即执行，不是"本地版首启"专属**。
- `server/server_app.py:37` `from modules import app_config as cfg` → **服务器版每次进程启动都会执行该迁移**。
- 迁移体：`(USER_DIR / "character", mode_character_dir("story"))`、`(USER_DIR / "data", mode_data_dir("story"))`（`:485-486`）+ `story/手账.md → story/journal/手账.md`（`:499-506`）；用 `shutil.move`（**移动即源消失**）、逐文件、`except OSError: pass` **静默吞错**、**无任何备份**。
- 作用目标是**共享的 `cfg.USER_DIR`**（服务器版 = `/opt/firefly/user_data`），**不是按账号目录**。

**对本报告第 6/7 章的修正**：本人先在 6 章把该迁移描述为"只做更早的平铺→分目录迁移"、在 7 章矩阵里把"R-02 恢复空窗"标为服务器版高危——但**漏掉了这条同样作用于服务器共享根、且在每次重启都重跑的移动式迁移**。它的实际风险面是：

| 场景 | 后果 |
|---|---|
| 运维把某份旧格式备份解到 `user_data/` 根（平铺 `character/`、`data/`）后重启 | **服务器启动时静默把它 move 进 `user_data/story/`** —— 变成"哪个账号的 story 数据"取决于巧合；跨账号污染面 |
| `move` 中途失败（跨盘、权限、文件被占用） | 逐文件 `except OSError: pass` → **部分迁移**：一半在旧位置、一半在新位置，两边都不完整且**无日志、无备份** |
| 每次重启重复执行 | 幂等性靠"目标已存在则跳过"（`:493`），但**没有"源目录已空则跳过"的短路** → 反复 `iterdir` 共享根目录（性能开销小，但语义上"启动即改动共享数据"本身违反最小惊讶原则） |

**建议（最小改动）**：
1. 把 `_migrate_legacy_layout()` 从 import 期移到**显式的启动初始化函数**里，并由 `server_app.py` 的 `main()` **仅在确认是"旧布局"时**调用（加一条显式环境开关或一次性标记文件 `user_data/.layout_migrated`）；
2. `move` 失败改为**可观测**（计数 + 启动日志 + 首屏提示），不再 `pass`；
3. 迁移前对涉及文件打一份 `pre-migrate-<ts>.zip`（与 4 处"备份失败仍继续"整改合并做）。

**验证**：在临时 `user_data` 根造平铺 `character/`+`data/` → 断言迁移后有日志、有备份、且失败时旧位置内容仍完整。

## 附录 F：v5 增补 —— 前端通道取证（含一条使 P0-1 升级的发现）

> 来源：并行审计（前端角色包交互通道）。F-1～F-5 已由本人逐条读源码核实；`[代理取证]` 标注项未逐行复核。

### F-1 [**P0**·数据丢失链闭合] 前端**没有导出入口** → 自建包目前**没有任何可用的备份路径**

**证据（[本人核实]）**：
- 全前端 grep `export-data` / `backup` / `/backup/` → **唯一命中是 `sync.js:69` 的冲突提示文案**（`.sync_backups`），**没有任何地方调用 `/export-data`、`/backup/create`、`/backups`**。
- 后端这三个能力**齐备**：`GET /export-data`（`app/routes.py:760`）、`POST /backup/create|restore|delete`（`:702-704`）、`GET /backups`（`:761`）。

**为什么这条把 P0-1 升级**：本人先前在 8.3 节把"用户误恢复坏快照 → 走 `{user_root}/backups/`（每模式 10 份）"列为回滚动作。但：
1. `/backup/*` **前端不可达** → 用户**无法自己创建**备份；
2. 唯一的 UI 备份入口是**全量快照**，而快照对自建包**恰恰是丢包的**（R-01，已复现）；
3. 于是自建包的数据在 UI 层面**既不能导出、也不能通过快照保住**——完整链路闭合为：**建包 → 无备份路径 → 换机/重装必然丢失**。

**建议（最小改动，两条二选一或都做）**：
- 短期：在下拉/设置里补一个「导出当前角色包」按钮，调既有 `GET /export-data?mode={CURRENT_MODE}`（后端零改动，纯前端 + 一次 `location.href`/blob 下载）；
- 同步修 R-01，使快照真正能承载自建包。
**验证**：新建自建包 → 导出 zip → 空环境导入 → 包可用（与 R-01 的回归用例同一条链路）。

### F-2 [P1·不可逆数据破坏] 自建包点「恢复默认」= 删除**唯一副本**

**证据（[本人核实]）**：
- 前端 `app/static/js/panels.js:635-646`：`rstBtn.onclick` 仅做 `confirm("恢复该文案为默认？（删除你的修改）")` → `POST /character-file/delete` → **不读响应体**，直接 `showToast("已恢复默认")`。
- 后端 `app/routes_pack.py:58-73` `delete_character_file`：白名单校验后 `fp.unlink(missing_ok=True)` → **无 `custom` 判断、无备份、无二次确认**。
- 而自建包的 `character/` **就是唯一副本**（`create_pack` 只在此处写模板，`:256-269`）→ 删除后 `resolve_character_file` 回落到 `bundled_character_dir(mode)`，该目录**对自建包不存在** → `load_slot` 返回空串（`llm_base.py:36-41`）→ **角色设定变空，且按钮文案写的是"恢复默认"**。
- 放大因素 [代理取证]：`get_pack_files` 的 `customized` 判定中 `bundled_text=""`（`routes_pack.py:91-93`）→ 自建包**每个文件恒显示"（已修改）"**，主动诱导用户去点那个按钮。
- 同类：`pack-asset/delete`（`:209-224`）删头像/封面副本，对自建包同样是删唯一副本。

**建议（最小改动）**：`delete_character_file` / `delete_pack_asset` 增加"包不存在 bundled 对应物时拒绝"分支（即 `not cfg.bundled_character_dir(mode).exists()` → 返回 `ok:false, "自建包无可恢复的默认内容，删除将清空该文件"`）；前端按 `data.custom` 改按钮文案与确认语。

### F-3 [P1·串包覆盖] 详情页无代际保护，且写回用点击时的 `CURRENT_MODE`

**证据（[本人核实]）**：
- `app/static/js/panels.js:517` `async function loadPackView()` —— 全函数**无 `_modeGen` 捕获/校验**；对比 `chat_history.js:113,119`（`const gen = _modeGen; … if (gen !== _modeGen) return;`）已有正确范式。
- 写回端一律取当前值：`panels.js:629`（保存文案）、`:642`（删除文案）、`:575`（资产删除）、`:661`（主动配置）。
- 现实前提 [代理取证]：`/pack-files` 每次都做**全量知识库 rglob**（`routes_pack.py:110-116` → `llm_retriever._source_dirs`，story 包挂 `knowledge/` + `database/dialogues_compiled/`）→ 响应不是毫秒级。

**触发链**：详情 A 的请求在飞 → 返回列表点开 B → A 的响应后到并**填充 B 的 DOM** → 点「保存」→ **A 的文案写进 B**（静默覆盖）。

**建议**：`loadPackView` 开头 `const gen = _modeGen;`，`await` 后校验；写回时改用**捕获的 mode** 而非 `CURRENT_MODE`。

### F-4 [P1·功能死锁] AI 向导「开始搭建」成功后按钮**永久禁用**

**证据（[本人核实]，`app/static/js/views.js:211-231`）**：
```js
211  const btn = document.getElementById("pf-start");
212  btn.disabled = true;                                  // ← 无条件先禁用
224  if (!data.ok) { _pfStatus(...); btn.disabled = false; return; }   // ← 只在失败时恢复
231  } catch (e) { _pfStatus("网络错误"); btn.disabled = false; }      // ← 只在异常时恢复
```
成功路径（`:225-230`）**不恢复** → 一次成功后想再建角色点不动，只能刷新页面。叠加 `_forge.drafts` 仅存内存（`views.js:194`）+ 后端 `finish` 先 `pop(session)`（`pack_forge.py:249-252`）→ 会话过期后草案全丢且无重开入口。

### F-5 [P2·显示] 自建包没有头像/封面 → **沿用上一个包的图**

**证据（[本人核实]）**：
- `app/static/js/views.js:453` `if (img && p.avatar) img.src = p.avatar;` —— **无 `else`**，无头像时**不清空 `src`** → 保留上一个包的图。
- `app/static/js/chat_render.js:37-38` 同型 → 新包消息行头像**无 src = 破图**。
- 根因：`create_pack`（`routes_pack.py:256-269`）与 `forge_finish`（`pack_forge.py:260-275`）**都不写 `assets/`** → `_slot_url` 返回 `""`（`routes_pack.py:100-107` 只 glob 已有文件）。
- 体感后果：**新建角色后"看起来还是流萤"**——这是"角色卡架构改动有隐患"最直观的用户可见症状。

**建议**：①无头像时 `img.removeAttribute("src")` 或填统一占位图；②建包时生成/拷贝占位 avatar+cover（可从 bundled 的某个通用占位或纯色图生成），并让首页卡片在缺图时显示包名首字。
